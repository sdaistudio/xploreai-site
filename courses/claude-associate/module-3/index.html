Session 3.1

Choosing the right Claude feature

Claude is more than a chat box. The exam expects you to pick the feature that fits the task, because the right feature often matters more than a clever prompt.

FeatureWhat it doesReach for it when
ChatA single conversationQuick questions, one-off drafts, thinking something through
ProjectsA workspace with its own instructions, knowledge files and chat historyOngoing work that reuses the same documents and context, alone or with a team
Web searchClaude looks things up on the web during the chatA simple factual question about something current
ResearchA deeper, multi-step investigation across the web and connected sources, with citationsQuestions that need many searches and synthesis, such as comparing several options
ArtifactsSubstantial, self-contained output in its own panelDocuments, code, diagrams or small tools you'll edit, reuse or share
Memory and chat searchClaude recalls details from past conversationsContinuing work without re-explaining the background

Anthropic's help articles add some useful detail. Research needs a paid plan with web search on, and it can draw on connected sources such as Gmail, Google Calendar and Google Docs as well as the web. Anthropic suggests Research for jobs needing many lookups over a few minutes, such as comparing competitors, and ordinary web search for simple factual lookups.

The same need, two features

A feature picker

The decision above can be written as a few rules. Running it on six requests shows how the choice follows from the task, not from habit.

Python
def pick_feature(task):
    t = task.lower()
    if any(w in t for w in ("compare", "landscape", "in-depth", "across sources", "competitor")):
        return "Research"
    if any(w in t for w in ("current", "latest", "today", "this week", "price of")):
        return "Web search"
    if any(w in t for w in ("every month", "each week", "recurring", "our style guide", "same documents")):
        return "Project"
    if any(w in t for w in ("dashboard", "calculator", "one-pager", "document to share", "slide")):
        return "Artifact"
    return "Chat"

for task in ["Compare five WhatsApp Business providers on price, features and support",
             "What is today's repo rate?",
             "Draft the patient newsletter every month using our style guide",
             "Build a calculator for treatment EMI options",
             "Explain what 'opt-in consent' means",
             "Write a one-pager to share with the owners on Sunday hours"]:
    print(f"{task:<66} -> {pick_feature(task)}")
Output · produced by running this code
Compare five WhatsApp Business providers on price, features and support -> Research
What is today's repo rate?                                         -> Web search
Draft the patient newsletter every month using our style guide     -> Project
Build a calculator for treatment EMI options                       -> Artifact
Explain what 'opt-in consent' means                                -> Chat
Write a one-pager to share with the owners on Sunday hours         -> Artifact
How to read it

Each request lands on a different feature. "Compare five providers" needs many sources and citations, so it gets Research; "today's repo rate" is one current fact, so web search; the monthly newsletter reuses the same documents, so a Project; the EMI calculator and the one-pager are things to reuse or share, so artifacts; a definition is a plain chat. Real decisions mix these: the newsletter Project might ask for its draft as an artifact.

Exam lens

Look for the clue in the scenario: recurring work with the same files points to Projects; current or external facts points to web search or Research; something to share or keep editing points to an artifact.

Practice questionA marketing coordinator writes a weekly social media plan using the same brand guide, product list and tone rules each time. Which feature best fits?

Recurring work that reuses the same documents and rules is exactly what Projects are for: the knowledge and instructions stay in place for every chat.

Practice questionA manager wants a cited comparison of six software vendors' pricing, security certifications and customer reviews. Which feature fits best?

Comparing many options across many sources is the kind of multi-step, cited investigation Research is designed for. A single search or plain chat won't cover it reliably.

Session 3.2

Haiku, Sonnet and Opus

Claude comes in model families that trade capability against speed and cost. The exam names three: Haiku, Sonnet and Opus. Version numbers change often, so learn the trade-off rather than the numbers.

FamilyPositioning (Anthropic's words, current versions)Relative speedUse it for
Haiku"For high-volume, latency-sensitive tasks such as classification, extraction, and routing"FastestMany simple, repetitive tasks where speed and cost matter most
Sonnet"The best combination of speed and intelligence"FastEveryday drafting, analysis and data work
Opus"For long-running agentic coding and knowledge work"ModerateHard reasoning, complex documents, work where quality outweighs cost

At the time of writing (October 2026), the current versions are Claude Haiku 5.5, Sonnet 5.5 and Opus 5.5. Anthropic also offers Claude Fable 5.1, above Opus, "for demanding reasoning and long-horizon agentic work". All of them share a context window of 1 million tokens.

The idea

A "token" is a chunk of text, roughly part of a word. Models read, write and are priced in tokens. Anthropic says 1 million tokens is roughly 555,000 words on current models, so about 1.8 tokens per English word. Other languages, and code, can use more tokens per word.

What the price difference means

Developers using the API pay per million tokens (MTok). Anthropic's published prices, as of October 2026:

ModelInput, per MTokOutput, per MTok
Haiku 5.5from $0.10from $0.50
Sonnet 5.5$2$10
Opus 5.5$4$20
Fable 5.1$10$50

In the Claude apps you pay for a plan rather than per token, but the trade-off is the same: a more capable model does more work per reply. The Python below turns the per-token prices into the cost of a real job: 20,000 short customer replies a month.

Python
PRICE = {                     # USD per million tokens: (input, output), Anthropic's published rates, Oct 2026
    "Haiku 5.5":  (0.10, 0.50),
    "Sonnet 5.5": (2.00, 10.00),
    "Opus 5.5":   (4.00, 20.00),
    "Fable 5.1":  (10.00, 50.00),
}
TOKENS_PER_WORD = 1.8         # from Anthropic: 1M tokens is roughly 555k words
USD_TO_INR = 84               # illustrative exchange rate

replies   = 20_000            # per month
in_words  = 250               # instructions + the customer's message
out_words = 90                # the drafted reply

in_tok  = replies * in_words  * TOKENS_PER_WORD
out_tok = replies * out_words * TOKENS_PER_WORD
print(f"{in_tok/1e6:.1f}M input tokens and {out_tok/1e6:.1f}M output tokens a month\n")
for model, (pin, pout) in PRICE.items():
    usd = in_tok / 1e6 * pin + out_tok / 1e6 * pout
    print(f"{model:<11} ${usd:8.2f} a month   (about ₹{usd * USD_TO_INR:9,.0f})")
Output · produced by running this code
9.0M input tokens and 3.2M output tokens a month

Haiku 5.5   $    2.52 a month   (about ₹      212)
Sonnet 5.5  $   50.40 a month   (about ₹    4,234)
Opus 5.5    $  100.80 a month   (about ₹    8,467)
Fable 5.1   $  252.00 a month   (about ₹   21,168)
How to read it

The same 20,000 replies cost about $2.50 a month on Haiku and about $100 on Opus, roughly 40 times as much. For short, routine replies where Haiku's quality is good enough, that difference buys nothing. For a task where Opus gets the answer right and Haiku doesn't, the extra cost is trivial compared with the cost of a wrong answer. Both points matter for the exam.

Practice questionWhich statement about Claude's model families is most accurate?

The families trade capability against speed and cost. Using the most capable model for everything wastes money and time; the right one depends on the task.

Session 3.3

Matching the model to the task

Anthropic's guidance says to weigh three things when choosing: the capabilities the task needs, the speed it must respond at, and the cost you can accept. It then describes two ways to start.

Efficiency-first
Start with the fast, low-cost model (Haiku).
Test it on your real task.
Move up only where it falls short.

Best for: high-volume, straightforward work; tight latency; tight budgets; prototypes.
Capability-first
Start with a highly capable model (Opus).
Get the quality right first.
Then try cheaper settings or models once it works.

Best for: complex reasoning, nuanced judgment, work where accuracy matters more than cost.

Either way, the deciding step is the same: test with your own real examples and compare accuracy, quality and how each model handles awkward cases. Then weigh the result against cost.

Typical matches

TaskGood starting pointWhy
Tagging 5,000 support tickets by topicHaikuSimple, repetitive, high volume
Drafting a weekly report from notesSonnetEveryday writing and analysis
Reviewing a complex contract for risksOpusNuance, long document, costly mistakes
Routing incoming messages to the right teamHaikuFast classification
Analysing survey data and writing recommendationsSonnet, or Opus if it's high-stakesBalanced, or quality first
Tip

Combine models. Anthropic describes pairing a lower-cost model with a frontier one: for example, a cheap model handles the bulk of the work and passes only the hard cases up. The same thinking works by hand: draft 200 product descriptions with Haiku, then use Opus to review the ten that matter most.

Scoring the options

When the choice isn't obvious, score it. The weights below say how much this task cares about quality, speed and cost; the model scores are rough relative ratings (5 is best) that you would adjust after testing on your own data.

Python
MODELS = {               # quality, speed, cost (5 = best value). Rough relative ratings, not benchmarks.
    "Haiku":  (3, 5, 5),
    "Sonnet": (4.5, 4, 3),
    "Opus":   (5, 3, 2),
}

def best_model(task, w_quality, w_speed, w_cost):
    scores = {m: w_quality * q + w_speed * s + w_cost * c for m, (q, s, c) in MODELS.items()}
    pick = max(scores, key=scores.get)
    print(f"{task:<44} " + "  ".join(f"{m} {v:4.1f}" for m, v in scores.items()) + f"  -> {pick}")

best_model("Tag 5,000 tickets by topic",               w_quality=0.2, w_speed=0.4, w_cost=0.4)
best_model("Weekly ops report from meeting notes",     w_quality=0.5, w_speed=0.3, w_cost=0.2)
best_model("Find risks in a 60-page supplier contract", w_quality=0.8, w_speed=0.1, w_cost=0.1)
Output · produced by running this code
Tag 5,000 tickets by topic                   Haiku  4.6  Sonnet  3.7  Opus  3.0  -> Haiku
Weekly ops report from meeting notes         Haiku  4.0  Sonnet  4.1  Opus  3.8  -> Sonnet
Find risks in a 60-page supplier contract    Haiku  3.4  Sonnet  4.3  Opus  4.5  -> Opus
How to read it

Ticket tagging is mostly about speed and cost, so Haiku wins clearly. The weekly report is a near tie, which is when testing both on real notes settles it: Sonnet edges ahead here because quality counts most. For the contract, quality dominates and Opus wins. The weights are where judgment lives: change them and the answer changes, which is exactly the trade-off the exam asks you to reason about.

Exam lens

The exam guide's own sample question has this shape: a high volume of short, simple drafts where speed and cost matter more than deep reasoning, so the answer is a faster, lower-cost model. Expect the reverse case too: a complex, high-stakes analysis calls for the more capable model.

Practice questionAn HR team needs Claude to classify 3,000 short employee survey comments as positive, negative or neutral by the end of the day. Which choice best fits?

Short, simple, high-volume classification is a classic fit for the fastest, lowest-cost model. Testing on a sample first confirms the quality is good enough.

Practice questionSelect 2Which TWO actions reflect Anthropic's guidance on choosing a model? (Select 2)

Choosing well means balancing capability, speed and cost, and testing on your own data. The newest or biggest model isn't automatically the best fit, and choices should be revisited as tasks and models change.

Session 3.4

Context limits and memory

The context window is everything Claude can consider at once: your instructions, the conversation so far, attached files and its own replies. Current models have a 1-million-token window, roughly 555,000 words. That is large, but long working sessions, big attachments and many back-and-forth turns still add up, and a very long, wandering thread is harder to work with than a focused one.

The exam objective puts it as three choices: restart, summarise or persist.

ChoiceWhat you doWhen
RestartOpen a fresh chatThe topic has changed, or the thread is cluttered with abandoned drafts and dead ends
SummariseAsk Claude for a handoff summary, then start a new chat with itLong, valuable work that must continue cleanly
PersistPut lasting context where it's reused automatically: Project knowledge and instructions, or memoryThe same background is needed across many chats
✎ Handoff summary
We're going to continue this work in a fresh chat. Write a handoff summary I can paste in, with:
1. The goal, in one sentence
2. Decisions we've made, and why
3. The current version of the draft, in full
4. Open questions and next steps

Leave out drafts and ideas we rejected.

Memory, chat search and incognito

Anthropic's help article describes three related tools, with settings under Settings > Your Claude:

  • Memory saves useful facts as topics while you chat: your role, projects, colleagues and preferences. You can view, edit or delete any memory, ask Claude to remember or forget something, pause memory, or reset it. Each Project has its own memory, and a Project can be cut off from your account-wide memory.
  • Chat search (paid plans) lets Claude look through your past conversations when you ask, and cite them. Inside a Project, it only searches that Project's chats.
  • Incognito chats (all plans) aren't saved to memory or history, and Claude won't search them later. On Team and Enterprise plans they still follow the organisation's data-retention rules.
Watch out

Memory has privacy implications. By default, sensitive topics such as health, religion and politics aren't saved, and some data (such as government ID numbers and financial account numbers) is never saved. On Team and Enterprise plans, an owner must enable memory for the organisation. Deleting a conversation doesn't delete memories made from it: remove those separately. Module 6 covers data sensitivity in depth.

Projects grow too

Project knowledge also counts against the context window. Anthropic's help article explains that on paid plans, when project knowledge approaches the limit, Claude automatically switches to retrieval (RAG) mode: instead of reading every file in full, it searches the knowledge for the passages relevant to each question, which can expand a Project's capacity by up to 10 times.

Tip

In RAG mode, Claude reads relevant extracts rather than whole files. If an answer seems to miss something you know is in a document, name the document or the section in your question.

Budgeting a long session

This small tracker estimates how a working session fills up, using Anthropic's rough figure of 1.8 tokens per word, and suggests when a handoff would help. The 25% threshold is a rule of thumb for keeping threads focused, not a hard limit.

Python
WINDOW = 1_000_000            # tokens, current Claude models
TOKENS_PER_WORD = 1.8

session = [                   # (what was added, words)
    ("project instructions", 400),
    ("brand guide + price sheet (project knowledge)", 9_000),
    ("annual report attached", 60_000),
    ("first draft and discussion", 4_500),
    ("three rounds of revisions", 7_000),
    ("second annual report attached", 85_000),
    ("rewrite for a new audience", 5_000),
    ("board pack attached", 150_000),
]

used = 0
for what, words in session:
    used += words * TOKENS_PER_WORD
    share = used / WINDOW
    advice = "handoff summary, then a fresh chat" if share > 0.25 else "fine"
    print(f"{what:<46} total {used/1000:7.1f}k tokens  {share:5.1%}  {advice}")

annual report attached                         total   124.9k tokens  12.5%  fine

How to read it

Instructions, knowledge and a few rounds of drafting barely dent the window. Each large report adds 100,000 tokens or more, and the second report takes the session to about 30% of the window. Nothing breaks there, but it's a good point to ask for a handoff summary and continue in a clean chat, with the reports in the Project rather than pasted again. Plenty of room remains; the point is a focused thread, not an emergency.

Practice questionAfter two hours of drafting, a chat contains many abandoned versions and the latest replies are drifting from decisions made earlier. What is the best next step?

Summarising and restarting keeps the valuable decisions while dropping the clutter. Starting with no context loses the work; repeating instructions in a cluttered thread rarely fixes the drift.

Practice questionA consultant wants to discuss a sensitive client matter without it being saved to memory or chat history. Which option fits?

Incognito chats aren't saved to memory or chat history, and Claude won't search them later. On Team and Enterprise plans they still follow the organisation's retention policy, so check that policy for truly sensitive matters (Module 6).
