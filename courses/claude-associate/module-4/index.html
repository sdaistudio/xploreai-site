Session 4.1

Analysing requirements and use cases

Before deciding how to use Claude, be clear on what problem you're solving and whether Claude is the right tool. A good use case for an Associate is one that's frequent, takes real time, and produces text or analysis a person can check.

Claude is useful at this stage in two ways: it can help you draw out requirements (by asking the questions you forgot), and it can help you assess use cases against criteria.

The idea

Separate the need from the proposed solution. "We need an AI chatbot" is a solution. The need might be "patients wait too long for replies on WhatsApp". Starting from the need opens better options, which might be a template library, a Claude-drafted reply that staff approve, or a change of opening hours.

Turning a request into requirements

✎ Requirements from a vague request
Here is a request from our operations manager:
"We spend too long on weekly reports. Can AI fix it?"

Help me turn this into requirements. Produce:
1. The underlying problem, in one sentence
2. Questions I should ask the manager before deciding anything (no more than six)
3. Possible approaches, from smallest change to biggest
4. What success would look like, in measurable terms

Don't recommend a tool yet.

Which use cases first?

Teams usually have more ideas than time. A simple scoring of value (how often and how long) against fit (how well it suits Claude and how safe it is) makes the choice explicit. The weights here are a sensible starting point, not a standard.

Python
use_cases = [
    # name,                         times/week, minutes each, checkable output?, sensitive data?, needs live system access?
    ("Draft replies to booking queries",  120,  4, True,  False, False),
    ("Weekly operations report",            1, 180, True,  False, False),
    ("Summarise patient feedback monthly",  0.25, 300, True, False, False),
    ("Answer clinical questions",          40,  6, False, True,  False),
    ("Auto-update the booking system",    150,  2, True,  False, True),
]

rows = []
for name, per_week, minutes, checkable, sensitive, live in use_cases:
    hours_month = per_week * minutes * 4.3 / 60
    fit = 3 + (1 if checkable else -2) - (2 if sensitive else 0) - (2 if live else 0)
    rows.append((hours_month * max(fit, 0), name, hours_month, fit, live))

for score, name, hours, fit, live in sorted(rows, reverse=True):
    note = " (needs integration: escalate to a developer)" if live else ""
    print(f"{name:<36} {hours:5.1f} h/month  fit {fit:+d}  priority {score:6.1f}{note}")
Output · produced by running this code
Draft replies to booking queries      34.4 h/month  fit +4  priority  137.6
Weekly operations report              12.9 h/month  fit +4  priority   51.6
Auto-update the booking system        21.5 h/month  fit +2  priority   43.0 (needs integration: escalate to a developer)
Summarise patient feedback monthly     5.4 h/month  fit +4  priority   21.5
Answer clinical questions             17.2 h/month  fit -1  priority    0.0
How to read it

Drafting booking replies wins: it's frequent, the output is easy to check, and it needs no special access. The weekly report saves far less time but fits well. Clinical answers score zero: they involve sensitive data and can't be safely checked by front-desk staff, so they're out of scope, not just low priority. Updating the booking system automatically saves real time, but it needs live system access, which is integration work for a developer or Claude Architect, not something an Associate builds alone.

Exam lens

The exam guide describes Associates as people who recognise limitations and escalate more complex or technical implementations. In scenario questions, an answer that involves building integrations, APIs or agents yourself is often the wrong one for an Associate. Identifying the need and handing it to the right specialist is the right one.

Practice questionA manager says, "We need AI to fix our slow invoice approvals." What is the best first step?

Requirements analysis starts with understanding the real problem and measurable success. Jumping to a tool risks solving the wrong problem.

Practice questionSelect 2Which TWO features make a task a strong first use case for an Associate using Claude? (Select 2)

Frequent, time-consuming tasks with checkable output give value with manageable risk. Live system changes need technical integration (escalate), and medical advice needs qualified professionals.

Session 4.2

Research, planning and process optimisation

Claude can help you understand a process, research how others handle it, plan a change and find where time is lost. Its role here is analyst and planner: you supply the facts about your organisation, and it supplies structure, options and questions.

Mapping a process

✎ Process mapping
Here's how a new patient booking works today (notes below, written by our front-desk lead).

Turn this into a numbered process map. For each step give: who does it, roughly how long it takes, and how long the patient waits before the next step.

Then identify the two steps that add the most delay, and explain why in one sentence each. Don't propose solutions yet.
Tip

Ask for the analysis before the solutions. If you ask for both at once, the solutions tend to anchor on the first problem mentioned rather than the biggest one.

Finding the bottleneck

The numbers below describe a new-patient booking process. The code adds up working time and waiting time, finds the biggest delay, then compares a redesigned version where Claude drafts the replies and a person approves them. Note the review time has been added, not ignored.

Python
current = [  # step, minutes of work, minutes the patient waits after it
    ("Read WhatsApp enquiry",        2,   0),
    ("Check dentist availability",   5,  30),
    ("Write reply with slots",       6, 120),
    ("Patient picks slot",           0, 180),
    ("Confirm and send forms",       8,  60),
]
redesigned = [
    ("Read WhatsApp enquiry",        2,   0),
    ("Check dentist availability",   5,   0),
    ("Claude drafts reply; staff review", 2, 10),
    ("Patient picks slot",           0, 180),
    ("Claude drafts confirmation; staff review", 2, 10),
]

def summarise(name, steps):
    work = sum(w for _, w, _ in steps)
    wait = sum(t for _, _, t in steps)
    worst = max(steps, key=lambda s: s[2])
    print(f"{name:<11} work {work:3d} min | waiting {wait:4d} min | total {(work + wait) / 60:4.1f} h | longest wait: '{worst[0]}' ({worst[2]} min)")

summarise("current", current)
summarise("redesigned", redesigned)
Output · produced by running this code
current     work  21 min | waiting  390 min | total  6.8 h | longest wait: 'Patient picks slot' (180 min)
redesigned  work  11 min | waiting  200 min | total  3.5 h | longest wait: 'Patient picks slot' (180 min)
How to read it

Staff work drops from 21 to 11 minutes per booking, and the patient's total time falls from about 6.8 hours to 3.5. But the biggest delay in both versions is the patient choosing a slot, which Claude doesn't touch. That's a useful finding in itself: the next improvement might be offering a booking link instead of a reply to wait for, which is a process change, not an AI one.

Watch out

Claude's research is a starting point. When it describes how other organisations handle something, or quotes a statistic, verify the important parts (Module 2) before they go into a proposal.

Practice questionClaude helped map a process and found that the longest delay is customers waiting for an approval email from a manager. What is the best interpretation?

Process analysis should target the real bottleneck. When the delay is a human decision, the fix is usually a process change. Faster drafting doesn't shorten a wait for approval.

Session 4.3

Supporting solution design

Once you know the need, Claude can help design a solution: options, trade-offs, a first version, and improvements based on feedback. The exam expects you to use Claude to support design, development and iteration, not to hand over judgment.

Tracing requirements to the design

A common design failure is quietly dropping a requirement. Tracing each requirement to the part of the solution that meets it makes gaps obvious.

Python
requirements = {
    "R1": "Reminder sent the day before",
    "R2": "Patient can reschedule from the message",
    "R3": "Messages in English, Hindi or Marathi",
    "R4": "No clinical details in the message",
    "R5": "Staff can see who confirmed",
}
design = {   # part of the Claude-assisted batch design -> requirements it meets
    "Evening batch in the 'Reminders' Project": ["R1"],
    "Template with booking link":              ["R1", "R2"],
    "Project instruction: language from booking record": ["R3"],
    "Project instruction: only date, time, clinic, link": ["R4"],
}

covered = {r for parts in design.values() for r in parts}
for rid, text in requirements.items():
    by = [part for part, rs in design.items() if rid in rs]
    print(f"{rid} {text:<40} {'covered by: ' + '; '.join(by) if by else 'NOT COVERED'}")
Output · produced by running this code
R1 Reminder sent the day before             covered by: Evening batch in the 'Reminders' Project; Template with booking link
R2 Patient can reschedule from the message  covered by: Template with booking link
R3 Messages in English, Hindi or Marathi    covered by: Project instruction: language from booking record
R4 No clinical details in the message       covered by: Project instruction: only date, time, clinic, link
R5 Staff can see who confirmed              NOT COVERED
How to read it

Four of five requirements are met. R5, staff seeing who confirmed, isn't covered by any part of the design: the batch sends messages, but replies come back to WhatsApp, not into a list. That's the kind of gap that's cheap to spot now and expensive to discover after rollout. Options: add a step where replies are pasted back into the Project for a summary, or accept it as a known limitation and say so.

Tip

Iterate like you did with prompts (Module 1): change one thing, test with real cases, keep what works. A pilot with one clinic for two weeks teaches more than a perfect plan.

Practice questionWhen using Claude to support solution design, what is the most appropriate role for Claude?

Claude supports design by widening the options and speeding up drafting and analysis. Decisions stay with people, and integration work is escalated to technical specialists.

Session 4.4

Augmenting or redesigning a workflow

There are two broad ways to bring Claude into existing work:

ApproachWhat changesExampleTrade-off
AugmentThe same workflow, with Claude speeding up a stepStaff still write the weekly report, but Claude drafts it from their notesQuick to start, modest gains
RedesignThe workflow itself is rebuilt around what Claude does wellTeams submit updates in a fixed format; a Project turns them into the report; the manager reviewsMore setup and change management, bigger gains
Augment
Monday: each clinic manager emails notes as usual.
Ops lead pastes the notes into Claude: "Draft this week's report."
Ops lead edits the draft for 40 minutes, then sends it.
Redesign
Friday: each clinic fills in a 5-field update form.
Monday: ops lead pastes the forms into the "Weekly report" Project, which has the template and rules.
Ops lead reviews for 15 minutes, then sends it.
The idea

Augment first, redesign once you've learned. Augmenting a step shows you where Claude helps and where it struggles, with little risk. That evidence is what justifies, and shapes, a redesign.

When does a redesign pay back?

Redesigning costs setup time (forms, instructions, training) before it saves time. The calculation below compares the two over twelve weeks, using hours as the cost.

Python
weeks = 12
baseline   = 3.0                     # hours a week, writing the report by hand
augment    = {"setup": 1.0, "weekly": 1.6}    # Claude drafts; ops lead edits
redesign   = {"setup": 8.0, "weekly": 0.6}    # forms + Project + training; review only

def cumulative(plan):
    return [plan["setup"] + plan["weekly"] * w for w in range(1, weeks + 1)]

aug, red, base = cumulative(augment), cumulative(redesign), [baseline * w for w in range(1, weeks + 1)]
for w in (1, 2, 4, 6, 8, 12):
    print(f"week {w:>2}: by hand {base[w-1]:5.1f} h | augment {aug[w-1]:5.1f} h | redesign {red[w-1]:5.1f} h")
breakeven = next(w for w in range(1, weeks + 1) if red[w-1] <= aug[w-1])
print(f"\nredesign overtakes augment in week {breakeven}; saved vs by-hand after {weeks} weeks: "
      f"augment {base[-1] - aug[-1]:.1f} h, redesign {base[-1] - red[-1]:.1f} h")
Output · produced by running this code
week  1: by hand   3.0 h | augment   2.6 h | redesign   8.6 h
week  2: by hand   6.0 h | augment   4.2 h | redesign   9.2 h
week  4: by hand  12.0 h | augment   7.4 h | redesign  10.4 h
week  6: by hand  18.0 h | augment  10.6 h | redesign  11.6 h
week  8: by hand  24.0 h | augment  13.8 h | redesign  12.8 h
week 12: by hand  36.0 h | augment  20.2 h | redesign  15.2 h

redesign overtakes augment in week 7; saved vs by-hand after 12 weeks: augment 15.8 h, redesign 20.8 h
How to read it

Augmenting saves time from week one. The redesign starts behind because of its 8 hours of setup, overtakes the augmented version in week 7, and by week 12 has saved 5 hours more. For a report that runs every week for a year, the redesign clearly wins. For a short-lived process, augmenting is the better choice. The numbers are illustrative; the shape of the trade-off is the lesson.

Watch out

Redesign changes people's jobs and habits. Involve the people who do the work, explain what changes and why, and keep a human review step. A redesign that saves the ops lead time but adds unexplained forms for clinic managers may just move the work around.

Practice questionA team has never used Claude for its monthly board report. What is usually the best way to start?

Augmenting first is low-risk and produces evidence about what works, which then guides any redesign. Removing human review from a board report would be inappropriate.

Session 4.5

Communicating value and limits

Part of the Associate role is explaining Claude to colleagues and managers: what it does well, what it doesn't, and what it's worth. Overselling damages trust faster than underselling.

What to say, and what to avoid

DoAvoid
"Claude drafts the report; Priya reviews it, saving about 2 hours a week""AI writes our reports now"
"It's good at summarising and drafting; we verify facts and figures""It's always accurate"
"It doesn't have access to our booking system; that would need a developer"Implying it can do things it can't
"In the pilot, X; we'll know more after Y"Promising results before measuring

An honest value estimate

Value estimates are guesses until measured, so give a range, not a single number, and include the costs: the plan's cost and the time people spend reviewing. All the figures below are illustrative assumptions.

Python
hourly_cost = 450            # ₹ per staff hour, fully loaded (illustrative)
seats, seat_cost = 3, 2_500  # ₹ per seat per month (illustrative assumption, not a quoted price)
scenarios = {                # hours saved per week, hours of review added per week
    "cautious": (4, 2.0),
    "expected": (8, 2.5),
    "optimistic": (12, 3.0),
}
for name, (saved, review) in scenarios.items():
    net_hours = (saved - review) * 4.3
    value = net_hours * hourly_cost - seats * seat_cost
    print(f"{name:<11} net {net_hours:5.1f} h/month -> net value ₹{value:8,.0f} a month")
Output · produced by running this code
cautious    net   8.6 h/month -> net value ₹  -3,630 a month
expected    net  23.6 h/month -> net value ₹   3,142 a month
optimistic  net  38.7 h/month -> net value ₹   9,915 a month
How to read it

The cautious case loses money, about ₹3,600 a month, once review time and seats are counted; the expected case gains about ₹3,100 and the optimistic one about ₹9,900. That spread is the honest message: with about 2½ hours of review a week, the pilot pays only if it saves more than about 6½ hours a week, so measure that first. Presenting the range, with review time visible, is more convincing than a single optimistic figure, and it tells stakeholders exactly what has to be true for the investment to pay. Replace the assumptions with your own measured numbers after a pilot.

Exam lens

Questions in this area reward balanced, evidence-based communication: clear about value, explicit about limitations and safeguards, and honest about what still needs human oversight or technical work.

Practice questionA director asks whether Claude can "replace" the team that writes customer emails. Which response best communicates value and limits?

A balanced answer states the realistic value, the limitation and the safeguard. Overclaiming and dismissing both mislead stakeholders.

Practice questionSelect 2When presenting the expected benefit of a Claude pilot to management, which TWO practices are most appropriate? (Select 2)

Honest value communication shows assumptions, ranges and all costs, including review time. Optimistic-only estimates and hidden limitations erode trust when reality differs.
