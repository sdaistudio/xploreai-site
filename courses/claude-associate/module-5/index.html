Session 5.1

Configuring a Project

A Project is a workspace with three things that apply to every chat inside it: instructions (how Claude should behave), knowledge (files it can draw on) and its own chat history and memory. Configuring a Project well is how an Associate turns good one-off prompts into a dependable, repeatable tool.

According to Anthropic's help article:

  • Projects are available on all plans; Free users can create up to five.
  • You create one from the Projects page with + New Project, then add a name and description. Claude can't see the name or description: anything Claude needs must go in the instructions or knowledge.
  • Instructions apply to every chat in the Project.
  • Knowledge is used across all chats in the Project.
  • Chats don't share context with each other unless the information is added to the Project knowledge.
  • On Team and Enterprise plans, Projects can be kept private or shared, with members given Can view (use it, chat, but not change it) or Can edit (change instructions and knowledge) access.
The idea

One Project, one job. A Project for "everything marketing" mixes instructions and files that conflict. Separate Projects for "Patient communications" and "Social media plans" keep each one's instructions focused and its knowledge relevant.

Check a configuration before you share it

A small script can catch common configuration mistakes before colleagues start relying on a Project. This one checks that the instructions point Claude at the knowledge, that only one version of each document is loaded, and that the knowledge isn't padded with files the job doesn't need.

Python
import re

instructions = ("You write messages to patients for a three-clinic dental chain in Mumbai. "
                "Use plain English, under 120 words, warm and direct. Use prices and timings only "
                "from the knowledge files; if something isn't there, say 'please confirm with the clinic'.")
knowledge = ["Price sheet - 2026-03.pdf", "Price sheet - 2025-11.pdf", "Clinic timings and addresses.docx",
             "Brand voice guide.pdf", "Message templates (approved).docx", "Staff salaries 2026.xlsx"]

def base_name(f):     # "Price sheet - 2026-03.pdf" -> "price sheet"
    return re.sub(r"[\s\-–]*\d{4}-\d{2}.*$|\.\w+$", "", f).strip().lower()

checks = []
checks.append(("instructions mention the knowledge", "knowledge" in instructions.lower()))
checks.append(("says what to do when unsure", "confirm" in instructions.lower() or "not sure" in instructions.lower()))
names = [base_name(f) for f in knowledge]
dupes = sorted({n for n in names if names.count(n) > 1})
checks.append((f"one version of each file (duplicates: {', '.join(dupes) or 'none'})", not dupes))
sensitive = [f for f in knowledge if re.search(r"salar|payroll|password|aadhaar|pan card", f, re.I)]
checks.append((f"no sensitive files (found: {', '.join(sensitive) or 'none'})", not sensitive))

for label, ok in checks:
    print(("✓ " if ok else "✗ ") + label)
Output · produced by running this code
✓ instructions mention the knowledge
✓ says what to do when unsure
✗ one version of each file (duplicates: price sheet)
✗ no sensitive files (found: Staff salaries 2026.xlsx)
How to read it

The instructions are in good shape. The knowledge isn't: there are two price sheets, so Claude may quote last November's prices, and a staff salaries file that has nothing to do with patient messages and shouldn't be in a shared Project at all. Remove the old price sheet and the salaries file before sharing. Module 6 covers why sensitive data needs this care.

Exam lens

Remember the detail that trips people up: Claude can't see a Project's name or description. If a scenario relies on the description to guide Claude, the fix is to move that guidance into the instructions.

Practice questionA team set up a Project with a detailed description explaining the tone to use, but Claude ignores it. What is the most likely fix?

Claude can't see a Project's name or description. Guidance about behaviour belongs in the Project instructions.

Practice questionOn a Team plan, the front-desk staff should use a shared Project but not change its instructions or files. Which access fits?

"Can view" lets members see the Project and chat in it without editing its instructions or knowledge. "Can edit" would let them change the configuration.

Session 5.2

Knowledge files and connectors

Curating knowledge

Project knowledge is only as good as what you put in. Every file in the knowledge competes for Claude's attention, and outdated or conflicting files produce outdated or conflicting answers.

Good practiceWhy
Upload current versions onlyOld prices or policies get quoted as if they're current
One version of each documentTwo versions force Claude to guess which is right
Descriptive file names with datesYou (and Claude) can tell what each file is and how fresh it is
Only what the job needsIrrelevant files dilute answers and widen data exposure
Clean, text-based documentsText is read reliably; scanned images of text are harder
Tip

Remember RAG mode (Module 3): when knowledge is large, Claude searches it for relevant passages instead of reading everything. Clear file names and headings help it find the right passage. If an answer misses something, name the file in your question.

Auditing a knowledge set

Here is a quick audit of a Project's knowledge list: flagging stale files, superseded versions and very large files that might be better split or summarised.

Python
from datetime import date

today = date(2026, 10, 26)
files = [  # name, last updated, pages
    ("Price sheet",                   date(2026, 9, 30),   2),
    ("Price sheet (old)",             date(2025, 11, 1),   2),
    ("Clinic timings and addresses",  date(2026, 6, 15),   1),
    ("Brand voice guide",             date(2024, 2, 10),  14),
    ("Treatment FAQ",                 date(2025, 8, 20),  38),
    ("Annual report 2023 (full)",     date(2024, 4, 5),  220),
]

for name, updated, pages in files:
    age = (today - updated).days
    flags = []
    if "old" in name.lower():
        flags.append("superseded: remove")
    elif age > 365:
        flags.append(f"{age // 30} months old: review")
    if pages > 100:
        flags.append("very large: does the job need all of it?")
    print(f"{name:<30} updated {updated}  {pages:>3} pp  {'; '.join(flags) or 'ok'}")
Output · produced by running this code
Price sheet                    updated 2026-09-30    2 pp  ok
Price sheet (old)              updated 2025-11-01    2 pp  superseded: remove
Clinic timings and addresses   updated 2026-06-15    1 pp  ok
Brand voice guide              updated 2024-02-10   14 pp  32 months old: review
Treatment FAQ                  updated 2025-08-20   38 pp  14 months old: review
Annual report 2023 (full)      updated 2024-04-05  220 pp  31 months old: review; very large: does the job need all of it?
How to read it

Two files are fine. The old price sheet should simply go. The brand voice guide is over two and a half years old, so it's worth checking it still reflects how the clinics speak. The 220-page annual report is probably the wrong document for a patient-messages Project: a one-page summary, or nothing, would serve better. The Treatment FAQ, at 14 months, is also due a check that its answers still match what the clinics offer.

Connectors

Connectors let Claude reach into other apps and services, read your data there and, with permission, take actions. Anthropic's help articles describe the Google Workspace connectors, available to all users of Claude and Claude Desktop:

ConnectorWhat Claude can do (per Anthropic's help article)
GmailSearch and read email; draft; send, reply and forward (asks for approval each time by default)
Google CalendarView events, find mutual availability, create and update events, respond to invitations
Google DriveSearch and read Docs, Sheets, Slides, PDFs and Office files; add Drive files to chats; upload and organise files

Key rules from the same articles:

  • You authenticate with your own account, and Claude can only reach what you already have permission to see.
  • On Team and Enterprise plans, an Owner must enable these connectors for the organisation first.
  • Turn connectors on or off per chat from the + menu, under Connectors.
  • Google Docs added to a chat or Project stay in sync with the latest version in Drive. Drive files can be added to the knowledge of private Projects only, not shared ones.
  • Actions such as sending email or sharing files ask for your approval before they run, by default.
Watch out

Connectors widen what Claude can see, so connect only what the task needs and check what's being retrieved. A connector brings your organisation's data into the conversation, and your data policies (Module 6) apply to it.

Practice questionA colleague says Claude found a confidential HR file through the Google Drive connector. What does Anthropic's documentation say about this?

Connectors mirror the user's existing permissions. If Claude found the file, the connected account could already open it, which is a permissions issue to raise with the Drive owner.

Practice questionSelect 2Which TWO statements about Project knowledge are good practice? (Select 2)

Current, single-version, clearly named files give consistent answers. Uploading everything, or several versions, leads to outdated or conflicting responses and wider data exposure.

Session 5.3

Writing system-level instructions

Project instructions work like a standing brief that applies to every chat: a system-level instruction. They're where you put everything that should be true of every answer, so users don't have to repeat it.

A strong set of instructions usually covers:

The idea

Write instructions for the cases that go wrong. Anthropic's prompting guidance applies here too: be clear and direct, explain why, and say what to do rather than only what not to do. The highest-value lines in Project instructions are usually about edge cases: what to do when information is missing, when a request is out of scope, or when something needs a human.

Weak instructions
Be helpful and professional. Don't make mistakes. NEVER give wrong prices!!! Keep it short.
Strong instructions
You draft replies for our front desk. Use prices only from the price sheet in the knowledge files. If a price isn't listed, write "[please confirm]" instead of estimating, because a wrong price causes complaints at the counter.

Keep replies under 120 words: patients read them on their phones.

The weak version expresses wishes ("don't make mistakes") without telling Claude how. The strong version names the source, the fallback, the reason and a measurable length.

An instruction linter

These checks look for common weaknesses in instructions: vague words that give Claude nothing to act on, shouting in capitals, and missing essentials such as a fallback for uncertainty.

Python
import re

def lint(text):
    issues = []
    vague = [w for w in ("helpful", "professional", "good", "nice", "appropriate", "don't make mistakes")
             if w in text.lower()]
    if vague:
        issues.append(f"vague wording with no action attached: {', '.join(vague)}")
    shouting = re.findall(r"\b[A-Z]{4,}\b", text)
    if shouting or "!!" in text:
        issues.append("capitals/exclamation marks instead of a reason")
    if not re.search(r"\b(if|when)\b.*\b(unsure|not sure|isn't|missing|not listed)\b", text, re.I):
        issues.append("no rule for missing or uncertain information")
    if not re.search(r"\b\d+\s*(words|lines|sentences)\b", text, re.I):
        issues.append("no measurable length")
    if not re.search(r"knowledge|price sheet|attached|file", text, re.I):
        issues.append("doesn't say which sources to use")
    return issues

weak = "Be helpful and professional. Don't make mistakes. NEVER give wrong prices!!! Keep it short."
strong = ("You draft replies for our front desk. Use prices only from the price sheet in the knowledge files. "
          "If a price isn't listed, write [please confirm] instead of estimating, because a wrong price causes "
          "complaints at the counter. Keep replies under 120 words: patients read them on their phones.")
for name, text in [("weak", weak), ("strong", strong)]:
    found = lint(text)
    print(f"{name}: {len(found)} issue(s)")
    for i in found:
        print(f"   - {i}")
Output · produced by running this code
weak: 5 issue(s)
   - vague wording with no action attached: helpful, professional, don't make mistakes
   - capitals/exclamation marks instead of a reason
   - no rule for missing or uncertain information
   - no measurable length
   - doesn't say which sources to use
strong: 0 issue(s)
How to read it

The weak instructions trip all five checks: vague wishes, capitals in place of a reason, no fallback, no measurable length and no named source. The strong version passes all five. A linter like this can't judge whether instructions are right for your business, but it catches the habits that make instructions unreliable.

Practice questionWhich line is the strongest addition to a Project's instructions?

It tells Claude exactly what to do in the situation that most often causes errors. The others express a wish without an action.

Session 5.4

Maintaining configurations

A Project is never finished. Prices change, policies update, templates improve, and team members join and leave. The exam expects you to inform, maintain and update configurations, knowledge sources and instructions over time.

TriggerWhat to update
New price sheet or policyReplace the knowledge file; remove the old one
Repeated corrections from usersAdd a rule to the instructions
New team or role using itReview access (Can view / Can edit)
A connector is no longer neededDisconnect it
A model or feature changesRe-run your test requests

What changed between versions?

When a knowledge file is updated, it helps to see exactly what changed, both to update any instructions that mention it and to tell users. Python's built-in difflib shows line-by-line differences:

Python
import difflib

old = """Consultation: Rs 500
Scaling & polishing: Rs 1,800
Root canal (molar): Rs 9,500
Teeth whitening: Rs 12,000""".splitlines()

new = """Consultation: Rs 500
Scaling & polishing: Rs 2,000
Root canal (molar): Rs 9,500
Clear aligners (consultation): Rs 1,000""".splitlines()

for line in difflib.unified_diff(old, new, "price-sheet-2026-03", "price-sheet-2026-10", lineterm="", n=0):
    print(line)
Output · produced by running this code
--- price-sheet-2026-03
+++ price-sheet-2026-10
@@ -2 +2 @@
-Scaling & polishing: Rs 1,800
+Scaling & polishing: Rs 2,000
@@ -4 +4 @@
-Teeth whitening: Rs 12,000
+Clear aligners (consultation): Rs 1,000
How to read it

Lines starting with - were removed and lines with + were added. Scaling went up from ₹1,800 to ₹2,000, teeth whitening disappeared, and clear-aligner consultations were added. Each change has a follow-up: check the message templates for the old scaling price, check whether any instruction or template still mentions whitening, and tell the front desk about aligners.

Re-testing after a change

Keep a small set of test requests with the facts each answer must contain. After every change to instructions or knowledge, run them again in the Project and tick them off. Here the expected facts are checked against answers pasted back from Claude (written here as stand-ins):

Python
tests = {
    "How much is scaling?":                ["2,000"],
    "Are you open on Sunday in Bandra?":   ["10", "4"],
    "Do you do teeth whitening?":          ["please confirm"],
}
answers = {   # pasted back from the Project after the October update (illustrative)
    "How much is scaling?": "Scaling and polishing is Rs 2,000 at all our clinics.",
    "Are you open on Sunday in Bandra?": "Yes, Bandra is open on Sundays from 10 am to 4 pm.",
    "Do you do teeth whitening?": "Teeth whitening is Rs 12,000.",
}
for q, must in tests.items():
    ok = all(m.lower() in answers[q].lower() for m in must)
    print(f"{'pass' if ok else 'FAIL'}  {q:<36} expects {must}")
Output · produced by running this code
pass  How much is scaling?                 expects ['2,000']
pass  Are you open on Sunday in Bandra?    expects ['10', '4']
FAIL  Do you do teeth whitening?           expects ['please confirm']
How to read it

Two tests pass. The whitening answer fails: it still quotes the old ₹12,000 price, even though whitening was removed from the new sheet. That's the signal to look for a leftover source, such as an old template or a second file in the knowledge, and fix the configuration rather than correcting answers one at a time.

Exam lens

Maintenance questions usually reward the systematic answer: update the source (the knowledge file or the instructions), remove what's outdated, re-test, and communicate the change, rather than fixing individual answers by hand.

Practice questionAfter a price change, staff notice a Project still sometimes quotes old prices. What is the best fix?

The root cause is outdated knowledge. Updating the source, removing old versions and re-testing fixes it for everyone, every time.

Practice questionSelect 2Which TWO practices help keep a shared Project reliable over time? (Select 2)

Ownership, a change log and re-testing keep a configuration accurate as things change. Unmanaged edits cause drift, and never updating lets the knowledge go stale.
