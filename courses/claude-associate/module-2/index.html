Session 2.1

Accuracy and completeness

Claude's writing is fluent, and fluent text sounds right. Evaluating output means separating how good it reads from how good it is. Two questions come first:

  • Is it accurate? Every fact, number, name and date matches the source or reality.
  • Is it complete? It does everything the request asked, nothing important is left out, and it doesn't quietly answer a slightly different question.
The idea

Completeness is checked against the request, not against the output. An output can be internally excellent and still miss half the brief. Keep the original request open beside the output and tick off each requirement.

A meeting summary, checked

You ask Claude to summarise a 40-minute project meeting "with every decision, and each action with an owner and a deadline". Here is a reply to check:

Meeting summaryIllustrative example, not a recorded output

Decisions

  • Launch the WhatsApp reminder pilot at the Andheri clinic first.
  • Keep the current SMS reminders running during the pilot.

Actions

  • Priya to draft the reminder message templates by 12 March.
  • Rahul to get a quote from the WhatsApp Business provider.
  • Front-desk team to collect patients' opt-in consent.

It reads well. But the request asked for an owner and a deadline on every action. Checking that by eye is easy to skip; checking it in code is not:

Python
import re

summary = """Decisions
- Launch the WhatsApp reminder pilot at the Andheri clinic first.
- Keep the current SMS reminders running during the pilot.
Actions
- Priya to draft the reminder message templates by 12 March.
- Rahul to get a quote from the WhatsApp Business provider.
- Front-desk team to collect patients' opt-in consent."""

actions = summary.split("Actions")[1].strip().splitlines()
DATE = r"\b(by|before|on)\s+\d{1,2}\s+(Jan|Feb|Mar|Apr|May|Jun|Jul|Aug|Sep|Oct|Nov|Dec)\w*"
for a in actions:
    owner = re.match(r"-\s*([A-Z][\w-]*(?:\s+team)?)\s+to\b", a)
    deadline = re.search(DATE, a)
    flags = [] if deadline else ["no deadline"]
    print(f"{'ok ' if not flags else 'FIX'} {a[2:60]:<58} owner: {owner.group(1) if owner else '?':<16} {', '.join(flags)}")
Output · produced by running this code
ok  Priya to draft the reminder message templates by 12 March. owner: Priya            
FIX Rahul to get a quote from the WhatsApp Business provider.  owner: Rahul            no deadline
FIX Front-desk team to collect patients' opt-in consent.       owner: Front-desk team  no deadline
How to read it

Only one of three actions meets the brief. Rahul's quote and the consent work have owners but no deadlines, so either the meeting set none (worth flagging to the organiser) or Claude dropped them. You can't tell which from the summary: go back to the transcript.

Tip

Build the check into the prompt itself: "If an action has no deadline in the transcript, write deadline: not set rather than leaving it out." Then a missing deadline becomes visible instead of silent.

Practice questionClaude's summary of a supplier contract is clear and well organised. What is the most important next step before relying on it?

Good organisation shows nothing about accuracy. Key terms have to be checked against the source document. Claude's self-reported confidence is not a reliable accuracy signal.

Session 2.2

Hallucinations, inconsistencies and bias

Hallucinations

A hallucination is content that sounds plausible but isn't true or isn't supported: an invented statistic, a citation to a report that doesn't exist, a subsection number that's nearly right, a quote nobody said. Hallucinations are most likely when Claude is asked for specific details it doesn't have: exact figures, citations, recent events, niche facts or details of your own organisation.

Higher riskLower risk
Exact numbers, dates, citations and quotesGeneral explanations of well-known ideas
Recent events and current rulesRewording text you supplied
Facts about your organisation it wasn't givenSummarising a document you attached
"Give me 10 sources on…""Using only the attached report…"

Anthropic's guidance gives practical ways to reduce them:

  • Allow "I don't know". Explicitly permit Claude to say it lacks the information. This alone can greatly reduce invented answers.
  • Ground it in quotes. For long documents, ask Claude to pull out the exact quotes it relies on first, then answer only from those quotes.
  • Restrict to the documents. Tell it to use only the material you provided, not its general knowledge.
  • Ask for citations, then verify them. Have it support each claim with a quote; if it can't find one, it must withdraw the claim.
✎ A grounded request
Using only the attached clinic policy document, answer: how long must we keep patient X-ray records?

First, quote the exact sentence(s) from the policy that answer this. Then give the answer in one sentence, citing the section.

If the policy doesn't cover this, say "The policy doesn't say" rather than giving a general answer.

Inconsistencies

One signal of hallucination is inconsistency: ask the same question several times (or in slightly different words) and compare. Facts that are really in the source tend to come back the same; invented details tend to change. Anthropic calls this best-of-N verification.

Below, three answers to the same question (written here to stand in for three runs) are compared automatically. The code pulls out every number and percentage and flags any that don't agree.

Python
import re
from collections import Counter

runs = [
    "The policy requires X-ray records to be kept for 10 years, and 5 years for routine notes.",
    "X-ray records must be retained for 10 years; routine clinical notes for 5 years.",
    "Keep X-ray records for 7 years and routine notes for 5 years, per section 4.2.",
]

def facts(text):
    return re.findall(r"\b\d+(?:\.\d+)?\s*(?:years?|%|days?)|section\s+\d+(?:\.\d+)*", text, re.I)

table = [facts(r) for r in runs]
for k, f in enumerate(table, 1):
    print(f"run {k}: {f}")

all_facts = Counter(x.lower() for f in table for x in set(f))
print("\nagree in every run:", [x for x, c in all_facts.items() if c == len(runs)])
print("disagree or appear once:", [x for x, c in all_facts.items() if c < len(runs)])
Output · produced by running this code
run 1: ['10 years', '5 years']
run 2: ['10 years', '5 years']
run 3: ['7 years', '5 years', 'section 4.2']

agree in every run: ['5 years']
disagree or appear once: ['10 years', '7 years', 'section 4.2']
How to read it

All three runs agree on 5 years for routine notes, so that's probably drawn from the document. The X-ray figure flips between 10 and 7 years, and one run cites a "section 4.2" the others never mention. Those are exactly the details to verify in the source before anyone acts on them. Agreement doesn't prove a fact is right; disagreement strongly suggests one isn't.

Bias

Outputs can also be biased: one-sided, stereotyped, or skewed towards whatever was most common in the data or the prompt. Watch for:

  • Stereotyped language, such as job ads that use words associated with one gender or age group.
  • One-sided framing, where only the benefits (or only the risks) are presented.
  • Over-representation, where a summary of feedback that reflects the loudest comments rather than the most common ones.
  • Assumptions about people based on names, locations or other cues.
Python
CODED = {
    "masculine-coded": ["aggressive", "dominant", "competitive", "rockstar", "ninja", "fearless", "assertive"],
    "age-coded":       ["young", "energetic", "digital native", "fresh graduate", "recent graduate"],
}
draft = ("We want a young, energetic front-desk rockstar who thrives in a competitive, "
         "fast-paced clinic and is fearless with difficult patients.")

for kind, words in CODED.items():
    hits = [w for w in words if w in draft.lower()]
    print(f"{kind:<16} {len(hits)} found: {', '.join(hits) or '-'}")
Output · produced by running this code
masculine-coded  3 found: competitive, rockstar, fearless
age-coded        2 found: young, energetic
How to read it

Five coded words in two sentences. Each one is common in job ads, but together they signal "young and competitive", which can put off good applicants and, in some places, raise legal concerns. A word list like this is a crude first pass, not a fairness audit. Ask Claude to rewrite with neutral, skill-based language, then read it again yourself.

Exam lens

Questions in this domain often give a confident-sounding output and ask what to do. The right answer is almost never "trust it because it sounds sure" or "ask Claude how confident it is". It's usually verifying against an authoritative source, or restricting Claude to supplied documents.

Practice questionWhich request is MOST likely to produce hallucinated details?

Requests for many specific citations, authors and years are classic hallucination territory, especially without a search tool. Rewording, summarising supplied text and explaining a general idea are much lower risk.

Practice questionSelect 2You ask Claude the same factual question three times and get the same date twice and a different date once. What does this suggest? (Select 2)

Disagreement between runs is a red flag that calls for verification. Agreement, even two out of three, doesn't prove correctness.

Session 2.3

Fact-checking techniques

Fact-checking means confirming each important claim against an authoritative source: the original document, the regulator's own website, your system of record. It does not mean asking Claude whether it's sure.

Let Claude help, but don't let it mark its own work

Claude can do a lot of the legwork: extracting the claims, finding quotes in documents you provide, and flagging statements it can't support. Anthropic's recommended pattern is to ask Claude to find a supporting quote for each claim after drafting, and to remove any claim it can't support.

Checking claims against a source, in code

The same idea, mechanically. For each claim, the code looks for the source line that shares the most important words with it, and checks whether the numbers match. It's a rough tool (it doesn't understand meaning), but it quickly shows which claims have no support at all.

Python
import re

source = """Scaling & polishing (full mouth): Rs 1,800
Consultation (any clinic, any day): Rs 500
Root canal treatment (molar): Rs 9,500
X-ray (single, digital): Rs 350"""

claims = [
    "Scaling and polishing costs Rs 1,800.",
    "A molar root canal costs Rs 8,500.",
    "Consultations are free on Sundays.",
    "A digital X-ray is Rs 350.",
]

def words(s):   # lower-case words of 3+ letters, plural "s" dropped, filler removed
    return {w.rstrip("s") for w in re.findall(r"[a-z]{3,}", s.lower())} - {"cost", "the", "are", "and", "any"}
def numbers(s): return set(re.findall(r"\d[\d,]*", s))

for c in claims:
    best = max(source.splitlines(), key=lambda line: len(words(c) & words(line)))
    overlap = words(c) & words(best)
    if not overlap:
        verdict = "NO SOURCE LINE"
    elif numbers(c) and numbers(c) != numbers(best):
        verdict = f"NUMBER MISMATCH (source says {', '.join(numbers(best))})"
    elif not numbers(c) and "free" in c.lower():
        verdict = "CHECK: source gives a price, claim says free"
    else:
        verdict = "supported"
    print(f"{c:<38} -> {verdict}")
Output · produced by running this code
Scaling and polishing costs Rs 1,800.  -> supported
A molar root canal costs Rs 8,500.     -> NUMBER MISMATCH (source says 9,500)
Consultations are free on Sundays.     -> CHECK: source gives a price, claim says free
A digital X-ray is Rs 350.             -> supported
How to read it

Two claims match their source lines exactly. The root canal claim found the right line but the wrong price (₹8,500 against ₹9,500), the kind of near-miss that's easy to read past. The "free on Sundays" claim matches the consultation line, but the source gives a price, not "free". Simple checks catch the mechanical errors; a person still decides what the right wording is.

Rules for verifying citations

  • Open the citation. Confirm the source exists and says what's claimed. A real-looking URL or section number proves nothing until you've seen it.
  • Prefer primary sources. The regulator's notice beats a news article about it; your billing system beats an email about prices.
  • Check the date. Rules, prices and names change. Confirm the source is current.
  • Watch for near-misses. Right document, wrong clause; right figure, wrong year.
Watch out

Asking Claude to "double-check its facts" without giving it a source mostly produces the same answer, more confidently. Verification needs something outside the conversation to check against.

Practice questionClaude's research summary cites "Section 12(3)" of a new regulation. What is the best way to validate this before it goes to the compliance team?

Specific-looking citations are a common form of hallucination. Validating means checking the authoritative source itself. Self-confirmation isn't independent, and deleting detail avoids the problem without solving it.

Session 2.4

When a human must review

Not every output needs the same scrutiny. A brainstorm of team-lunch ideas needs none; a letter telling a patient about a diagnosis needs an expert. The skill the exam tests is matching the level of review to the risk.

FactorLower reviewHigher review
StakesInternal draft, easy to fixMoney, health, legal, safety or reputation
AudienceYou or your teamCustomers, patients, regulators, the public
ReversibilityCan be corrected laterHard to undo once sent or acted on
Expertise neededGeneral knowledgeMedical, legal, financial or technical judgment
Source qualityGrounded in documents you gave itFrom general knowledge or the web

A routing rule you could write down

Teams often turn this judgment into a simple, written rule so it's applied consistently. Here is one, as a scoring function, applied to six everyday requests.

Python
def review_level(stakes, external, irreversible, expert_topic, grounded):
    """stakes: 0 low, 1 medium, 2 high. Other arguments are True/False."""
    if expert_topic and stakes >= 1:
        return "expert sign-off"
    score = stakes * 2 + external * 2 + irreversible + (not grounded)
    if score >= 4:  return "full review"
    if score >= 2:  return "spot-check"
    return "use as is"

tasks = [
    ("Brainstorm team-lunch venues",                   0, False, False, False, False),
    ("Summarise our own meeting notes for the team",   0, False, False, False, True),
    ("Draft a WhatsApp offer to all patients",         1, True,  True,  False, True),
    ("Answer a patient's question about a medicine",   2, True,  True,  True,  False),
    ("Summarise a new tax rule for the finance team",  1, False, False, True,  False),
    ("Turn our price list into a website table",       1, True,  False, False, True),
]
for name, *f in tasks:
    print(f"{name:<48} -> {review_level(*f)}")
Output · produced by running this code
Brainstorm team-lunch venues                     -> use as is
Summarise our own meeting notes for the team     -> use as is
Draft a WhatsApp offer to all patients           -> full review
Answer a patient's question about a medicine     -> expert sign-off
Summarise a new tax rule for the finance team    -> expert sign-off
Turn our price list into a website table         -> full review
How to read it

The brainstorm and the meeting summary need little or no review. The patient offer is external and can't be unsent, so it gets a full read. The medicine question and the tax rule need someone qualified, because both are expert topics with real consequences. The point isn't these exact weights: it's that a written rule makes the decision consistent and explainable.

The idea

Escalation is part of the role. The exam guide describes the Associate as someone who recognises limitations and escalates more complex or technical work. Knowing when to hand off to an expert, a developer or a Claude Architect is a skill, not a failure.

Practice questionWhich output most clearly needs review by a qualified professional before use?

Medical advice to a patient is high-stakes, external, hard to undo and needs professional expertise. The other outputs are internal, low-stakes or will be edited anyway.

Session 2.5

Editing for the audience

The same facts need different words for different readers. A clinic's new booking system means "API integration and slot logic" to the developer, "fewer missed calls and a 15% cut in front-desk time" to the owner, and "book in two taps on WhatsApp" to patients. Part of evaluating output is asking: is this right for the person reading it?

AudienceUsually wantsEdit for
Executives and ownersThe decision, the impact, the costLead with the conclusion; one page; numbers
SpecialistsAccuracy and detailPrecise terms, method, caveats
Customers and patientsWhat it means for them, what to doPlain words, short sentences, a clear next step
Regulators and auditorsEvidence and complianceExact references, no claims you can't support

One update, three versions

For the clinic owners
Recommendation: roll out WhatsApp booking to all three clinics in April.

The Andheri pilot cut missed calls by 38% and freed about 6 front-desk hours a week. Set-up cost is ₹45,000 per clinic, recovered in roughly four months through fewer no-shows.

Decision needed by 20 March.
For patients
You can now book your dental appointment on WhatsApp.

Send "Hi" to 98XXX XXXXX, pick a time, and you're done. You'll get a reminder the day before.

Prefer to call? Our phone line hasn't changed.
✎ Adapting for an audience
Rewrite the attached project update for our patients.

They are not technical, and many read on their phones. Use short sentences and everyday words, no more than 60 words in total, and end with exactly what they should do next.

Leave out costs, staffing and internal metrics: patients don't need them.

Measuring readability

A simple way to compare versions is a readability score. The Flesch Reading Ease formula uses sentence length and syllables per word: higher means easier to read (60–70 is plain English; below 30 is hard going). Here it is from scratch, applied to a technical and a patient version of the same message.

Python
import re

def syllables(word):
    word = word.lower()
    groups = re.findall(r"[aeiouy]+", word)
    n = len(groups) - (1 if word.endswith("e") and len(groups) > 1 else 0)
    return max(n, 1)

def flesch(text):
    sentences = max(len(re.findall(r"[.!?]+", text)), 1)
    words = re.findall(r"[A-Za-z']+", text)
    syl = sum(syllables(w) for w in words)
    return 206.835 - 1.015 * (len(words) / sentences) - 84.6 * (syl / len(words)), len(words) / sentences

technical = ("The implementation integrates the scheduling application programming interface with the "
             "WhatsApp Business platform, enabling automated appointment confirmation and configurable "
             "reminder notifications.")
patient = ("You can now book on WhatsApp. Send Hi, pick a time, and you are done. "
           "We will remind you the day before.")

for name, text in [("technical", technical), ("patient", patient)]:
    score, wps = flesch(text)
    print(f"{name:<10} reading ease {score:6.1f}   words per sentence {wps:4.1f}")
Output · produced by running this code
technical  reading ease  -56.2   words per sentence 21.0
patient    reading ease  103.3   words per sentence  7.3
How to read it

The technical sentence scores far below zero, which means very hard to read: one 21-word sentence packed with long words. The patient version scores above 100, which is very easy reading: short sentences and short words. Scores like this are approximate (the syllable counter is a heuristic), but they're a fast, objective check that an output fits a general audience. Specialists can handle a lower score; patients shouldn't have to.

Practice questionClaude produced an accurate, detailed technical summary of a system change. It now needs to go to senior leadership. What is the most appropriate edit?

Executives need the conclusion, impact and decision up front. Accuracy is necessary but not enough: the output must also suit its audience. Removing numbers or padding the text makes it worse.

Session 2.6

Choosing the output format

The exam guide names three kinds of output format to choose from: inline replies in the chat, artifacts, and structured data. Choosing well makes the result easier to use, check and reuse.

FormatWhat it isChoose it when
InlineA normal reply in the conversationQuick answers, explanations, short text you'll read once
ArtifactSubstantial, self-contained content in its own panel beside the chat, which you can edit, reuse and shareDocuments, reports, code, diagrams, small interactive tools, anything you'll iterate on
Structured dataA table, CSV or JSON with fixed fieldsData going into a spreadsheet, a system or another step of a workflow

According to Anthropic's help article on artifacts, Claude typically creates one when the content is substantial, self-contained and likely to be reused, such as a document, a single-page website, an SVG image, a diagram or an interactive component. You can also simply ask for one.

Asking for structured data

When output feeds another tool, specify the exact fields and what to do when information is missing. Otherwise, each run may name things differently.

✎ Structured extraction
From each patient enquiry below, extract the details as JSON, one object per enquiry, with exactly these keys:

- "name": the patient's name, or null if not given
- "treatment": one of "cleaning", "filling", "root canal", "braces", "other"
- "preferred_date": in YYYY-MM-DD format, or null if not given
- "urgent": true only if the patient mentions pain or swelling

Return only the JSON array, with no other text.
Structured replyIllustrative example, not a recorded output

[

{"name": "Anita Desai", "treatment": "cleaning", "preferred_date": "2026-03-14", "urgent": false},

{"name": null, "treatment": "root canal", "preferred_date": "next week", "urgent": true}

]

Even with clear instructions, check structured output before you load it anywhere. Here is that check in Python, run against the reply above:

Python
import json, re

reply = '''[
  {"name": "Anita Desai", "treatment": "cleaning", "preferred_date": "2026-03-14", "urgent": false},
  {"name": null, "treatment": "root canal", "preferred_date": "next week", "urgent": true}
]'''

ALLOWED = {"cleaning", "filling", "root canal", "braces", "other"}
records = json.loads(reply)                       # step 1: is it valid JSON at all?
for k, r in enumerate(records, 1):
    problems = []
    if set(r) != {"name", "treatment", "preferred_date", "urgent"}:
        problems.append(f"unexpected keys {sorted(r)}")
    if r.get("treatment") not in ALLOWED:
        problems.append(f"treatment '{r.get('treatment')}' not allowed")
    d = r.get("preferred_date")
    if d is not None and not re.fullmatch(r"\d{4}-\d{2}-\d{2}", d):
        problems.append(f"date '{d}' is not YYYY-MM-DD")
    if not isinstance(r.get("urgent"), bool):
        problems.append("urgent is not true/false")
    print(f"record {k}: " + ("ok" if not problems else "; ".join(problems)))
Output · produced by running this code
record 1: ok
record 2: date 'next week' is not YYYY-MM-DD
How to read it

The reply is valid JSON and has the right fields, so it would look fine in a quick glance. But record 2's date is "next week", which isn't in the format asked for and would break a booking system expecting a real date. Validating structured output against the rules you set catches this before it reaches the system. The fix belongs in the prompt: "if the patient gives a relative date such as 'next week', set preferred_date to null and copy their words into a 'notes' field".

Exam lens

Match the format to what happens next. If a scenario says the output will be imported into a spreadsheet or tool, the answer is structured data with defined fields. If it will be edited and shared as a document, an artifact. If it's a quick answer, inline.

Practice questionA team needs Claude to turn 200 customer emails into rows for a tracking spreadsheet with consistent columns. Which output approach is best?

Data going into a spreadsheet needs consistent, named fields and a rule for missing values, then validation before import. Prose summaries and reports don't load cleanly into columns.

Practice questionSelect 2Which TWO situations are good reasons to ask for an artifact rather than an inline reply? (Select 2)

Artifacts suit substantial, self-contained content you'll edit, reuse or share. Quick answers and explanations work best inline.
