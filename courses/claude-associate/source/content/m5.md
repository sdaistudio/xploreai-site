## 5.1 | Configuring a Project

A **Project** is a workspace with three things that apply to every chat inside it: **instructions** (how Claude should behave), **knowledge** (files it can draw on) and its own **chat history and memory**. Configuring a Project well is how an Associate turns good one-off prompts into a dependable, repeatable tool.

According to Anthropic's help article:

- Projects are available on **all plans**; Free users can create up to five.
- You create one from the Projects page with **+ New Project**, then add a name and description. **Claude can't see the name or description**: anything Claude needs must go in the instructions or knowledge.
- **Instructions** apply to every chat in the Project.
- **Knowledge** is used across all chats in the Project.
- **Chats don't share context with each other** unless the information is added to the Project knowledge.
- On **Team and Enterprise** plans, Projects can be kept private or shared, with members given **Can view** (use it, chat, but not change it) or **Can edit** (change instructions and knowledge) access.

```screen title="Project: Patient communications (simplified)"
Instructions: You write messages to patients for a three-clinic dental chain in Mumbai. Use plain English, under 120 words, warm and direct. Use prices and timings only from the knowledge files; if something isn't there, say "please confirm with the clinic".
Knowledge:
- Price sheet — 2026-03.pdf
- Clinic timings and addresses.docx
- Brand voice guide.pdf
- Message templates (approved).docx
Visibility: Shared with organisation
Members:
- Ops lead (Can edit)
- Front-desk team (Can view)
Memory: Project memory only ("Use account memory" off)
```

```flow title="Setting up a Project"
Define the job | One clear purpose per Project
Write instructions | Role, audience, rules, format, what to do when unsure
Add knowledge | Current, curated files: one version of each
Set access | Who can use it, and who can change it
Test | Run real requests; fix the instructions, not each answer
```

> [concept] **One Project, one job.** A Project for "everything marketing" mixes instructions and files that conflict. Separate Projects for "Patient communications" and "Social media plans" keep each one's instructions focused and its knowledge relevant.

### Check a configuration before you share it

A small script can catch common configuration mistakes before colleagues start relying on a Project. This one checks that the instructions point Claude at the knowledge, that only one version of each document is loaded, and that the knowledge isn't padded with files the job doesn't need.

```python
import re

instructions = ("You write messages to patients for a three-clinic dental chain in Mumbai. "
                "Use plain English, under 120 words, warm and direct. Use prices and timings only "
                "from the knowledge files; if something isn't there, say 'please confirm with the clinic'.")
knowledge = ["Price sheet - 2026-03.pdf", "Price sheet - 2025-11.pdf", "Clinic timings and addresses.docx",
             "Brand voice guide.pdf", "Message templates (approved).docx", "Staff salaries 2026.xlsx"]

def base_name(f):     # "Price sheet - 2026-03.pdf" -> "price sheet"
    return re.sub(r"[\s\-–]*\d{4}-\d{2}.*$|\.\w+$", "", f).strip().lower()

checks = []
checks.append(("instructions mention the knowledge", "knowledge" in instructions.lower()))
checks.append(("says what to do when unsure", "confirm" in instructions.lower() or "not sure" in instructions.lower()))
names = [base_name(f) for f in knowledge]
dupes = sorted({n for n in names if names.count(n) > 1})
checks.append((f"one version of each file (duplicates: {', '.join(dupes) or 'none'})", not dupes))
sensitive = [f for f in knowledge if re.search(r"salar|payroll|password|aadhaar|pan card", f, re.I)]
checks.append((f"no sensitive files (found: {', '.join(sensitive) or 'none'})", not sensitive))

for label, ok in checks:
    print(("✓ " if ok else "✗ ") + label)
```

> [read] The instructions are in good shape. The knowledge isn't: there are two price sheets, so Claude may quote last November's prices, and a staff salaries file that has nothing to do with patient messages and shouldn't be in a shared Project at all. Remove the old price sheet and the salaries file before sharing. Module 6 covers why sensitive data needs this care.

> [exam] Remember the detail that trips people up: **Claude can't see a Project's name or description.** If a scenario relies on the description to guide Claude, the fix is to move that guidance into the instructions.

```quiz
why: Claude can't see a Project's name or description. Guidance about behaviour belongs in the Project instructions.
```

## 5.2 | Knowledge files and connectors

### Curating knowledge

Project knowledge is only as good as what you put in. Every file in the knowledge competes for Claude's attention, and outdated or conflicting files produce outdated or conflicting answers.

| Good practice | Why |
|---|---|
| Upload **current** versions only | Old prices or policies get quoted as if they're current |
| One version of each document | Two versions force Claude to guess which is right |
| **Descriptive file names** with dates | You (and Claude) can tell what each file is and how fresh it is |
| Only what the job needs | Irrelevant files dilute answers and widen data exposure |
| Clean, text-based documents | Text is read reliably; scanned images of text are harder |

> [tip] Remember RAG mode (Module 3): when knowledge is large, Claude searches it for relevant passages instead of reading everything. Clear file names and headings help it find the right passage. If an answer misses something, name the file in your question.

### Auditing a knowledge set

Here is a quick audit of a Project's knowledge list: flagging stale files, superseded versions and very large files that might be better split or summarised.

```python
from datetime import date

today = date(2026, 10, 26)
files = [  # name, last updated, pages
    ("Price sheet",                   date(2026, 9, 30),   2),
    ("Price sheet (old)",             date(2025, 11, 1),   2),
    ("Clinic timings and addresses",  date(2026, 6, 15),   1),
    ("Brand voice guide",             date(2024, 2, 10),  14),
    ("Treatment FAQ",                 date(2025, 8, 20),  38),
    ("Annual report 2023 (full)",     date(2024, 4, 5),  220),
]

for name, updated, pages in files:
    age = (today - updated).days
    flags = []
    if "old" in name.lower():
        flags.append("superseded: remove")
    elif age > 365:
        flags.append(f"{age // 30} months old: review")
    if pages > 100:
        flags.append("very large: does the job need all of it?")
    print(f"{name:<30} updated {updated}  {pages:>3} pp  {'; '.join(flags) or 'ok'}")
```

> [read] Two files are fine. The old price sheet should simply go. The brand voice guide is over two and a half years old, so it's worth checking it still reflects how the clinics speak. The 220-page annual report is probably the wrong document for a patient-messages Project: a one-page summary, or nothing, would serve better. The Treatment FAQ, at 14 months, is also due a check that its answers still match what the clinics offer.

### Connectors

**Connectors** let Claude reach into other apps and services, read your data there and, with permission, take actions. Anthropic's help articles describe the Google Workspace connectors, available to all users of Claude and Claude Desktop:

| Connector | What Claude can do (per Anthropic's help article) |
|---|---|
| Gmail | Search and read email; draft; send, reply and forward (asks for approval each time by default) |
| Google Calendar | View events, find mutual availability, create and update events, respond to invitations |
| Google Drive | Search and read Docs, Sheets, Slides, PDFs and Office files; add Drive files to chats; upload and organise files |

Key rules from the same articles:

- You **authenticate with your own account**, and Claude can only reach what **you** already have permission to see.
- On **Team and Enterprise** plans, an **Owner** must enable these connectors for the organisation first.
- Turn connectors on or off per chat from the **+** menu, under **Connectors**.
- Google Docs added to a chat or Project **stay in sync** with the latest version in Drive. Drive files can be added to the knowledge of **private** Projects only, not shared ones.
- Actions such as sending email or sharing files ask for **your approval** before they run, by default.

```chat title="Using connectors with approval"
you: Find the email from Dr Shah last week about the new X-ray machine, check my calendar for a free hour on Thursday, and draft a reply proposing that slot.
claude: I found Dr Shah's email from 21 October ("New X-ray unit — training"). Your Thursday is free from 2 pm to 3 pm. Here's a draft reply proposing that time. Would you like me to save it as a Gmail draft, or send it?
note: Claude read the email and calendar with your permissions, and it asks before sending anything.
```

> [warn] Connectors widen what Claude can see, so connect only what the task needs and check what's being retrieved. A connector brings your organisation's data into the conversation, and your data policies (Module 6) apply to it.

```quiz
Q: A colleague says Claude found a confidential HR file through the Google Drive connector. What does Anthropic's documentation say about this?

- [x] Claude can only reach files the connected user already has permission to see, so the user must already have had access
- [ ] Connectors bypass Google permissions for convenience
- [ ] Drive files can never be read by Claude
why: Connectors mirror the user's existing permissions. If Claude found the file, the connected account could already open it, which is a permissions issue to raise with the Drive owner.
```

```quiz
Q: Which TWO statements about Project knowledge are good practice? (Select 2)
- [x] Keep only the current version of each document
- [x] Use descriptive file names that include dates
- [ ] Upload every document the team has, in case it's useful

```

## 5.3 | Writing system-level instructions

Project instructions work like a standing brief that applies to every chat: a **system-level instruction**. They're where you put everything that should be true of *every* answer, so users don't have to repeat it.

A strong set of instructions usually covers:

```anatomy
[role]You support the front-desk team of a three-clinic dental chain in Mumbai.[/role]

[task]Your job is to draft replies to patient messages about bookings, timings, prices and directions.[/task]

[context]Patients are mostly working professionals and families. Many write in Hinglish; reply in the language they used. The knowledge files hold the current price sheet, clinic timings, and approved templates.[/context]

[constraints]Use prices and timings only from the knowledge files. Never give medical advice: if a message describes pain, swelling or a clinical question, reply only that a dentist will call back, and mark the draft URGENT.[/constraints]

[format]Keep replies under 120 words. End with the clinic's phone number. Use no more than one emoji.[/format]

[fallback]If you aren't sure of a detail, write "[please confirm]" in its place rather than guessing.[/fallback]
```

> [concept] **Write instructions for the cases that go wrong.** Anthropic's prompting guidance applies here too: be clear and direct, explain why, and say what to do rather than only what not to do. The highest-value lines in Project instructions are usually about edge cases: what to do when information is missing, when a request is out of scope, or when something needs a human.

```compare
# Weak instructions
Be helpful and professional. Don't make mistakes. NEVER give wrong prices!!! Keep it short.
---
# Strong instructions
You draft replies for our front desk. Use prices only from the price sheet in the knowledge files. If a price isn't listed, write "[please confirm]" instead of estimating, because a wrong price causes complaints at the counter.

Keep replies under 120 words: patients read them on their phones.
```

The weak version expresses wishes ("don't make mistakes") without telling Claude *how*. The strong version names the source, the fallback, the reason and a measurable length.

### An instruction linter

These checks look for common weaknesses in instructions: vague words that give Claude nothing to act on, shouting in capitals, and missing essentials such as a fallback for uncertainty.

```python
import re

def lint(text):
    issues = []
    vague = [w for w in ("helpful", "professional", "good", "nice", "appropriate", "don't make mistakes")
             if w in text.lower()]
    if vague:
        issues.append(f"vague wording with no action attached: {', '.join(vague)}")
    shouting = re.findall(r"\b[A-Z]{4,}\b", text)
    if shouting or "!!" in text:
        issues.append("capitals/exclamation marks instead of a reason")
    if not re.search(r"\b(if|when)\b.*\b(unsure|not sure|isn't|missing|not listed)\b", text, re.I):
        issues.append("no rule for missing or uncertain information")
    if not re.search(r"\b\d+\s*(words|lines|sentences)\b", text, re.I):
        issues.append("no measurable length")
    if not re.search(r"knowledge|price sheet|attached|file", text, re.I):
        issues.append("doesn't say which sources to use")
    return issues

weak = "Be helpful and professional. Don't make mistakes. NEVER give wrong prices!!! Keep it short."
strong = ("You draft replies for our front desk. Use prices only from the price sheet in the knowledge files. "
          "If a price isn't listed, write [please confirm] instead of estimating, because a wrong price causes "
          "complaints at the counter. Keep replies under 120 words: patients read them on their phones.")
for name, text in [("weak", weak), ("strong", strong)]:
    found = lint(text)
    print(f"{name}: {len(found)} issue(s)")
    for i in found:
        print(f"   - {i}")
```

> [read] The weak instructions trip all five checks: vague wishes, capitals in place of a reason, no fallback, no measurable length and no named source. The strong version passes all five. A linter like this can't judge whether instructions are *right* for your business, but it catches the habits that make instructions unreliable.

```quiz
Q: Which line is the strongest addition to a Project's instructions?
- [ ] "Always be accurate."
- [ ] "NEVER EVER guess!!!"
- [x] "If the knowledge files don't contain the answer, say so and suggest who to ask, rather than guessing."
- [ ] "Be as helpful as possible."
why: It tells Claude exactly what to do in the situation that most often causes errors. The others express a wish without an action.
```

## 5.4 | Maintaining configurations

A Project is never finished. Prices change, policies update, templates improve, and team members join and leave. The exam expects you to **inform, maintain and update** configurations, knowledge sources and instructions over time.

```flow title="Keeping a Project healthy"
Own it | Name one person responsible for each Project
Log changes | Record what changed in instructions or knowledge, and why
Re-test | Run the same test requests after every change
Review on a schedule | Check files and instructions monthly or quarterly
Tell users | Announce changes that affect how people use it
```

| Trigger | What to update |
|---|---|
| New price sheet or policy | Replace the knowledge file; remove the old one |
| Repeated corrections from users | Add a rule to the instructions |
| New team or role using it | Review access (Can view / Can edit) |
| A connector is no longer needed | Disconnect it |
| A model or feature changes | Re-run your test requests |

### What changed between versions?

When a knowledge file is updated, it helps to see exactly what changed, both to update any instructions that mention it and to tell users. Python's built-in `difflib` shows line-by-line differences:

```python
import difflib

old = """Consultation: Rs 500
Scaling & polishing: Rs 1,800
Root canal (molar): Rs 9,500
Teeth whitening: Rs 12,000""".splitlines()

new = """Consultation: Rs 500
Scaling & polishing: Rs 2,000
Root canal (molar): Rs 9,500
Clear aligners (consultation): Rs 1,000""".splitlines()

for line in difflib.unified_diff(old, new, "price-sheet-2026-03", "price-sheet-2026-10", lineterm="", n=0):
    print(line)
```

> [read] Lines starting with `-` were removed and lines with `+` were added. Scaling went up from ₹1,800 to ₹2,000, teeth whitening disappeared, and clear-aligner consultations were added. Each change has a follow-up: check the message templates for the old scaling price, check whether any instruction or template still mentions whitening, and tell the front desk about aligners.

### Re-testing after a change

Keep a small set of **test requests** with the facts each answer must contain. After every change to instructions or knowledge, run them again in the Project and tick them off. Here the expected facts are checked against answers pasted back from Claude (written here as stand-ins):

```python
tests = {
    "How much is scaling?":                ["2,000"],
    "Are you open on Sunday in Bandra?":   ["10", "4"],
    "Do you do teeth whitening?":          ["please confirm"],
}
answers = {   # pasted back from the Project after the October update (illustrative)
    "How much is scaling?": "Scaling and polishing is Rs 2,000 at all our clinics.",
    "Are you open on Sunday in Bandra?": "Yes, Bandra is open on Sundays from 10 am to 4 pm.",
    "Do you do teeth whitening?": "Teeth whitening is Rs 12,000.",
}
for q, must in tests.items():
    ok = all(m.lower() in answers[q].lower() for m in must)
    print(f"{'pass' if ok else 'FAIL'}  {q:<36} expects {must}")
```

> [read] Two tests pass. The whitening answer fails: it still quotes the old ₹12,000 price, even though whitening was removed from the new sheet. That's the signal to look for a leftover source, such as an old template or a second file in the knowledge, and fix the configuration rather than correcting answers one at a time.

> [exam] Maintenance questions usually reward the **systematic** answer: update the source (the knowledge file or the instructions), remove what's outdated, re-test, and communicate the change, rather than fixing individual answers by hand.

```quiz
Q: After a price change, staff notice a Project still sometimes quotes old prices. What is the best fix?
- [ ] Ask staff to correct each reply by hand
- [x] Replace the price file in the knowledge, remove any old versions or templates that contain old prices, then re-test with standard questions
- [ ] Add "use new prices" to the end of each chat
- [ ] Create a new Project every time prices change
why: The root cause is outdated knowledge. Updating the source, removing old versions and re-testing fixes it for everyone, every time.
```

```quiz
Q: Which TWO practices help keep a shared Project reliable over time? (Select 2)
- [x] Naming an owner who reviews the instructions and knowledge on a schedule
```
