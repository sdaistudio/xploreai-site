## 7.1 | Diagnosing poor outputs

When an output is poor, the temptation is to rephrase and try again. That sometimes works by luck. A better habit is to **diagnose first**: name the symptom, find the likely cause, and change the thing that's actually wrong. Almost every problem traces back to one of six areas covered in this course.

| Symptom | Likely cause | Where to fix it | Module |
|---|---|---|---|
| Generic, could apply to anyone | Missing context | Add audience, purpose, specifics | 1 |
| Right content, wrong shape | No format specified | State length, structure, destination | 1 |
| Inconsistent from run to run | No examples, vague instructions | Add examples; tighten instructions | 1, 5 |
| Wrong or invented facts | No source, or no "I don't know" option | Ground in documents; allow uncertainty; verify | 2 |
| Outdated information | Old knowledge file, or no web access | Update knowledge; use web search or Research | 3, 5 |
| Shallow on a hard task | Task too big, or model too small | Decompose; try a more capable model | 1, 3 |
| Forgets earlier decisions | Long, cluttered thread | Handoff summary and fresh chat; persist in Project | 3 |
| Ignores a Project rule | Rule in the description, or conflicting instructions | Move it to instructions; remove conflicts | 5 |

```flow title="Diagnose before you fix"
Name the symptom | What exactly is wrong? Compare with the success criteria
Check the inputs | Did Claude have the context, sources and format it needed?
Check the setup | Right feature, model, knowledge files and instructions?
Change one thing | The most likely cause first
Re-test | Same inputs; did that fix it without breaking anything?
```

> [concept] **Fix the cause, not the output.** Editing a bad answer by hand fixes it once. Changing the prompt, the instructions or the knowledge fixes it for every future answer. When the same correction keeps coming up, it belongs upstream.

```chat title="Asking Claude to help diagnose"
you: I asked for a one-page summary of our Q3 patient feedback for the owners, but the result is three pages and mostly lists individual comments. Here's my prompt (pasted). What's wrong with it, and how would you change it?
claude: Your prompt asks Claude to "summarise the feedback", but it doesn't say who the summary is for, how long it should be, or that it should group comments into themes. So I defaulted to covering everything. I'd add: "for the clinic owners", "one page, under 400 words", "group into no more than five themes, with counts", and "end with three recommended actions". Want me to rewrite the prompt with those changes?
note: Claude is a good diagnostic partner for its own prompts. Give it the prompt, the output and what you wanted.
```

### Finding the pattern in a week of problems

When a team uses Claude daily, individual complaints hide a pattern. Logging each poor output with a rough cause shows where to spend effort. This is a simple **Pareto** analysis: sort causes by frequency, and see how few causes account for most problems.

```python
from collections import Counter

log = [  # one entry per output a reviewer flagged this week (cause chosen from the table above)
    "missing context", "wrong format", "outdated info", "missing context", "invented fact",
    "missing context", "wrong format", "outdated info", "outdated info", "missing context",
    "too big a task", "outdated info", "missing context", "wrong format", "ignored project rule",
    "missing context", "outdated info", "wrong format", "missing context", "invented fact",
]
counts = Counter(log).most_common()
total, running = len(log), 0
for cause, n in counts:
    running += n
    print(f"{cause:<22} {n:>2} {'█' * n:<9} cumulative {running / total:5.0%}")
```

> [read] Three causes account for 80% of this week's problems: missing context, outdated information and wrong format. That points to three concrete fixes: add audience and purpose to the team's prompt templates, replace the stale file in the Project knowledge, and add a format rule to the instructions. The rare causes (an invented fact, a too-big task) still matter, especially if they're high-stakes, but they aren't where most of the time is going.

> [exam] Troubleshooting questions usually describe a symptom and offer several fixes. Pick the one that addresses the **root cause** the scenario points to (missing context, stale knowledge, wrong model or feature), not the one that just tries harder ("ask again", "use capital letters", "say please").

```quiz
Q: A Project keeps quoting last quarter's prices even though the team told Claude the new prices in several chats. What is the most likely root cause and fix?
- [ ] Claude is ignoring the team; tell it more firmly in each chat
- [x] An outdated price file is still in the Project knowledge, and chats don't share context; replace the file and remove the old one
- [ ] The model is too small; switch to the most capable model
- [ ] Turn off memory
why: Context isn't shared across chats within a Project unless it's in the knowledge, and the old file is still the source. Fixing the knowledge fixes every future chat.
```

```quiz
Q: Outputs for a recurring task are well written but vary in structure every time. Which change addresses the cause?
- [ ] Ask Claude to "be more consistent"
- [x] Add an example of the exact structure, and a format rule, to the instructions or prompt template
- [ ] Use a different model each time
- [ ] Shorten the prompt
why: Inconsistent structure usually means Claude hasn't been shown the target structure. An example plus a clear format rule is the targeted fix.
```

## 7.2 | Adjusting from feedback

Feedback tells you whether a change worked. Sources include what users say, what reviewers correct, and how much each draft had to be edited before it was used. The exam objective is to **adjust your approach based on feedback and results**, which means acting on evidence, not on the last complaint you heard.

| Feedback source | What it tells you |
|---|---|
| How much drafts are edited before use | Whether the output is close to what's needed |
| Reviewer corrections, by type | Which instruction or source is causing errors |
| User ratings or comments | Whether people find it useful, and why not |
| Re-test results (Module 5) | Whether a change fixed the problem without breaking others |

### Measuring how much drafts are edited

When people edit Claude's drafts before sending them, the size of the edit is free, objective feedback. Python's built-in `difflib` gives a similarity ratio between the draft and the final version (1.0 means unchanged). Low similarity on one template, week after week, says that template's prompt needs work.

```python
import difflib

pairs = {  # template: (Claude's draft, what staff actually sent)
    "booking confirmation": ("Your appointment at our Bandra clinic is confirmed for Tue 14 Mar at 11 am. Reply C to cancel.",
                             "Your appointment at our Bandra clinic is confirmed for Tue 14 Mar at 11 am. Reply C to cancel."),
    "reminder":             ("Reminder: your dental appointment is tomorrow at 4 pm at our Andheri clinic.",
                             "Reminder: your dental appointment is tomorrow at 4 pm at our Andheri clinic. Please bring your X-rays."),
    "post-treatment care":  ("Thank you for visiting us today. We hope your experience was pleasant and look forward to seeing you again.",
                             "After your filling today: avoid hot drinks for 2 hours and chew on the other side until tomorrow. Call us if pain lasts beyond 3 days."),
}
for name, (draft, final) in pairs.items():
    ratio = difflib.SequenceMatcher(None, draft, final).ratio()
    verdict = "fine" if ratio > 0.9 else "minor edits: consider a small prompt tweak" if ratio > 0.6 else "rewritten: fix the template's prompt"
    print(f"{name:<22} similarity {ratio:.2f} -> {verdict}")
```

> [read] Booking confirmations go out unchanged. Reminders get a small addition ("bring your X-rays"), worth adding to the template. The post-treatment message is essentially rewritten: Claude produced a generic thank-you, but staff needed specific aftercare instructions. That's a missing-context problem, and the fix is to give the template the treatment type and the clinic's approved aftercare notes, which are clinical content a dentist should have approved first.

### Closing the loop

```flow title="From feedback to fix"
Collect | Edits, corrections, comments, re-test results
Group | By template, task and cause
Prioritise | Frequent or high-stakes problems first
Change | One targeted fix to prompt, instructions or knowledge
Check | Did similarity and corrections improve next week?
```

> [warn] Don't over-react to a single piece of feedback. One complaint can be a one-off; a pattern across many outputs is a signal. And when you change something, check that it didn't make other outputs worse: re-run the standard test requests (Module 5).

```quiz
Q: Staff heavily rewrite one particular type of Claude draft every week, while other drafts are sent almost unchanged. What is the best response?
- [ ] Stop using Claude for all drafts
- [x] Examine what staff change in that draft type and update its prompt or instructions to include what's missing
- [ ] Ask staff to stop editing the drafts
- [ ] Switch every task to the most capable model
why: Consistent heavy edits on one draft type point to a specific gap in that template's prompt or context. Fixing it there improves that output without disturbing the ones that already work.
```

## 7.3 | Optimising workflows

Once outputs are good, the next step is making the whole workflow **efficient and effective**: less time, fewer steps, lower cost and fewer errors. Most of the levers have appeared earlier in the course.

| Lever | How it helps | From |
|---|---|---|
| Reusable prompt templates | No rewriting the same request each time | Module 1 |
| Projects with instructions and knowledge | No re-uploading files or re-explaining context | Module 5 |
| The right model for each step | Faster, cheaper models for routine work; capable ones for hard steps | Module 3 |
| Batching | One request handles many similar items | Module 3 |
| Structured output | Results drop straight into spreadsheets or tools | Module 2 |
| Fewer review rounds, risk-matched | Spot-check low-risk items; fully review high-risk ones | Module 2 |
| Connectors | Pull data from Drive, Gmail or Calendar instead of copy-pasting | Module 5 |

### Before and after

The workflow below is a monthly patient-feedback report, first as an ad hoc process and then optimised with the levers above. Time is in minutes per month.

```python
before = [  # step, minutes
    ("Export feedback from forms; copy into a chat",           25),
    ("Re-explain context and report format",                    15),
    ("Prompt, read, re-prompt (about 4 rounds)",                60),
    ("Reformat themes into the report template by hand",        45),
    ("Fact-check every number against the export",              40),
    ("Owner review and edits",                                  30),
]
after = [
    ("Feedback sheet pulled from Drive via the connector",      5),
    ("'Feedback report' Project: instructions + template",      0),
    ("One prompt from the saved template (1–2 rounds)",         15),
    ("Themes returned as a table, pasted into the template",    10),
    ("Spot-check: verify the top 5 figures against the sheet",  15),
    ("Owner review and edits",                                  20),
]
for name, steps in [("before", before), ("after", after)]:
    total = sum(m for _, m in steps)
    print(f"{name:<7} {total:4d} min/month ({total / 60:.1f} h)   steps: {len(steps)}")
saved = sum(m for _, m in before) - sum(m for _, m in after)
print(f"\nsaved {saved} min a month ({saved / sum(m for _, m in before):.0%}); "
      f"biggest single gain: prompting rounds {60 - 15} min")
```

> [read] The monthly report drops from about 3.6 hours to just over an hour, a 70% saving. The largest gain comes from not re-prompting four times, thanks to a saved template inside a Project. Note what wasn't removed: fact-checking became a targeted spot-check of the figures that matter, and owner review stayed. Optimising means removing waste, not removing the safeguards from Module 2.

> [tip] Stop optimising when the next gain isn't worth the effort. Shaving the last five minutes off a monthly task rarely matters; making a daily, high-volume task reliable usually does. Use the value thinking from Module 4.

```quiz
Q: A team re-uploads the same three reference documents and re-explains the report format every week. Which optimisation helps most?
- [ ] Use a more capable model
- [x] Create a Project with the documents as knowledge and the report format in its instructions, plus a saved prompt template
- [ ] Write longer prompts each week
- [ ] Skip the review step to save time
why: Repeated setup is the waste here, and Projects with saved instructions and knowledge remove it. A bigger model doesn't remove repeated work, and skipping review trades time for risk.
```

```quiz
Q: Which TWO changes optimise a workflow without weakening its safeguards? (Select 2)
- [x] Replacing full fact-checking of low-risk figures with a targeted spot-check of the key numbers
- [x] Using a faster, lower-cost model for routine classification steps that were tested and found accurate
- [ ] Removing human review of customer-facing messages
- [ ] Turning off verification because outputs have been good lately
why: Risk-matched review and model choice based on testing improve efficiency while keeping proportionate oversight. Removing review of external messages, or verification altogether, gives up the safeguards.
```

## 7.4 | Bringing it together for the exam

That completes the seven domains. Before you book the exam, run through this checklist against the official blueprint.

| Domain | Weight | Can you… |
|---|---|---|
| 1. Prompting and Task Execution | 14% | Write a prompt with role, task, context, format and constraints; decompose a big task; iterate against criteria? |
| 2. Output Evaluation and Validation | 21% | Spot likely hallucinations, verify against sources, decide the level of human review, pick the output format? |
| 3. Product and Model Selection | 12% | Choose between chat, Projects, Research and artifacts, and between Haiku, Sonnet and Opus? Manage long contexts? |
| 4. Workflow Integration and Solution Design | 16% | Analyse a use case, map a process, augment or redesign it, and explain value and limits honestly? |
| 5. Configuration and Knowledge Management | 12% | Set up a Project with instructions and knowledge, manage connectors, maintain it over time? |
| 6. Governance, Risk, and Responsible Use | 15% | Recognise high-risk uses, protect sensitive data, follow policy, weigh ethics? |
| 7. Troubleshooting and Optimization | 10% | Diagnose root causes, act on feedback, optimise without weakening safeguards? |

> [exam] **How the questions tend to work.** Most are scenarios with one best answer, or a stated number of answers to select. The best answer is usually the one that is specific, evidence-based, proportionate to the risk, and within an Associate's scope (escalating technical work). Answers that rely on Claude's self-confidence, "trying harder", skipping review or ignoring policy are usually distractors.

> [tip] Read the official Exam Guide once more before booking: check the current fee, the format, and the identification and retake rules. It's linked from this course's home page. Good luck.
