## 4.1 | Analysing requirements and use cases

Before deciding *how* to use Claude, be clear on *what problem* you're solving and *whether Claude is the right tool*. A good use case for an Associate is one that's frequent, takes real time, and produces text or analysis a person can check.

Claude is useful at this stage in two ways: it can help you **draw out requirements** (by asking the questions you forgot), and it can help you **assess use cases** against criteria.

```chat title="Claude as a requirements interviewer"
you: Our front desk wants "an AI to handle patient messages". Before we build anything, interview me to pin down the requirements. Ask one question at a time, and stop after the most important five.
claude: Let's start with the scope. Which kinds of patient messages should this cover: booking and rescheduling, questions about treatment, billing, complaints, or all of these?
you: Booking, rescheduling and simple questions like timings and location. Not clinical questions.
claude: Good, that's a clear boundary. Second question: when a message is clinical or unclear, who should it go to, and how quickly do they need to see it?
note: Five questions later, you have scope, escalation rules, volume, languages and success measures, before anything has been built.
```

> [concept] **Separate the need from the proposed solution.** "We need an AI chatbot" is a solution. The need might be "patients wait too long for replies on WhatsApp". Starting from the need opens better options, which might be a template library, a Claude-drafted reply that staff approve, or a change of opening hours.

### Turning a request into requirements

```prompt title="Requirements from a vague request"
Here is a request from our operations manager:
"We spend too long on weekly reports. Can AI fix it?"

Help me turn this into requirements. Produce:
1. The underlying problem, in one sentence
2. Questions I should ask the manager before deciding anything (no more than six)
3. Possible approaches, from smallest change to biggest
4. What success would look like, in measurable terms

Don't recommend a tool yet.
```

### Which use cases first?

Teams usually have more ideas than time. A simple scoring of **value** (how often and how long) against **fit** (how well it suits Claude and how safe it is) makes the choice explicit. The weights here are a sensible starting point, not a standard.

```python
use_cases = [
    # name,                         times/week, minutes each, checkable output?, sensitive data?, needs live system access?
    ("Draft replies to booking queries",  120,  4, True,  False, False),
    ("Weekly operations report",            1, 180, True,  False, False),
    ("Summarise patient feedback monthly",  0.25, 300, True, False, False),
    ("Answer clinical questions",          40,  6, False, True,  False),
    ("Auto-update the booking system",    150,  2, True,  False, True),
]

rows = []
for name, per_week, minutes, checkable, sensitive, live in use_cases:
    hours_month = per_week * minutes * 4.3 / 60
    fit = 3 + (1 if checkable else -2) - (2 if sensitive else 0) - (2 if live else 0)
    rows.append((hours_month * max(fit, 0), name, hours_month, fit, live))

for score, name, hours, fit, live in sorted(rows, reverse=True):
    note = " (needs integration: escalate to a developer)" if live else ""
    print(f"{name:<36} {hours:5.1f} h/month  fit {fit:+d}  priority {score:6.1f}{note}")
```

> [read] Drafting booking replies wins: it's frequent, the output is easy to check, and it needs no special access. The weekly report saves far less time but fits well. Clinical answers score zero: they involve sensitive data and can't be safely checked by front-desk staff, so they're out of scope, not just low priority. Updating the booking system automatically saves real time, but it needs live system access, which is integration work for a developer or Claude Architect, not something an Associate builds alone.

> [exam] The exam guide describes Associates as people who **recognise limitations and escalate** more complex or technical implementations. In scenario questions, an answer that involves building integrations, APIs or agents yourself is often the wrong one for an Associate. Identifying the need and handing it to the right specialist is the right one.

```quiz
Q: A manager says, "We need AI to fix our slow invoice approvals." What is the best first step?
- [ ] Set up a Claude Project immediately and start drafting approvals
- [x] Clarify the underlying problem: where approvals get stuck, how many there are, and what "fixed" would look like
- [ ] Recommend the most capable model
- [ ] Tell the manager AI can't help with approvals
why: Requirements analysis starts with understanding the real problem and measurable success. Jumping to a tool risks solving the wrong problem.
```

```quiz
Q: Which TWO features make a task a strong first use case for an Associate using Claude? (Select 2)
- [x] It happens often and takes meaningful time
- [x] Its output is something a person can readily check
- [ ] It requires direct, automatic changes to a live company database
- [ ] It involves giving patients medical advice
why: Frequent, time-consuming tasks with checkable output give value with manageable risk. Live system changes need technical integration (escalate), and medical advice needs qualified professionals.
```

## 4.2 | Research, planning and process optimisation

Claude can help you understand a process, research how others handle it, plan a change and find where time is lost. Its role here is **analyst and planner**: you supply the facts about your organisation, and it supplies structure, options and questions.

```flow title="Optimising a process with Claude"
Map | Describe the current steps, who does them and how long each takes
Measure | Find the waits and the slowest steps
Research | Look up how others solve the same bottleneck
Redesign | Draft a new process; check it against constraints
Plan | Sequence the change: pilot, measure, roll out
```

### Mapping a process

```prompt title="Process mapping"
Here's how a new patient booking works today (notes below, written by our front-desk lead).

Turn this into a numbered process map. For each step give: who does it, roughly how long it takes, and how long the patient waits before the next step.

Then identify the two steps that add the most delay, and explain why in one sentence each. Don't propose solutions yet.
```

> [tip] Ask for the analysis before the solutions. If you ask for both at once, the solutions tend to anchor on the first problem mentioned rather than the biggest one.

### Finding the bottleneck

The numbers below describe a new-patient booking process. The code adds up working time and waiting time, finds the biggest delay, then compares a redesigned version where Claude drafts the replies and a person approves them. Note the review time has been added, not ignored.

```python
current = [  # step, minutes of work, minutes the patient waits after it
    ("Read WhatsApp enquiry",        2,   0),
    ("Check dentist availability",   5,  30),
    ("Write reply with slots",       6, 120),
    ("Patient picks slot",           0, 180),
    ("Confirm and send forms",       8,  60),
]
redesigned = [
    ("Read WhatsApp enquiry",        2,   0),
    ("Check dentist availability",   5,   0),
    ("Claude drafts reply; staff review", 2, 10),
    ("Patient picks slot",           0, 180),
    ("Claude drafts confirmation; staff review", 2, 10),
]

def summarise(name, steps):
    work = sum(w for _, w, _ in steps)
    wait = sum(t for _, _, t in steps)
    worst = max(steps, key=lambda s: s[2])
    print(f"{name:<11} work {work:3d} min | waiting {wait:4d} min | total {(work + wait) / 60:4.1f} h | longest wait: '{worst[0]}' ({worst[2]} min)")

summarise("current", current)
summarise("redesigned", redesigned)
```

> [read] Staff work drops from 21 to 11 minutes per booking, and the patient's total time falls from about 6.8 hours to 3.5. But the biggest delay in both versions is the patient choosing a slot, which Claude doesn't touch. That's a useful finding in itself: the next improvement might be offering a booking link instead of a reply to wait for, which is a process change, not an AI one.

> [warn] Claude's research is a starting point. When it describes how other organisations handle something, or quotes a statistic, verify the important parts (Module 2) before they go into a proposal.

```quiz
Q: Claude helped map a process and found that the longest delay is customers waiting for an approval email from a manager. What is the best interpretation?
- [ ] Claude should write the approval emails faster
- [x] The bottleneck is the approval step itself, so options include changing who approves or what needs approval, not just faster drafting
- [ ] The process map must be wrong
- [ ] Switch to a more capable model
why: Process analysis should target the real bottleneck. When the delay is a human decision, the fix is usually a process change. Faster drafting doesn't shorten a wait for approval.
```

## 4.3 | Supporting solution design

Once you know the need, Claude can help design a solution: options, trade-offs, a first version, and improvements based on feedback. The exam expects you to use Claude to **support** design, development and iteration, not to hand over judgment.

```flow title="Design and iterate"
Options | Ask for three approaches, from simple to ambitious
Trade-offs | Compare effort, risk, cost and fit
Prototype | Build the simplest version that tests the idea
Feedback | Try it with real users and real cases
Iterate | Change one thing at a time; keep what works
```

```chat title="Exploring options before committing"
you: We want patients to get a reminder the day before their appointment, with a way to reschedule. Give me three approaches, from the simplest to the most automated, with what each needs from our team.
claude: Here are three, from least to most effort:
- Manual with templates: staff send a pre-written WhatsApp message each evening from the booking list. Needs: a template and 20 minutes a day.
- Claude-assisted batch: each evening, paste tomorrow's bookings into a Project and get personalised messages to send. Needs: a Project with instructions; a staff member to review and send.
- Fully automated: the booking system sends reminders and handles replies. Needs: a developer, integration with your booking system and WhatsApp's business tools.
note: The third option is integration work: an Associate would scope it and escalate it, not build it.
```

### Tracing requirements to the design

A common design failure is quietly dropping a requirement. Tracing each requirement to the part of the solution that meets it makes gaps obvious.

```python
requirements = {
    "R1": "Reminder sent the day before",
    "R2": "Patient can reschedule from the message",
    "R3": "Messages in English, Hindi or Marathi",
    "R4": "No clinical details in the message",
    "R5": "Staff can see who confirmed",
}
design = {   # part of the Claude-assisted batch design -> requirements it meets
    "Evening batch in the 'Reminders' Project": ["R1"],
    "Template with booking link":              ["R1", "R2"],
    "Project instruction: language from booking record": ["R3"],
    "Project instruction: only date, time, clinic, link": ["R4"],
}

covered = {r for parts in design.values() for r in parts}
for rid, text in requirements.items():
    by = [part for part, rs in design.items() if rid in rs]
    print(f"{rid} {text:<40} {'covered by: ' + '; '.join(by) if by else 'NOT COVERED'}")
```

> [read] Four of five requirements are met. R5, staff seeing who confirmed, isn't covered by any part of the design: the batch sends messages, but replies come back to WhatsApp, not into a list. That's the kind of gap that's cheap to spot now and expensive to discover after rollout. Options: add a step where replies are pasted back into the Project for a summary, or accept it as a known limitation and say so.

> [tip] Iterate like you did with prompts (Module 1): change one thing, test with real cases, keep what works. A pilot with one clinic for two weeks teaches more than a perfect plan.

```quiz
Q: When using Claude to support solution design, what is the most appropriate role for Claude?
- [ ] Make the final decision on which solution to adopt
- [x] Generate options and trade-offs, draft prototypes, and help analyse feedback, while people make the decisions
- [ ] Only check spelling in the final design document
- [ ] Build integrations with company systems directly
why: Claude supports design by widening the options and speeding up drafting and analysis. Decisions stay with people, and integration work is escalated to technical specialists.
```

## 4.4 | Augmenting or redesigning a workflow

There are two broad ways to bring Claude into existing work:

| Approach | What changes | Example | Trade-off |
|---|---|---|---|
| Augment | The same workflow, with Claude speeding up a step | Staff still write the weekly report, but Claude drafts it from their notes | Quick to start, modest gains |
| Redesign | The workflow itself is rebuilt around what Claude does well | Teams submit updates in a fixed format; a Project turns them into the report; the manager reviews | More setup and change management, bigger gains |

```compare style=neutral
# Augment
Monday: each clinic manager emails notes as usual.
Ops lead pastes the notes into Claude: "Draft this week's report."
Ops lead edits the draft for 40 minutes, then sends it.
---
# Redesign
Friday: each clinic fills in a 5-field update form.
Monday: ops lead pastes the forms into the "Weekly report" Project, which has the template and rules.
Ops lead reviews for 15 minutes, then sends it.
```

> [concept] **Augment first, redesign once you've learned.** Augmenting a step shows you where Claude helps and where it struggles, with little risk. That evidence is what justifies, and shapes, a redesign.

### When does a redesign pay back?

Redesigning costs setup time (forms, instructions, training) before it saves time. The calculation below compares the two over twelve weeks, using hours as the cost.

```python
weeks = 12
baseline   = 3.0                     # hours a week, writing the report by hand
augment    = {"setup": 1.0, "weekly": 1.6}    # Claude drafts; ops lead edits
redesign   = {"setup": 8.0, "weekly": 0.6}    # forms + Project + training; review only

def cumulative(plan):
    return [plan["setup"] + plan["weekly"] * w for w in range(1, weeks + 1)]

aug, red, base = cumulative(augment), cumulative(redesign), [baseline * w for w in range(1, weeks + 1)]
for w in (1, 2, 4, 6, 8, 12):
    print(f"week {w:>2}: by hand {base[w-1]:5.1f} h | augment {aug[w-1]:5.1f} h | redesign {red[w-1]:5.1f} h")
breakeven = next(w for w in range(1, weeks + 1) if red[w-1] <= aug[w-1])
print(f"\nredesign overtakes augment in week {breakeven}; saved vs by-hand after {weeks} weeks: "
      f"augment {base[-1] - aug[-1]:.1f} h, redesign {base[-1] - red[-1]:.1f} h")
```

> [read] Augmenting saves time from week one. The redesign starts behind because of its 8 hours of setup, overtakes the augmented version in week 7, and by week 12 has saved 5 hours more. For a report that runs every week for a year, the redesign clearly wins. For a short-lived process, augmenting is the better choice. The numbers are illustrative; the shape of the trade-off is the lesson.

> [warn] Redesign changes people's jobs and habits. Involve the people who do the work, explain what changes and why, and keep a human review step. A redesign that saves the ops lead time but adds unexplained forms for clinic managers may just move the work around.

```quiz
Q: A team has never used Claude for its monthly board report. What is usually the best way to start?
- [x] Augment the existing process (for example, Claude drafts from the usual inputs) and learn where it helps before redesigning
- [ ] Redesign the whole reporting process before trying Claude at all
- [ ] Fully automate the report so no one needs to review it
- [ ] Wait until the process is perfect before involving Claude
why: Augmenting first is low-risk and produces evidence about what works, which then guides any redesign. Removing human review from a board report would be inappropriate.
```

## 4.5 | Communicating value and limits

Part of the Associate role is explaining Claude to colleagues and managers: what it does well, what it doesn't, and what it's worth. Overselling damages trust faster than underselling.

### What to say, and what to avoid

| Do | Avoid |
|---|---|
| "Claude drafts the report; Priya reviews it, saving about 2 hours a week" | "AI writes our reports now" |
| "It's good at summarising and drafting; we verify facts and figures" | "It's always accurate" |
| "It doesn't have access to our booking system; that would need a developer" | Implying it can do things it can't |
| "In the pilot, X; we'll know more after Y" | Promising results before measuring |

```chat title="Briefing a sceptical stakeholder"
you: The clinic owner asked me: "Is this AI thing safe to use with patients?" Help me draft a short, honest answer.
claude: Here's a draft:
"We're using Claude to draft routine messages (booking confirmations and reminders), and a staff member reviews every message before it's sent. It doesn't make clinical decisions and doesn't have access to patient records. We remove personal details before using it for analysis, in line with our data policy. In the four-week pilot, it saved about 6 front-desk hours a week, with no complaints. The main limitation is that it can occasionally get details wrong, which is why every message is checked."
note: Value, safeguards and limits in five sentences, with nothing promised beyond the evidence.
```

### An honest value estimate

Value estimates are guesses until measured, so give a range, not a single number, and include the costs: the plan's cost and the time people spend reviewing. All the figures below are illustrative assumptions.

```python
hourly_cost = 450            # ₹ per staff hour, fully loaded (illustrative)
seats, seat_cost = 3, 2_500  # ₹ per seat per month (illustrative assumption, not a quoted price)
scenarios = {                # hours saved per week, hours of review added per week
    "cautious": (4, 2.0),
    "expected": (8, 2.5),
    "optimistic": (12, 3.0),
}
for name, (saved, review) in scenarios.items():
    net_hours = (saved - review) * 4.3
    value = net_hours * hourly_cost - seats * seat_cost
    print(f"{name:<11} net {net_hours:5.1f} h/month -> net value ₹{value:8,.0f} a month")
```

> [read] The cautious case *loses* money, about ₹3,600 a month, once review time and seats are counted; the expected case gains about ₹3,100 and the optimistic one about ₹9,900. That spread is the honest message: with about 2½ hours of review a week, the pilot pays only if it saves more than about 6½ hours a week, so measure that first. Presenting the range, with review time visible, is more convincing than a single optimistic figure, and it tells stakeholders exactly what has to be true for the investment to pay. Replace the assumptions with your own measured numbers after a pilot.

> [exam] Questions in this area reward **balanced, evidence-based** communication: clear about value, explicit about limitations and safeguards, and honest about what still needs human oversight or technical work.

```quiz

- [ ] "Yes, it can replace them completely."
- [ ] "No, AI isn't useful for writing emails."

- [ ] "It depends; let's not discuss it until the technology is perfect."
why: A balanced answer states the realistic value, the limitation and the safeguard. Overclaiming and dismissing both mislead stakeholders.
```
