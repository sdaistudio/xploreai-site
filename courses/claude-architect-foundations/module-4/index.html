Task statement 4.1

Explicit criteria

Instructions like "be conservative" or "only report high-confidence findings" don't improve precision: the model has no shared definition of conservative, and its confidence isn't calibrated. What works is specific, categorical criteria: which issues to report and which to skip.

✗ Vague
Review this PR. Be conservative and only report
issues you're confident about. Check that the
comments are accurate.
✓ Explicit criteria
Report only:
- Bugs: wrong logic, unhandled None, off-by-one, race conditions
- Security: injection, missing authorisation, secrets in code or logs
- Comments whose claimed behaviour contradicts what the code actually does
Do not report: formatting, naming preferences, patterns used consistently elsewhere in this repo.
Severity: HIGH = exploitable or data-corrupting (e.g. SQL built with f-strings);
MEDIUM = wrong result in an edge case (e.g. empty list crashes);
LOW = misleading comment with no behavioural effect.
The idea

False positives cost trust across the board. If one category (say, "performance") is wrong half the time, developers start ignoring all findings, including the accurate security ones. A pragmatic fix is to temporarily disable the high-false-positive categories while you improve their criteria, restoring trust in the rest.

Here's that decision made from a month of review data, using how often developers dismissed each category's findings.

Python
FINDINGS = {  # category: (posted, dismissed by developers as wrong)
    "security":        (48, 3),
    "bug":             (160, 22),
    "comment-accuracy": (35, 6),
    "performance":     (120, 71),
    "style":           (310, 236),
}
total_posted = sum(p for p, _ in FINDINGS.values())
total_wrong = sum(d for _, d in FINDINGS.values())
print(f"overall: {total_wrong / total_posted:.0%} of all findings dismissed\n")
keep = {}
for cat, (posted, wrong) in sorted(FINDINGS.items(), key=lambda kv: kv[1][1] / kv[1][0]):
    fp_rate = wrong / posted
    action = "keep" if fp_rate <= 0.25 else "DISABLE while criteria are rewritten"
    if action == "keep": keep[cat] = (posted, wrong)
    print(f"{cat:<17} false-positive rate {fp_rate:>4.0%}  → {action}")
kp = sum(p for p, _ in keep.values()); kw = sum(w for _, w in keep.values())
print(f"\nafter disabling: {kw / kp:.0%} of findings dismissed ({kp} posted instead of {total_posted})")
Output · produced by running this code
overall: 50% of all findings dismissed

security          false-positive rate   6%  → keep
bug               false-positive rate  14%  → keep
comment-accuracy  false-positive rate  17%  → keep
performance       false-positive rate  59%  → DISABLE while criteria are rewritten
style             false-positive rate  76%  → DISABLE while criteria are rewritten

after disabling: 13% of findings dismissed (243 posted instead of 673)
How to read it

Half of all findings were being dismissed, almost entirely because of the style and performance categories. Disabling those two while their criteria are rewritten drops the dismissal rate to about 13% and keeps every security finding flowing. That's how you rebuild developer trust without losing the valuable categories.

Practice questionAn automated reviewer's false-positive rate is high. A teammate proposes adding "Only report findings you are highly confident about." What does the exam guide say?

The model's self-assessed confidence isn't calibrated, and "confident" means nothing specific. Categorical criteria (report X, skip Y) with severity examples do improve precision.

Practice questionSelect 2Developers have started ignoring all automated review comments because one category is wrong most of the time. What's a sound short-term step? (Select 2)

Turning off the noisy category restores trust in the accurate ones, and concrete severity criteria make classification consistent.

Task statement 4.2

Few-shot examples

When detailed instructions still produce inconsistent output, few-shot examples are the most effective fix. The guide's recipe: 2–4 targeted examples for the ambiguous cases, each showing why one action was chosen over plausible alternatives, not just the answer. Examples also:

  • Show the output format you need (location, issue, severity, suggested fix).
  • Distinguish acceptable patterns from genuine issues, which cuts false positives while still letting the model generalise.
  • Demonstrate extraction from varied document structures (inline citations vs bibliographies; narrative vs tables), which reduces empty or invented values.
A targeted example that shows reasoning (review prompt excerpt)
<example>
<code>
items = fetch_items(order_id)
total = sum(i.price for i in items)
</code>
<finding>none</finding>
<reasoning>Looks like it might crash on an empty order, but sum() of an empty
sequence is 0, which is the correct total. Not a bug, so no finding. (Contrast:
`items[0].price` on an empty list WOULD be a HIGH finding.)</reasoning>
</example>

Examples are easy to get subtly wrong. Here's a check over a candidate example set: does each example carry reasoning, follow the required output format, and cover a distinct ambiguity?

Python
REQUIRED_FORMAT = {"location", "issue", "severity", "fix"}
EXAMPLES = [
    {"ambiguity": "empty-sequence sum", "finding": None, "reasoning": "sum([]) is 0, the correct total; not a bug"},
    {"ambiguity": "SQL via f-string", "finding": {"location": "db.py:12", "issue": "SQL injection", "severity": "HIGH", "fix": "parameterise"},
     "reasoning": "user input reaches the query string; parameters exist in this codebase"},
    {"ambiguity": "SQL via f-string", "finding": {"location": "db.py:40", "issue": "SQL injection", "severity": "HIGH", "fix": "parameterise"},
     "reasoning": None},
    {"ambiguity": "TODO comment", "finding": {"location": "api.py:7", "issue": "TODO left"}, "reasoning": "style only"},
]
seen = set()
for i, ex in enumerate(EXAMPLES, 1):
    problems = []
    if not ex["reasoning"]: problems.append("no reasoning: teaches the answer, not the judgement")
    if ex["finding"] and not REQUIRED_FORMAT <= set(ex["finding"]): problems.append(f"missing format fields {sorted(REQUIRED_FORMAT - set(ex['finding']))}")
    if ex["ambiguity"] in seen: problems.append("duplicates an ambiguity already covered")
    seen.add(ex["ambiguity"])
    print(f"example {i} ({ex['ambiguity']}): {'; '.join(problems) or 'ok'}")
print(f"\n{len(seen)} distinct ambiguities in {len(EXAMPLES)} examples (target: 2–4 targeted, each different)")
Output · produced by running this code
example 1 (empty-sequence sum): ok
example 2 (SQL via f-string): ok
example 3 (SQL via f-string): no reasoning: teaches the answer, not the judgement; duplicates an ambiguity already covered
example 4 (TODO comment): missing format fields ['fix', 'severity']

3 distinct ambiguities in 4 examples (target: 2–4 targeted, each different)
How to read it

Examples 1 and 2 are good: each demonstrates a different judgement and explains it. Example 3 repeats example 2 with no reasoning, so it adds tokens and nothing new. Example 4 breaks the output format (no severity or fix), so it would teach the model to omit them, and its "finding" is a style issue the criteria say to skip.

Practice questionA team adds ten examples that show only the final classification for clear-cut cases. Inconsistency on borderline cases persists. What should change?

Examples teach judgement when they target the ambiguous cases and show the reasoning; answer-only examples of easy cases add tokens without resolving the ambiguity.

Practice questionAn extraction prompt returns null for "methodology" when papers describe it inside the introduction rather than in a section titled "Methods". What helps most?

Examples that demonstrate varied structures (embedded details vs dedicated sections) teach the model where to look, reducing empty extractions.

Task statement 4.3

Structured output with tool use

Defining an extraction "tool" whose input schema is the structure you want and reading the model's tool_use input is, in the guide's words, the most reliable way to get schema-compliant output: no more JSON syntax errors.

Pythonshown, not run here
extract_invoice = {
    "name": "extract_invoice",
    "description": "Record the fields of one supplier invoice.",
    "input_schema": {
        "type": "object",
        "properties": {
            "invoice_number": {"type": "string"},
            "invoice_date":   {"type": ["string", "null"], "description": "ISO date; null if not stated"},
            "po_number":      {"type": ["string", "null"], "description": "Purchase order; null if absent"},
            "category":       {"type": "string", "enum": ["goods", "services", "freight", "other", "unclear"]},
            "category_detail": {"type": ["string", "null"], "description": "Required when category is 'other'"},
            "line_items":     {"type": "array", "items": {"type": "object", "properties": {"amount": {"type": "number"}}}},
            "stated_total":   {"type": "number"},
        },
        "required": ["invoice_number", "category", "line_items", "stated_total"],
    },
}
response = client.messages.create(model="claude-sonnet-5-5", max_tokens=2048, tools=[extract_invoice],
                                  messages=[{"role": "user", "content": [pdf_block, {"type": "text", "text": "Record this invoice with extract_invoice."}]}])
data = next(b.input for b in response.content if b.type == "tool_use")
Watch out

Schemas stop syntax errors, not semantic ones. A perfectly valid object can still have line items that don't sum to the total, or a value in the wrong field. And a required field the document doesn't contain invites the model to fabricate a value to satisfy the schema. Make such fields optional and nullable, add "unclear" to enums for ambiguous cases, and use "other" plus a detail field for extensible categories.

Here's the fabrication risk made concrete: the same document under two schemas. The "model" fills fields the way an over-eager extractor would (a stand-in, labelled as such); the schema validation is real.

Python
DOC = "Invoice INV-5521 from Kaveri Freight. Items: haulage ₹18,000; loading ₹2,500. Total ₹20,500."

def stand_in_extract(schema_required):
    out = {"invoice_number": "INV-5521", "category": "freight", "line_items": [18000, 2500], "stated_total": 20500}
    for f in ("invoice_date", "po_number"):
        out[f] = ("2026-10-01" if f == "invoice_date" else "PO-0001") if f in schema_required else None
    return out

def validate(record, required, enums=("goods", "services", "freight", "other", "unclear")):
    errs = [f"missing {f}" for f in required if record.get(f) is None]
    if record["category"] not in enums: errs.append("category not in enum")
    if record["category"] == "other" and not record.get("category_detail"): errs.append("'other' needs category_detail")
    return errs or ["schema-valid"]

for label, required in [("date and PO required", ["invoice_number", "invoice_date", "po_number"]),
                        ("date and PO nullable", ["invoice_number"])]:
    rec = stand_in_extract(required)
    invented = [f for f in ("invoice_date", "po_number") if rec[f] is not None and rec[f] not in DOC]
    print(f"{label:<22} {validate(rec, required)}  invented values: {invented or 'none'}")
Output · produced by running this code
date and PO required   ['schema-valid']  invented values: ['invoice_date', 'po_number']
date and PO nullable   ['schema-valid']  invented values: none
How to read it

Both records pass their schemas, which is the point: validation can't tell that "2026-10-01" and "PO-0001" appear nowhere in the document. With the fields required, the extractor had to put something there; with them nullable, it could honestly return null.

tool_choice for structured output

The guide's patterns: "any" guarantees a tool call when several extraction schemas exist and the document type is unknown; {"type": "tool", "name": "extract_metadata"} forces a particular extraction to run before enrichment. Then vs now: Opus 5.5, Sonnet 5.5 and Fable 5.1 reject both with a 400; on those models use auto with an instruction and check that the call happened, add strict: true for schema-valid input, or use structured outputs (output_config.format).

Practice questionAn extraction schema makes "po_number" required. Many invoices have no PO, and audits find invented PO numbers. What's the fix?

A required field the source lacks pressures the model to fabricate. Nullable fields let it represent absence honestly.

Practice questionSelect 2Which statements about tool-use structured output are true? (Select 2)

Schemas guarantee shape, not meaning: semantic checks such as totals still need validation. "unclear" and "other"+detail give the model honest options; required fields can cause fabrication.

Task statement 4.4

Validation, retry and feedback

Retry with error feedback: when validation fails, send a follow-up containing the original document, the failed extraction and the specific validation errors, and ask for a corrected extraction. It works for format and structural errors. It doesn't work when the information simply isn't in the document (it's in an attachment you didn't send, say); retrying then just invites invention.

Build semantic checks into the extraction itself: extract a calculated_total alongside the stated_total, and a conflict_detected flag when the source contradicts itself.

Python
import re

def check(rec):
    errs = []
    if rec.get("invoice_date") and not re.fullmatch(r"\d{4}-\d{2}-\d{2}", rec["invoice_date"]):
        errs.append(f"invoice_date {rec['invoice_date']!r} is not ISO YYYY-MM-DD")
    calc = sum(rec["line_items"])
    if calc != rec["stated_total"] and not rec.get("conflict_detected"):
        errs.append(f"line items sum to {calc} but stated_total is {rec['stated_total']}; set conflict_detected if the document itself disagrees")
    if rec.get("gst_number") is None and rec.get("_gst_only_in_attachment"):
        errs.append("gst_number missing")
    return errs

ATTEMPTS = [  # what a stand-in model returns on each try
    {"invoice_date": "14/10/26", "line_items": [18000, 2500], "stated_total": 21500, "gst_number": None, "_gst_only_in_attachment": True},
    {"invoice_date": "2026-10-14", "line_items": [18000, 2500], "stated_total": 21500, "conflict_detected": True, "gst_number": None, "_gst_only_in_attachment": True},
]
for i, rec in enumerate(ATTEMPTS, 1):
    errs = check(rec)
    print(f"attempt {i}: {errs or 'valid'}")
    fixable = [e for e in errs if "gst_number" not in e]
    if errs and not fixable:
        print("   remaining error is about information that isn't in this document → stop retrying; leave gst_number null and flag for review")
        break
Output · produced by running this code
attempt 1: ["invoice_date '14/10/26' is not ISO YYYY-MM-DD", 'line items sum to 20500 but stated_total is 21500; set conflict_detected if the document itself disagrees', 'gst_number missing']
attempt 2: ['gst_number missing']
   remaining error is about information that isn't in this document → stop retrying; leave gst_number null and flag for review
How to read it

The first retry fixes everything that can be fixed from the document: the date format, and an honest conflict_detected because the invoice's own total is wrong (20,500 vs 21,500). The GST number only exists in an attachment that wasn't sent, so a further retry can't help; the pipeline stops, keeps the field null and routes it to review.

Tip

Close the loop on review findings too. Add a detected_pattern field to each finding (e.g. "f-string SQL", "bare except") so that when developers dismiss findings you can see which patterns produce false positives and fix the criteria for those.

Practice questionValidation reports that an extracted "contract_end_date" is missing. The contract says the end date is "as set out in Schedule B", which wasn't provided. Will retry-with-error-feedback help?

Retries fix format and structural errors. When the source doesn't contain the value, the right action is to record its absence or fetch the missing document.

Practice questionWhich design helps catch extractions whose numbers don't add up?

Having both values makes discrepancies checkable in code, and the flag lets the model report a genuinely inconsistent source rather than "fixing" it.

Task statement 4.5

Batch processing

The Message Batches API: 50% cost saving, processing within a 24-hour window, no guaranteed latency. Each request is matched to its result by custom_id. It suits non-blocking work (overnight reports, weekly audits, nightly test generation) and not blocking work (pre-merge checks developers wait on). One more constraint: a batch request can't do multi-turn tool calling (it can't pause mid-request for your code to run a tool and return the result).

Meeting an SLA with batches

If results are promised within 30 hours and a batch can take up to 24, documents must be submitted within 6 hours of arriving. Submitting every 4 hours leaves margin for retries.

Python
def worst_case_hours(submit_every, batch_max=24):
    return submit_every + batch_max            # a document arriving just after a submission waits a full interval

SLA = 30
for every in (2, 4, 6, 8, 12):
    w = worst_case_hours(every)
    print(f"submit every {every:>2} h → worst case {w} h  {'meets' if w <= SLA else 'BREAKS'} the {SLA} h SLA" + ("  (margin for one resubmission cycle)" if SLA - w >= 2 else ""))

results = {"doc-001": "succeeded", "doc-002": "errored: prompt too long", "doc-003": "succeeded", "doc-004": "expired"}
resubmit = {cid: ("split into chunks" if "too long" in r else "resubmit unchanged") for cid, r in results.items() if r != "succeeded"}
print("\nresubmit only failures, by custom_id:", resubmit)
Output · produced by running this code
submit every  2 h → worst case 26 h  meets the 30 h SLA  (margin for one resubmission cycle)
submit every  4 h → worst case 28 h  meets the 30 h SLA  (margin for one resubmission cycle)
submit every  6 h → worst case 30 h  meets the 30 h SLA
submit every  8 h → worst case 32 h  BREAKS the 30 h SLA
submit every 12 h → worst case 36 h  BREAKS the 30 h SLA

resubmit only failures, by custom_id: {'doc-002': 'split into chunks', 'doc-004': 'resubmit unchanged'}
How to read it

Every 4 hours gives a 28-hour worst case, inside 30 with a little margin; every 8 or 12 hours breaks the SLA even though most batches finish far sooner, because the API gives no latency guarantee. When a batch returns, resubmit only the failed custom_ids, adapted to the failure (chunk the oversized document), and refine the prompt on a sample before the big run so fewer documents fail at all.

Practice questionA manager proposes moving both the blocking pre-merge check and the overnight technical-debt report to the Batches API for the 50% saving. What's the right call?

Batches can take up to 24 hours with no latency guarantee, which is unacceptable for a blocking check but ideal overnight. Ordering isn't a problem: custom_id correlates results.

Practice questionWhy can't an agent workflow that calls tools mid-conversation simply be moved to the Batches API?

Each batch request runs to completion on its own; the interactive request–execute–return loop needs synchronous calls.

Task statement 4.6

Multi-instance and multi-pass review

A model reviewing its own work in the same session keeps the reasoning that produced it, and is less likely to question its own decisions. The guide is specific: an independent instance without that context catches subtle issues better than self-review instructions or extended thinking.

PatternUse
Independent review instanceA second Claude instance reviews generated code with only the diff and the criteria
Multi-pass reviewPer-file passes for local issues, plus a separate integration pass for cross-file data flow; avoids attention dilution and contradictory findings
Verification pass with confidenceThe reviewer reports a confidence with each finding, so findings can be routed: high-confidence to the PR, low-confidence to a human or dropped

Self-reported confidence is only useful once calibrated against labelled data. Here's that calibration on a set of past findings that developers labelled as real or not.

Python
LABELLED = [  # (reviewer's self-reported confidence, was it a real issue?)
    *[(0.9, True)] * 46, *[(0.9, False)] * 4,
    *[(0.7, True)] * 30, *[(0.7, False)] * 20,
    *[(0.5, True)] * 12, *[(0.5, False)] * 38,
]
for c in (0.9, 0.7, 0.5):
    bucket = [real for conf, real in LABELLED if conf == c]
    precision = sum(bucket) / len(bucket)
    route = "post to PR" if precision >= 0.85 else ("human triage" if precision >= 0.5 else "drop (log for pattern analysis)")
    print(f"confidence {c}: {len(bucket)} findings, {precision:.0%} real → {route}")
Output · produced by running this code
confidence 0.9: 50 findings, 92% real → post to PR
confidence 0.7: 50 findings, 60% real → human triage
confidence 0.5: 50 findings, 24% real → drop (log for pattern analysis)
How to read it

Findings the reviewer marks 0.9 are real 92% of the time, so they can go straight to the PR. At 0.7 it's 60%, worth a quick human look. At 0.5 only about a quarter are real, so posting them would erode trust. The thresholds come from labelled data, not from the model's raw numbers.

Practice questionClaude generated a module and was then asked, in the same session, to review it carefully. It approved everything; a colleague later found two subtle bugs. What's the better design?

The generating session retains its reasoning and tends to confirm it. An independent instance reviews the code on its own merits.

Practice questionA reviewer outputs a confidence score with each finding. How should those scores be used for routing?

Self-reported confidence isn't calibrated by default. Measuring precision per confidence level on labelled data turns it into a usable routing signal.
