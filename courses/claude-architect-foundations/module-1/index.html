Task statement 1.1

Agentic loops

An agentic loop turns one model call into a goal-directed process: send the request, read stop_reason, run any requested tools, append the results, and go again. The model decides which tool to call next from the context it has; your code executes and feeds back. That's model-driven decision-making, as opposed to a pre-configured decision tree where your code fixes the sequence.

stop_reasonYour loop should
tool_useExecute every tool requested, append results, continue
end_turnStop: the model has finished
max_tokensNot finished: raise the limit or continue; don't treat as done
pause_turn / refusalResume a paused server-tool turn / handle the refusal, never as a normal answer
Watch out

The anti-patterns the guide names. Don't decide the loop is over by parsing natural-language signals ("I'm done", "Task complete"), by checking whether the assistant returned text, or by an arbitrary iteration cap used as the main stopping rule. Claude often writes text and calls a tool in the same turn ("Let me check that order…"), and a cap stops correct runs mid-task. A cap is a safety net; stop_reason is the control signal.

Correct control versus the anti-patterns, run side by side

The model here is a scripted stand-in that behaves the way Claude does: text alongside tool calls, the word "done" appearing mid-task, and a run that legitimately needs five turns.

Python
SCRIPT = [
    {"stop_reason": "tool_use", "content": [{"type": "text", "text": "Let me look up the customer first."},
                                             {"type": "tool_use", "id": "t1", "name": "get_customer", "input": {"email": "meera@example.com"}}]},
    {"stop_reason": "tool_use", "content": [{"type": "text", "text": "Customer lookup done. Now the order."},
                                             {"type": "tool_use", "id": "t2", "name": "lookup_order", "input": {"order_id": "ORD-1182"}}]},
    {"stop_reason": "tool_use", "content": [{"type": "tool_use", "id": "t3", "name": "check_return_window", "input": {"order_id": "ORD-1182"}}]},
    {"stop_reason": "tool_use", "content": [{"type": "tool_use", "id": "t4", "name": "process_refund", "input": {"order_id": "ORD-1182", "amount": 42.0}}]},
    {"stop_reason": "end_turn", "content": [{"type": "text", "text": "Refund of $42.00 issued for ORD-1182."}]},
]

def run(stop_rule, max_iter=10):
    history, turns = [{"role": "user", "content": "My blender arrived broken, refund please."}], 0
    for turn in range(max_iter):
        reply = SCRIPT[turn]; turns += 1
        history.append({"role": "assistant", "content": reply["content"]})
        if stop_rule(reply, turn):
            break
        results = [{"type": "tool_result", "tool_use_id": b["id"], "content": "ok"} for b in reply["content"] if b["type"] == "tool_use"]
        history.append({"role": "user", "content": results})
    called = [b["name"] for m in history if m["role"] == "assistant" for b in m["content"] if b["type"] == "tool_use"]
    executed = called if stop_rule(SCRIPT[turns - 1], turns - 1) is False or SCRIPT[turns - 1]["stop_reason"] == "end_turn" else called[:-1]
    return turns, executed

RULES = {
    "stop_reason == end_turn (correct)": lambda r, t: r["stop_reason"] == "end_turn",
    "stop when the reply contains text": lambda r, t: any(b["type"] == "text" for b in r["content"]),
    "stop when text says 'done'":        lambda r, t: any("done" in b.get("text", "").lower() for b in r["content"]),
    "stop after 3 iterations (cap)":     lambda r, t: t + 1 >= 3,
}
for name, rule in RULES.items():
    turns, executed = run(rule)
    print(f"{name:<36} stopped after {turns} turn(s); tools run: {executed}")
Output · produced by running this code
stop_reason == end_turn (correct)    stopped after 5 turn(s); tools run: ['get_customer', 'lookup_order', 'check_return_window', 'process_refund']
stop when the reply contains text    stopped after 1 turn(s); tools run: []
stop when text says 'done'           stopped after 2 turn(s); tools run: ['get_customer']
stop after 3 iterations (cap)        stopped after 3 turn(s); tools run: ['get_customer', 'lookup_order']
How to read it

Only the stop_reason rule completes the task and issues the refund. "Stop on text" quits on the very first turn, because Claude explained what it was about to do. "Stop on 'done'" quits after the customer lookup ("Customer lookup done"). The iteration cap stops before the refund. Each anti-pattern produces a plausible-looking but unfinished run.

Practice questionAn agent's loop ends whenever the assistant's response contains a text block. Users report tasks left half-done. Why?

Text presence isn't a completion signal. stop_reason is: "tool_use" means execute tools and continue, "end_turn" means finished.

Practice questionSelect 2Which are anti-patterns for deciding when an agentic loop should stop? (Select 2)

Natural-language signals and arbitrary caps both end runs at the wrong time. A cap is fine as a safety limit, but stop_reason is the control signal.

Task statement 1.2

Coordinator–subagent orchestration

In hub-and-spoke orchestration, a coordinator manages all communication between subagents, all error handling and all information routing. Subagents never talk to each other directly, which gives you one place to observe, handle errors consistently and control what flows where. Each subagent has an isolated context: it doesn't inherit the coordinator's conversation.

The coordinator's jobs, as the guide frames them:

  • Select subagents dynamically. A simple factual query shouldn't run the full search–analyse–synthesise–report pipeline.
  • Partition scope so subagents don't duplicate each other: distinct subtopics, or distinct source types.
  • Avoid over-narrow decomposition. If "AI in creative industries" becomes three visual-arts subtasks, music, writing and film are never researched, however well each subagent performs.
  • Refine iteratively: evaluate the synthesis for gaps, re-delegate targeted queries, re-synthesise.

Here is that loop in code. The subagents are stand-ins that return findings for the subtopics they're given; the coordinator's selection, partitioning and gap-driven re-delegation are real.

Python
TOPIC_AREAS = {"AI in creative industries": ["visual arts", "music", "writing", "film", "games"]}

def plan(query, complexity):
    if complexity == "simple":
        return {"search": [query]}                         # one subagent, no full pipeline
    areas = TOPIC_AREAS[query]
    return {"search": areas[:3], "analysis": areas[3:]}    # distinct partitions, no overlap

def run_subagents(assignments, unavailable=()):
    found = {}
    for agent, subtopics in assignments.items():
        for s in subtopics:
            found[s] = None if s in unavailable else f"{agent}: 3 sourced findings on {s}"
    return found

def coordinate(query, complexity="complex", max_rounds=3):
    required = TOPIC_AREAS.get(query, [query])
    assignments = plan(query, complexity)
    findings = run_subagents(assignments, unavailable={"games"})        # first pass: games source down
    for rnd in range(1, max_rounds + 1):
        gaps = [s for s in required if not findings.get(s)]
        print(f"round {rnd}: covered {len(required) - len(gaps)}/{len(required)}  gaps={gaps}")
        if not gaps:
            break
        findings.update(run_subagents({"search": gaps}))       # re-delegate only the gaps
    return findings

print("assignments:", plan("AI in creative industries", "complex"))
print("simple query:", plan("When did the EU AI Act enter into force?", "simple"))
result = coordinate("AI in creative industries")
Output · produced by running this code
assignments: {'search': ['visual arts', 'music', 'writing'], 'analysis': ['film', 'games']}
simple query: {'search': ['When did the EU AI Act enter into force?']}
round 1: covered 4/5  gaps=['games']
round 2: covered 5/5  gaps=[]
How to read it

The complex query is partitioned so search and analysis never cover the same subtopic, while the simple factual query goes to one agent. The first pass leaves a gap (the games source was unavailable); the coordinator notices it by checking coverage against the topic's areas and re-delegates only the gap, and the second round reaches full coverage. Without the coverage check, the report would silently omit games.

Practice questionA research system's reports on "impact of AI on creative industries" cover only visual arts. Every subagent completed its task correctly. The coordinator's log shows subtasks "AI in digital art", "AI in graphic design" and "AI in photography". What is the root cause?

The subagents did exactly what they were given. The coordinator's decomposition omitted most of the topic, which is a coordinator problem, not a downstream one.

Practice questionSelect 2Why route all subagent communication through the coordinator rather than letting subagents call each other? (Select 2)

Hub-and-spoke centralises observability, error handling and routing. Subagents still have isolated contexts, so context must still be passed explicitly.

Task statement 1.3

Subagent invocation and context passing

In the Claude Agent SDK and Claude Code, a coordinator spawns subagents with the Task tool. The guide states that a coordinator's allowedTools must include "Task" to invoke subagents. Each subagent type is defined by an AgentDefinition: a description (when to use it), a system prompt, and tool restrictions.

Pythonshown, not run here
from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

options = ClaudeAgentOptions(
    allowed_tools=["Task", "Read"],                 # the guide: "Task" must be allowed for delegation
    agents={
        "web-search": AgentDefinition(
            description="Searches the web for one assigned subtopic and returns sourced findings.",
            prompt="Return JSON findings: claim, excerpt, source_url, published_date. No prose.",
            tools=["WebSearch", "WebFetch"]),
        "synthesis": AgentDefinition(
            description="Combines findings into a cited report. Use only after findings exist.",
            prompt="Preserve every claim's source. Mark conflicts; don't resolve them silently.",
            tools=["Read"]),
    },
)
Tip

Then vs now. In current Claude Code (2.1.63 and later) the subagent tool is named Agent; Task still works as an alias, and current docs say the tool doesn't require a permission prompt either way. For the exam, answer with the guide's rule: no Task in allowedTools means the coordinator can't delegate. In real projects, check the delegation tool is available whatever it's called.

Context must be passed explicitly

Subagents don't inherit the coordinator's conversation and don't share memory between invocations. Everything a subagent needs goes in its prompt: the complete findings from earlier agents, the goal, the quality criteria, the output format. Pass findings as structured data that separates content from metadata (source URL, document, page, date), or attribution is lost on the way to the report.

Python
findings = [
    {"claim": "Generative tools cut storyboard time by ~40%", "source": "https://studio-survey.example/2026", "page": None, "date": "2026-03"},
    {"claim": "Session musicians report 18% fewer bookings", "source": "Musicians' Union report.pdf", "page": 12, "date": "2026-06"},
    {"claim": "Session musicians report 11% fewer bookings", "source": "https://labour-stats.example/q2", "page": None, "date": "2025-12"},
]

prose_handoff = "Findings: storyboards are faster with AI; session musicians are getting fewer bookings."

def structured_handoff(items):
    lines = ["<findings>"]
    for i, f in enumerate(items, 1):
        where = f"{f['source']}" + (f", p.{f['page']}" if f["page"] else "")
        lines.append(f'  <finding id="{i}" date="{f["date"]}" source="{where}">{f["claim"]}</finding>')
    lines.append("</findings>")
    return "\n".join(lines)

synthesis_prompt = ("Goal: a cited brief on AI's impact on creative work for a union audience.\n"
                    "Quality bar: every claim keeps its source; if sources disagree, show both with dates.\n\n"
                    + structured_handoff(findings))
print(synthesis_prompt)
print("\nsources available to synthesis — structured:", len({f['source'] for f in findings}), "| prose:", 0)

  <finding id="1" date="2026-03" source="https://studio-survey.example/2026">Generative tools cut storyboard time by ~40%</finding>

How to read it

The prose handoff reads fine but carries zero sources, so the synthesis agent can't cite anything and can't see that the two booking figures come from different sources and dates. The structured handoff keeps claim, source, page and date together, which makes attribution and conflict handling possible downstream (Module 5 returns to this). Note too that the prompt states the goal and quality bar, not step-by-step procedure: subagents adapt better to goals than to scripts.

Parallel spawning

To run subagents in parallel, the coordinator emits several Task tool calls in a single response, not one per turn. Independent work then runs concurrently; dependent work (synthesis needs the findings) runs after.

Practice questionA coordinator's subagents never run: the coordinator writes the research itself, slowly. The configuration's allowedTools lists ["Read", "WebSearch"]. According to the exam guide, what's the fix?

The guide states the Task tool is the mechanism for spawning subagents and must be in the coordinator's allowedTools. (In current Claude Code it's named Agent, with Task as an alias.)

Practice questionHow should a coordinator spawn three independent research subagents to run in parallel?

Multiple Task calls in one response run concurrently. Spreading them across turns serialises the work.

Task statement 1.4

Enforcement and handoff

Some workflow rules are preferences; some are requirements. "Verify the customer's identity before any refund" is a requirement: a prompt instruction makes it likely, but prompt compliance has a non-zero failure rate. When the consequence is financial or regulatory, enforce it programmatically: a prerequisite gate that blocks downstream tools until the prerequisite has succeeded.

Python
class PrerequisiteGate:
    def __init__(self):
        self.verified_customer = None
        self.orders_for = {"C-7731": {"ORD-1182", "ORD-1190"}}

    def call(self, tool, args):
        if tool == "get_customer":
            if args.get("email") == "meera@example.com" and args.get("phone_last4") == "4471":
                self.verified_customer = "C-7731"
                return "verified C-7731"
            return "not verified"
        if tool in ("lookup_order", "process_refund"):
            if not self.verified_customer:
                return f"BLOCKED {tool}: no verified customer yet (call get_customer first)"
            if args["order_id"] not in self.orders_for[self.verified_customer]:
                return f"BLOCKED {tool}: {args['order_id']} does not belong to {self.verified_customer}"
            return f"{tool} ok for {args['order_id']}"
        return "unknown tool"

g = PrerequisiteGate()
for tool, args in [("process_refund", {"order_id": "ORD-1182"}),                   # agent skipped verification
                   ("get_customer", {"email": "meera@example.com", "phone_last4": "4471"}),
                   ("lookup_order", {"order_id": "ORD-2001"}),                      # someone else's order
                   ("process_refund", {"order_id": "ORD-1182"})]:
    print(f"{tool:<15} → {g.call(tool, args)}")
Output · produced by running this code
process_refund  → BLOCKED process_refund: no verified customer yet (call get_customer first)
get_customer    → verified C-7731
lookup_order    → BLOCKED lookup_order: ORD-2001 does not belong to C-7731
process_refund  → process_refund ok for ORD-1182
How to read it

The refund attempted before verification is blocked, whatever the model believed, and so is a lookup of an order belonging to someone else. This is the official sample answer for an agent that skips get_customer in 12% of cases: a programmatic prerequisite, not a stronger prompt, more few-shot examples, or a routing classifier (which controls which tools are available, not their order).

Multi-concern requests and structured handoffs

A message like "my blender arrived broken, I was charged twice, and I want to change my address" holds three concerns. Decompose it into distinct items, investigate each (in parallel where they're independent, with shared context such as the verified customer), then synthesise one resolution.

When escalating mid-process, remember the human agent doesn't see the transcript. Compile a structured handoff: customer ID, the issue, root cause, what was already done, amounts, and the recommended action.

Python
handoff = {
    "customer_id": "C-7731", "verified": True,
    "issues": [
        {"item": "Blender ORD-1182 arrived broken", "status": "refund issued $42.00", "done": True},
        {"item": "Charged twice for ORD-1190", "root_cause": "payment retried after gateway timeout; two captures",
         "amount": 129.00, "status": "needs billing-team review before refund", "done": False},
    ],
    "recommended_action": "Confirm both captures settled, then refund the duplicate $129.00 on ORD-1190",
    "customer_preference": "Prefers email updates; frustrated about the double charge",
}
print("ESCALATION HANDOFF")
for k, v in handoff.items():
    if k != "issues": print(f"  {k}: {v}")
for i in handoff["issues"]:
    print(f"  - {i['item']}: {i['status']}" + (f" (root cause: {i['root_cause']})" if "root_cause" in i else ""))

Practice questionIn 12% of conversations, a support agent calls lookup_order using only the name the customer gave, skipping get_customer, which occasionally leads to refunds on the wrong account. What change most effectively fixes this?

Critical ordering with financial consequences needs a deterministic guarantee. Prompt instructions and examples are probabilistic; a routing classifier changes which tools exist, not the order they're called in.

Task statement 1.5

Hooks for interception and normalisation

Hooks are code that runs at fixed points in an agent's life cycle, whatever the model decides. They give deterministic guarantees where prompts give probabilistic compliance. Two patterns are central to this exam:

HookRunsUse it to
Tool-call interception (PreToolUse)Before a tool executesBlock policy-violating calls (refunds above a limit) and redirect to an alternative workflow (human escalation)
PostToolUseAfter a tool returns, before the model processes the resultTransform results: normalise heterogeneous formats from different MCP tools so the agent reasons over consistent data

Here are both, run on calls from three MCP tools that report timestamps and statuses three different ways.

Python
from datetime import datetime, timezone

REFUND_LIMIT = 500.00
STATUS_CODES = {0: "pending", 1: "processing", 2: "completed", 9: "failed"}

def pre_tool_use(tool, args):
    if tool == "process_refund" and args["amount"] > REFUND_LIMIT:
        return {"decision": "deny",
                "reason": f"Refunds over ${REFUND_LIMIT:.0f} need a person. Call escalate_to_human with the order, amount and reason."}
    return {"decision": "allow"}

def to_iso(v):
    if isinstance(v, (int, float)):                                   # Unix seconds
        return datetime.fromtimestamp(v, tz=timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")
    if "/" in v:                                                      # 20/10/2026 (day first)
        return datetime.strptime(v, "%d/%m/%Y").strftime("%Y-%m-%dT00:00:00Z")
    return v.replace("+00:00", "Z")                                   # already ISO 8601

def post_tool_use(tool, result):
    out = dict(result)
    for key in ("ts", "created", "updated_at"):
        if key in out: out["processed_at"] = to_iso(out.pop(key))
    if isinstance(out.get("status"), int): out["status"] = STATUS_CODES.get(out["status"], "unknown")
    return out

print(pre_tool_use("process_refund", {"order_id": "ORD-1190", "amount": 650.00}))
print(pre_tool_use("process_refund", {"order_id": "ORD-1182", "amount": 42.00}))
raw = [("refund_api", {"status": 2, "ts": 1792828800}),
       ("orders_mcp", {"status": "completed", "created": "20/10/2026"}),
       ("billing_mcp", {"status": 1, "updated_at": "2026-10-20T06:40:00+00:00"})]
for tool, r in raw:
    print(f"{tool:<12} {str(r):<55} → {post_tool_use(tool, r)}")
Output · produced by running this code
{'decision': 'deny', 'reason': 'Refunds over $500 need a person. Call escalate_to_human with the order, amount and reason.'}
{'decision': 'allow'}
refund_api   {'status': 2, 'ts': 1792828800}                         → {'status': 'completed', 'processed_at': '2026-10-24T08:00:00Z'}
orders_mcp   {'status': 'completed', 'created': '20/10/2026'}        → {'status': 'completed', 'processed_at': '2026-10-20T00:00:00Z'}
billing_mcp  {'status': 1, 'updated_at': '2026-10-20T06:40:00+00:00'} → {'status': 'processing', 'processed_at': '2026-10-20T06:40:00Z'}
How to read it

The $650 refund never executes: the hook denies it and tells the agent the alternative (escalate). Three tools, three timestamp formats and two status conventions arrive at the model as one consistent shape, so it doesn't misread a Unix timestamp or treat status 2 as a quantity. Both behaviours hold on every call, which no prompt instruction can promise.

Practice questionPolicy says refunds over $500 must be approved by a person. The current system prompt states this rule, but audits find occasional large automatic refunds. What should the architect implement?

A business rule that must always hold needs a deterministic control before the action. Logging after the fact can't prevent the refund.

Practice questionThree MCP tools return dates as Unix timestamps, "DD/MM/YYYY" strings and ISO 8601. The agent sometimes miscalculates return windows. What's the most robust fix?

Normalising in a PostToolUse hook gives the model consistent data on every call, deterministically, without waiting on upstream changes.

Task statement 1.6

Task decomposition strategies

Choose the decomposition pattern to fit the work:

PatternShapeFits
Prompt chaining (fixed sequential pipeline)Steps known in advance, each feeding the nextPredictable, multi-aspect work: e.g. a code review split into per-file analysis, then a cross-file integration pass
Dynamic, adaptive decompositionGenerate subtasks from what's discovered at each stepOpen-ended investigation: "add comprehensive tests to this legacy codebase", "find why checkout is slow"
The idea

Why split a big review? Analysing 14 files in one pass dilutes attention: some files get depth, others a skim, and the same pattern can be flagged in one file and approved in another. Per-file passes give consistent local depth; a separate integration pass looks only at cross-file data flow.

For open-ended work, an adaptive plan first maps the structure, then identifies high-impact areas, then builds a prioritised plan that changes as dependencies are discovered. Here's that for "add tests to a legacy codebase".

Python
MODULES = {  # module: (lines, changes in last 90 days, test coverage %, business-critical)
    "billing/charges.py":   (820, 34, 12, True),
    "billing/refunds.py":   (410, 21, 0,  True),
    "orders/cart.py":       (650, 18, 55, True),
    "reports/export.py":    (300, 2,  0,  False),
    "utils/dates.py":       (120, 9,  20, False),
}
def impact(m):
    lines, churn, cov, critical = MODULES[m]
    return round(churn * (100 - cov) / 100 * (2 if critical else 1), 1)

plan = sorted(MODULES, key=impact, reverse=True)
print("step 1, mapped structure:", len(MODULES), "modules")
print("step 2, prioritised by impact (churn × untested share × criticality):")
for m in plan: print(f"   {impact(m):>6}  {m}")

discovered = {"billing/refunds.py": ["billing/charges.py", "utils/dates.py"]}       # found while writing refund tests
print("\nstep 3, adapt: writing refund tests revealed dependencies", discovered["billing/refunds.py"])
adapted = []
for m in plan:
    for dep in discovered.get(m, []):
        if dep not in adapted: adapted.append(dep)
    if m not in adapted: adapted.append(m)
print("adapted order:", adapted)

     59.8  billing/charges.py
     42.0  billing/refunds.py
     16.2  orders/cart.py
      7.2  utils/dates.py
      2.0  reports/export.py

How to read it

Charges and refunds lead on impact: frequently changed, barely tested, business-critical. Then the plan adapts: testing refunds properly turns out to need charges and the date utilities under test first, so they move ahead of it. A fixed pipeline couldn't make that move; that's the case for dynamic decomposition on open-ended tasks.

Practice questionA pull request changes 14 files. A single-pass review gives deep feedback on some files, superficial comments on others, and contradictory verdicts on identical code. How should the review be restructured?

The root cause is attention dilution across many files. Focused per-file passes restore consistent depth, and the integration pass covers cross-file issues. Consensus filtering would suppress real but intermittently caught bugs.

Practice question"Add comprehensive tests to our legacy codebase" is best approached with which decomposition?

Open-ended work reveals its shape as you go. An adaptive plan prioritises by impact and reorders when dependencies appear.

Task statement 1.7

Sessions: resume and fork

Long investigations span work sessions. Claude Code and the Agent SDK let you continue or branch them:

MechanismWhat it doesUse when
claude --resume <session-name>Continues a specific named prior conversationThe prior context is still mostly valid
Fork (fork_session in the SDK, --fork-session / /branch in Claude Code)Creates an independent branch from a shared baselineComparing two approaches (two refactoring strategies, two test plans) from the same codebase analysis
Fresh session + structured summaryStarts clean, injecting a summary of key findingsPrior tool results are stale (files changed since)
Terminal
# Name the investigation so it can be resumed later
claude -n refund-flow-investigation
# ...next day...
claude --resume refund-flow-investigation
# Branch to compare two approaches from the same analysis
claude --resume refund-flow-investigation --fork-session
Pythonshown, not run here
from claude_agent_sdk import query, ClaudeAgentOptions

# Branch B: same baseline analysis, different strategy, without touching branch A
options = ClaudeAgentOptions(resume=baseline_session_id, fork_session=True)
async for msg in query(prompt="Try the strangler-fig migration approach instead.", options=options):
    ...
The idea

Stale context is worse than none. A resumed session still "remembers" file contents and test results from before yesterday's changes, and will reason from them confidently. If the files changed, either tell the resumed session exactly what changed (for targeted re-analysis) or start fresh with a structured summary.

Python
def resume_or_fresh(files_analysed, files_changed_since, days_since):
    stale = len(set(files_analysed) & set(files_changed_since)) / len(files_analysed)
    if stale == 0:
        return "resume as is", None
    if stale <= 0.25:
        note = ("Since we last spoke these files changed: " + ", ".join(sorted(set(files_analysed) & set(files_changed_since)))
                + ". Re-read only those before continuing; earlier findings for other files still hold.")
        return "resume + tell it what changed", note
    return "start fresh with a structured summary of findings", None

analysed = ["billing/refunds.py", "billing/charges.py", "orders/cart.py", "utils/dates.py", "api/refunds.py", "tests/test_refunds.py", "models/order.py", "models/payment.py"]
for changed in ([], ["billing/refunds.py"], ["billing/refunds.py", "billing/charges.py", "orders/cart.py", "models/order.py"]):
    choice, note = resume_or_fresh(analysed, changed, 1)
    print(f"{len(changed)} changed → {choice}")
    if note: print("   message:", note)

How to read it

With nothing changed, resume. With one of eight files changed, resume and say which file changed, so the session re-reads just that one instead of re-exploring everything. With half the analysed files changed, the old tool results are mostly stale: a fresh session seeded with a structured summary is more reliable. The 25% threshold is a judgement call, not a rule; the principle is to keep stale results from being trusted.

Practice questionYesterday's named investigation session analysed 8 files. Overnight, a teammate changed 1 of them. What's the best way to continue?

Most of the prior context is still valid. Naming the changed file lets the session re-read it in a targeted way instead of reasoning from a stale version.
