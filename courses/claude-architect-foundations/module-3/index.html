Task statement 3.1

The CLAUDE.md hierarchy

LevelLocationShared with the team?
User~/.claude/CLAUDE.mdNo: it applies only to you and isn't in version control
ProjectCLAUDE.md at the repo root, or .claude/CLAUDE.mdYes, via the repository
DirectoryCLAUDE.md in a subdirectoryYes; applies when working in that part of the tree

Keep the hierarchy modular rather than one giant file:

  • @import pulls in other files, e.g. a package's CLAUDE.md importing only the standards relevant to it (@docs/standards/api.md).
  • .claude/rules/ holds topic-specific rule files (testing.md, api-conventions.md, deployment.md) as an alternative to a monolithic CLAUDE.md.
  • /memory shows which memory files are loaded: the first thing to check when behaviour differs between people or sessions.
packages/billing/CLAUDE.md
# Billing package
@../../docs/standards/api-conventions.md
@../../docs/standards/money-handling.md

- Amounts are integers in paise; never floats.
- Every public function in this package has a test in tests/billing/.

Here's how those files resolve for two developers on the same repository. Imports are expanded recursively (with a guard against cycles).

Python
import re

FILES = {
    "~/.claude/CLAUDE.md": "- Prefer early returns.\n- Team rule: run `make lint` before committing.",
    "CLAUDE.md": "# Monorepo\n- Python 3.12, pytest.\n@docs/standards/testing.md",
    "docs/standards/testing.md": "- Tests use factories in tests/factories.\n@docs/standards/fixtures.md",
    "docs/standards/fixtures.md": "- Fixtures live in conftest.py at package level.",
    "packages/billing/CLAUDE.md": "@docs/standards/money-handling.md\n- Amounts in paise.",
    "docs/standards/money-handling.md": "- Use Decimal for display only; integers internally.\n@docs/standards/testing.md",
}

def expand(path, seen=None):
    seen = seen or set()
    if path in seen: return [f"(skipped repeat import of {path})"]
    seen.add(path)
    out = []
    for line in FILES[path].splitlines():
        m = re.match(r"@(\S+)", line)
        out += expand(m.group(1), seen) if m else [line]
    return out

for dev, has_user_file in [("Asha (wrote the team rule in her user file)", True), ("Ravi (new teammate)", False)]:
    sources = (["~/.claude/CLAUDE.md"] if has_user_file else []) + ["CLAUDE.md", "packages/billing/CLAUDE.md"]
    lines = [l for s in sources for l in expand(s) if l.startswith("-")]
    print(f"{dev}: {len(lines)} instructions; has 'make lint' rule: {any('make lint' in l for l in lines)}")
Output · produced by running this code
Asha (wrote the team rule in her user file): 9 instructions; has 'make lint' rule: True
Ravi (new teammate): 7 instructions; has 'make lint' rule: False
How to read it

Imports nest (testing pulls in fixtures; money-handling pulls testing again, and the repeat is skipped). The diagnosis the exam loves: the "run make lint" team rule lives in Asha's user file, so Ravi never gets it. Moving it to the project CLAUDE.md (or a .claude/rules/ file) fixes it for everyone; /memory on Ravi's machine would show it isn't loaded.

Practice questionA new team member's Claude Code ignores the team's commit conventions, while everyone else's follows them. The conventions turn out to be in a senior engineer's ~/.claude/CLAUDE.md. What's the fix?

User-level files apply only to their owner and aren't shared via version control. Team conventions belong at project level.

Practice questionSelect 2A monorepo's root CLAUDE.md has grown to 900 lines covering every package. What does the guide recommend? (Select 2)

Modular organisation keeps each context relevant: topic files in .claude/rules/ and selective @imports per package.

Task statement 3.2

Slash commands and skills

ItemTeam-wide (version-controlled)Personal
Custom slash commands.claude/commands/ in the repository~/.claude/commands/
Skills.claude/skills/<name>/SKILL.md~/.claude/skills/<name>/SKILL.md

Skill front matter supports options the exam names:

OptionDoes
context: forkRuns the skill in an isolated subagent, so its verbose or exploratory output doesn't pollute the main conversation
allowed-toolsRestricts the tools available while the skill runs (e.g. only file writes, nothing destructive)
argument-hintPrompts the developer for required parameters when they invoke the skill without arguments
.claude/skills/codebase-map/SKILL.md
---
name: codebase-map
description: Map an unfamiliar area of the codebase: entry points, main flows, dependencies. Use when asked to explain or explore a module.
context: fork
allowed-tools: Read, Grep, Glob
argument-hint: <directory or module to map>
---
Map $ARGUMENTS. Return: entry points, the 3–5 main flows with file:line references,
external dependencies, and anything surprising. At most 40 lines. Do not edit files.
Tip

Skills or CLAUDE.md? CLAUDE.md is for always-loaded universal standards. Skills are for on-demand, task-specific workflows. To customise a team skill for yourself, create a personal variant with a different name in ~/.claude/skills/ so you don't change behaviour for teammates.

Here's why context: fork matters for the main conversation, plus argument-hint and allowed-tools doing their jobs.

Python
def invoke(skill, args, main_context_tokens):
    if skill["argument_hint"] and not args:
        return main_context_tokens, f"prompt user: {skill['argument_hint']}"
    exploration = 46_000                         # files read, searches run while mapping
    summary = 900                                # what the skill returns
    if skill["context"] == "fork":
        return main_context_tokens + summary, "ran in an isolated subagent"
    return main_context_tokens + exploration + summary, "ran inline"

def tool_allowed(skill, tool):
    return tool in skill["allowed_tools"]

forked = {"argument_hint": "<directory or module to map>", "context": "fork", "allowed_tools": {"Read", "Grep", "Glob"}}
inline = dict(forked, context=None)

for label, sk in [("context: fork", forked), ("inline", inline)]:
    tokens, how = invoke(sk, "src/payments", 12_000)
    print(f"{label:<14} main conversation after skill: {tokens:>6,} tokens ({how})")
print("no arguments:", invoke(forked, "", 12_000)[1])
print("skill tries Bash(rm -rf build):", "allowed" if tool_allowed(forked, "Bash") else "blocked by allowed-tools")
Output · produced by running this code
context: fork  main conversation after skill: 12,900 tokens (ran in an isolated subagent)
inline         main conversation after skill: 58,900 tokens (ran inline)
no arguments: prompt user: <directory or module to map>
skill tries Bash(rm -rf build): blocked by allowed-tools
How to read it

Run inline, the mapping work leaves about 46,000 tokens of file reads and searches in the main conversation; forked, only the 900-token summary comes back. Invoked without a target, the skill asks for one instead of guessing, and its allowed-tools list stops it running Bash at all.

Practice questionYou want a /review command running the team's checklist to be available to every developer who clones the repository. Where does it go?

Project-scoped commands in .claude/commands/ are version-controlled and available to everyone. ~/.claude/commands/ is personal, CLAUDE.md is for instructions, and the config.json option doesn't exist.

Practice questionA codebase-analysis skill floods the main conversation with file contents, and later answers degrade. Which front-matter option addresses this?

context: fork runs the skill in an isolated subagent; only its result returns to the main conversation.

Task statement 3.3

Path-specific rules

Files in .claude/rules/ can carry YAML front matter with a paths field of glob patterns. A path-scoped rule loads only when Claude edits a matching file, cutting irrelevant context and tokens. Globs reach files wherever they live, which is the advantage over directory-level CLAUDE.md files for conventions that span the codebase (test files next to their source, Terraform under several folders).

.claude/rules/testing.md
---
paths: ["**/*.test.tsx", "**/*.test.ts"]
---
# Test conventions
- Arrange / act / assert, one behaviour per test.
- Use renderWithProviders from test/utils, never raw render.
Python
import fnmatch

RULES = {
    "react.md":     (["src/components/**/*.tsx"], 900),
    "api.md":       (["src/api/**/*"], 1_200),
    "testing.md":   (["**/*.test.tsx", "**/*.test.ts"], 700),
    "terraform.md": (["terraform/**/*"], 1_600),
    "db.md":        (["src/db/**/*"], 800),
}
def matches(path, pattern):                       # fnmatch's * crosses '/', so '**/' just needs an optional prefix
    return fnmatch.fnmatch(path, pattern) or fnmatch.fnmatch(path, pattern.replace("**/", ""))

for edited in [["src/components/Button.tsx", "src/components/Button.test.tsx"], ["src/api/refunds.ts", "src/api/refunds.test.ts"], ["terraform/prod/main.tf"]]:
    loaded = [r for r, (pats, _) in RULES.items() if any(matches(f, p) for f in edited for p in pats)]
    tokens = sum(RULES[r][1] for r in loaded)
    print(f"editing {edited}\n   loads {loaded} ({tokens:,} tokens of {sum(t for _, t in RULES.values()):,})")
Output · produced by running this code
editing ['src/components/Button.tsx', 'src/components/Button.test.tsx']
   loads ['react.md', 'testing.md'] (1,600 tokens of 5,200)
editing ['src/api/refunds.ts', 'src/api/refunds.test.ts']
   loads ['api.md', 'testing.md'] (1,900 tokens of 5,200)
editing ['terraform/prod/main.tf']
   loads ['terraform.md'] (1,600 tokens of 5,200)
How to read it

The test conventions load alongside React rules in one session and alongside API rules in another, because the glob follows test files across folders. Terraform work loads only the Terraform rule. A directory CLAUDE.md couldn't do the test-file case without copying the same text into every folder.

Practice questionReact components, API handlers and database models each follow different conventions. Test files sit next to their source files throughout the codebase, and all tests should follow one set of conventions. What's the most maintainable way to apply the right conventions automatically?

Globs apply conventions by file path regardless of directory, which handles tests spread across the tree. A single file relies on inference, skills need invocation, and directory files can't follow scattered files.

Task statement 3.4

Plan mode or direct execution

ChooseWhenExamples
Plan modeLarge-scale changes, several valid approaches, architectural decisions, many filesMonolith to microservices; a library migration touching 45+ files; choosing between integration approaches with different infrastructure needs
Direct executionSimple, well-scoped, well-understood changesA single-file bug fix with a clear stack trace; adding a date-validation check
BothPlan the investigation and design, then execute the agreed plan directlyPlan a library migration; then implement it step by step

Plan mode explores and designs before changing anything, preventing costly rework. For verbose discovery phases, the Explore subagent reads widely and returns a summary, keeping the main conversation's context free for decisions.

Python
def mode_for(task):
    signals = []
    if task["files"] > 10:            signals.append(f"{task['files']} files")
    if task["approaches"] > 1:        signals.append(f"{task['approaches']} valid approaches")
    if task["architectural"]:         signals.append("architectural decision")
    if signals:
        return "plan mode", signals
    return "direct execution", ["small, clear scope"]

tasks = [
    ("Split the monolith into services",                 dict(files=60, approaches=3, architectural=True)),
    ("Fix the KeyError in invoice.py (stack trace given)", dict(files=1, approaches=1, architectural=False)),
    ("Migrate from requests to httpx (45 files)",          dict(files=45, approaches=1, architectural=False)),
    ("Add a date-range check to create_booking()",         dict(files=1, approaches=1, architectural=False)),
    ("Webhooks or a queue for partner notifications?",     dict(files=6, approaches=2, architectural=True)),
]
for name, t in tasks:
    mode, why = mode_for(t)
    print(f"{mode:<17} {name:<50} ({', '.join(why)})")
Output · produced by running this code
plan mode         Split the monolith into services                   (60 files, 3 valid approaches, architectural decision)
direct execution  Fix the KeyError in invoice.py (stack trace given) (small, clear scope)
plan mode         Migrate from requests to httpx (45 files)          (45 files)
direct execution  Add a date-range check to create_booking()         (small, clear scope)
plan mode         Webhooks or a queue for partner notifications?     (2 valid approaches, architectural decision)

Practice questionYou're asked to restructure a monolith into microservices, with decisions about service boundaries across dozens of files. Which approach fits?

The complexity is stated up front: many files, architectural choices, several valid approaches. Plan mode is designed for exactly that and prevents rework.

Practice questionDuring a multi-phase migration, discovery output (hundreds of file reads) is exhausting the main context. What helps?

The Explore subagent isolates verbose discovery and returns only what matters, preserving the main conversation's context.

Task statement 3.5

Iterative refinement

When Claude's output isn't right, how you iterate matters:

TechniqueUse it when
2–3 concrete input/output examplesProse descriptions of a transformation are interpreted inconsistently
Test-driven iterationWrite tests (behaviour, edge cases, performance) first; then share the failures to guide each round
The interview patternIn an unfamiliar domain, ask Claude to question you first to surface considerations (cache invalidation, failure modes)
One message for interacting issuesFixes affect each other: describe them together
Sequential fixes for independent issuesEach can be fixed and verified alone

Here's test-driven iteration on a migration helper: tests first, a first version, the failures shared back, and a second version.

Python
TESTS = [  # (input row, expected output) for normalising legacy phone numbers
    ({"phone": "98200 12345"},  "+919820012345"),
    ({"phone": "+91-98200-12345"}, "+919820012345"),
    ({"phone": None},           None),                 # edge case: missing value
    ({"phone": "022 2345 6789"}, "+912223456789"),     # landline with STD code
]

def v1(row):
    digits = "".join(c for c in row["phone"] if c.isdigit())
    return "+91" + digits[-10:]

def v2(row):
    if row["phone"] is None:
        return None
    digits = "".join(c for c in row["phone"] if c.isdigit())
    if digits.startswith("91") and len(digits) == 12:
        digits = digits[2:]
    if digits.startswith("0"):
        digits = digits[1:]
    return "+91" + digits

def run_tests(fn):
    failures = []
    for row, want in TESTS:
        try:
            got = fn(row)
        except Exception as e:
            got = f"{type(e).__name__}"
        if got != want: failures.append(f"input {row} → got {got!r}, expected {want!r}")
    return failures

for name, fn in [("v1", v1), ("v2", v2)]:
    f = run_tests(fn)
    print(f"{name}: {len(TESTS) - len(f)}/{len(TESTS)} pass")
    for line in f: print("   ", line)
Output · produced by running this code
v1: 3/4 pass
    input {'phone': None} → got 'TypeError', expected None
v2: 4/4 pass
How to read it

The first version gets the formats right but crashes on the missing phone value, an edge case the prose request never mentioned. That exact failure message, with its input and expected output, is what you send back. The second version passes all four. Concrete failing cases beat "handle edge cases better", which gives the model nothing specific to fix.

Practice questionYou've described a data transformation in prose three times, and Claude interprets it differently each time. What's the most effective next step?

Concrete examples communicate expected transformations more precisely than prose that keeps being read inconsistently.

Practice questionTwo bugs in a function interact: fixing the rounding changes which branch handles negative totals. How should you give the fixes to Claude?

Interacting issues need to be solved together; sequential fixes suit independent issues.

Task statement 3.6

Claude Code in CI/CD

CI review step
claude -p "Review the diff in pr.diff against CLAUDE.md review criteria. \
Report only issues that are new or still unaddressed compared with prior_findings.json." \
  --output-format json \
  --json-schema "$(cat schemas/findings.json)" > review.json
PracticeWhy
-p (--print)Non-interactive mode: processes the prompt, prints, exits. Without it the job hangs waiting for input
--output-format json + --json-schemaMachine-parseable findings to post as inline PR comments
CLAUDE.md as CI contextTesting standards, fixture conventions and review criteria reach the CI-invoked instance too
An independent review instanceThe session that generated code is less likely to question its own reasoning
Prior findings in context on re-runsReport only new or still-unaddressed issues, avoiding duplicate comments after each commit
Existing tests in context for test generationAvoids suggesting scenarios the suite already covers

The re-run rule is easy to get wrong. Here's de-duplication against the previous review, keyed on a stable fingerprint (file, rule, code snippet) rather than line numbers, which shift with every commit.

Python
import hashlib, json

def fp(f): return hashlib.sha1(f"{f['file']}|{f['rule']}|{f['snippet'].strip()}".encode()).hexdigest()[:10]

prior = [
    {"file": "api/refunds.py", "line": 41, "rule": "missing-authz-check", "snippet": "def refund(req):"},
    {"file": "api/refunds.py", "line": 77, "rule": "float-money", "snippet": "total = price * 1.18"},
    {"file": "db/models.py",   "line": 12, "rule": "n-plus-one", "snippet": "for o in orders: o.items.all()"},
]
current = [   # after the developer's new commit: lines moved, one issue fixed, one new
    {"file": "api/refunds.py", "line": 45, "rule": "missing-authz-check", "snippet": "def refund(req):"},
    {"file": "db/models.py",   "line": 14, "rule": "n-plus-one", "snippet": "for o in orders: o.items.all()"},
    {"file": "api/refunds.py", "line": 90, "rule": "secret-in-log", "snippet": "log(f'card={card}')"},
]
prior_fps = {fp(f): f for f in prior}
for f in current:
    status = "still unaddressed (reply on the existing comment)" if fp(f) in prior_fps else "NEW: post a comment"
    print(f"{f['file']}:{f['line']:<4} {f['rule']:<20} {status}")
resolved = [f for k, f in prior_fps.items() if k not in {fp(c) for c in current}]
print("resolved since last review:", [f"{r['file']}:{r['line']} {r['rule']}" for r in resolved])
Output · produced by running this code
api/refunds.py:45   missing-authz-check  still unaddressed (reply on the existing comment)
db/models.py:14   n-plus-one           still unaddressed (reply on the existing comment)
api/refunds.py:90   secret-in-log        NEW: post a comment
resolved since last review: ['api/refunds.py:77 float-money']
How to read it

Two findings moved lines but are the same issues, so they're "still unaddressed", not new comments. One was fixed (the float arithmetic on money) and can be marked resolved, and one is genuinely new. Keyed on line numbers, all three current findings would have been posted as new, burying developers in duplicates.

Practice questionA pipeline runs claude "Analyze this pull request for security issues" and hangs waiting for input. What's the correct fix?

-p (--print) is the documented non-interactive mode: it prints the result and exits. The other options don't exist or are workarounds.

Practice questionAfter each new commit, the CI review re-posts comments developers have already seen. What should change?

Giving the reviewer the previous findings lets it separate new issues from known ones, avoiding duplicate comments.
