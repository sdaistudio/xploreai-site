## 5.1 | Preserving critical information

Four things erode context in long interactions:

| Problem | What happens | Fix |
|---|---|---|
| **Progressive summarisation** | Amounts, percentages, dates and what the customer was promised become vague ("about $90", "early next week") | Keep transactional facts in a persistent **case facts** block outside the summarised history |
| **Lost in the middle** | Findings in the middle of long inputs get less attention than the start and end | Put a **key findings summary first**; organise details under explicit section headers |
| **Tool-result bloat** | A 40-field order lookup when 5 fields matter, repeated every turn | **Trim** tool outputs to the relevant fields before they accumulate |
| **Missing history** | Requests sent without the full conversation lose coherence | Always pass the **complete** history (minus what you've deliberately trimmed) |

For **multi-issue sessions**, keep a structured layer per issue (order ID, amount, status) so three problems in one conversation don't blur together. In multi-agent systems, have upstream agents return **structured facts with metadata** (dates, sources, relevance) rather than long prose and reasoning, especially when downstream agents have small context budgets.

```python
import json

order_lookup = {   # what the orders API returns (abridged here: imagine 40+ fields)
    "order_id": "ORD-1182", "status": "delivered", "delivered_at": "2026-10-09", "total": 42.00, "currency": "USD",
    "items": [{"sku": "BLD-200", "name": "Blender", "qty": 1, "price": 42.00, "returnable": True}],
    "warehouse": "PNQ-3", "carrier": "BlueDart", "carrier_events": [{"t": i, "e": "scan"} for i in range(14)],
    "billing_address": "...", "shipping_address": "...", "gift_wrap": False, "loyalty_points": 84,
    "fraud_score": 0.02, "marketing_opt_in": True, "audit": {"created_by": "web", "version": 7},
}
RETURN_FIELDS = ["order_id", "status", "delivered_at", "total", "items"]
trimmed = {k: order_lookup[k] for k in RETURN_FIELDS}
trimmed["items"] = [{k: i[k] for k in ("name", "price", "returnable")} for i in trimmed["items"]]

case_facts = {"issues": [
    {"id": 1, "order": "ORD-1182", "problem": "blender arrived broken", "amount": 42.00, "status": "refund issued"},
    {"id": 2, "order": "ORD-1190", "problem": "charged twice", "amount": 129.00, "status": "awaiting billing review"},
], "promised": "update on issue 2 by email before 17:00 IST, 28 Oct"}

print(f"raw lookup ≈ {len(json.dumps(order_lookup)) // 4} tokens; trimmed ≈ {len(json.dumps(trimmed)) // 4} tokens")
print("trimmed:", trimmed)
print("\n<case_facts>" + json.dumps(case_facts) + "</case_facts>   ← carried verbatim every turn")
```

> [read] The trimmed lookup keeps exactly what a return decision needs at about a fifth of the size, and that saving repeats on every later turn. The case-facts block holds both issues' exact amounts and the specific promise made to the customer, so a summary that drifts to "some refund, will update soon" can't erase them.

## 5.2 | Escalation and ambiguity

| Trigger | Escalate? | How |
|---|---|---|
| Customer **explicitly asks** for a human | ✓ Immediately | Don't investigate first; hand over with a structured summary |
| **Policy is ambiguous or silent** on the request (a policy gap) | ✓ | E.g. competitor price matching when policy only covers own-site adjustments |
| **Can't make meaningful progress** | ✓ | After real attempts; with what was tried |
| Customer is **frustrated**, issue is straightforward | ✗ Not on its own | Acknowledge the frustration, offer the resolution; escalate if they **reiterate** they want a person |
| **Complex** but within policy and capability | ✗ Not on its own | Keep working |

> [warn] **Two unreliable proxies.** Sentiment-based escalation and the model's **self-reported confidence** don't track case complexity. An agent that's wrongly confident on hard policy-exception cases will rate itself highly on exactly those. Calibrate escalation with **explicit criteria plus few-shot examples** in the system prompt, the official sample answer for an agent stuck at 55% first-contact resolution.

```seq title="Frustrated, straightforward: resolve first; a repeated request: hand over"
Customer, Agent, Orders tool, Human queue
Customer -> Agent: "THIRD TIME asking! My kettle arrived broken." (photo)
note Agent: Frustrated, but within policy and capability: no trigger yet
Agent -> Orders tool: lookup_order + check_damage_policy
Orders tool --> Agent: eligible for replacement
Agent --> Customer: apologises, arranges the replacement, offers a person
Customer -> Agent: "No, I want a person."
Agent -> Human queue: escalate now, with a structured summary
```

**Ambiguous matches need clarification, not guesswork.** When a lookup returns several customers, ask for another identifier; never pick one by heuristic ("the most recent", "the first").

```python
def handle(turn):
    if turn.get("asks_for_human"):
        return "ESCALATE now with a structured summary (don't investigate first)"
    if turn.get("policy") == "silent":
        return "ESCALATE: policy gap — a person must decide"
    matches = turn.get("customer_matches", 1)
    if matches > 1:
        return f"ASK for another identifier ({matches} customers match); never guess"
    if turn.get("frustrated") and turn.get("straightforward"):
        if turn.get("reiterated_human"):
            return "ESCALATE: they asked again for a person"
        return "acknowledge frustration, offer the fix, mention a person is available"
    return "resolve"

turns = [
    ("'Just get me a human.'",                                        dict(asks_for_human=True)),
    ("'Match AnyMart's price, it's ₹400 cheaper.'",                   dict(policy="silent")),
    ("'I'm Rahul Shah, refund my order.' (3 Rahul Shahs found)",      dict(customer_matches=3)),
    ("'THIRD TIME asking! Replace my damaged kettle!' (photo attached)", dict(frustrated=True, straightforward=True)),
    ("Same customer: 'No, I want a person.'",                         dict(frustrated=True, straightforward=True, reiterated_human=True)),
    ("Standard damage replacement with photo evidence",               dict(straightforward=True)),
]
for text, t in turns:
    print(f"{handle(t):<74} ← {text}")
```

> [read] Frustration alone gets resolution, not escalation, until the customer reiterates that they want a person; then it's immediate. The standard damage replacement with a photo is resolved autonomously, which is exactly what the 55%-resolution agent was escalating wrongly. Three customers called Rahul Shah means asking for an email or order number, not picking one.

```quiz
Q: An agent resolves 55% of contacts against an 80% target. It escalates routine damage replacements that have photo evidence, but tries to handle policy exceptions on its own. What's the most effective first improvement?
- [x] Add explicit escalation criteria with few-shot examples of when to escalate versus resolve
- [ ] Have the agent self-rate its confidence 1–10 and escalate below a threshold
- [ ] Train a separate classifier on historical tickets
- [ ] Escalate when sentiment analysis detects frustration
why: The decision boundary is unclear, so state it with examples. Self-reported confidence is poorly calibrated (it's already confident on the hard cases), a classifier is over-engineered as a first step, and sentiment doesn't measure complexity.
```

```quiz

```

## 5.3 | Error propagation across agents

When a subagent fails, what the coordinator receives decides what it can do. A **structured error context** carries: the **failure type**, **what was attempted**, any **partial results**, and possible **alternatives**. Two anti-patterns the guide names:

- **Suppressing** errors: returning an empty result marked "success". The coordinator thinks the search worked and found nothing.
- **Terminating** the whole workflow on one subagent failure, when partial results and alternatives could still produce a useful report.

Subagents should **recover locally** from transient failures (a bounded retry) and propagate only what they can't resolve. The final synthesis should carry **coverage annotations**: which findings are well supported, which areas have gaps because a source was unavailable.

```seq title="A timeout, propagated usefully"
Coordinator, Web search subagent, Search API
Coordinator -> Web search subagent: research "EU rules on AI in hiring"
Web search subagent -> Search API: query (retry once on timeout)
Search API --> Web search subagent: timeout again
Web search subagent --> Coordinator: {failure: timeout, attempted: 2 queries, partial: 4 sources, alternatives: [use the document-analysis agent's EU corpus]}
Coordinator -> Web search subagent: narrower query for the missing subtopic
note Coordinator: Report ships with a coverage note on what's thin
```

```python
OUTCOMES = {
    "regulation":  {"ok": True,  "findings": 6},
    "case law":    {"ok": False, "failure": "timeout", "attempted": "2 queries", "partial": 2, "alternatives": ["legal DB via analysis agent"]},
    "vendor tools": {"ok": True,  "findings": 0},                               # searched; genuinely nothing
    "worker views": {"ok": False, "failure": "permission", "attempted": "survey archive", "partial": 0, "alternatives": []},
}
def coordinate(outcomes):
    report = []
    for topic, o in outcomes.items():
        if o["ok"] and o["findings"]:   report.append((topic, f"well supported ({o['findings']} sources)"))
        elif o["ok"]:                   report.append((topic, "searched: no relevant sources exist"))
        elif o["alternatives"]:         report.append((topic, f"PARTIAL: {o['partial']} sources; retrying via {o['alternatives'][0]}"))
        else:                           report.append((topic, f"GAP: {o['failure']} on {o['attempted']}; not covered"))
    return report

for topic, note in coordinate(OUTCOMES):
    print(f"{topic:<13} {note}")
```

> [read] The report still ships, and it's honest about coverage: one area is solid, one has partial results with an alternative route under way, one was searched and genuinely has nothing, and one is a gap because of a permission failure. Had the failures been suppressed as empty successes, the last two lines would have read the same as "vendor tools": a false claim that nothing exists.

```quiz
Q: A web search subagent times out. Which way of reporting it back best enables recovery?
- [x] Structured context: failure type, the attempted query, partial results and possible alternatives
- [ ] Retry with backoff inside the subagent, then return a generic "search unavailable"
- [ ] Return an empty result marked as success
- [ ] Raise the exception to a top-level handler that ends the workflow
why: Structured context lets the coordinator retry differently, try an alternative or proceed with partial results. Generic statuses hide information, suppression fakes success, and termination throws away recoverable work.
```

## 5.4 | Exploring large codebases

In long exploration sessions, context degrades: answers become inconsistent, and the model starts citing "typical patterns" instead of the specific classes it found an hour ago. The guide's countermeasures:

| Technique | Does |
|---|---|
| **Scratchpad files** | The agent writes key findings to a file and re-reads it for later questions |
| **Subagent delegation** | "Find all test files", "trace the refund flow's dependencies" run in subagents; the main agent keeps the high-level picture |
| **Summaries between phases** | Summarise one phase's findings and inject that summary into the next phase's subagents |
| **State manifests for crash recovery** | Each agent exports state to a known location; on resume, the coordinator loads the manifest and injects it into prompts |
| **`/compact`** | Reduces context usage when it fills with verbose discovery output |

Here's a scratchpad and a manifest surviving a crash, using real files in a temporary folder.

```python
import json, os, tempfile

work = tempfile.mkdtemp()
scratch, manifest = os.path.join(work, "scratchpad.md"), os.path.join(work, "manifest.json")

def note(line):
    with open(scratch, "a") as f: f.write(f"- {line}\n")

def save_state(agent, state):
    m = json.load(open(manifest)) if os.path.exists(manifest) else {}
    m[agent] = state
    json.dump(m, open(manifest, "w"), indent=1)

# Phase 1: exploration (findings persisted as we go)
note("Refund entry point: api/refunds.py:post_refund → services/refunds.py:issue_refund")
note("Money stored as integer paise in models/payment.py (Payment.amount_paise)")
save_state("explorer", {"phase": "trace-refund-flow", "done": ["api", "services"], "next": ["gateway client", "webhooks"]})
save_state("test-mapper", {"phase": "find-tests", "done": ["tests/api"], "next": ["tests/services"]})
# ... process crashes here ...

# Resume: coordinator loads the manifest and scratchpad and injects them
state = json.load(open(manifest))
resume_prompt = "Resuming. Key findings so far:\n" + open(scratch).read() + "\nAgent state:\n" + "\n".join(f"  {a}: {json.dumps(s)}" for a, s in state.items())
print(resume_prompt)
```

> [read] After the crash nothing has to be rediscovered: the coordinator rebuilds each agent's prompt from the manifest (what's done, what's next) and the scratchpad's specific findings, such as the exact entry point and the integer-paise rule. Those are precisely the details that degrade into "typical patterns" in a long, overflowing session.

```quiz
Q: Two hours into exploring a legacy codebase, the agent starts answering with generic descriptions ("typically, services call repositories") instead of the specific classes it found earlier. What helps? (Select 2)
- [x] Have the agent maintain a scratchpad file of key findings and consult it for later questions
- [ ] Ask the same question again
- [x] Delegate focused investigations to subagents and keep only summaries in the main context
- [ ] Switch off CLAUDE.md
why: Context degradation in long sessions is countered by persisting specific findings outside the context and isolating verbose exploration in subagents.
```

## 5.5 | Human review and confidence

Before reducing human review, verify accuracy **by segment**. An aggregate like "97% accurate" can hide a document type or field that's far worse. Then:

- Have the model output **field-level confidence**, and **calibrate** thresholds on a labelled validation set.
- Route **low-confidence** extractions, and those from **ambiguous or contradictory** sources, to people first; reviewer capacity is limited.
- Keep measuring the "trusted" path with **stratified random sampling** of high-confidence extractions, so you catch new error patterns.

```python
import random
random.seed(9)

RESULTS = {  # (document type, field): (checked, correct)
    ("typed invoice", "total"):    (4_000, 3_964), ("typed invoice", "date"): (4_000, 3_952),
    ("scanned receipt", "total"):  (1_500, 1_455), ("scanned receipt", "date"): (1_500, 1_440),
    ("handwritten note", "total"): (300, 231),     ("handwritten note", "date"): (300, 249),
}
checked = sum(c for c, _ in RESULTS.values()); correct = sum(k for _, k in RESULTS.values())
print(f"overall accuracy: {correct / checked:.1%}\n")
for (doc, field), (c, k) in RESULTS.items():
    acc = k / c
    print(f"{doc:<17}{field:<6} {acc:6.1%}{'  ← below 95%: keep full human review' if acc < 0.95 else ''}")

high_conf = [("typed invoice", i) for i in range(3_000)] + [("scanned receipt", i) for i in range(900)] + [("handwritten note", i) for i in range(40)]
per_stratum = 25
sample = {d: random.sample([x for x in high_conf if x[0] == d], per_stratum) for d in ("typed invoice", "scanned receipt", "handwritten note")}
print("\nweekly audit of high-confidence extractions:", {d: len(s) for d, s in sample.items()}, "(equal per type, not proportional)")
```

> [read] The headline 97.3% hides handwritten notes at 77% (totals) and 83% (dates): automating those on the strength of the overall number would let roughly one in five through wrong. The audit samples the same number from each document type, so the rare handwritten notes get checked as often as the abundant typed invoices; a simple random sample would almost never pick them.

```quiz
Q: An extraction pipeline is 97% accurate overall, and the team wants to stop human review of high-confidence extractions. What should happen first?
- [ ] Stop reviewing immediately: 97% is high
- [x] Analyse accuracy by document type and field, confirm every segment performs consistently, and keep stratified sampling of high-confidence extractions
- [ ] Lower the confidence threshold
- [ ] Review only the lowest-confidence 1%
why: Aggregates can mask weak segments. Segment-level validation before automating, plus ongoing stratified sampling, protects against hidden error pockets and new patterns.
```

## 5.6 | Provenance and uncertainty

When findings are summarised and merged, **source attribution is easily lost**: a claim survives, but nobody can say where it came from. In multi-source synthesis:

- Require subagents to output **claim–source mappings** (source URL or document, excerpt, **publication or collection date**), and require the synthesis agent to **preserve and merge** them.
- When credible sources **conflict**, include both values with attribution and annotate the conflict; don't silently pick one. Let the coordinator decide how to reconcile.
- Check **dates** first: two figures from different years may be a trend, not a contradiction.
- Structure the report into **well-established** and **contested** findings, keep each source's own characterisation, and render each content type appropriately: financial data as tables, news as prose, technical findings as lists.

```seq title="Keeping sources attached through synthesis"
Search subagent, Analysis subagent, Coordinator, Synthesis subagent
Search subagent --> Coordinator: claims + source URL + excerpt + date
Analysis subagent --> Coordinator: claims + document + page + date
note Coordinator: Conflicting values kept side by side, annotated; dates checked
Coordinator -> Synthesis subagent: merged claim–source map (nothing paraphrased away)
Synthesis subagent --> Coordinator: report: well-established vs contested, every claim cited
```

```python
CLAIMS = [
    {"metric": "AI use in hiring (share of firms)", "value": "38%", "source": "EU Labour Survey", "date": "2025-11"},
    {"metric": "AI use in hiring (share of firms)", "value": "41%", "source": "Recruiters Assoc. report", "date": "2025-12"},
    {"metric": "AI use in hiring (share of firms)", "value": "23%", "source": "EU Labour Survey", "date": "2023-06"},
    {"metric": "Candidates told about AI screening", "value": "12%", "source": "Consumer Watch", "date": "2026-02"},
    {"metric": "Candidates told about AI screening", "value": "31%", "source": "HR Tech Index", "date": "2026-03"},
]
from collections import defaultdict
by_metric = defaultdict(list)
for c in CLAIMS: by_metric[c["metric"]].append(c)

for metric, cs in by_metric.items():
    print(f"\n{metric}")
    years = {c["date"][:4] for c in cs}
    recent = [c for c in cs if c["date"][:4] == max(years)] if len(years) > 1 else cs
    older = [c for c in cs if c not in recent]
    for c in older:
        print(f"   trend context: {c['value']} ({c['source']}, {c['date']}) — earlier year, not a contradiction")
    vals = {c["value"] for c in recent}
    spread = max(float(v[:-1]) for v in vals) - min(float(v[:-1]) for v in vals)
    label = "WELL-ESTABLISHED (sources agree within 5 points)" if spread <= 5 else "CONTESTED: show both, with sources"
    print(f"   {label}")
    for c in recent:
        print(f"     {c['value']:<5} {c['source']} ({c['date']})")
```

> [read] For AI use in hiring, the 2023 figure is placed as earlier context rather than flagged as conflicting, and the two recent figures agree within a few points: well established. For disclosure to candidates, 12% and 31% from similar dates genuinely conflict, so both go into the report with their sources under "contested", instead of the synthesis quietly picking one.
