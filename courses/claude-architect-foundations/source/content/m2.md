## 2.1 | Tool interfaces and descriptions

**Tool descriptions are the primary mechanism Claude uses to choose a tool.** With minimal descriptions ("Retrieves customer information" / "Retrieves order details") and similar input formats, the model has little to tell the tools apart, and it misroutes. A complete description states:

| Element | Example for `lookup_order` |
|---|---|
| What it does | "Returns one order's status, items, delivery date and refund state." |
| Input formats | "`order_id` like ORD-12345 or #12345; or a tracking number like 1Z…" |
| Example queries | "'check my order #12345', 'where is my parcel 1Z999…'" |
| Edge cases | "Orders older than 2 years return not_found; ask the customer to confirm the number." |
| **Boundaries vs similar tools** | "For account details (address, email, loyalty tier) use `get_customer`, not this tool." |

> [concept] **The "versus similar tools" clause matters most.** Each tool's description is read on its own merits, so overlapping tools look equally plausible unless each one says *when not to use it* and *what to use instead*.

Here's selection on four realistic queries, simulated by matching query words against each tool's description (a crude stand-in for how a model weighs descriptions, but it shows the effect of vocabulary and boundaries).

```python
import re

MINIMAL = {"get_customer": "Retrieves customer information.",
           "lookup_order": "Retrieves order details."}
COMPLETE = {
    "get_customer": "Returns a customer's account: name, email, address, phone, loyalty tier. Input: email or customer ID like C-7731. "
                    "Use for account, address or profile questions. Not for orders, parcels or deliveries: use lookup_order.",
    "lookup_order": "Returns one order: status, items, delivery date, refund state. Input: order number like ORD-12345 or #12345, "
                    "or a parcel tracking number. Use for 'where is my order', delivery, return and refund questions about an order.",
}
STOP = set("a an the my is of for to and or i me it this like use not on".split())
def stem(w): return w[:-3] + "y" if w.endswith("ies") else (w[:-1] if w.endswith("s") and len(w) > 3 else w)
def words(s): return {stem(w) for w in re.findall(r"[a-z]+", s.lower()) if w not in STOP}

def score(query, desc):
    pos, _, neg = desc.partition("Not for")                  # the boundary clause counts against the tool
    return len(words(query) & words(pos)) - 2 * len(words(query) & words(neg))

def choose(query, tools):
    scores = {t: score(query, d) for t, d in tools.items()}
    best = max(scores.values())
    return [t for t, v in scores.items() if v == best][0] if best > 0 else "get_customer (default: first tool)"

QUERIES = [("check my order #12345", "lookup_order"), ("where is my parcel, it was due Tuesday", "lookup_order"),
           ("change the email on my account", "get_customer"), ("has my refund for the blender gone through", "lookup_order")]
for label, tools in [("minimal", MINIMAL), ("complete", COMPLETE)]:
    right = 0
    for q, want in QUERIES:
        got = choose(q, tools); right += got.startswith(want)
    print(f"{label:<9} descriptions: {right}/{len(QUERIES)} routed correctly")
    for q, want in QUERIES:
        print(f"    {q!r:<44} → {choose(q, tools)}")
```

> [read] With one-line descriptions, only two of four route correctly, and one of those only by accident: nothing matched, so it fell through to the first tool, which happened to be right. With complete descriptions, all four route correctly, helped by the boundary clause ("Not for orders… use lookup_order") counting against the wrong tool. That's the official sample answer for this scenario: expand the descriptions first. Few-shot routing examples add token overhead without fixing the cause, a keyword router bypasses the model's understanding, and merging the tools is a bigger change than a first step warrants.

### Split generic tools; check the system prompt

- **Split** a vague, generic tool into purpose-specific ones with clear input/output contracts: `analyze_document` becomes `extract_data_points`, `summarize_content` and `verify_claim_against_source`.
- **Rename** tools whose functions overlap (`analyze_content` vs `analyze_document`) so names and descriptions no longer compete.
- **Review the system prompt** for keyword-sensitive instructions. A line like "always check the customer's account first" can pull requests toward `get_customer` and override well-written descriptions.

## 2.2 | Structured error responses

When an MCP tool fails, return the failure with the **`isError`** flag and enough structure for the agent to decide what to do. A generic "Operation failed" leaves it guessing: it may retry something that can never succeed, or give up on something a retry would fix.

| Category | Example | Retryable? | Agent should |
|---|---|---|---|
| **Transient** | Timeout, service unavailable | Yes | Retry (bounded), maybe later |
| **Validation** | Malformed order ID | No, until the input changes | Fix the input or ask the user |
| **Business** | Return window expired; refund over policy | No | Explain to the customer in plain words; offer alternatives |
| **Permission** | Not authorised for this account | No | Don't retry; escalate or request access |

```seq title="Same failure, two responses"
Agent, Refund tool (MCP)
Agent -> Refund tool (MCP): process_refund(ORD-0931, $60)
Refund tool (MCP) --> Agent: ✗ "Operation failed" → agent retries 3 times, then apologises vaguely
Agent -> Refund tool (MCP): process_refund(ORD-0931, $60)
Refund tool (MCP) --> Agent: ✓ isError, errorCategory: business, isRetryable: false, customerMessage: "outside the 30-day window"
note Agent: No retry; explains the policy and offers the warranty route
```

```python
import json

def tool_error(category, message, retryable, customer_message=None, **extra):
    return {"isError": True, "content": [{"type": "text", "text": json.dumps(
        {"errorCategory": category, "isRetryable": retryable, "message": message,
         **({"customerMessage": customer_message} if customer_message else {}), **extra})}]}

def agent_decision(result):
    if not result.get("isError"):
        data = json.loads(result["content"][0]["text"])
        return "valid empty result: tell the customer there are no matches" if data.get("matches") == [] else "use the data"
    e = json.loads(result["content"][0]["text"])
    if e["isRetryable"]:                   return f"retry ({e['errorCategory']}), bounded"
    if e["errorCategory"] == "business":   return f"don't retry; tell the customer: {e['customerMessage']}"
    if e["errorCategory"] == "validation": return "don't retry as is; fix the input or ask the user"
    return "don't retry; escalate or request access"

results = {
    "timeout":        tool_error("transient", "orders service timed out after 10s", True),
    "bad id":         tool_error("validation", "order_id 'ORD12' doesn't match ORD-NNNNN", False),
    "window closed":  tool_error("business", "return window closed 2026-09-30", False,
                                 customer_message="This order is outside the 30-day return window, but it may still be under warranty."),
    "no access":      tool_error("permission", "agent role can't read corporate accounts", False),
    "no matches":     {"isError": False, "content": [{"type": "text", "text": json.dumps({"matches": []})}]},
}
for name, r in results.items():
    print(f"{name:<14} → {agent_decision(r)}")
```

> [read] Five outcomes, five different correct responses, and only one of them is a retry. Note the last line: an empty result is **not** an error. "I searched and found nothing" and "I couldn't search" look identical if both come back empty, but they need opposite handling (Module 5 returns to this).

> [tip] Inside a multi-agent system, let subagents **recover locally** from transient failures (a bounded retry) and propagate to the coordinator only what they can't resolve, together with what they attempted and any partial results.

```quiz

why: Generic errors hide whether a retry can work. Structured metadata lets the agent skip pointless retries and explain policy outcomes to the customer.
```

```quiz

```

## 2.3 | Distributing tools and tool_choice

Give an agent too many tools (the guide's example is 18 instead of 4–5) and selection reliability drops: more options, more overlap, more decisions. Agents with tools outside their specialisation also tend to **misuse** them, for example a synthesis agent starting its own web searches. Scope each agent's tools to its role.

| Technique | Example |
|---|---|
| **Role-scoped tools** | Search agent: web search and fetch. Synthesis agent: read and write the report. |
| **Constrained alternatives** | Replace a generic `fetch_url` with `load_document`, which only accepts URLs from approved document stores |
| **Scoped cross-role tools for frequent needs** | Give synthesis a narrow `verify_fact` for simple checks; complex verification still goes through the coordinator to the search agent |

That last row is the official sample answer for a synthesis agent bouncing every fact-check through the coordinator. Here's why it works, with the guide's split of 85% simple checks and 15% deep ones (round-trip counts are illustrative).

```python
checks = 100
simple, deep = 85, 15
via_coordinator_trips = 3          # synthesis → coordinator → search → synthesis
verify_fact_trips = 1              # one scoped tool call

before = checks * via_coordinator_trips
after = simple * verify_fact_trips + deep * via_coordinator_trips
print(f"round trips per 100 checks: {before} before, {after} with a scoped verify_fact tool ({1 - after / before:.0%} fewer)")

ALLOWED_STORES = ("https://docs.internal.example/", "https://policies.internal.example/")
def load_document(url):
    if not url.startswith(ALLOWED_STORES):
        return {"isError": True, "errorCategory": "validation", "isRetryable": False,
                "message": "load_document only accepts approved document stores"}
    return {"isError": False, "content": f"(document text from {url})"}
for u in ["https://docs.internal.example/refund-policy", "https://evil.example/payload.html"]:
    print(f"{u:<48} → {'loaded' if not load_document(u)['isError'] else 'rejected: not an approved store'}")
```

> [read] The scoped tool removes about 57% of round trips while keeping complex verification on the existing, observable path. Giving synthesis *all* the search tools would over-provision it; batching checks to the end would block synthesis steps that depend on verified facts. The constrained `load_document` shows the same least-privilege idea at the tool level: it can't be pointed at arbitrary URLs.

### tool_choice

| Setting | Behaviour | Use for |
|---|---|---|
| `{"type": "auto"}` | Claude may call a tool **or** reply with text | Normal agent turns |
| `{"type": "any"}` | Claude **must** call a tool, but chooses which | Guaranteeing structured output when several extraction schemas exist and the document type is unknown |
| `{"type": "tool", "name": "extract_metadata"}` | Claude **must** call that tool | Forcing a step to run first (metadata before enrichment), then continuing in follow-up turns |

> [warn] **Then vs now.** The exam guide teaches `any` and forced tool selection, and you should know them for the exam. On current models, **Claude Opus 5.5, Sonnet 5.5 and Fable 5.1 reject forced `tool_choice` (`any` or a named tool) with a 400 error.** There, use `auto` with an instruction to call the tool, `strict: true` on the tool for schema-valid input, check that the call was made, or use structured outputs (`output_config.format`) when the forced call only existed to get JSON.

## 2.4 | Integrating MCP servers

In Claude Code, MCP servers are configured at two main scopes:

| Scope | File | For |
|---|---|---|
| **Project** | `.mcp.json` in the repository, **committed** | Shared team tooling (Jira, GitHub, internal APIs) |
| **User** | `~/.claude.json` | Personal or experimental servers |

Use **environment variable expansion** in `.mcp.json` so credentials never enter version control. Tools from **all** configured servers are discovered at connection time and are available to the agent **simultaneously**.

```file title=".mcp.json (committed)" lang=json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": { "Authorization": "Bearer ${GITHUB_TOKEN}" }
    },
    "orders": {
      "command": "python",
      "args": ["tools/orders_mcp.py"],
      "env": { "ORDERS_API_KEY": "${ORDERS_API_KEY}" }
    }
  }
}
```

```seq title="Session start: every configured server's tools at once"
Claude Code, .mcp.json (project), ~/.claude.json (user), Servers
Claude Code -> .mcp.json (project): read github, orders (expand ${GITHUB_TOKEN}, ${ORDERS_API_KEY})
Claude Code -> ~/.claude.json (user): read scratch-notes
Claude Code -> Servers: connect to each and list its tools
Servers --> Claude Code: github: 2 tools · scratch-notes: 2 tools · orders: auth failed
note Claude Code: The agent sees all connected servers' tools together
```

```python
import os, re

PROJECT = {"github": {"headers": {"Authorization": "Bearer ${GITHUB_TOKEN}"}, "tools": ["create_issue", "search_code"]},
           "orders": {"env": {"ORDERS_API_KEY": "${ORDERS_API_KEY}"}, "tools": ["lookup_order", "process_refund"]}}
USER = {"scratch-notes": {"env": {}, "tools": ["save_note", "find_note"]}}
ENV = {"GITHUB_TOKEN": "ghp_(set in the shell)"}                        # ORDERS_API_KEY missing on this machine

def expand(obj, env, missing):
    if isinstance(obj, dict): return {k: expand(v, env, missing) for k, v in obj.items()}
    if isinstance(obj, list): return [expand(v, env, missing) for v in obj]
    if isinstance(obj, str):
        for var in re.findall(r"\$\{(\w+)\}", obj):
            if var not in env: missing.append(var)
        return re.sub(r"\$\{(\w+)\}", lambda m: env.get(m.group(1), "<MISSING>"), obj)
    return obj

available = []
for scope, servers in (("project", PROJECT), ("user", USER)):
    for name, cfg in servers.items():
        missing = []
        expand(cfg, ENV, missing)
        status = f"credential missing: {missing}" if missing else "connected"
        if not missing: available += [f"mcp__{name}__{t}" for t in cfg["tools"]]
        print(f"{scope:<8}{name:<14}{status}")
print("\ntools available together:", available)
```

> [read] The GitHub and personal notes servers connect, and their tools appear side by side in one tool list. The orders server fails because `ORDERS_API_KEY` isn't set in this shell, which is the most common "the MCP tool isn't there" cause after typos and unapproved servers. The committed file never contained the key itself.

### Make MCP tools win over built-ins, and expose catalogs as resources

- If an agent keeps using **Grep** where a richer MCP search tool exists, the MCP tool's description is usually too thin. Explain its capabilities and outputs in detail.
- Prefer **existing community MCP servers** for standard integrations (Jira, GitHub); build custom servers for team-specific workflows.
- Expose **content catalogs as MCP resources** (issue summaries, documentation trees, database schemas) so the agent can see what exists without exploratory tool calls.

## 2.5 | The built-in tools

Agents built on Claude Code and the Agent SDK come with built-in tools. Choosing the right one is a tested skill:

| Tool | Does | Use for |
|---|---|---|
| **Grep** | Searches file **contents** for a pattern | Callers of a function, an error message, an import |
| **Glob** | Matches file **paths** by pattern | All test files: `**/*.test.tsx`; all migrations |
| **Read** / **Write** | Load or replace a whole file | Understanding a file; rewriting it completely |
| **Edit** | Targeted change by matching **unique** text | Small, precise edits |
| **Bash** | Runs commands | Tests, builds, git |

> [tip] Build understanding **incrementally**: Grep to find entry points, Read to follow imports and trace the flow. Don't read every file up front. If Edit fails because its anchor text isn't unique, fall back to Read + Write. To trace usage through wrapper modules, first find every name the wrapper exports, then search for each.

Here are those moves on a small in-memory repository.

```python
import fnmatch

REPO = {
    "src/payments/refund.py": "from .client import charge\n\ndef issue_refund(order, amount):\n    log('refund start')\n    result = charge(order, -amount)\n    log('refund done')\n    return result\n",
    "src/payments/client.py": "def charge(order, amount):\n    log('charge')\n    return gateway.post(order, amount)\n",
    "src/payments/__init__.py": "from .refund import issue_refund as refund\nfrom .client import charge as raw_charge\n",
    "src/api/routes.py": "from payments import refund\n\ndef post_refund(req):\n    return refund(req.order, req.amount)\n",
    "src/ui/Button.test.tsx": "test('renders')\n", "src/ui/Modal.test.tsx": "test('opens')\n",
}
grep = lambda pat: [(p, i + 1) for p, src in REPO.items() for i, line in enumerate(src.splitlines()) if re.search(pat, line)]
glob = lambda pat: sorted(p for p in REPO if fnmatch.fnmatch(p, pat))

print("Glob **/*.test.tsx:", glob("*.test.tsx"))           # fnmatch's * also crosses folders, like **
print("Grep 'log\\(' (content):", grep(r"log\("))

def edit(path, old, new):
    count = REPO[path].count(old)
    if count != 1:
        return f"Edit failed: {count} matches for {old!r}; fall back to Read + Write"
    REPO[path] = REPO[path].replace(old, new); return "edited"
print("Edit 'log(' → 'audit(' in refund.py:", edit("src/payments/refund.py", "log(", "audit("))
src = REPO["src/payments/refund.py"]                                    # fallback: Read the whole file...
REPO["src/payments/refund.py"] = src.replace("log(", "audit(")         # ...and Write the corrected version
print("after Read + Write:", re.findall(r"\w+\('refund \w+'\)", REPO["src/payments/refund.py"]))

exports = re.findall(r"import (\w+) as (\w+)", REPO["src/payments/__init__.py"])
print("\nwrapper exports:", exports)
for original, alias in exports:
    print(f"  callers of {alias} (wraps {original}):", [p for p, _ in grep(rf"\b{alias}\(")])
```

> [read] Glob finds files by name wherever they live; Grep finds `log(` calls by content. The Edit fails because `log(` appears twice in the file, so there's no unique anchor; Read + Write then updates both calls reliably. Tracing through the `payments` wrapper only works after listing its exports: callers use the alias `refund`, not `issue_refund`, so a search for the original name alone would find nothing in the API layer.
