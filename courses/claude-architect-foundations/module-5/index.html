Task statement 5.1

Preserving critical information

Four things erode context in long interactions:

ProblemWhat happensFix
Progressive summarisationAmounts, percentages, dates and what the customer was promised become vague ("about $90", "early next week")Keep transactional facts in a persistent case facts block outside the summarised history
Lost in the middleFindings in the middle of long inputs get less attention than the start and endPut a key findings summary first; organise details under explicit section headers
Tool-result bloatA 40-field order lookup when 5 fields matter, repeated every turnTrim tool outputs to the relevant fields before they accumulate
Missing historyRequests sent without the full conversation lose coherenceAlways pass the complete history (minus what you've deliberately trimmed)

For multi-issue sessions, keep a structured layer per issue (order ID, amount, status) so three problems in one conversation don't blur together. In multi-agent systems, have upstream agents return structured facts with metadata (dates, sources, relevance) rather than long prose and reasoning, especially when downstream agents have small context budgets.

Python
import json

order_lookup = {   # what the orders API returns (abridged here: imagine 40+ fields)
    "order_id": "ORD-1182", "status": "delivered", "delivered_at": "2026-10-09", "total": 42.00, "currency": "USD",
    "items": [{"sku": "BLD-200", "name": "Blender", "qty": 1, "price": 42.00, "returnable": True}],
    "warehouse": "PNQ-3", "carrier": "BlueDart", "carrier_events": [{"t": i, "e": "scan"} for i in range(14)],
    "billing_address": "...", "shipping_address": "...", "gift_wrap": False, "loyalty_points": 84,
    "fraud_score": 0.02, "marketing_opt_in": True, "audit": {"created_by": "web", "version": 7},
}
RETURN_FIELDS = ["order_id", "status", "delivered_at", "total", "items"]
trimmed = {k: order_lookup[k] for k in RETURN_FIELDS}
trimmed["items"] = [{k: i[k] for k in ("name", "price", "returnable")} for i in trimmed["items"]]

case_facts = {"issues": [
    {"id": 1, "order": "ORD-1182", "problem": "blender arrived broken", "amount": 42.00, "status": "refund issued"},
    {"id": 2, "order": "ORD-1190", "problem": "charged twice", "amount": 129.00, "status": "awaiting billing review"},
], "promised": "update on issue 2 by email before 17:00 IST, 28 Oct"}

print(f"raw lookup ≈ {len(json.dumps(order_lookup)) // 4} tokens; trimmed ≈ {len(json.dumps(trimmed)) // 4} tokens")
print("trimmed:", trimmed)
print("\n<case_facts>" + json.dumps(case_facts) + "</case_facts>   ← carried verbatim every turn")

trimmed: {'order_id': 'ORD-1182', 'status': 'delivered', 'delivered_at': '2026-10-09', 'total': 42.0, 'items': [{'name': 'Blender', 'price': 42.0, 'returnable': True}]}

<case_facts>{"issues": [{"id": 1, "order": "ORD-1182", "problem": "blender arrived broken", "amount": 42.0, "status": "refund issued"}, {"id": 2, "order": "ORD-1190", "problem": "charged twice", "amount": 129.0, "status": "awaiting billing review"}], "promised": "update on issue 2 by email before 17:00 IST, 28 Oct"}</case_facts>   ← carried verbatim every turn
How to read it

The trimmed lookup keeps exactly what a return decision needs at about a fifth of the size, and that saving repeats on every later turn. The case-facts block holds both issues' exact amounts and the specific promise made to the customer, so a summary that drifts to "some refund, will update soon" can't erase them.

Practice questionIn long support conversations, the agent later quotes refund amounts and promised dates vaguely or wrongly. History is being summarised to stay within limits. What's the fix?

Summaries are lossy by design. A small structured block of exact facts survives any amount of summarisation.

Practice questionSelect 2A synthesis agent receives 30 pages of aggregated subagent output and keeps missing findings from the middle sections. Which changes help? (Select 2)

Models attend most reliably to the start and end of long inputs. A leading summary and clear sections counter the position effect.

Task statement 5.2

Escalation and ambiguity

TriggerEscalate?How
Customer explicitly asks for a human✓ ImmediatelyDon't investigate first; hand over with a structured summary
Policy is ambiguous or silent on the request (a policy gap)✓E.g. competitor price matching when policy only covers own-site adjustments
Can't make meaningful progress✓After real attempts; with what was tried
Customer is frustrated, issue is straightforward✗ Not on its ownAcknowledge the frustration, offer the resolution; escalate if they reiterate they want a person
Complex but within policy and capability✗ Not on its ownKeep working
Watch out

Two unreliable proxies. Sentiment-based escalation and the model's self-reported confidence don't track case complexity. An agent that's wrongly confident on hard policy-exception cases will rate itself highly on exactly those. Calibrate escalation with explicit criteria plus few-shot examples in the system prompt, the official sample answer for an agent stuck at 55% first-contact resolution.

Ambiguous matches need clarification, not guesswork. When a lookup returns several customers, ask for another identifier; never pick one by heuristic ("the most recent", "the first").

Python
def handle(turn):
    if turn.get("asks_for_human"):
        return "ESCALATE now with a structured summary (don't investigate first)"
    if turn.get("policy") == "silent":
        return "ESCALATE: policy gap — a person must decide"
    matches = turn.get("customer_matches", 1)
    if matches > 1:
        return f"ASK for another identifier ({matches} customers match); never guess"
    if turn.get("frustrated") and turn.get("straightforward"):
        if turn.get("reiterated_human"):
            return "ESCALATE: they asked again for a person"
        return "acknowledge frustration, offer the fix, mention a person is available"
    return "resolve"

turns = [
    ("'Just get me a human.'",                                        dict(asks_for_human=True)),
    ("'Match AnyMart's price, it's ₹400 cheaper.'",                   dict(policy="silent")),
    ("'I'm Rahul Shah, refund my order.' (3 Rahul Shahs found)",      dict(customer_matches=3)),
    ("'THIRD TIME asking! Replace my damaged kettle!' (photo attached)", dict(frustrated=True, straightforward=True)),
    ("Same customer: 'No, I want a person.'",                         dict(frustrated=True, straightforward=True, reiterated_human=True)),
    ("Standard damage replacement with photo evidence",               dict(straightforward=True)),
]
for text, t in turns:
    print(f"{handle(t):<74} ← {text}")

ESCALATE now with a structured summary (don't investigate first)           ← 'Just get me a human.'
ESCALATE: policy gap — a person must decide                                ← 'Match AnyMart's price, it's ₹400 cheaper.'
ASK for another identifier (3 customers match); never guess                ← 'I'm Rahul Shah, refund my order.' (3 Rahul Shahs found)
acknowledge frustration, offer the fix, mention a person is available      ← 'THIRD TIME asking! Replace my damaged kettle!' (photo attached)
ESCALATE: they asked again for a person                                    ← Same customer: 'No, I want a person.'

How to read it

Frustration alone gets resolution, not escalation, until the customer reiterates that they want a person; then it's immediate. The standard damage replacement with a photo is resolved autonomously, which is exactly what the 55%-resolution agent was escalating wrongly. Three customers called Rahul Shah means asking for an email or order number, not picking one.

Practice questionAn agent resolves 55% of contacts against an 80% target. It escalates routine damage replacements that have photo evidence, but tries to handle policy exceptions on its own. What's the most effective first improvement?

The decision boundary is unclear, so state it with examples. Self-reported confidence is poorly calibrated (it's already confident on the hard cases), a classifier is over-engineered as a first step, and sentiment doesn't measure complexity.

Practice questionget_customer returns two accounts named "Priya Nair". What should the agent do?

Picking by heuristic risks acting on the wrong account. Asking for one more identifier resolves the ambiguity safely and quickly.

Task statement 5.3

Error propagation across agents

When a subagent fails, what the coordinator receives decides what it can do. A structured error context carries: the failure type, what was attempted, any partial results, and possible alternatives. Two anti-patterns the guide names:

  • Suppressing errors: returning an empty result marked "success". The coordinator thinks the search worked and found nothing.
  • Terminating the whole workflow on one subagent failure, when partial results and alternatives could still produce a useful report.

Subagents should recover locally from transient failures (a bounded retry) and propagate only what they can't resolve. The final synthesis should carry coverage annotations: which findings are well supported, which areas have gaps because a source was unavailable.

Python
OUTCOMES = {
    "regulation":  {"ok": True,  "findings": 6},
    "case law":    {"ok": False, "failure": "timeout", "attempted": "2 queries", "partial": 2, "alternatives": ["legal DB via analysis agent"]},
    "vendor tools": {"ok": True,  "findings": 0},                               # searched; genuinely nothing
    "worker views": {"ok": False, "failure": "permission", "attempted": "survey archive", "partial": 0, "alternatives": []},
}
def coordinate(outcomes):
    report = []
    for topic, o in outcomes.items():
        if o["ok"] and o["findings"]:   report.append((topic, f"well supported ({o['findings']} sources)"))
        elif o["ok"]:                   report.append((topic, "searched: no relevant sources exist"))
        elif o["alternatives"]:         report.append((topic, f"PARTIAL: {o['partial']} sources; retrying via {o['alternatives'][0]}"))
        else:                           report.append((topic, f"GAP: {o['failure']} on {o['attempted']}; not covered"))
    return report

for topic, note in coordinate(OUTCOMES):
    print(f"{topic:<13} {note}")
Output · produced by running this code
regulation    well supported (6 sources)
case law      PARTIAL: 2 sources; retrying via legal DB via analysis agent
vendor tools  searched: no relevant sources exist
worker views  GAP: permission on survey archive; not covered
How to read it

The report still ships, and it's honest about coverage: one area is solid, one has partial results with an alternative route under way, one was searched and genuinely has nothing, and one is a gap because of a permission failure. Had the failures been suppressed as empty successes, the last two lines would have read the same as "vendor tools": a false claim that nothing exists.

Practice questionA web search subagent times out. Which way of reporting it back best enables recovery?

Structured context lets the coordinator retry differently, try an alternative or proceed with partial results. Generic statuses hide information, suppression fakes success, and termination throws away recoverable work.

Task statement 5.4

Exploring large codebases

In long exploration sessions, context degrades: answers become inconsistent, and the model starts citing "typical patterns" instead of the specific classes it found an hour ago. The guide's countermeasures:

TechniqueDoes
Scratchpad filesThe agent writes key findings to a file and re-reads it for later questions
Subagent delegation"Find all test files", "trace the refund flow's dependencies" run in subagents; the main agent keeps the high-level picture
Summaries between phasesSummarise one phase's findings and inject that summary into the next phase's subagents
State manifests for crash recoveryEach agent exports state to a known location; on resume, the coordinator loads the manifest and injects it into prompts
/compactReduces context usage when it fills with verbose discovery output

Here's a scratchpad and a manifest surviving a crash, using real files in a temporary folder.

Python
import json, os, tempfile

work = tempfile.mkdtemp()
scratch, manifest = os.path.join(work, "scratchpad.md"), os.path.join(work, "manifest.json")

def note(line):
    with open(scratch, "a") as f: f.write(f"- {line}\n")

def save_state(agent, state):
    m = json.load(open(manifest)) if os.path.exists(manifest) else {}
    m[agent] = state
    json.dump(m, open(manifest, "w"), indent=1)

# Phase 1: exploration (findings persisted as we go)
note("Refund entry point: api/refunds.py:post_refund → services/refunds.py:issue_refund")
note("Money stored as integer paise in models/payment.py (Payment.amount_paise)")
save_state("explorer", {"phase": "trace-refund-flow", "done": ["api", "services"], "next": ["gateway client", "webhooks"]})
save_state("test-mapper", {"phase": "find-tests", "done": ["tests/api"], "next": ["tests/services"]})
# ... process crashes here ...

# Resume: coordinator loads the manifest and scratchpad and injects them
state = json.load(open(manifest))
resume_prompt = "Resuming. Key findings so far:\n" + open(scratch).read() + "\nAgent state:\n" + "\n".join(f"  {a}: {json.dumps(s)}" for a, s in state.items())
print(resume_prompt)
Output · produced by running this code
Resuming. Key findings so far:
- Refund entry point: api/refunds.py:post_refund → services/refunds.py:issue_refund
- Money stored as integer paise in models/payment.py (Payment.amount_paise)

Agent state:
  explorer: {"phase": "trace-refund-flow", "done": ["api", "services"], "next": ["gateway client", "webhooks"]}
  test-mapper: {"phase": "find-tests", "done": ["tests/api"], "next": ["tests/services"]}
How to read it

After the crash nothing has to be rediscovered: the coordinator rebuilds each agent's prompt from the manifest (what's done, what's next) and the scratchpad's specific findings, such as the exact entry point and the integer-paise rule. Those are precisely the details that degrade into "typical patterns" in a long, overflowing session.

Practice questionSelect 2Two hours into exploring a legacy codebase, the agent starts answering with generic descriptions ("typically, services call repositories") instead of the specific classes it found earlier. What helps? (Select 2)

Context degradation in long sessions is countered by persisting specific findings outside the context and isolating verbose exploration in subagents.

Task statement 5.5

Human review and confidence

Before reducing human review, verify accuracy by segment. An aggregate like "97% accurate" can hide a document type or field that's far worse. Then:

  • Have the model output field-level confidence, and calibrate thresholds on a labelled validation set.
  • Route low-confidence extractions, and those from ambiguous or contradictory sources, to people first; reviewer capacity is limited.
  • Keep measuring the "trusted" path with stratified random sampling of high-confidence extractions, so you catch new error patterns.
Python
import random
random.seed(9)

RESULTS = {  # (document type, field): (checked, correct)
    ("typed invoice", "total"):    (4_000, 3_964), ("typed invoice", "date"): (4_000, 3_952),
    ("scanned receipt", "total"):  (1_500, 1_455), ("scanned receipt", "date"): (1_500, 1_440),
    ("handwritten note", "total"): (300, 231),     ("handwritten note", "date"): (300, 249),
}
checked = sum(c for c, _ in RESULTS.values()); correct = sum(k for _, k in RESULTS.values())
print(f"overall accuracy: {correct / checked:.1%}\n")
for (doc, field), (c, k) in RESULTS.items():
    acc = k / c
    print(f"{doc:<17}{field:<6} {acc:6.1%}{'  ← below 95%: keep full human review' if acc < 0.95 else ''}")

high_conf = [("typed invoice", i) for i in range(3_000)] + [("scanned receipt", i) for i in range(900)] + [("handwritten note", i) for i in range(40)]
per_stratum = 25
sample = {d: random.sample([x for x in high_conf if x[0] == d], per_stratum) for d in ("typed invoice", "scanned receipt", "handwritten note")}
print("\nweekly audit of high-confidence extractions:", {d: len(s) for d, s in sample.items()}, "(equal per type, not proportional)")
Output · produced by running this code
overall accuracy: 97.3%

typed invoice    total   99.1%
typed invoice    date    98.8%
scanned receipt  total   97.0%
scanned receipt  date    96.0%
handwritten note total   77.0%  ← below 95%: keep full human review
handwritten note date    83.0%  ← below 95%: keep full human review

How to read it

The headline 97.3% hides handwritten notes at 77% (totals) and 83% (dates): automating those on the strength of the overall number would let roughly one in five through wrong. The audit samples the same number from each document type, so the rare handwritten notes get checked as often as the abundant typed invoices; a simple random sample would almost never pick them.

Practice questionAn extraction pipeline is 97% accurate overall, and the team wants to stop human review of high-confidence extractions. What should happen first?

Aggregates can mask weak segments. Segment-level validation before automating, plus ongoing stratified sampling, protects against hidden error pockets and new patterns.

Task statement 5.6

Provenance and uncertainty

When findings are summarised and merged, source attribution is easily lost: a claim survives, but nobody can say where it came from. In multi-source synthesis:

  • Require subagents to output claim–source mappings (source URL or document, excerpt, publication or collection date), and require the synthesis agent to preserve and merge them.
  • When credible sources conflict, include both values with attribution and annotate the conflict; don't silently pick one. Let the coordinator decide how to reconcile.
  • Check dates first: two figures from different years may be a trend, not a contradiction.
  • Structure the report into well-established and contested findings, keep each source's own characterisation, and render each content type appropriately: financial data as tables, news as prose, technical findings as lists.
Python
CLAIMS = [
    {"metric": "AI use in hiring (share of firms)", "value": "38%", "source": "EU Labour Survey", "date": "2025-11"},
    {"metric": "AI use in hiring (share of firms)", "value": "41%", "source": "Recruiters Assoc. report", "date": "2025-12"},
    {"metric": "AI use in hiring (share of firms)", "value": "23%", "source": "EU Labour Survey", "date": "2023-06"},
    {"metric": "Candidates told about AI screening", "value": "12%", "source": "Consumer Watch", "date": "2026-02"},
    {"metric": "Candidates told about AI screening", "value": "31%", "source": "HR Tech Index", "date": "2026-03"},
]
from collections import defaultdict
by_metric = defaultdict(list)
for c in CLAIMS: by_metric[c["metric"]].append(c)

for metric, cs in by_metric.items():
    print(f"\n{metric}")
    years = {c["date"][:4] for c in cs}
    recent = [c for c in cs if c["date"][:4] == max(years)] if len(years) > 1 else cs
    older = [c for c in cs if c not in recent]
    for c in older:
        print(f"   trend context: {c['value']} ({c['source']}, {c['date']}) — earlier year, not a contradiction")
    vals = {c["value"] for c in recent}
    spread = max(float(v[:-1]) for v in vals) - min(float(v[:-1]) for v in vals)
    label = "WELL-ESTABLISHED (sources agree within 5 points)" if spread <= 5 else "CONTESTED: show both, with sources"
    print(f"   {label}")
    for c in recent:
        print(f"     {c['value']:<5} {c['source']} ({c['date']})")

   trend context: 23% (EU Labour Survey, 2023-06) — earlier year, not a contradiction
   WELL-ESTABLISHED (sources agree within 5 points)
     38%   EU Labour Survey (2025-11)

How to read it

For AI use in hiring, the 2023 figure is placed as earlier context rather than flagged as conflicting, and the two recent figures agree within a few points: well established. For disclosure to candidates, 12% and 31% from similar dates genuinely conflict, so both go into the report with their sources under "contested", instead of the synthesis quietly picking one.

Practice questionTwo credible sources report 12% and 31% for the same statistic, published a month apart. How should the synthesis handle it?

Arbitrarily choosing or averaging hides a real disagreement. Preserving both with attribution lets readers, or the coordinator, weigh the sources.

Practice questionA report says sources "contradict each other" on adoption: 23% versus 40%. The first is from 2023, the second from 2025. What went wrong upstream?

Requiring dates in structured outputs lets synthesis tell temporal change from genuine conflict.
