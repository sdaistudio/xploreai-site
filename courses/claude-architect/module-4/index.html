Session 4.1

Evaluation metrics

An eval is only as good as its metrics. An architect defines them before building, across five dimensions, each with a target agreed with stakeholders:

DimensionExample metricsTypical target form
AccuracyTask success rate; field-level precision/recall/F1 for extraction; groundedness (claims supported by sources)"≥ 95% task success; F1 ≥ 0.97 on the 14 claim fields"
LatencyTime to first token and total time, at p50 and p95"TTFT p95 ≤ 1.5 s; total p95 ≤ 8 s"
Cost$ per request; $ per successful task (includes retries and escalations)"≤ ₹4 per settled claim"
SafetyHarmful-output rate; over-refusal rate on legitimate requests; escalation precision"0 unsafe outputs on the red-team set; over-refusal ≤ 1%"
SecurityPrompt-injection success rate; PII leakage rate; unauthorised tool-call attempts blocked"0 successful injections on the attack set"
The idea

Measure success per task, not per call. A cheaper configuration that needs two retries, or escalates 30% of cases to a person, can cost more per completed task than a pricier one that gets it right first time. Cost and latency metrics should follow the task to its end.

Here's a scorecard computed from one eval run. The case results are a sample we wrote; the metric calculations are real.

Python
CASES = [  # gold fields, predicted fields, latency_s, cost_inr, retries, is_attack, attack_succeeded, unsafe, wrongly_refused
    ({"amount": "850", "date": "2026-10-14", "doctor": "Rao"},  {"amount": "850", "date": "2026-10-14", "doctor": "Rao"},  3.1, 2.4, 0, False, False, False, False),
    ({"amount": "1200", "date": "2026-10-02", "doctor": "Iyer"}, {"amount": "1200", "date": "2026-10-20", "doctor": "Iyer"}, 4.0, 2.6, 0, False, False, False, False),
    ({"amount": "430", "date": "2026-09-30", "doctor": "Shah"},  {"amount": "430", "date": "2026-09-30"},                   2.8, 2.2, 1, False, False, False, False),
    ({"amount": "9900", "date": "2026-10-11", "doctor": "Rao"},  {},                                                       1.2, 0.9, 0, False, False, False, True),
    ({}, {}, 2.2, 1.8, 0, True, False, False, False),
    ({}, {}, 2.9, 2.0, 0, True, True,  False, False),
    ({"amount": "300", "date": "2026-10-19", "doctor": "Desai"}, {"amount": "300", "date": "2026-10-19", "doctor": "Desai"}, 9.4, 3.9, 2, False, False, False, False),
]

tp = fp = fn = 0
for gold, pred, *_ in CASES:
    for k, v in pred.items():
        if gold.get(k) == v: tp += 1
        else: fp += 1
    fn += sum(1 for k in gold if gold.get(k) != pred.get(k))
precision, recall = tp / (tp + fp), tp / (tp + fn)
f1 = 2 * precision * recall / (precision + recall)

normal = [c for c in CASES if not c[5]]
success = [c for c in normal if c[0] and c[0] == c[1]]
lat = sorted(c[2] for c in CASES)
p95 = lat[min(len(lat) - 1, int(0.95 * len(lat)))]
cost_per_success = sum(c[3] for c in normal) / len(success)
attacks = [c for c in CASES if c[5]]

card = [("field F1", f1, 0.97, ">="), ("task success", len(success) / len(normal), 0.95, ">="),
        ("total p95 (s)", p95, 8.0, "<="), ("₹ per successful task", cost_per_success, 4.0, "<="),
        ("over-refusal rate", sum(c[8] for c in normal) / len(normal), 0.01, "<="),
        ("injection success", sum(c[6] for c in attacks) / len(attacks), 0.0, "<=")]
for name, value, target, op in card:
    ok = value >= target if op == ">=" else value <= target
    print(f"{'PASS' if ok else 'FAIL'}  {name:<22} {value:>7.2f}   target {op} {target}")
Output · produced by running this code

FAIL  task success              0.40   target >= 0.95
FAIL  total p95 (s)             9.40   target <= 8.0
FAIL  ₹ per successful task     6.00   target <= 4.0
FAIL  over-refusal rate         0.20   target <= 0.01
FAIL  injection success         0.50   target <= 0.0
How to read it

Every target fails in this small run, and each for a different reason. Field precision is high (10 of 11 extracted fields are right), but recall is only two-thirds because of a missing field and a wrongly refused document, so F1 fails. Cost per successful task is ₹6, even though no single call costs more than ₹3.9, because failures and retries are paid for too. And one of two injection attempts succeeded: a security failure that a pure accuracy metric would never show.

Practice questionA configuration costs ₹2 per call and another ₹3 per call. The cheaper one fails 35% of tasks, which then need a retry or a human. Which metric should decide between them?

Per-call cost hides the price of failures. The cost of getting a task done, including retries and human handling, is what the business pays.

Practice questionSelect 2Which metrics belong in an evaluation of a customer-facing Claude assistant's safety and security? (Select 2)

Safety covers both harmful outputs and refusing legitimate work; security covers attacks such as injection. Prompt length and sampling settings are configuration, not outcome metrics.

Session 4.2

Eval datasets and mixed methods

An evaluation dataset should look like production, plus the cases production hasn't shown you yet. Build it from several sources and keep it versioned like code.

SourceGives youWatch out for
Golden set (expert-labelled real cases)The reference for accuracySmall and expensive; refresh as the domain changes
Production samplesToday's real distributionNeed labelling and PII scrubbing
Edge casesRare formats, ambiguous inputs, long documentsEasy to under-represent
Adversarial / red-teamInjection, jailbreaks, abuseKeep separate so it doesn't skew accuracy scores
Synthetic (model-generated)Volume and coverage of rare categoriesCan be unrealistic; spot-check with people
Production failuresExactly what brokeThe most valuable additions; add every incident

Mixed methods means using the right grader for each criterion: code for anything objective (fields, format, numbers), an LLM judge for nuanced qualities at scale (tone, faithfulness to sources), and people for high-stakes calls and for labelling the reference data that validates the judge.

Python
import random
random.seed(3)

POOLS = {"golden": 180, "production": 2_400, "edge": 95, "adversarial": 60, "synthetic": 500, "incidents": 22}
QUOTA = {"golden": 120, "production": 200, "edge": 60, "adversarial": 60, "synthetic": 40, "incidents": 22}
CATEGORIES = ["outpatient", "diagnostics", "pharmacy", "dental", "maternity"]

dataset = []
for source, n in QUOTA.items():
    for i in range(min(n, POOLS[source])):
        dataset.append({"id": f"{source}-{i}", "source": source,
                        "category": random.choice(CATEGORIES if source != "edge" else CATEGORIES[3:])})
print(f"eval set v12: {len(dataset)} items")
for source in QUOTA:
    print(f"  {source:<12} {sum(d['source'] == source for d in dataset):>4}")
by_cat = {c: sum(d["category"] == c for d in dataset if d["source"] != "adversarial") for c in CATEGORIES}
print("by category (excluding adversarial):", by_cat)

GRADERS = {"field accuracy": "code", "output format": "code", "faithful to policy text": "LLM judge (validated vs human labels)",
           "tone for anxious patients": "LLM judge", "payout eligibility decision": "human expert", "injection resisted": "code"}
print("\ngrading plan:")
for criterion, method in GRADERS.items():
    print(f"  {criterion:<28} → {method}")

How to read it

All 22 incident cases are included, every one of them a real failure, while the 2,400 production samples are capped at 200 so they don't swamp the rarer slices. Edge cases skew toward dental and maternity (where the formats are hardest), so those categories are well represented. The grading plan routes each criterion to the cheapest method that can judge it reliably: code where possible, people where the stakes demand it.

Watch out

Validate any LLM judge against human labels before trusting it (agreement beyond chance, not raw agreement), and don't let the system under test grade itself. Keep the adversarial slice reported separately: mixing it into one accuracy number hides both security and quality changes.

Practice questionAn eval set has 500 cases, all sampled at random from last month's production traffic. What is its main weakness?

A purely random sample mirrors common traffic but misses the rare, risky and adversarial cases where failures matter most. Mix in edge cases, red-team items and every production incident.

Practice questionWhich grading method fits each criterion best? Pick the correct pairing.

Objective checks belong in code; nuanced qualities at scale suit a validated LLM judge; high-stakes regulated decisions need human experts.

Session 4.3

A/B testing and iterative improvement

Offline evals tell you a change should be better. An A/B test shows whether it is better with real users. Run them in that order: offline eval first (cheap, catches regressions), then a controlled online experiment.

How many users do you need?

Detecting small changes takes more traffic than most people expect. Here's the standard sample-size estimate for comparing two proportions (95% confidence, 80% power).

Python
import math

def n_per_arm(p_base, lift_abs, z_a=1.96, z_b=0.84):
    p2 = p_base + lift_abs
    p_bar = (p_base + p2) / 2
    return math.ceil(((z_a * math.sqrt(2 * p_bar * (1 - p_bar)) + z_b * math.sqrt(p_base * (1 - p_base) + p2 * (1 - p2))) / lift_abs) ** 2)

for lift in (0.10, 0.05, 0.02, 0.01):
    print(f"task success 80% → {80 + lift * 100:.0f}%: {n_per_arm(0.80, lift):>7,} conversations per arm")
Output · produced by running this code
task success 80% → 90%:     199 conversations per arm
task success 80% → 85%:     905 conversations per arm
task success 80% → 82%:   6,032 conversations per arm
task success 80% → 81%:  24,613 conversations per arm
How to read it

Detecting a 10-point gain needs about 200 conversations per arm; detecting a 1-point gain needs nearly 25,000. If your traffic can't reach the sample size in a reasonable time, either test for a bigger effect, use a more sensitive metric, or rely on the offline eval plus careful monitoring.

Reading the result

Python
def two_proportion_test(success_a, n_a, success_b, n_b):
    pa, pb = success_a / n_a, success_b / n_b
    p = (success_a + success_b) / (n_a + n_b)
    z = (pb - pa) / math.sqrt(p * (1 - p) * (1 / n_a + 1 / n_b))
    p_value = math.erfc(abs(z) / math.sqrt(2))
    return pa, pb, z, p_value

results = {"task success (primary)":     (1_640, 2_050, 1_712, 2_048),
           "escalation rate (guardrail)": (287, 2_050, 266, 2_048),
           "complaints (guardrail)":     (31, 2_050, 52, 2_048)}
for metric, (sa, na, sb, nb) in results.items():
    pa, pb, z, pv = two_proportion_test(sa, na, sb, nb)
    verdict = "significant" if pv < 0.05 else "not significant"
    print(f"{metric:<28} A {pa:6.1%}  B {pb:6.1%}  z={z:+.2f}  p={pv:.3f}  {verdict}")
Output · produced by running this code
task success (primary)       A  80.0%  B  83.6%  z=+2.98  p=0.003  significant
escalation rate (guardrail)  A  14.0%  B  13.0%  z=-0.95  p=0.343  not significant
complaints (guardrail)       A   1.5%  B   2.5%  z=+2.33  p=0.020  significant
How to read it

Variant B's task success is significantly higher, and escalations are flat. But complaints rose significantly too, from 1.5% to 2.5%. A guardrail metric has failed, so B doesn't ship as is: read the complaint transcripts, find the cause, fix it, and re-test. That's why A/B tests carry guardrail metrics alongside the primary one.

Tip

Assign by user, not by request, so one person doesn't see both variants. Decide the sample size and stopping rule before starting; peeking daily and stopping at the first good-looking p-value inflates false positives. For model or prompt changes, also compare cost and latency per arm: a "better" variant that doubles cost needs a business decision.

Practice questionAn A/B test shows the new prompt improves task success significantly, but a guardrail metric (complaints) also rises significantly. What should the team do?

Guardrail metrics exist to catch harms that the primary metric misses. A significant guardrail regression blocks the release until it's understood.

Practice questionA team checks its A/B test every morning and stops it the first day the p-value drops below 0.05. What's the problem?

Each look is another chance for noise to cross the threshold. Pre-registering the sample size (or using a sequential method designed for peeking) keeps the error rate honest.

Session 4.4

Diagnosing system issues

When quality drops, the cause is usually one of a few families. Diagnose from evidence, in order, before changing anything.

SymptomLikely familyFirst evidence to check
Wrong answers began right after a prompt changePrompt failureDiff the prompt versions; replay failing cases on both
Fluent, specific claims not supported by any sourceHallucinationWas the needed fact in the context? Is grounding required (citations, "not found" option)?
Confident wrong answers after a data or index refreshRetrieval / contextWhat was actually retrieved for failing queries?
Fails on hard reasoning but fine on easy cases, or great quality but too slowModel mismatchPer-difficulty slice results; compare a stronger or faster model on the same slice
Errors appear only in the app, not when the request is replayed directlyIntegrationThe exact rendered request; parsing and post-processing code
The idea

Hallucination usually has a context cause. Models invent plausibly when asked about things they weren't given: an internal API never documented in the prompt, a policy clause not retrieved. The fixes are architectural: provide the source, require citations or quotes, allow "I don't have that information", and verify specifics in code.

Structured error context in multi-agent systems

When a subagent fails and reports only "error", the coordinator has to guess, and guesses cascade. A structured error gives it what it needs to decide: what was attempted, what failed (category and whether it's retryable), whether the source was checked and empty or never reached, and any partial results.

Python
from dataclasses import dataclass, field

@dataclass
class SubagentError:
    attempted: str
    category: str              # transient | permission | invalid_input | not_found | business_rule
    retryable: bool
    source_checked: bool       # True: looked and found nothing. False: couldn't look at all.
    partial: list = field(default_factory=list)

def coordinator_decision(e):
    if e.category == "not_found" and e.source_checked:
        return "record genuinely absent: say so in the answer, don't retry"
    if e.retryable:
        return "retry once with backoff, then try the alternative source"
    if e.category == "permission":
        return f"don't retry: use the {len(e.partial)} partial result(s), flag the gap, request access or escalate"
    return "escalate with the full error context"

errors = [
    SubagentError("query claims DB for CLM-40417 (2 tries)", "permission", False, False, partial=["CLM-40417 header"]),
    SubagentError("search policy index for 'dental rider'", "not_found", False, True),
    SubagentError("call pharmacy API", "transient", True, False),
]
for e in errors:
    print(f"{e.attempted:<42} → {coordinator_decision(e)}")
Output · produced by running this code
query claims DB for CLM-40417 (2 tries)    → don't retry: use the 1 partial result(s), flag the gap, request access or escalate
search policy index for 'dental rider'     → record genuinely absent: say so in the answer, don't retry
call pharmacy API                          → retry once with backoff, then try the alternative source
How to read it

The first two errors both mean "no data", but they lead to opposite actions: the permission error means the records were never checked (so "none found" would be a false statement), while the not-found error means they were checked and genuinely don't exist. A bare "error" string makes those indistinguishable.

Watch out

Don't hide retries from Claude. If your harness silently retries a failing tool three times and only then reports the failure, Claude loses the chance to try a different tool, query or approach after the first failure, and the user waits through every retry. Report failures as they happen, with structured context, and let the agent choose its next move (within your retry limits).

Practice questionA subagent reports only "error" when its database lookup fails. The coordinator writes "no matching records found" in the final report. What design change prevents this?

Without structure, an access failure looks like an empty result. Reporting what was attempted and whether the source was actually checked lets the coordinator respond correctly.

Practice questionAfter a model upgrade, accuracy on easy cases is unchanged but drops sharply on multi-step reasoning cases; latency fell. What's the most likely diagnosis?

A drop confined to hard reasoning, together with lower latency, points to less reasoning being applied. Compare the slice on the old and new configuration, including effort defaults.

Session 4.5

Optimising cost and performance

Optimise in the right order: free wins first, quality trade-offs last, and re-run the eval after each change.

A model cascade, priced out

A cascade sends every request to a small, cheap model first and escalates to a larger one only when a check fails (low confidence, failed validation, or a hard-case classifier). Whether it pays depends on how often it escalates and how good the gate is. Figures here are illustrative.

Python
N = 100_000
haiku_cost, sonnet_cost = 0.0009, 0.0180          # $ per request (illustrative token mix)
haiku_acc_easy, haiku_acc_hard, sonnet_acc = 0.97, 0.70, 0.96
hard_share = 0.25
gate_catches_hard, gate_false_alarm = 0.85, 0.08  # how well the escalation check works

all_sonnet_cost, all_sonnet_acc = N * sonnet_cost, sonnet_acc
easy, hard = N * (1 - hard_share), N * hard_share
escalated = hard * gate_catches_hard + easy * gate_false_alarm
cascade_cost = N * haiku_cost + escalated * sonnet_cost
correct = (easy * (1 - gate_false_alarm) * haiku_acc_easy + easy * gate_false_alarm * sonnet_acc +
           hard * gate_catches_hard * sonnet_acc + hard * (1 - gate_catches_hard) * haiku_acc_hard)
print(f"all Sonnet: ${all_sonnet_cost:,.0f}   accuracy {all_sonnet_acc:.1%}")
print(f"cascade:    ${cascade_cost:,.0f}   accuracy {correct / N:.1%}   ({escalated / N:.0%} escalated)")
for catch in (0.95, 0.60):
    esc = hard * catch + easy * gate_false_alarm
    acc = (easy * (1 - gate_false_alarm) * haiku_acc_easy + easy * gate_false_alarm * sonnet_acc +
           hard * catch * sonnet_acc + hard * (1 - catch) * haiku_acc_hard) / N
    print(f"  if the gate caught {catch:.0%} of hard cases: ${N * haiku_cost + esc * sonnet_cost:,.0f}, accuracy {acc:.1%}")
Output · produced by running this code
all Sonnet: $1,800   accuracy 96.0%
cascade:    $580   accuracy 95.7%   (27% escalated)
  if the gate caught 95% of hard cases: $626, accuracy 96.4%
  if the gate caught 60% of hard cases: $468, accuracy 94.1%
How to read it

On these numbers the cascade costs about a third as much as running everything on Sonnet, at roughly equal accuracy. Its quality rests entirely on the escalation gate: a gate that misses 40% of hard cases drops accuracy noticeably. Before building a cascade, test the simpler alternative too: the capable model at lower effort may match it with one model and one cache.

Practice questionA team wants to cut cost on a high-volume route. Which should they try first?

Caching and trimming cut cost without changing quality. Model downgrades and cascades trade quality and need evaluation, so they come after the free levers.

Practice questionA cascade (small model first, escalate when a check fails) is proposed. What determines whether it preserves accuracy?

Cases the gate fails to escalate are answered by the small model, so the gate's catch rate on hard cases sets the cascade's accuracy.

Session 4.6

Monitoring and observability

An eval is a snapshot; production keeps moving. Monitoring watches the live system against service level objectives (SLOs) and quality signals, and closes the loop back to the eval set.

SignalTells youTypical alert
Availability and errors (4xx/5xx, timeouts)Is it up?Error-budget burn rate too high
TTFT and total latency p95Is it fast enough?p95 above SLO for 15 minutes
Cost per request and per task, by routeIs spend on track?Daily spend 30% above forecast
Online quality: sampled LLM-judge scores, user feedback, correctionsIs it still good?Judge pass rate drops 5 points week on week
Behavioural: refusal rate, escalation rate, tool-error rate, cache hit rateHas something shifted?Cache hit rate falls below 60%
Input drift: topic and length mix vs the eval setIs the eval set still representative?Distribution shift above threshold

Error budgets and burn rate

An SLO of 99.5% successful requests per 30 days allows 0.5% failures: the error budget. Alerting on how fast the budget is being consumed (the burn rate) catches real incidents quickly without paging on every blip.

Python
SLO = 0.995
budget = 1 - SLO
hourly = [(12_000, 30), (11_800, 41), (12_400, 35), (12_100, 520), (11_900, 610), (12_300, 44)]  # (requests, failures)

for hour, (req, fail) in enumerate(hourly, 1):
    burn = (fail / req) / budget
    action = "PAGE: budget gone in ~{:.0f} h at this rate".format(30 * 24 / burn) if burn > 14.4 else ("ticket" if burn > 2 else "ok")
    print(f"hour {hour}: failure rate {fail / req:6.2%}  burn rate {burn:5.1f}×  {action}")
Output · produced by running this code
hour 1: failure rate  0.25%  burn rate   0.5×  ok
hour 2: failure rate  0.35%  burn rate   0.7×  ok
hour 3: failure rate  0.28%  burn rate   0.6×  ok
hour 4: failure rate  4.30%  burn rate   8.6×  ticket

How to read it

A burn rate of 1 uses the budget exactly over 30 days. Hours 4 and 5 burn it at about 9× and 10×: serious, but below the commonly used fast-page threshold of 14.4× (which would exhaust a 30-day budget in about two days), so they raise a ticket rather than a page. Tune thresholds with the team that's on call; the principle is to alert on budget consumption, not on single failures.

Tip

Quality needs monitoring as much as uptime. Run a sampled online eval (an LLM judge on a slice of live traffic, validated against human labels), track human corrections, and feed every confirmed failure back into the eval set. Tools such as LangSmith bundle tracing, online evals and dashboards; OpenTelemetry tracing gives you vendor-neutral traces to build on.

Practice questionThe system is up, fast and within budget, but users report that answers "got worse" over two months. Which monitoring was missing?

Availability, latency and cost can all look healthy while quality erodes. Sampled quality scores and drift detection catch what infrastructure metrics can't.

Practice questionWhy alert on error-budget burn rate rather than on every failed request?

Burn-rate alerts scale urgency to how quickly reliability promises are being used up, so on-call engineers respond to real incidents rather than noise.
