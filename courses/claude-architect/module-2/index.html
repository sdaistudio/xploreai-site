Session 2.1

Model selection trade-offs

An architect chooses a model per workload, not per company. The same application may use a small fast model for routing, a mid-tier model for most replies, and the most capable model for the hard 5%. Current Claude models (list prices per million tokens on the Claude API, input / output):

ModelPriceContextTypical role
Claude Fable 5.1$10 / $501MHardest reasoning, long-horizon agents
Claude Opus 5.5$4 / $201MComplex reasoning, agentic coding, analysis
Claude Sonnet 5.5$2 / $101MHigh-volume production work that needs judgement
Claude Haiku 5.5$0.10 / $0.50 (≤100K-token prompts)1MClassification, extraction, routing, sub-agents

A weighted decision, not a favourite

Score candidate models against what this workload needs, with weights agreed with stakeholders. Scores here are illustrative; in practice they come from your eval set and load tests.

Python
WEIGHTS = {"quality": 0.40, "latency": 0.25, "cost": 0.25, "platform fit": 0.10}
SCORES = {   # 1–5, from evals, load tests and procurement (illustrative)
    "Haiku 5.5":  {"quality": 3, "latency": 5, "cost": 5, "platform fit": 5},
    "Sonnet 5.5": {"quality": 4, "latency": 4, "cost": 4, "platform fit": 5},
    "Opus 5.5":   {"quality": 5, "latency": 3, "cost": 3, "platform fit": 5},
}
MIN_QUALITY = 4     # the eval floor this workload must clear

for model, s in SCORES.items():
    total = sum(WEIGHTS[k] * v for k, v in s.items())
    note = "" if s["quality"] >= MIN_QUALITY else "  ✗ below the quality floor: excluded whatever its score"
    print(f"{model:<11} weighted {total:.2f}{note}")

eligible = {m: sum(WEIGHTS[k] * v for k, v in s.items()) for m, s in SCORES.items() if s["quality"] >= MIN_QUALITY}
print("\nchoice:", max(eligible, key=eligible.get))
Output · produced by running this code
Haiku 5.5   weighted 4.20  ✗ below the quality floor: excluded whatever its score
Sonnet 5.5  weighted 4.10
Opus 5.5    weighted 4.00

choice: Sonnet 5.5
How to read it

Haiku has the highest weighted score, yet it's excluded: it doesn't clear the quality floor for this workload. Treat hard requirements (quality floor, data residency, a certified platform) as gates before weighing the soft trade-offs; otherwise a cheap, fast model can "win" a decision it should never have entered.

Time to first token

Time to first token (TTFT) is how long the user waits before anything appears; the rest follows at generation speed. It only reaches the user if you stream. Before the first token, the model must process the whole prompt, so prompt size, model choice and prompt caching all move TTFT.

Python
def timings(prompt_tokens, cached_tokens, output_tokens, prefill_per_1k=0.06, overhead=0.35, out_tps=70):
    """Illustrative latency model: prefill time grows with uncached prompt tokens."""
    ttft = overhead + (prompt_tokens - cached_tokens) / 1000 * prefill_per_1k
    return ttft, ttft + output_tokens / out_tps

cases = [("40K prompt, no cache, not streamed", 40_000, 0, 500, False),
         ("40K prompt, no cache, streamed",     40_000, 0, 500, True),
         ("40K prompt, 38K cached, streamed",   40_000, 38_000, 500, True)]
for label, p, c, o, streamed in cases:
    ttft, total = timings(p, c, o)
    seen = ttft if streamed else total
    print(f"{label:<36} first words after {seen:4.1f}s   complete after {total:4.1f}s")
Output · produced by running this code
40K prompt, no cache, not streamed   first words after  9.9s   complete after  9.9s
40K prompt, no cache, streamed       first words after  2.8s   complete after  9.9s
40K prompt, 38K cached, streamed     first words after  0.5s   complete after  7.6s
How to read it

Without streaming, the user waits for the whole answer (9.9 s here) even though the first token was ready at 2.8 s. Streaming shows that first token; caching the stable 38K-token prefix brings it to about half a second. The figures come from an illustrative model, but the shape holds: stream for perceived speed, cache for real speed.

Pinning and breaking changes

A model ID names one fixed model; from the 4.6 generation on, IDs are dateless (claude-sonnet-5-5) but still fixed. Pin the full ID in configuration, never an alias that moves, and treat a model upgrade as a migration: newer models can remove parameters (prefill, fixed thinking budgets, non-default sampling), change defaults (Opus 5.5's effort defaults to medium), change tokenizers (more tokens for the same text since Opus 4.7), and change behaviour. Cloud platforms can lag the Claude API on new models and features, so check availability per platform before committing a design to it.

Practice questionA routing step must classify 2 million messages a day in under 300 ms. Eval results show Haiku 5.5 meets the accuracy target. What should the architect choose?

The smallest model that clears the quality gate and meets latency and cost requirements is the right one. Pin it, because aliases move, and re-run evals before migrating.

Practice questionUsers of a document assistant complain it "freezes" for several seconds. Logs show TTFT of 3 s and total time of 12 s, and responses are not streamed. What change most improves perceived latency?

Without streaming, users experience the full 12 s. Streaming surfaces the first token at TTFT, and caching the stable prefix lowers TTFT itself.

Session 2.2

System prompts, templates and guardrails

The system prompt is a component, written once and reused for every request. It carries the role, standing rules, output format and tone; the user turn carries this request's task and data. Keeping them apart keeps the system prompt stable, which is also what makes it cacheable.

The idea

Guardrails in the prompt are about scope and edges. State what the assistant handles and what it doesn't; what to do when a request is out of scope (decline, ask, hand off); and what to do when information is missing, so the model has an option other than guessing. These guide behaviour. Controls that must always hold (no payouts, no data leaving a region) belong outside the model (Module 5).

Templates, variables and versions

A production prompt is a template plus runtime variables. Version the template like code; log the version with every call. Here's a small renderer that refuses to send a prompt with a missing variable, keeps user content inside tags, and checks the template covers the guardrail elements a reviewer expects.

Python
import hashlib, re

TEMPLATES = {
    "claims-assistant@v7": """You are the claims assistant for {insurer}. You help claims staff, not policyholders.
Handle outpatient claims only; for anything else reply "Route to senior adjuster" with a reason.
If a needed fact is missing, list it under "Missing" instead of assuming.
If documents contradict each other, quote both and mark the clause "unclear".
Return: Summary, Eligibility, Missing, Recommended next step.""",
}
GUARDRAIL_CHECKS = {
    "scope stated":            r"\bonly\b",
    "out-of-scope behaviour":  r"for anything else|out of scope|route to",
    "missing-information rule": r"missing",
    "conflict rule":           r"contradict",
    "output format":           r"\breturn\b|format",
}

def render(template_id, variables, user_docs):
    tpl = TEMPLATES[template_id]
    needed = set(re.findall(r"{(\w+)}", tpl))
    missing = needed - set(variables)
    if missing:
        raise ValueError(f"refusing to send: missing variables {sorted(missing)}")
    system = tpl.format(**variables)
    user = "\n".join(f'<document name="{n}">\n{t}\n</document>' for n, t in user_docs.items())
    return {"system": system, "user": user,
            "_log": {"template": template_id, "sha": hashlib.sha256(tpl.encode()).hexdigest()[:8]}}

tpl = TEMPLATES["claims-assistant@v7"]
for check, pattern in GUARDRAIL_CHECKS.items():
    print(f"{'✓' if re.search(pattern, tpl, re.I) else '✗'} {check}")

req = render("claims-assistant@v7", {"insurer": "Sahyadri Health Insurance"}, {"bill.pdf": "OPD consult ₹1,200"})
print("\nlogged with the call:", req["_log"])
try:
    render("claims-assistant@v7", {}, {})
except ValueError as e:
    print("blocked:", e)
Output · produced by running this code
✓ scope stated
✓ out-of-scope behaviour
✓ missing-information rule
✓ conflict rule
✓ output format

logged with the call: {'template': 'claims-assistant@v7', 'sha': '28a8d15c'}
blocked: refusing to send: missing variables ['insurer']
Tip

Write rules as what to do, with the reason ("plain sentences, because replies go by WhatsApp"), not lists of prohibitions. Claude generalises from the reason to cases you didn't list. And keep personas honest: a persona changes tone and focus, not what the system is allowed to do.

Practice questionA team edits the system prompt directly in production whenever a stakeholder asks for a tweak. Output quality varies week to week and nobody can explain a bad answer from last month. What should the architect introduce?

Untracked prompt edits are untested production changes with no history. Versioned templates with evals and per-call logging make behaviour reproducible and explainable.

Practice questionSelect 2Which belong in the system prompt rather than the user turn? (Select 2)

Standing role, rules and format belong in the stable system prompt. Per-request documents and volatile values like timestamps belong in the user turn, which also keeps the system prompt cacheable.

Session 2.3

Prompting techniques

TechniqueWhat it isReach for it when
Zero-shotClear instructions, no examplesThe task is common and well specified: always start here
Few-shotInstructions plus a few worked examplesOutput format or judgement on ambiguous cases stays inconsistent despite clear instructions
Chain-of-thoughtThe model reasons before answeringMulti-condition or multi-step problems where skipping a step causes errors

Few-shot: targeted, not random

Study material for this exam recommends 2–4 targeted examples. Fewer gives Claude too little to generalise from; more spends context on examples instead of work. "Targeted" is the important word: each example should demonstrate a different ambiguity or failure mode the instructions alone didn't resolve. Three situations call for them:

  • Output format varies across runs despite explicit format instructions.
  • Borderline cases (which tool, which category) are handled differently each time.
  • Extraction returns empty fields when the source states them in unusual forms.

Here's example selection done deliberately: from a pool of candidate examples, pick the smallest set that covers every failure mode seen in testing.

Python
FAILURE_MODES = {"citation inline", "citation in bibliography", "date as words", "two claims in one letter", "no amount stated"}
POOL = {   # candidate example → failure modes it demonstrates
    "ex01 simple bill, all fields clean":          set(),
    "ex02 inline citation of policy clause":       {"citation inline"},
    "ex03 clause cited only in bibliography":      {"citation in bibliography"},
    "ex04 'fifth of March', two claims in one":    {"date as words", "two claims in one letter"},
    "ex05 estimate letter with no amount":         {"no amount stated"},
    "ex06 inline citation, date as words":         {"citation inline", "date as words"},
}

chosen, uncovered = [], set(FAILURE_MODES)
while uncovered:
    best = max(POOL, key=lambda e: len(POOL[e] & uncovered))
    if not POOL[best] & uncovered: break
    chosen.append(best); uncovered -= POOL[best]
print(f"{len(chosen)} examples cover all {len(FAILURE_MODES)} failure modes:")
for c in chosen: print("  ", c, sorted(POOL[c]))
print("never chosen (adds nothing new):", [e for e in POOL if e not in chosen])
Output · produced by running this code
4 examples cover all 5 failure modes:
   ex04 'fifth of March', two claims in one ['date as words', 'two claims in one letter']
   ex02 inline citation of policy clause ['citation inline']
   ex03 clause cited only in bibliography ['citation in bibliography']
   ex05 estimate letter with no amount ['no amount stated']
never chosen (adds nothing new): ['ex01 simple bill, all fields clean', 'ex06 inline citation, date as words']
How to read it

Four examples cover all five failure modes, inside the 2–4 range, and the "clean, simple" example is never picked: it teaches nothing the instructions don't. The same logic applies when an example set grows over time: prune examples that duplicate a failure mode another already covers.

Chain-of-thought

Asking the model to reason before answering helps on problems with several conditions (a refund rule with four tests, a diagnosis with several factors). Keep the instruction general ("work through each condition before deciding") unless the task has a required order; a long hand-written procedure often reasons worse than a short instruction. Current Claude models can also reason with built-in adaptive thinking, controlled by effort, rather than in the visible output. When you do want visible reasoning, separate it from the result with tags so code reads only the answer:

Python
reply = """<thinking>
Order date 2 Oct, request 20 Oct: within 30 days. Category: footwear, eligible.
Opened: yes, but footwear allows opened returns. Discount: 40%, and the policy excludes items over 30% off.
</thinking>
<answer>{"eligible": false, "reason": "discount over 30% (40%)"}</answer>"""

def answer_only(text):
    m = re.search(r"<answer>\s*(.*?)\s*</answer>", text, re.S)
    if not m:
        raise ValueError("no <answer> block: treat as a failed response, don't parse the reasoning")
    return m.group(1)

print("app reads:   ", answer_only(reply))
print("audit keeps: ", len(re.search(r"<thinking>(.*?)</thinking>", reply, re.S).group(1).split()), "words of reasoning")
Output · produced by running this code
app reads:    {"eligible": false, "reason": "discount over 30% (40%)"}
audit keeps:  30 words of reasoning
How to read it

The fourth condition (the discount) is the one a direct answer would most likely skip; stating each condition first forces it to be checked. The app parses only the answer, and the reasoning is kept for audit, which is useful in regulated decisions where you must show how an outcome was reached.

Practice questionA classifier has explicit category definitions, but borderline messages flip between two categories from run to run. Which technique is most appropriate?

Instructions already exist; what's missing is a demonstration of the judgement on ambiguous cases. A few targeted examples resolve exactly that.

Practice questionWhen is chain-of-thought most likely to improve results?

Reasoning first makes the model address each condition before committing. It adds tokens and latency, so it's wasted on simple tasks.

Session 2.4

Engineering the context window

The context window is a budget shared by the system prompt, tool definitions, history, retrieved material and the reply. More isn't better: past a point, accuracy and recall fall as the window fills. Context engineering decides what goes in, in what form, and where.

Where things go: long material first, question last

Models attend most strongly to the beginning and end of long contexts; material in the middle is more easily under-weighted (the lost-in-the-middle effect). Anthropic's guidance is to put long documents at the top and the question, instructions and examples at the bottom; its testing found this can improve response quality by up to 30%.

Case facts: protecting precision from summarisation

Long conversations and agent runs get compressed: history is summarised to make room, and summaries are lossy. Exact figures turn into approximations, dates into "early January". A case facts block keeps the details that must stay exact (amounts, dates, IDs, commitments) in a small structured block that's carried forward verbatim on every turn, outside whatever gets summarised.

Python
history = "Customer Meera Iyer, policy SHI-77120. Agreed refund ₹8,999.50 on 14 Jan 2026 for claim CLM-40417, to be paid by 21 Jan."

def lossy_summary(text):
    """Stand-in for repeated summarisation: each pass keeps the gist and drops precision."""
    text = re.sub(r"₹([\d,]+)\.\d\d", lambda m: "about ₹" + format(round(int(m.group(1).replace(",", "")), -3), ","), text)
    text = re.sub(r"on \d{1,2} Jan 2026", "in mid-January", text)
    text = re.sub(r"by \d{1,2} Jan", "by late January", text)
    return text.replace("claim CLM-40417", "the claim").replace("policy SHI-77120", "her policy")

CASE_FACTS = {"customer": "Meera Iyer", "policy": "SHI-77120", "claim": "CLM-40417",
              "refund_amount": "₹8,999.50", "agreed_on": "2026-01-14", "pay_by": "2026-01-21"}

after = lossy_summary(history)
print("summary after compression:\n ", after)
print("\ncase facts block carried every turn:")
print("  <case_facts>" + "; ".join(f"{k}={v}" for k, v in CASE_FACTS.items()) + "</case_facts>")
Output · produced by running this code
summary after compression:
  Customer Meera Iyer, her policy. Agreed refund about ₹9,000 in mid-January for the claim, to be paid by late January.

case facts block carried every turn:
  <case_facts>customer=Meera Iyer; policy=SHI-77120; claim=CLM-40417; refund_amount=₹8,999.50; agreed_on=2026-01-14; pay_by=2026-01-21</case_facts>
How to read it

After compression, the summary still reads well, but the refund is "about ₹9,000", the dates are "mid-January" and "late January", and the claim and policy IDs are gone: exactly the details a payout or a complaint depends on. The case facts block costs a few dozen tokens and keeps them exact, however many times the history is summarised.

Trim verbose tool results

APIs return whole objects when the task needs three fields. Every extra token crowds the window, buries the useful data and slows the request. Trim at the tool boundary, before results enter the context.

Python
import json

raw = {"status": 200, "request_id": "a8f3-77c1", "pagination": {"page": 1, "pages": 1, "per_page": 50},
       "data": {"member": {"id": "SHI-77120", "name": "Meera Iyer", "dob": "1979-03-05", "address": {"line1": "12 Palm Grove", "city": "Pune", "pin": "411001"},
                "plan": {"code": "OPD-GOLD", "opd_limit": 25000, "opd_used": 17800, "copay_pct": 10, "network": ["Ruby Hall", "Jehangir"],
                         "riders": [{"code": "DENTAL", "limit": 5000}, {"code": "VISION", "limit": 3000}]},
                "claims_history": [{"id": f"CLM-{40000 + i}", "amount": 900 + i * 37, "status": "settled"} for i in range(40)],
                "audit": {"created": "2019-04-01", "updated": "2026-10-20", "by": "sys"}}}}

def trim_for_eligibility(r):
    m = r["data"]["member"]; p = m["plan"]
    return {"member_id": m["id"], "plan": p["code"], "opd_remaining": p["opd_limit"] - p["opd_used"],
            "copay_pct": p["copay_pct"], "recent_claims": [c["id"] for c in m["claims_history"][-3:]]}

def approx_tokens(obj): return len(json.dumps(obj)) // 4
trimmed = trim_for_eligibility(raw)
print(f"raw result:     ~{approx_tokens(raw):,} tokens")
print(f"trimmed result: ~{approx_tokens(trimmed):,} tokens  {trimmed}")
Output · produced by running this code
raw result:     ~717 tokens
trimmed result: ~36 tokens  {'member_id': 'SHI-77120', 'plan': 'OPD-GOLD', 'opd_remaining': 7200, 'copay_pct': 10, 'recent_claims': ['CLM-40037', 'CLM-40038', 'CLM-40039']}
Tip

Trim to what the task needs, and compute derived values (remaining limit) in code rather than asking the model to do arithmetic on raw fields. If a later step might need more, return an ID it can use to fetch details on demand rather than everything up front.

Practice questionIn a long support conversation, the assistant later quotes a refund of "about ₹9,000" when ₹8,999.50 was agreed. History is being summarised to stay within the window. What's the best fix?

Summarisation is lossy by design. A small structured block of critical facts preserves precision cheaply, whatever happens to the rest of the history.

Practice questionA prompt places the user's question first, followed by 60 pages of contract text. Answers miss details from the middle of the document. Which change follows Anthropic's guidance?

Long content first and the query last improves long-context answers. Tags around each document also help the model keep sections apart.

Session 2.5

Prompt reuse: caching, modules and Skills

Three reuse strategies, at different levels:

StrategyReusesSaves
Prompt cachingThe exact prefix of a request, across requestsCost and TTFT on repeated stable content
Modular promptsPieces of prompts (role, format, policy, examples) across featuresMaintenance; consistency; and they're cache-friendly if stable pieces go first
SkillsPackaged instructions and scripts the model loads when relevantContext: only descriptions are always loaded; bodies load on demand

Prefix ordering decides what can be cached

Requests are assembled in a fixed order: tools, then system, then messages. Caching reuses an identical prefix up to a breakpoint, and a change at any level invalidates that level and everything after it. So stable content goes first, and anything that varies (the user's question, retrieved results, timestamps) goes last.

Python
p_in = 2.00                                  # Claude Sonnet 5.5 input, $/MTok
TOOLS, POLICY, QUESTION = 3_000, 8_000, 150  # tokens

def run(layout, n=1_000):
    """Return (cost of input tokens, cache hit rate) for n requests with this layout."""
    cost, hits = 0.0, 0
    for i in range(n):
        if layout == "timestamp in system prompt":
            cached = 0                                         # prefix differs every request
        elif layout == "tools edited per request":
            cached = 0                                         # first block changes: nothing after it survives
        else:                                                  # stable tools + system first, question last
            cached = TOOLS + POLICY if i > 0 else 0
        uncached = TOOLS + POLICY + QUESTION - cached
        write = (TOOLS + POLICY) * 0.25 if (layout == "stable prefix, question last" and i == 0) else 0
        cost += (uncached + write + cached * 0.10) * p_in / 1e6
        hits += cached > 0
    return cost, hits / n

for layout in ["timestamp in system prompt", "tools edited per request", "stable prefix, question last"]:
    cost, rate = run(layout)
    print(f"{layout:<32} input cost for 1,000 requests ${cost:6.2f}   cache hits {rate:.0%}")
Output · produced by running this code
timestamp in system prompt       input cost for 1,000 requests $ 22.30   cache hits 0%
tools edited per request         input cost for 1,000 requests $ 22.30   cache hits 0%
stable prefix, question last     input cost for 1,000 requests $  2.53   cache hits 100%
How to read it

This is the exam guide's own sample scenario: an 8,000-token system prompt and policy on every request, a short varying question after it. Ordering the static parts first and caching them cuts input cost by nearly 90% here and shrinks TTFT. Truncating the policy loses required content, downsizing the model risks quality, and moving the policy into few-shot examples doesn't create a reusable prefix.

Watch out

Two placements break caching silently: a timestamp or request ID early in the system prompt, and tool definitions that change between requests (or are serialised in a different order). Put the breakpoint on the last block that's identical across the requests you want to share a cache, and check cache_read_input_tokens in responses to confirm it's working.

Modular prompts and when Skills take over

A modular prompt is assembled from reusable pieces: role and behaviour, output format, reference material, examples, and the task input. Your code chooses which pieces each request needs. That works well for a handful of tasks; as specialised instruction sets multiply, either your selection logic grows, or you send everything every time and pay for it. Skills move that selection to the model: each skill's short description is always visible, and its full instructions load only when a task matches.

Python
MODULES = {"role.claims": 350, "format.eligibility": 180, "policy.outpatient": 8_000, "policy.dental": 2_400,
           "policy.vision": 1_900, "examples.extraction": 1_200, "examples.letters": 900}
NEEDS = {"outpatient eligibility": ["role.claims", "format.eligibility", "policy.outpatient", "examples.extraction"],
         "dental eligibility":     ["role.claims", "format.eligibility", "policy.dental", "examples.extraction"],
         "missing-document letter": ["role.claims", "examples.letters"]}

everything = sum(MODULES.values())
for task, mods in NEEDS.items():
    print(f"{task:<25} assembled {sum(MODULES[m] for m in mods):>6,} tokens   vs send-everything {everything:,}")
skills_baseline = 7 * 100
print(f"\nas Skills: ~{skills_baseline} tokens of descriptions always loaded; each task loads only its own bodies")

Exam lens

Prompt reuse questions usually hinge on what is being reused. Same long prefix on every request → caching with stable-first ordering. Same instruction blocks across many features → modular prompts. Many specialised procedures, each needed occasionally → Skills, so only descriptions occupy the context until one is needed.

Practice questionAn application sends the same 8,000-token system prompt and policy document on every request, followed by a short, varying user message. Latency and cost are both concerns. Which optimisation most directly addresses both?

Stable content first plus caching lets the repeated prefix be reused, cutting both per-request cost and time to first token without discarding required context.

Practice questionA team has 40 specialised procedures (each 2,000–6,000 tokens), and any given request needs at most one or two. What's the most context-efficient way to make them available?

Skills load progressively: descriptions are cheap and always present, full instructions load only when a task matches. Caching 40 procedures still fills the context on every request.
