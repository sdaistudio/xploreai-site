Session 3.1

Capability bloat and tool scoping

Every tool you give an agent is a capability it might use wrongly and a choice it might get wrong. Capability bloat is an agent configured with more tools, permissions or connections than its job needs. It hurts in three ways:

ProblemWhy it happens
Worse tool selectionClaude picks tools by reading names, descriptions and schemas; with dozens of similar options, choosing becomes a search problem and adjacent-but-wrong picks rise
Less room to thinkEvery definition occupies the context window, crowding out instructions, history and documents
Bigger blast radiusA mistake or a prompt injection can only use the tools that are there. Tools that aren't granted can't be misused
The idea

Scope tools to roles. Write each agent's job in one sentence; list the tools that are required for it (not convenient); remove duplicates; move tools that belong to another phase to the agent that owns that phase. Study material for this exam suggests most agents work best with roughly 10–20 tools, simple single-purpose agents with 3–5, and recommends splitting an agent rather than growing its list past about 20. Treat those as signals, not rules: measure tool-selection accuracy on your own routing eval.

Auditing a configuration

Here's an audit of a customer-support agent's tool configuration against its role and a month of usage logs. This is the exam guide's own sample scenario: support staff only read tickets and draft replies.

Python
ROLE = "Help support staff read tickets and draft replies."
REQUIRED_FOR_ROLE = {"read_ticket", "search_kb", "draft_reply", "get_customer"}
CONFIGURED = {   # tool: (risk, calls in the last 30 days)
    "read_ticket":     ("low", 18_420), "search_kb":   ("low", 9_310), "draft_reply":  ("low", 17_980),
    "get_customer":    ("low", 6_200),  "lookup_order": ("low", 4_870), "get_order":   ("low", 12),
    "issue_refund":    ("high", 3),     "delete_account": ("critical", 0), "run_sql":    ("critical", 1),
    "send_sms":        ("medium", 0),
}
SIMILAR = [("lookup_order", "get_order")]

print(f"role: {ROLE}\n{len(CONFIGURED)} tools configured, {len(REQUIRED_FOR_ROLE)} required\n")
for tool, (risk, calls) in sorted(CONFIGURED.items(), key=lambda kv: kv[1][1], reverse=True):
    reasons = []
    if tool not in REQUIRED_FOR_ROLE:
        reasons.append("not required by the role")
    if risk in ("high", "critical") and tool not in REQUIRED_FOR_ROLE:
        reasons.append(f"{risk}-risk capability")
    if calls == 0:
        reasons.append("never used")
    for a, b in SIMILAR:
        if tool == b: reasons.append(f"duplicates {a}")
    verdict = "REMOVE" if reasons and tool not in REQUIRED_FOR_ROLE and tool != "lookup_order" else "keep"
    print(f"{verdict:<7}{tool:<16}{risk:<9}{calls:>7,} calls  {'; '.join(reasons)}")

How to read it

The refund, delete and SQL tools are removed, not guarded: the role never needs them, so the safest version of them is absence. lookup_order is kept for now as a judgement call (it's heavily used, so the role description may be incomplete; that's a conversation with the business, not a silent removal). The near-duplicate get_order goes, which also removes a routing ambiguity.

Exam lens

This is the official sample question for Domain 3. The right answer is to remove the refund and delete tools entirely. Logging is a detective control and confirmation prompts are compensating controls: both leave the unnecessary privilege in place. Model size has nothing to do with authorisation scope.

Practice questionA team exposes a customer-support agent that can read tickets, draft replies, issue refunds and delete user accounts. Support staff only ever need to read tickets and draft replies. Applying least privilege, which change best reduces risk?

Least privilege removes capabilities the role doesn't need, eliminating the attack surface instead of monitoring or guarding it. Logging and confirmations are detective or compensating controls; model size is unrelated to authorisation scope.

Practice questionAn orchestrator agent has 46 tools covering research, coding, email and calendar. Tool-selection errors are rising. What's the best architectural change?

Past a certain size, a single tool list degrades selection and crowds the context. Distributing tools across role-scoped agents restores accuracy and limits each agent's blast radius.

Session 3.2

Authentication and authorisation gaps

Integrations are where identity goes wrong. An architect reviews every path between Claude and a system with two questions: who is calling (authentication) and what may they do, on whose behalf (authorisation).

GapWhat it looks likeFix
Over-privileged service accountThe agent's tools use one database account that can read every customerScope the account; enforce per-user authorisation inside each tool
Confused deputyA user asks the agent for data they can't see; the agent, which can, fetches itTools act on behalf of the authenticated user and check that user's rights
Model-chosen identifiersget_invoice(invoice_id) returns any invoice the model namesBind lookups to the session's identity, not to IDs in the prompt
Shared or long-lived keysOne API key for every environment and serviceSeparate keys per environment and service, rotation, short-lived tokens
Token pass-throughA user's broad OAuth token is forwarded to an MCP server or third partyExchange for narrowly scoped, audience-bound tokens
Unauthenticated internal endpoints"It's internal, so no auth" on a tool's backing serviceAuthenticate every hop; zero-trust between services

Here's a review of an integration inventory against those rules, the kind of table an architect produces in a design review.

Python
INTEGRATIONS = [
    {"name": "patient records tool", "auth": "service_account", "scope": "all_clinics", "checks_user_rights": False, "key_age_days": 30},
    {"name": "billing API",          "auth": "api_key",         "scope": "billing",     "checks_user_rights": True,  "key_age_days": 410, "shared_across_envs": True},
    {"name": "tickets MCP server",   "auth": "oauth_passthrough", "scope": "user_full", "checks_user_rights": True,  "key_age_days": 0},
    {"name": "scheduling service",   "auth": "none",            "scope": "internal",    "checks_user_rights": False, "key_age_days": 0},
    {"name": "knowledge base",       "auth": "oauth_scoped",    "scope": "kb.read",     "checks_user_rights": True,  "key_age_days": 1},
]

def review(i):
    gaps = []
    if i["auth"] == "none": gaps.append("unauthenticated endpoint")
    if i["auth"] == "service_account" and i["scope"] == "all_clinics" and not i["checks_user_rights"]:
        gaps.append("confused-deputy risk: broad service account, no per-user check")
    if i["auth"] == "oauth_passthrough": gaps.append("token pass-through: exchange for a narrow, audience-bound token")
    if i.get("shared_across_envs"): gaps.append("one key shared across environments")
    if i["key_age_days"] > 90: gaps.append(f"credential {i['key_age_days']} days old: rotate")
    return gaps

for i in INTEGRATIONS:
    gaps = review(i)
    print(f"{'GAP' if gaps else 'OK '} {i['name']:<22} {'; '.join(gaps)}")
Output · produced by running this code
GAP patient records tool   confused-deputy risk: broad service account, no per-user check
GAP billing API            one key shared across environments; credential 410 days old: rotate
GAP tickets MCP server     token pass-through: exchange for a narrow, audience-bound token
GAP scheduling service     unauthenticated endpoint
OK  knowledge base
Tip

Authorisation belongs in the tool, evaluated against the authenticated session, every call. The model can be tricked into asking for anything; the tool decides what it gets. Log both identities on every call (the end user and the service acting for them) so audits can tell them apart.

Practice questionAn HR assistant's lookup tool uses a service account with read access to all employee records. Any employee can ask about any colleague's salary, and the assistant answers. What is the core gap?

Users are authenticated, but the tool doesn't check what this user may see. Enforcing the caller's rights inside the tool (and narrowing the service account) closes the gap.

Practice questionSelect 2Which are authentication or authorisation gaps an architect should flag in a design review? (Select 2)

Shared keys widen the impact of any leak, and token pass-through hands a third party far more access than the integration needs. Scoped tokens and per-call permission checks are the fixes, not gaps.

Session 3.3

Accuracy versus latency

Most configuration choices trade accuracy against speed (and cost): a larger model, higher effort, more retrieved chunks, a re-ranking step, a verification pass. An architect justifies the chosen configuration with measurements against the requirement, not with a preference.

The method: measure candidate configurations on the eval set, keep only those that meet the hard constraints (accuracy floor, p95 SLA), and pick the cheapest of those. Configurations that are worse on every dimension than another can be discarded outright: they're dominated.

Python
CONFIGS = [  # name, accuracy on eval, p95 seconds, $ per 1,000 requests (illustrative measurements)
    ("Haiku, k=5",                         0.86, 1.6,  1.1),
    ("Haiku, k=10 + rerank",               0.91, 2.2,  1.9),
    ("Sonnet, k=5",                        0.92, 3.1,  8.0),
    ("Sonnet, k=10 + rerank",              0.95, 3.8,  9.4),
    ("Sonnet, k=20 + rerank",              0.95, 4.9, 12.6),
    ("Opus, k=10 + rerank",                0.96, 6.4, 18.5),
    ("Sonnet, k=10 + rerank + verify",     0.97, 6.9, 15.2),
]
FLOOR, SLA = 0.94, 5.0

def dominated(c, others):
    return any(o[1] >= c[1] and o[2] <= c[2] and o[3] <= c[3] and o != c for o in others)

print(f"{'config':<34}{'acc':>5}{'p95':>6}{'$/1k':>7}  verdict")
for c in CONFIGS:
    if dominated(c, CONFIGS):            verdict = "dominated: another is as good or better on every axis"
    elif c[1] < FLOOR:                   verdict = "below accuracy floor"
    elif c[2] > SLA:                     verdict = "breaks the p95 SLA"
    else:                                verdict = "eligible"
    print(f"{c[0]:<34}{c[1]:>5.0%}{c[2]:>6.1f}{c[3]:>7.1f}  {verdict}")
best = min((c for c in CONFIGS if c[1] >= FLOOR and c[2] <= SLA), key=lambda c: c[3])
print(f"\nchoice: {best[0]}. Cheapest config meeting {FLOOR:.0%} accuracy within {SLA}s p95.")

config                              acc   p95   $/1k  verdict
Haiku, k=5                          86%   1.6    1.1  below accuracy floor
Haiku, k=10 + rerank                91%   2.2    1.9  below accuracy floor
Sonnet, k=5                         92%   3.1    8.0  below accuracy floor
Sonnet, k=10 + rerank               95%   3.8    9.4  eligible
Sonnet, k=20 + rerank               95%   4.9   12.6  dominated: another is as good or better on every axis

How to read it

Retrieving 20 chunks instead of 10 adds latency and cost with no accuracy gain, so that config is dominated. Opus and the verification pass are more accurate but break the 5-second SLA. The justification writes itself: "Sonnet with 10 re-ranked chunks is the cheapest configuration that meets both the accuracy floor and the latency SLA; higher-accuracy options exceed the SLA."

Tip

When accuracy and latency can't both be met, don't silently pick one: take the trade-off to stakeholders with the numbers (Module 6). Options include a slower "thorough" path for high-stakes requests only, streaming to improve perceived latency, or caching to cut time to first token.

Practice questionTwo configurations meet the accuracy floor and the latency SLA. One is 40% cheaper with equal accuracy. A senior engineer prefers the other "because it uses the bigger model". What should the architect recommend?

When both meet the requirements on measured evidence, the cheaper one is the justified choice. Record the measurements in the decision record so the choice can be revisited when the evidence changes.

Session 3.4

Observability at scale

A prototype can be debugged by reading transcripts. A system handling a million requests a day can't. Observability at scale means deciding what to record, how much of it to keep, and how to find the signal without drowning in data or exposing sensitive content.

LayerRecordsAnswers
TracesEach request's steps: model calls, tool calls, retrieval, timings, IDs"Why did this request go wrong?"
MetricsAggregates: p50/p95 latency, error rates, tokens, cost, refusals, escalations, by route"Is the system healthy? What changed?"
Logs and payloadsPrompts and outputs (redacted), for sampled requests"What exactly did the model see and say?"
Quality signalsUser feedback, human corrections, online eval scores"Is it still good, not just up?"

Every trace should carry: a trace ID, tenant and route, model ID, prompt version, token counts (input, cached, output), latency (TTFT and total), tool calls with outcomes, stop_reason, and the final outcome. Without the model and prompt versions, you can't connect a quality change to a release.

Sampling: keep what's useful

Storing every full payload is expensive and a privacy liability. A common pattern: keep all errors and high-risk requests, a sample of the rest, and metrics for everything.

Python
import random

random.seed(7)
N = 1_000_000                                            # requests in a day
requests = [{"error": random.random() < 0.012, "high_risk": random.random() < 0.03,
             "flagged": random.random() < 0.004} for _ in range(N)]

def keep_payload(r, success_rate=0.02):
    return r["error"] or r["high_risk"] or r["flagged"] or random.random() < success_rate

kept = [r for r in requests if keep_payload(r)]
payload_kb = 24                                          # redacted prompt + output + trace, compressed
print(f"requests: {N:,}   payloads kept: {len(kept):,} ({len(kept) / N:.1%})")
print(f"  errors kept:      {sum(r['error'] for r in kept):,} of {sum(r['error'] for r in requests):,}")
print(f"  high-risk kept:   {sum(r['high_risk'] for r in kept):,} of {sum(r['high_risk'] for r in requests):,}")
print(f"storage per day: {len(kept) * payload_kb / 1e6:.1f} GB sampled vs {N * payload_kb / 1e6:.0f} GB keeping everything")
Output · produced by running this code
requests: 1,000,000   payloads kept: 64,747 (6.5%)
  errors kept:      12,028 of 12,028
  high-risk kept:   29,913 of 29,913
storage per day: 1.6 GB sampled vs 24 GB keeping everything
How to read it

About 6.5% of payloads are kept, every error and every high-risk request among them, at about a fifteenth of the storage of keeping everything. Metrics still cover 100% of traffic. Tune the success-sampling rate to how many examples your reviewers and online evals can actually use.

Watch out

Two scale traps. Cardinality: tagging metrics with user IDs or free text explodes metric storage; use bounded labels (route, model, tenant tier) and put identifiers in traces. Sensitive payloads: redact PII before storage, restrict access, and set retention to match your compliance obligations (Module 5). Standards such as OpenTelemetry, and LLM-focused tools such as LangSmith, help, but the decisions above are yours.

Practice questionAfter a release, answer quality drops for one customer segment. Traces exist but don't record which prompt version or model ID served each request. What does this prevent?

Version identifiers on every trace are what link behaviour to releases. Without them, a regression can't be attributed to the prompt, the model or something else.

Practice questionSelect 2Which observability practices suit a high-volume Claude system? (Select 2)

Targeted sampling keeps what's diagnostically useful at sustainable cost, and version-rich traces make changes attributable. Unbounded labels explode metric storage, and indefinite raw storage is a cost and privacy risk.

Session 3.5

Designing a RAG pipeline

Retrieval-augmented generation (RAG) retrieves relevant passages from your own sources and puts them in the context before Claude answers, so answers are grounded in current, proprietary material. A RAG system has two pipelines, and most quality problems start in the first.

Chunking decides what can be found

A chunk is the unit you retrieve. Too small and it loses context ("the limit is 30 days": the limit of what?); too large and it dilutes relevance and wastes context. Common strategies:

StrategyHowGood for
Fixed size (with overlap)Every N tokens, overlapping by MUniform text without structure; simple baseline
Structure-awareSplit on headings, sections, clauses, list itemsPolicies, contracts, manuals, documentation
SemanticSplit where the topic shiftsLong narrative documents
ContextualPrepend a short note situating each chunk in its document before indexing (Anthropic's contextual retrieval technique)Any corpus where chunks lose meaning out of context

Here's the same policy section chunked two ways. Watch what happens to the clause that matters.

Python
POLICY = """## 4. Outpatient claims
4.1 Consultations are covered up to ₹1,500 per visit.
4.2 Diagnostics are covered up to ₹10,000 per policy year.
## 5. Exclusions
5.1 Cosmetic procedures are not covered.
5.2 Claims must be filed within 30 days of the visit; later claims are rejected unless the delay was caused by hospitalisation."""

def fixed_chunks(text, size=120, overlap=0):
    return [text[i:i + size] for i in range(0, len(text), size - overlap)]

def heading_chunks(text):
    chunks, current, heading = [], [], ""
    for line in text.splitlines():
        if line.startswith("## "):
            if current: chunks.append(heading + "\n" + "\n".join(current))
            heading, current = line, []
        else:
            current.append(line)
    chunks.append(heading + "\n" + "\n".join(current))
    return chunks

for name, chunks in [("fixed 120 chars", fixed_chunks(POLICY)), ("by heading", heading_chunks(POLICY))]:
    print(f"--- {name}: {len(chunks)} chunks")
    for c in chunks:
        if "30 days" in c or "hospitalisation" in c:
            print(repr(c))
Output · produced by running this code
--- fixed 120 chars: 3 chunks
'per policy year.\n## 5. Exclusions\n5.1 Cosmetic procedures are not covered.\n5.2 Claims must be filed within 30 days of th'
'e visit; later claims are rejected unless the delay was caused by hospitalisation.'
--- by heading: 2 chunks
'## 5. Exclusions\n5.1 Cosmetic procedures are not covered.\n5.2 Claims must be filed within 30 days of the visit; later claims are rejected unless the delay was caused by hospitalisation.'
How to read it

Fixed-size chunking splits clause 5.2 across chunks: one holds "filed within 30 days", the next "unless the delay was caused by hospitalisation", and neither says it's about exclusions. A question about late claims might retrieve only the first half and get a confidently wrong "rejected". Heading-aware chunks keep the clause whole and labelled.

Indexing and metadata

Store each chunk with metadata (source, section, effective date, product, region, access control) so queries can filter before ranking. Filtering by the user's access at retrieval time is what stops RAG from becoming a data-leak path: a user should never get chunks from documents they couldn't open themselves.

Exam lens

The official sample question: a RAG system suddenly gives confident but wrong answers after a document refresh, with model version and latency unchanged. Look first at retrieval and indexing: a broken re-index, stale or duplicated chunks, or mismatched embeddings feeding poor context. The model hasn't changed, and nothing else was triggered by the refresh.

Practice questionA RAG system returns confident but incorrect answers immediately after a document refresh, while latency and model version are unchanged. What is the most likely first place to investigate?

The refresh is the only change, and it touches ingestion and the index. A broken re-index or mismatched embeddings would feed the model poor context, producing fluent wrong answers.

Practice questionAnswers about contract obligations often miss conditions that appear later in the same clause. Chunks are fixed 300-token windows with no overlap. What is the best fix?

Fixed windows split clauses mid-sentence. Chunking along the document's structure keeps conditions with the rule they qualify.

Session 3.6

Retrieval strategies

No single retrieval method suits every data shape and query pattern. Match them:

Data and queryStrategyWhy
Exact identifiers, codes, names ("ICD J45.4", "clause 5.2")Keyword (BM25)Embeddings blur exact tokens; keyword search matches them precisely
Paraphrased questions ("trouble breathing at night")Semantic (embeddings)Matches meaning, not wording
Mixed real-world queriesHybrid: keyword + semantic, merged (e.g. reciprocal rank fusion), then re-rankedRobust to both; the common production default
Structured facts and aggregates ("claims over ₹50,000 last quarter")Structured query (SQL, an API) via a toolText retrieval can't count or sum reliably
Relationships ("which policies cover dependants of retirees?")Graph or relational traversalThe answer is in links between entities
Recency- or permission-boundMetadata filters before rankingRemoves ineligible chunks rather than hoping they rank low

Here are keyword and "semantic" retrieval on a tiny corpus, plus hybrid fusion. The keyword scorer is a real BM25. Real semantic search uses embedding models; to keep this runnable without one, the semantic scorer below matches through a small hand-written synonym map: a stand-in that behaves like embeddings on these examples, not an embedding model.

Python
import math, re
from collections import Counter

DOCS = {
    "d1": "Asthma J45.4: inhaled corticosteroids covered under OPD-GOLD.",
    "d2": "Night-time breathlessness should be assessed by a pulmonologist within 7 days.",
    "d3": "Claims for J45.9 require a spirometry report.",
    "d4": "Cosmetic dermatology is excluded.",
}
tok = lambda s: re.findall(r"[a-z0-9.]+", s.lower())

def bm25_scores(query, k1=1.5, b=0.75):
    docs = {d: tok(t) for d, t in DOCS.items()}
    avg = sum(len(t) for t in docs.values()) / len(docs)
    scores = {}
    for d, terms in docs.items():
        tf, s = Counter(terms), 0.0
        for q in tok(query):
            n = sum(q in t for t in docs.values())
            if n:
                idf = math.log(1 + (len(docs) - n + 0.5) / (n + 0.5))
                s += idf * tf[q] * (k1 + 1) / (tf[q] + k1 * (1 - b + b * len(terms) / avg))
        scores[d] = round(s, 2)
    return scores

def bm25(query):
    s = bm25_scores(query); return sorted((d for d in s if s[d] > 0), key=s.get, reverse=True)   # matches only

CONCEPTS = {"breath": "breath", "breathing": "breath", "breathlessness": "breath", "breathless": "breath", "night": "night", "night-time": "night", "dark": "night",
            "nocturnal": "night", "asthma": "asthma", "wheezing": "asthma", "skin": "derm", "dermatology": "derm", "cosmetic": "derm"}
def concepts(s): return {CONCEPTS[w] for w in re.findall(r"[a-z-]+", s.lower()) if w in CONCEPTS}
def semantic(query):
    q = concepts(query)
    return sorted((d for d in DOCS if q & concepts(DOCS[d])), key=lambda d: len(q & concepts(DOCS[d])), reverse=True)

def rrf(*rankings, k=60):
    score = Counter()
    for r in rankings:
        for i, d in enumerate(r): score[d] += 1 / (k + i + 1)
    return [d for d, _ in score.most_common()]

for q in ["J45.4", "short of breath after dark"]:
    kw = bm25_scores(q)
    sem = {d: len(concepts(q) & concepts(DOCS[d])) for d in DOCS}
    print(f"query: {q!r}")
    print(f"  keyword scores  {kw}")
    print(f"  semantic scores {sem}")
    print(f"  hybrid ranking  {rrf(bm25(q), semantic(q))}")
Output · produced by running this code
query: 'J45.4'
  keyword scores  {'d1': 1.19, 'd2': 0.0, 'd3': 0.0, 'd4': 0.0}
  semantic scores {'d1': 0, 'd2': 0, 'd3': 0, 'd4': 0}
  hybrid ranking  ['d1']
query: 'short of breath after dark'
  keyword scores  {'d1': 0.0, 'd2': 0.0, 'd3': 0.0, 'd4': 0.0}
  semantic scores {'d1': 0, 'd2': 2, 'd3': 0, 'd4': 0}
  hybrid ranking  ['d2']
How to read it

For the exact code, only keyword search can tell the documents apart: d1 scores, everything else is zero, while every semantic score is zero because a code carries no meaning to match. For the paraphrase it's the reverse: no document shares a word with "short of breath after dark", so every keyword score is zero, and the semantic scorer finds d2 (breathlessness at night-time). Hybrid fusion (of the documents each method actually matched) puts the right document first for both queries. That robustness is why hybrid plus re-ranking is the usual production starting point.

Practice questionUsers search a parts catalogue by exact part numbers like "BRK-4471-A", and semantic search often returns similar-looking but wrong parts. What should the architect add?

Exact identifiers are a keyword problem. Embeddings are good at meaning, poor at exact tokens; hybrid retrieval gets both right.

Practice questionFinance asks "What was the total value of claims over ₹50,000 in Q3, by region?" over the claims database. Which retrieval approach fits?

Aggregates over structured data are a database job. Text retrieval can't reliably filter, sum and group; a scoped query tool can, and Claude explains the result.

Session 3.7

MCP, API/CLI or agent-to-agent

Four integration mechanisms, each right in different conditions:

MechanismWhat it isChoose it when
Direct API call (in your code or a custom tool)Your application calls a REST/HTTP APIOne application needs the capability; you want full control in code
CLIThe agent runs an installed command-line tool as a subprocessLocal developer tooling, scripts, file-system work (common in Claude Code)
MCP serverA standard server exposing tools, resources and prompts to any MCP hostThe capability should be reused across several applications and maintained independently
Agent-to-agent (e.g. A2A)Independent agents discover each other (via Agent Cards) and delegate tasksThe other side is an agent with its own reasoning, tools and permissions, often another team's or organisation's
The idea

These layer rather than compete. MCP servers usually wrap an API or a CLI, standardising how hosts reach it. A2A connects agents to agents; MCP connects an agent to tools and data. A system can use all of them: an agent reaches its tools through MCP and delegates a sub-task to a partner's agent through A2A.

Python
def choose_mechanism(n):
    if n["counterpart_is_agent"]:                       return "agent-to-agent (A2A)"
    if n["consumers"] > 1 or n["owned_by_other_team"]:  return "MCP server (wrapping the API/CLI)"
    if n["local_tool"]:                                 return "CLI (run as a subprocess)"
    return "direct API call in a custom tool"

Watch out

Some study material names the project file differently and describes remote servers as using SSE. In current Claude Code, project servers live in .mcp.json, and remote servers use Streamable HTTP (the older SSE transport is deprecated). Whatever the file, the rule is the same: commit server definitions, never the secrets. Reference them as environment variables.

Diagnosing "the MCP tool isn't there"

Python
def diagnose(s):
    if not s["declared"]:                 return "not declared in .mcp.json or user config (check the name and scope)"
    if s["transport"] != s["expected"]:   return f"wrong transport: configured {s['transport']}, server speaks {s['expected']}"
    if not s["reachable"]:                return "server not running / URL unreachable: check the process or endpoint, and its logs"
    if not s["approved"]:                 return "declared but not approved: project servers need approval (see /mcp)"
    if s["missing_env"]:                  return f"credential missing: {s['missing_env']} isn't set in the shell running Claude Code"
    if s["tool_disabled"]:                return "server connected, but the tool is denied or filtered by settings"
    return "connected"

Session 3.8

Progressive discovery vs monolithic context

There are two ways to give Claude what it might need. Monolithic context loads everything up front: all tool definitions, all reference documents, all instructions. Progressive discovery loads a small index up front and lets Claude fetch details when needed: tool search, Skills (descriptions first, bodies on demand), just-in-time retrieval, and file-system exploration.

Up-front tokensHigh, on every requestLow
LatencyOne round trip, but slow TTFT on big promptsExtra steps when something must be fetched
Selection qualityDegrades as options multiplyChoices stay small at each step
CachingLarge stable prefix caches wellSmaller prefix; fetched parts vary
FitsSmall, stable toolsets and references used on most requestsLarge toolsets, big corpora, many specialised procedures

On the Claude API, tool search implements progressive discovery for tools: you mark most tools defer_loading: true and include a tool-search tool; Claude sees only the search tool and any non-deferred ones, and loads matching definitions when it needs them.

Here's the trade-off in numbers for an assistant with 140 tools, where a typical request needs three of them.

Python
n_tools, tokens_per_def, needed = 140, 350, 3
search_tool_tokens, always_loaded = 400, 2
monolithic = n_tools * tokens_per_def
progressive = search_tool_tokens + always_loaded * tokens_per_def + needed * tokens_per_def
print(f"monolithic:  {monolithic:>7,} tokens of tool definitions on every request; {n_tools} options to choose between")
print(f"progressive: {progressive:>7,} tokens (search tool + {always_loaded} core tools + {needed} found on demand); a short list at each step")
per_month = 2_000_000
saved = (monolithic - progressive) * per_month * 2.00 / 1e6
print(f"at {per_month:,} requests/month on Sonnet 5.5: ≈ ${saved:,.0f} less input before any caching")

progressive:   2,150 tokens (search tool + 2 core tools + 3 found on demand); a short list at each step

How to read it

Loading all 140 definitions costs about 49,000 tokens per request and asks Claude to choose among 140 options. Progressive discovery uses about 2,150 and keeps every choice small. Caching would soften the monolithic cost but not the selection problem. The trade-off is an extra search step on requests that need an unusual tool, which is usually worth it once toolsets reach this size.

Exam lens

Domain 3 asks you to evaluate the two strategies, not to always pick one. A small, stable toolset used on nearly every request is better loaded up front and cached. A large or growing toolset, a big document corpus, or many occasional procedures call for progressive discovery: tool search, retrieval, or Skills.

Practice questionAn enterprise assistant has 180 integrations, and any single request uses two or three. Tool definitions take most of the context and the wrong tool is often chosen. What's the best strategy?

Caching reduces the cost of a large prefix but not the selection difficulty. Deferring tools behind search keeps both context use and the choice set small.

Practice questionWhen is a monolithic (load-everything) context the better choice?

For small, stable, frequently used context, loading it up front avoids extra discovery steps and caches well. Progressive discovery wins as size and variability grow.
