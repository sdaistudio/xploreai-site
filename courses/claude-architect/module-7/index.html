Session 7.1

Configuring Claude Code for teams

When Claude Code behaves differently for two developers on the same repository, the cause is almost always configuration scope: an instruction in one person's user file, a rule that loads only in one folder, a setting nobody committed. An architect designs the team configuration deliberately.

Directory CLAUDE.md or path-scoped rule?

The deciding question is where the targeted files live. If they're neatly inside one folder (everything in services/payments/), a directory CLAUDE.md fits. If they're scattered (test files next to source files across dozens of folders, every *.sql migration, every React component), a path-scoped rule with a glob reaches all of them without duplicating instructions.

.claude/rules/tests.md
---
paths: ["**/*.test.ts", "**/*.spec.ts"]
---
# Test conventions
- One behaviour per test; name tests "does X when Y".
- Use the factories in test/factories; never hard-code patient data.
- Mock the Claude API with test/fakes/claude.ts. Tests must never call the real API.

Why scope matters for the token budget

CLAUDE.md files and unscoped rules load at the start of every session, and they cost context (and adherence) whether or not they're relevant. Anthropic's guidance is to keep each CLAUDE.md concise (on the order of 200 lines); path-scoped rules load only when matching files are touched. Here's one session's cost under two layouts.

Python
import fnmatch

SECTIONS = {  # instruction set: (tokens, paths it applies to; None = everywhere)
    "core standards":        (900,   None),
    "API conventions":       (1_400, ["services/*/api/*.py"]),
    "test conventions":      (1_100, ["*.test.ts", "*.spec.ts"]),
    "Terraform checklist":   (2_600, ["infra/*.tf"]),
    "React components":      (1_800, ["web/src/components/*.tsx"]),
    "SQL migrations":        (1_200, ["db/migrations/*.sql"]),
}
touched = ["web/src/components/Button.tsx", "web/src/components/Button.test.ts", "web/src/styles.css"]

monolithic = sum(t for t, _ in SECTIONS.values())
scoped = 0
for name, (tokens, paths) in SECTIONS.items():
    if paths is None or any(fnmatch.fnmatch(f, p) or fnmatch.fnmatch(f.split("/")[-1], p) for f in touched for p in paths):
        scoped += tokens
        print(f"loaded   {name:<20} {tokens:>6,}")
    else:
        print(f"skipped  {name:<20} {tokens:>6,}")
print(f"\none big CLAUDE.md: {monolithic:,} tokens every session   path-scoped rules: {scoped:,} this session")

How to read it

A front-end session loads the core standards, the React rules and the test rules: 3,800 tokens instead of 9,000. The Terraform checklist, API and SQL conventions never enter the context because no matching file was touched. Fewer irrelevant instructions also means better adherence to the relevant ones.

Skills for procedures, context: fork for noisy ones

Universal standards belong in CLAUDE.md; task-specific procedures (a security audit, a release checklist, a performance investigation) belong in skills, which load only when needed. A skill with context: fork in its front matter runs in a separate subagent: the skill body becomes that subagent's task, it doesn't see the conversation history, and only its result returns. Use it for work that would otherwise flood the main conversation with intermediate steps: scanning hundreds of files, trying several approaches.

.claude/skills/dependency-audit/SKILL.md
---
name: dependency-audit
description: Audit project dependencies for known vulnerabilities, licence problems and outdated majors. Use when asked to audit, check or review dependencies.
context: fork
allowed-tools: Read, Grep, Glob, Bash(npm audit *), Bash(pip-audit *)
---
Run the audit tools for every package manifest in the repository.
Group findings by severity. For each critical or high finding give the package,
installed and fixed versions, and whether it is reachable from production code.
Return a table and at most 5 recommended actions. Do not modify any files.

Practice questionTest files live next to their source files across 40 folders. The team wants test conventions applied whenever Claude works on any test file. What's the best place for them?

Scattered files of one kind are exactly what path globs are for: one rule, no duplication, and it loads only when a matching file is touched. A root CLAUDE.md would spend those tokens on every session.

Practice questionOne developer's Claude Code follows the team's naming conventions; another's ignores them. What should be checked first?

Inconsistent behaviour across developers almost always points to configuration scope. Team conventions must live in committed, shared files.

Session 7.2

AI-assisted developer workflows

Claude Code improves developer workflows in three places: in the editor and terminal (interactive work), in the pipeline (headless runs in CI), and across the team (shared skills, commands and plugins). The architect's job is to choose where it helps, put the guardrails in, and measure the effect.

ModeAnswersUse for
Headless (claude -p)Is a person at the keyboard?CI jobs, scheduled tasks, scripts
Streaming output (--output-format stream-json)How is output delivered?Live logs, other programs consuming events
Auto / permission modesWho approves each action?Less prompting in trusted, sandboxed runs; never a substitute for deny rules and isolation
Tip

Keep generation and review in separate sessions: a session that wrote the code tends to agree with its own reasoning. Give the CI reviewer the team's standards through CLAUDE.md and a review skill, request structured output, and bound the run (--max-turns, a narrow --allowedTools).

Measuring whether it helps

"Developers like it" isn't a business case. Measure delivery outcomes before and after, and the quality of the AI's own contributions. The numbers below are a sample team's; the calculations are real.

Python
BEFORE = {"PR cycle time (h, median)": 31.0, "review wait (h, median)": 14.0, "escaped defects / 100 PRs": 4.2, "PRs per dev-week": 3.1}
AFTER  = {"PR cycle time (h, median)": 22.5, "review wait (h, median)": 6.5,  "escaped defects / 100 PRs": 4.6, "PRs per dev-week": 3.6}
LOWER_IS_BETTER = {"PR cycle time (h, median)", "review wait (h, median)", "escaped defects / 100 PRs"}

for metric in BEFORE:
    b, a = BEFORE[metric], AFTER[metric]
    change = (a - b) / b
    better = (change < 0) == (metric in LOWER_IS_BETTER)
    print(f"{metric:<28} {b:>6} → {a:<6} {change:+.0%}  {'better' if better else 'WORSE'}")

findings = {"accepted by humans": 312, "dismissed as wrong": 141, "dismissed as noise/nit": 210}
total = sum(findings.values())
print(f"\nAI review findings: {findings['accepted by humans'] / total:.0%} accepted, "
      f"{findings['dismissed as wrong'] / total:.0%} wrong, {findings['dismissed as noise/nit'] / total:.0%} noise")
Output · produced by running this code

review wait (h, median)        14.0 → 6.5    -54%  better
escaped defects / 100 PRs       4.2 → 4.6    +10%  WORSE
PRs per dev-week                3.1 → 3.6    +16%  better

How to read it

Cycle time and review waits fell sharply and throughput rose, but escaped defects crept up and over half of the AI review's findings were dismissed. The next step isn't "more AI" or "less AI"; it's tuning: tighten the review skill to skip nits, require evidence for each finding, and add the escaped defects to the reviewer's eval set. Watch the defect rate as the guardrail metric.

Practice questionA CI job runs Claude Code to review PRs, using the same session that generated the code. Reviews rarely find problems. What change is most likely to help?

The generating session carries its own reasoning and tends to confirm it. A fresh session reviews like an independent colleague.

Practice questionAfter rolling out AI-assisted coding, cycle time falls 27% but escaped defects rise. What should the architect recommend?

Productivity gains that raise defects can cost more than they save. Investigating, adding the cases to the reviewer's evals and re-measuring keeps the gain and fixes the regression.

Session 7.3

Debugging and operations

Claude is a strong partner in operations work: reading logs and traces faster than a person, correlating events, drafting hypotheses, and following runbooks. It needs the same discipline as any other agent: read-only access during diagnosis, runbooks as skills, and people approving any change to production.

Turning a log flood into a hypothesis

A practical first step in any incident is grouping thousands of log lines into a handful of signatures: normalise away IDs and numbers, count, and line them up against deploy times. Here it is on a synthetic incident log.

Python
import re
from collections import Counter, defaultdict

LOGS = [
    "14:01:12 INFO checkout ok order=88121 ms=412",
    "14:03:40 WARN payments slow ms=2210 order=88140",
    "14:05:03 DEPLOY checkout v2.31.0 (commit 7f3c2e1: 'switch tax service client to async')",
    *[f"14:{5 + i // 6:02d}:{10 + (i * 7) % 50:02d} ERROR checkout TaxClientTimeout after 3000ms order={88200 + i}" for i in range(42)],
    *[f"14:{6 + i // 3:02d}:{10 + (i * 11) % 50:02d} ERROR checkout NullPointer in CartTotal line 118 cart={5500 + i}" for i in range(9)],
    "14:09:44 WARN payments slow ms=2050 order=88310",
    "14:12:30 ERROR auth TokenExpired user=1201",
]

def secs(t): h, m, s = map(int, t.split(":")); return h * 3600 + m * 60 + s

def signature(line):
    msg = line.split(" ", 2)[2]
    return re.sub(r"\b\d+(ms)?\b", "<n>", re.sub(r"=\S+", "=<id>", msg))

deploys = [(l[:8], l[16:]) for l in LOGS if " DEPLOY " in l]
errors = sorted((l for l in LOGS if " ERROR " in l), key=lambda l: secs(l[:8]))
groups, first_seen = Counter(), {}
for l in errors:
    sig = signature(l)
    groups[sig] += 1
    first_seen.setdefault(sig, l[:8])

print("deploys:", deploys)
for sig, n in groups.most_common():
    near = [d for t, d in deploys if 0 <= secs(first_seen[sig]) - secs(t) <= 300]   # began within 5 min of a deploy
    print(f"{n:>3}×  first {first_seen[sig]}  {sig}")
    if near: print(f"       began within 5 min of deploy: {near[-1]}")

 42×  first 14:05:10  checkout TaxClientTimeout after <n> order=<id>
       began within 5 min of deploy: checkout v2.31.0 (commit 7f3c2e1: 'switch tax service client to async')
  9×  first 14:06:10  checkout NullPointer in CartTotal line <n> cart=<id>

How to read it

Fifty-odd error lines collapse into three signatures. The two big ones (tax-client timeouts and a null pointer in the cart total) both start within a minute or two of the 14:05 deploy that switched the tax client to async; the single auth error starts seven minutes later with no matching change, so it isn't linked: unrelated noise. That's a strong, evidence-backed hypothesis to hand to the on-call engineer, who decides whether to roll back. The analysis is the kind of work Claude does quickly; the production decision stays with a person.

Operational guardrails for AI-assisted ops

PracticeWhy
Read-only MCP servers and credentials for observability during triageDiagnosis never needs write access; an injected instruction in a log line can't cause harm
Runbooks as skillsConsistent procedures, loaded only when relevant
Deny rules and PreToolUse hooks for production commands"Never touch production" enforced, not requested
Everything Claude ran recorded in the incident timelinePost-incident review and audit
Post-incident: add the failure to evals, runbooks and alertsThe organisation learns, not just the person on call
Watch out

Logs and tickets are untrusted input: they can contain text written by users or attackers. An incident-triage agent that can also run commands is a prompt-injection target. Keep triage read-only, and route any action through a person or a tightly scoped, approved tool.

Practice questionA team wants Claude to help during production incidents. Which configuration is most appropriate?

Diagnosis needs reading, not writing. Least privilege, runbooks and human-executed changes give speed without handing production to an agent that reads untrusted text.

Practice questionSelect 2During triage, thousands of error lines appear after a deploy. Which approaches help Claude produce a useful hypothesis quickly? (Select 2)

Grouping turns a flood into a few patterns, and timing against changes points to likely causes. Raw dumps waste context and bury the signal.
