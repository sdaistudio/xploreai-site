Session 5.1

Guardrails and safety controls

A guardrail is any control that keeps a system within acceptable behaviour. An architect thinks about them in two ways at once: where they sit in the flow, and what kind of control each one is.

KindPurposeExamples
PreventiveStop the bad thing happeningLeast-privilege tools, permission rules, PreToolUse hooks, input validation, approval gates
DetectiveNotice it when it happensOutput checks, audit logs, anomaly alerts, sampled reviews
CorrectiveLimit and repair the damageRollback, kill switches, incident runbooks, notifying affected users
DirectiveTell the system and people what's expectedSystem-prompt policy, content policy, usage guidelines, training
The idea

Secure by design and defence in depth. Decide access, data flows and approval points during design, not after an incident; and make sure every serious threat meets at least one preventive control that doesn't depend on the model's judgement. Prompts are directive controls: valuable, but never the only thing standing between an attacker and a harmful action.

Checking a control design for gaps

Here's a control matrix for a claims agent, checked for threats that rely only on soft (directive or model-dependent) controls.

Python
CONTROLS = {   # control: (kind, hard = enforced outside the model?)
    "system-prompt scope rules":       ("directive", False),
    "input screening for injection":   ("preventive", False),
    "read-only claims tool":           ("preventive", True),
    "payout tool removed from agent":  ("preventive", True),
    "adjuster approval for decisions": ("preventive", True),
    "PreToolUse hook: block bulk export": ("preventive", True),
    "output PII check":                ("detective", True),
    "audit log of every tool call":    ("detective", True),
    "kill switch per route":           ("corrective", True),
}
THREATS = {
    "prompt injection via claim documents": ["input screening for injection", "system-prompt scope rules", "payout tool removed from agent"],
    "unauthorised payout":                  ["payout tool removed from agent", "adjuster approval for decisions", "audit log of every tool call"],
    "bulk export of patient data":          ["PreToolUse hook: block bulk export", "output PII check", "audit log of every tool call"],
    "off-topic or harmful replies":         ["system-prompt scope rules"],
    "hallucinated policy clauses":          ["system-prompt scope rules", "input screening for injection"],
}

for threat, used in THREATS.items():
    kinds = {CONTROLS[c][0] for c in used}
    hard_preventive = any(CONTROLS[c] == ("preventive", True) for c in used)
    gaps = []
    if not hard_preventive: gaps.append("no hard preventive control")
    if "detective" not in kinds: gaps.append("no detective control")
    print(f"{'GAP' if gaps else 'OK '} {threat:<38} {'; '.join(gaps)}")
Output · produced by running this code
GAP prompt injection via claim documents   no detective control
OK  unauthorised payout                    
OK  bulk export of patient data            
GAP off-topic or harmful replies           no hard preventive control; no detective control
GAP hallucinated policy clauses            no hard preventive control; no detective control
How to read it

Payouts and bulk export are covered both ways: a hard preventive control and a detective one. Injection has a strong preventive control (the payout tool is gone), but nothing would detect an attempt, so add flagging and logging of injection-like content in documents. The last two threats rely on the system prompt alone. Hallucinated policy clauses need a grounding check (citations verified against the policy text, in code) plus a detective control such as sampled review; harmful replies need an output policy check. Neither fix makes the model "better behaved": they make the system safe when it isn't.

Practice questionA design's only control against an agent issuing unauthorised refunds is a system-prompt rule: "Never issue refunds above ₹5,000." What should the architect add first?

A prompt rule is a directive control that the model usually follows but can be manipulated past. High-impact actions need hard preventive controls and detective logging.

Practice questionSelect 2Which pair correctly classifies these controls? (Select 2)

Audit logs detect; removing capabilities prevents. A system-prompt policy is directive (it relies on the model), and a kill switch is corrective.

Session 5.2

Risks and failure modes

LLM systems share a recognisable set of risks. Name them, estimate them, assign owners and controls, and revisit them: a risk register is a living document, not a launch checklist.

RiskWhat it looks like
HallucinationConfident, specific, unsupported claims: invented clauses, citations, API fields
Prompt injectionUntrusted content redirects the model, especially dangerous for agents with tools
Data leakagePII or confidential data reaches the wrong person, log or vendor
Excessive agencyThe agent can do more than its task needs, so mistakes and attacks have a big blast radius
Bias and unfairnessSystematically worse outcomes for some groups or languages
Over-reliancePeople stop checking outputs; automation bias erodes human oversight
Drift and silent regressionInputs, data or prompts change; quality falls without any error
Non-determinismThe same input gives different outputs; one passing test proves little
Cascading failureIn multi-step agents, one weak step's errors compound downstream
Availability and dependencyProvider outages, rate limits, deprecated models

A risk register in code

Score inherent risk (likelihood × impact before controls) and residual risk (after controls). Residual risks above the organisation's appetite need more controls or explicit acceptance by an accountable owner.

Python
APPETITE = 6   # residual scores above this need action or a signed acceptance
REGISTER = [  # risk, likelihood 1–5, impact 1–5, control effectiveness 0–1, owner
    ("Prompt injection triggers a payout",    3, 5, 0.85, "Security"),
    ("Hallucinated policy clause in a letter", 4, 4, 0.40, "Claims product"),
    ("PHI written to application logs",       3, 5, 0.70, "Platform"),
    ("Over-reliance: adjusters stop checking", 4, 4, 0.25, "Claims operations"),
    ("Model deprecation breaks the pipeline", 2, 3, 0.80, "Platform"),
    ("Lower accuracy on Marathi documents",   3, 4, 0.20, "Claims product"),
]
rows = []
for risk, l, i, eff, owner in REGISTER:
    inherent = l * i
    residual = round(inherent * (1 - eff), 1)
    rows.append((residual, risk, inherent, owner))
print(f"{'risk':<40}{'inherent':>9}{'residual':>9}  owner")
for residual, risk, inherent, owner in sorted(rows, reverse=True):
    flag = "  ← above appetite" if residual > APPETITE else ""
    print(f"{risk:<40}{inherent:>9}{residual:>9}  {owner}{flag}")

risk                                     inherent residual  owner
Over-reliance: adjusters stop checking         16     12.0  Claims operations  ← above appetite
Lower accuracy on Marathi documents            12      9.6  Claims product  ← above appetite
Hallucinated policy clause in a letter         16      9.6  Claims product  ← above appetite
PHI written to application logs                15      4.5  Platform
Prompt injection triggers a payout             15      2.3  Security
Model deprecation breaks the pipeline           6      1.2  Platform
How to read it

The scariest-sounding risk, injection triggering a payout, is low after controls because the payout tool was removed and approvals are enforced. The top residual risks are human and linguistic: adjusters over-trusting drafts, hallucinated clauses, and weaker accuracy on Marathi documents. Those need different controls (UX that forces review of key fields, grounding checks, per-language evals), and owners outside the engineering team.

Practice questionIn a risk review, which risk is best described as "excessive agency"?

Excessive agency is capability beyond what the task requires: it enlarges the blast radius of any error or attack. The fix is removing the unneeded tools and permissions.

Practice questionAfter launch, reviewers approve 99.7% of AI-drafted claim letters within seconds, and audits find errors that should have been caught. Which risk has materialised?

Near-total approval at speed alongside missed errors signals that oversight has eroded. Controls include sampling with feedback, highlighting uncertain fields, and measuring reviewer accuracy.

Session 5.3

Human-in-the-loop validation

Human oversight is a design decision with costs on both sides. Over-escalating wastes people's time, slows resolution and defeats the purpose of automation. Under-escalating lets the system make decisions it has no authority or ability to make. Calibrate escalation on clear triggers.

TriggerValid?Why
The user explicitly asks for a person✓ Escalate immediatelyUser autonomy: don't try "one more answer" first
Authority gap: policy is silent or ambiguous on what's being asked✓The agent lacks permission, not ability: a person must decide
Verification flag: a check failed, a result contradicts expectations, an action needs approval✓Correctness or safety must be confirmed before continuing
High stakes with low confidence✓A wrong guess costs too much
Frustration alone✗Tone isn't a blocker; resolve the issue (often simple), or escalate if one of the valid triggers applies
Complexity alone✗Hard isn't broken; agent loops are built for long, multi-step work

An escalation policy, tested

Python
def should_escalate(case):
    if case.get("asks_for_human"):                        return True,  "explicit request: hand over now, with context"
    if case.get("policy_covers") is False:                return True,  "authority gap: policy silent or ambiguous"
    if case.get("check_failed"):                          return True,  "verification flag: confirm before continuing"
    if case.get("stakes") == "high" and case.get("confidence", 1) < 0.7:
                                                          return True,  "high stakes, low confidence"
    reasons = [r for r, k in (("frustration", "frustrated"), ("complexity", "complex")) if case.get(k)]
    return False, ("not a trigger on its own: " + " and ".join(reasons)) if reasons else "resolve"

cases = [
    ("Angry customer, refund status question",           dict(frustrated=True, policy_covers=True)),
    ("Calm customer: 'can I talk to a person?'",         dict(asks_for_human=True)),
    ("Asks us to match a competitor's price",            dict(policy_covers=False)),
    ("Refactor across 30 files, tests still passing",    dict(complex=True, policy_covers=True)),
    ("Dosage question, model unsure",                    dict(stakes="high", confidence=0.55, policy_covers=True)),
    ("Bank details on file don't match the claim form",  dict(check_failed=True)),
    ("Angry and asks for a manager",                     dict(frustrated=True, asks_for_human=True)),
]
for name, c in cases:
    esc, why = should_escalate(c)
    print(f"{'ESCALATE' if esc else 'resolve ':<8}  {name:<50} {why}")
Output · produced by running this code
resolve   Angry customer, refund status question             not a trigger on its own: frustration
ESCALATE  Calm customer: 'can I talk to a person?'           explicit request: hand over now, with context
ESCALATE  Asks us to match a competitor's price              authority gap: policy silent or ambiguous
resolve   Refactor across 30 files, tests still passing      not a trigger on its own: complexity
ESCALATE  Dosage question, model unsure                      high stakes, low confidence
ESCALATE  Bank details on file don't match the claim form    verification flag: confirm before continuing
ESCALATE  Angry and asks for a manager                       explicit request: hand over now, with context
How to read it

Frustration and complexity never escalate on their own, but a frustrated customer who asks for a manager is escalated at once, because of the request, not the tone. The competitor price-match case escalates even though the agent could compute a price: it has no policy authority to grant one.

Designing review so it stays real

Reviewing everything is rarely affordable and quickly becomes a rubber stamp. Common patterns: threshold review (send low-confidence or high-impact items to people), random audit sampling of the rest (to measure the automated path's real error rate), and two-person review for the highest-stakes decisions. Size the threshold to the reviewers you actually have.

Python
import random
random.seed(5)
confidences = [min(1.0, max(0.0, random.gauss(0.86, 0.09))) for _ in range(4_000)]   # one day's items
REVIEWERS, PER_REVIEWER = 6, 90          # items each reviewer can check properly per day
AUDIT_RATE = 0.02

for threshold in (0.70, 0.75, 0.80, 0.85):
    flagged = sum(c < threshold for c in confidences)
    audited = round((len(confidences) - flagged) * AUDIT_RATE)
    load = flagged + audited
    fits = "fits" if load <= REVIEWERS * PER_REVIEWER else "over capacity"
    print(f"review below {threshold:.2f}: {flagged:>5} flagged + {audited:>3} audit samples = {load:>5}  ({fits}: capacity {REVIEWERS * PER_REVIEWER})")
Output · produced by running this code
review below 0.70:   165 flagged +  77 audit samples =   242  (fits: capacity 540)
review below 0.75:   444 flagged +  71 audit samples =   515  (fits: capacity 540)
review below 0.80:  1037 flagged +  59 audit samples =  1096  (over capacity: capacity 540)
review below 0.85:  1819 flagged +  44 audit samples =  1863  (over capacity: capacity 540)
How to read it

A threshold of 0.85 would send almost half the day's items to six reviewers who can properly check 540: guaranteed rubber-stamping. 0.75 fits capacity with an audit sample on top. If the threshold that's safe doesn't fit capacity, that's a staffing or scope decision for stakeholders, not something to resolve by quietly lowering the bar. (Confidence must also be calibrated: check that low-confidence items really do fail more often.)

Practice questionA customer writes calmly, "I'd like to speak to a human, please." The agent is confident it can solve the issue. What should it do?

An explicit request for a person is a valid trigger on its own, and user autonomy means honouring it immediately rather than attempting another automated answer.

Practice questionSelect 2Which situations are valid escalation triggers? (Select 2)

An authority gap and a failed verification are real blockers. Frustration and complexity alone aren't: the agent should resolve the simple issue and keep working through complex tasks.

Session 5.4

Regulatory compliance

Architects don't replace legal counsel, but they must turn regulatory requirements into design decisions early: where data lives, who processes it, how long it's kept, who can see it, and when a person must decide. Three regimes the blueprint names:

RegulationApplies toDesign implications for a Claude system
GDPR (EU/EEA)Personal data of people in the EULawful basis and purpose limitation; data minimisation; data processing agreements with vendors; transfer safeguards for data leaving the EU; honouring access and erasure requests (including in logs and indexes); impact assessments for high-risk processing; a right to human involvement in solely automated decisions with legal or similarly significant effects
HIPAA (US healthcare)Protected health information (PHI) handled by covered entities and their business associatesA business associate agreement (BAA) with every vendor that processes PHI; minimum-necessary access; encryption; audit trails; breach procedures. Confirm which provider offerings and configurations are covered by a BAA before PHI flows
FedRAMP (US federal)Cloud services used by US federal agenciesUse a deployment path with the required FedRAMP authorisation level (e.g. Moderate or High), typically through a cloud platform's authorised government regions; keep the whole data path inside the authorised boundary
Watch out

Compliance is end to end. A compliant model endpoint doesn't help if prompts are logged to an unapproved analytics tool, embeddings are stored in the wrong region, or a third-party MCP server receives the data. Map every hop: input, retrieval stores, model calls, tool calls, logs, traces, backups. India's Digital Personal Data Protection Act and sector rules (banking, insurance) raise similar questions for Indian deployments, and AI-specific laws are emerging: check current obligations with counsel.

A design checked against requirements

Python
DESIGN = {
    "data_region": "ap-south-1", "model_path": "Claude via cloud platform, India region",
    "vendor_agreements": {"model provider": "DPA", "vector DB": "DPA", "logging SaaS": None},
    "baa_signed_with": [], "phi_in_scope": True, "eu_users": True,
    "log_retention_days": 365, "erasure_covers": ["database"], "human_decides_significant": True,
    "encryption_at_rest": True, "audit_trail": True, "fedramp_needed": False,
}

def check(d):
    gaps = []
    missing = [v for v, a in d["vendor_agreements"].items() if a is None]
    if missing: gaps.append(("GDPR", f"no data processing agreement with: {', '.join(missing)}"))
    if d["eu_users"] and d["data_region"] not in ("eu-west-1", "eu-central-1"):
        gaps.append(("GDPR", "EU personal data stored outside the EU: confirm a valid transfer mechanism"))
    if set(["logs", "vector index"]) - set(d["erasure_covers"]):
        gaps.append(("GDPR", "erasure requests don't reach logs and the vector index"))
    if d["phi_in_scope"] and len(d["baa_signed_with"]) < len(d["vendor_agreements"]):
        gaps.append(("HIPAA", "PHI in scope but BAAs not in place with every vendor that processes it"))
    if d["log_retention_days"] > 180:
        gaps.append(("policy", f"logs kept {d['log_retention_days']} days: justify or shorten (minimisation)"))
    if d["fedramp_needed"]:
        gaps.append(("FedRAMP", "confirm the authorisation level of the whole data path"))
    return gaps

for regime, gap in check(DESIGN):
    print(f"{regime:<8} {gap}")
Output · produced by running this code
GDPR     no data processing agreement with: logging SaaS
GDPR     EU personal data stored outside the EU: confirm a valid transfer mechanism
GDPR     erasure requests don't reach logs and the vector index
HIPAA    PHI in scope but BAAs not in place with every vendor that processes it
policy   logs kept 365 days: justify or shorten (minimisation)
How to read it

Five findings, none of them about the model. A logging tool without a processing agreement, EU data stored in an Indian region, erasure that can't reach logs or the vector index, PHI flowing to vendors without BAAs, and a long log retention period. This is why compliance belongs in the architecture review, with every data hop on the diagram.

Practice questionA US hospital wants a Claude-based discharge-summary assistant that processes PHI. What must be in place before PHI flows to any vendor in the pipeline?

HIPAA requires BAAs with business associates handling PHI, along with safeguards. FedRAMP applies to US federal agency use, not to hospitals in general.

Practice questionSelect 2An EU customer asks for their personal data to be erased. The application deletes their database records. Which gaps commonly remain in Claude systems? (Select 2)

Personal data often persists in logs, traces and retrieval indexes. Conversations through the API don't retrain the model's weights, and the system prompt doesn't hold customer data.

Session 5.5

Bias, fairness and transparency

LLM systems can produce systematically different outcomes for different groups: by language, region, dialect, name, gender, age or disability. Fairness has to be measured on your task, not assumed from the model.

ConceptQuestion it asksHow to check
Outcome parityDo groups receive favourable outcomes at similar rates?Compare approval or resolution rates by group
Error parityIs the system equally accurate for each group?Compare error rates (false rejections, false approvals) against ground truth, by group
Counterfactual consistencyDoes changing only a protected attribute change the result?Swap names, gender, language markers; compare outputs
TransparencyDo people know AI is involved, and can decisions be explained?Disclosure, reasons with evidence, documentation of limitations, a route to a person

Measuring it

Here are eval results for an eligibility-drafting step, broken down by the language of the claim documents. Ground truth comes from expert adjusters.

Python
RESULTS = {  # language: (cases, eligible per experts, AI said eligible, AI correct on eligible, AI correct on ineligible)
    "English":  (400, 300, 296, 291, 95),
    "Hindi":    (250, 185, 176, 172, 61),
    "Marathi":  (150, 112, 92,  90,  36),
}
print(f"{'language':<9}{'AI approval':>12}{'expert approval':>16}{'missed eligible':>16}{'accuracy':>10}")
for lang, (n, elig, ai_yes, tp, tn) in RESULTS.items():
    missed = (elig - tp) / elig
    print(f"{lang:<9}{ai_yes / n:>12.0%}{elig / n:>16.0%}{missed:>16.1%}{(tp + tn) / n:>10.0%}")
Output · produced by running this code
language  AI approval expert approval missed eligible  accuracy
English           74%             75%            3.0%       96%
Hindi             70%             74%            7.0%       93%
Marathi           61%             75%           19.6%       84%
How to read it

Experts find similar eligibility rates across languages (74–75%), but the AI approves noticeably fewer Marathi claims, and it misses about 20% of eligible Marathi claims against 3% for English. That's an error-parity problem with real harm (wrongful denials), invisible in the overall accuracy figure. Likely causes are in the pipeline (OCR of Devanagari scans, chunking, prompts tested mostly in English), so the fixes are there too, along with a per-language eval slice and a human-review rule for Marathi claims until parity is restored.

Tip

Counterfactual tests are cheap and revealing: run the same case with only the claimant's name or language changed, and diff the outputs. For transparency, tell people when they're dealing with AI, give reasons with the evidence used, document the system's intended use and known limitations for stakeholders and auditors, and provide a clear route to a person.

Practice questionOverall accuracy is 94%, but per-group analysis shows eligible claims from one language group are wrongly rejected five times as often as others. Which fairness concept is violated?

Error parity compares mistakes against ground truth by group. A much higher false-rejection rate for one group is unfair even when the aggregate looks good.

Practice questionSelect 2Which practices support transparency in a Claude-assisted decision process? (Select 2)

Disclosure, explanations grounded in evidence and documented limitations make the process understandable and contestable. Concealment undermines trust, and secrets never belong in public documentation.
