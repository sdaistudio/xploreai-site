## 5.1 | Guardrails and safety controls

A guardrail is any control that keeps a system within acceptable behaviour. An architect thinks about them in two ways at once: **where** they sit in the flow, and **what kind** of control each one is.

| Kind | Purpose | Examples |
|---|---|---|
| **Preventive** | Stop the bad thing happening | Least-privilege tools, permission rules, PreToolUse hooks, input validation, approval gates |
| **Detective** | Notice it when it happens | Output checks, audit logs, anomaly alerts, sampled reviews |
| **Corrective** | Limit and repair the damage | Rollback, kill switches, incident runbooks, notifying affected users |
| **Directive** | Tell the system and people what's expected | System-prompt policy, content policy, usage guidelines, training |

```flow title="Where guardrails sit in an agentic request"
Input | Authenticate, validate, screen, tag untrusted content.
Context | Least-privilege data access; retrieval filtered by the user's rights.
Model | Model's own safety training; system-prompt policy for this app.
Actions | Scoped tools; hooks and permission rules; approval for high-impact actions.
Output | Policy, leakage and grounding checks before anything is shown or sent.
Operations | Logging, monitoring, red-team testing, incident response.
```

> [concept] **Secure by design and defence in depth.** Decide access, data flows and approval points *during* design, not after an incident; and make sure every serious threat meets at least one **preventive** control that doesn't depend on the model's judgement. Prompts are directive controls: valuable, but never the only thing standing between an attacker and a harmful action.

### Checking a control design for gaps

Here's a control matrix for a claims agent, checked for threats that rely only on soft (directive or model-dependent) controls.

```python
CONTROLS = {   # control: (kind, hard = enforced outside the model?)
    "system-prompt scope rules":       ("directive", False),
    "input screening for injection":   ("preventive", False),
    "read-only claims tool":           ("preventive", True),
    "payout tool removed from agent":  ("preventive", True),
    "adjuster approval for decisions": ("preventive", True),
    "PreToolUse hook: block bulk export": ("preventive", True),
    "output PII check":                ("detective", True),
    "audit log of every tool call":    ("detective", True),
    "kill switch per route":           ("corrective", True),
}
THREATS = {
    "prompt injection via claim documents": ["input screening for injection", "system-prompt scope rules", "payout tool removed from agent"],
    "unauthorised payout":                  ["payout tool removed from agent", "adjuster approval for decisions", "audit log of every tool call"],
    "bulk export of patient data":          ["PreToolUse hook: block bulk export", "output PII check", "audit log of every tool call"],
    "off-topic or harmful replies":         ["system-prompt scope rules"],
    "hallucinated policy clauses":          ["system-prompt scope rules", "input screening for injection"],
}

for threat, used in THREATS.items():
    kinds = {CONTROLS[c][0] for c in used}
    hard_preventive = any(CONTROLS[c] == ("preventive", True) for c in used)
    gaps = []
    if not hard_preventive: gaps.append("no hard preventive control")
    if "detective" not in kinds: gaps.append("no detective control")
    print(f"{'GAP' if gaps else 'OK '} {threat:<38} {'; '.join(gaps)}")
```

> [read] Payouts and bulk export are covered both ways: a hard preventive control and a detective one. Injection has a strong preventive control (the payout tool is gone), but nothing would *detect* an attempt, so add flagging and logging of injection-like content in documents. The last two threats rely on the system prompt alone. Hallucinated policy clauses need a grounding check (citations verified against the policy text, in code) plus a detective control such as sampled review; harmful replies need an output policy check. Neither fix makes the model "better behaved": they make the system safe when it isn't.

## 5.2 | Risks and failure modes

LLM systems share a recognisable set of risks. Name them, estimate them, assign owners and controls, and revisit them: a **risk register** is a living document, not a launch checklist.

| Risk | What it looks like |
|---|---|
| **Hallucination** | Confident, specific, unsupported claims: invented clauses, citations, API fields |
| **Prompt injection** | Untrusted content redirects the model, especially dangerous for agents with tools |
| **Data leakage** | PII or confidential data reaches the wrong person, log or vendor |
| **Excessive agency** | The agent can do more than its task needs, so mistakes and attacks have a big blast radius |
| **Bias and unfairness** | Systematically worse outcomes for some groups or languages |
| **Over-reliance** | People stop checking outputs; automation bias erodes human oversight |
| **Drift and silent regression** | Inputs, data or prompts change; quality falls without any error |
| **Non-determinism** | The same input gives different outputs; one passing test proves little |
| **Cascading failure** | In multi-step agents, one weak step's errors compound downstream |
| **Availability and dependency** | Provider outages, rate limits, deprecated models |

### A risk register in code

Score **inherent risk** (likelihood × impact before controls) and **residual risk** (after controls). Residual risks above the organisation's appetite need more controls or explicit acceptance by an accountable owner.

```python
APPETITE = 6   # residual scores above this need action or a signed acceptance
REGISTER = [  # risk, likelihood 1–5, impact 1–5, control effectiveness 0–1, owner
    ("Prompt injection triggers a payout",    3, 5, 0.85, "Security"),
    ("Hallucinated policy clause in a letter", 4, 4, 0.40, "Claims product"),
    ("PHI written to application logs",       3, 5, 0.70, "Platform"),
    ("Over-reliance: adjusters stop checking", 4, 4, 0.25, "Claims operations"),
    ("Model deprecation breaks the pipeline", 2, 3, 0.80, "Platform"),
    ("Lower accuracy on Marathi documents",   3, 4, 0.20, "Claims product"),
]
rows = []
for risk, l, i, eff, owner in REGISTER:
    inherent = l * i
    residual = round(inherent * (1 - eff), 1)
    rows.append((residual, risk, inherent, owner))
print(f"{'risk':<40}{'inherent':>9}{'residual':>9}  owner")
for residual, risk, inherent, owner in sorted(rows, reverse=True):
    flag = "  ← above appetite" if residual > APPETITE else ""
    print(f"{risk:<40}{inherent:>9}{residual:>9}  {owner}{flag}")
```

> [read] The scariest-sounding risk, injection triggering a payout, is low after controls because the payout tool was removed and approvals are enforced. The top residual risks are human and linguistic: adjusters over-trusting drafts, hallucinated clauses, and weaker accuracy on Marathi documents. Those need different controls (UX that forces review of key fields, grounding checks, per-language evals), and owners outside the engineering team.

## 5.3 | Human-in-the-loop validation

Human oversight is a design decision with costs on both sides. **Over-escalating** wastes people's time, slows resolution and defeats the purpose of automation. **Under-escalating** lets the system make decisions it has no authority or ability to make. Calibrate escalation on clear triggers.

| Trigger | Valid? | Why |
|---|---|---|
| **The user explicitly asks for a person** | ✓ Escalate **immediately** | User autonomy: don't try "one more answer" first |
| **Authority gap**: policy is silent or ambiguous on what's being asked | ✓ | The agent lacks *permission*, not ability: a person must decide |
| **Verification flag**: a check failed, a result contradicts expectations, an action needs approval | ✓ | Correctness or safety must be confirmed before continuing |
| **High stakes with low confidence** | ✓ | A wrong guess costs too much |
| **Frustration alone** | ✗ | Tone isn't a blocker; resolve the issue (often simple), or escalate if one of the valid triggers applies |
| **Complexity alone** | ✗ | Hard isn't broken; agent loops are built for long, multi-step work |

```seq title="Frustrated customer, simple issue: resolve, don't escalate"
Customer, Agent, Order system
Customer -> Agent: "THIS IS RIDICULOUS. Where is my refund?!"
note Agent: Frustration noted. Valid trigger? No explicit request, no authority gap, no failed check
Agent -> Order system: refund_status(ORD-104233)
Order system --> Agent: processed 24 Oct; arrives by 29 Oct
Agent --> Customer: Apologises, gives the exact date and reference, offers a person if they'd like one
note Customer: If they now ask for a person → hand over immediately, with the context
```

### An escalation policy, tested

```python
def should_escalate(case):
    if case.get("asks_for_human"):                        return True,  "explicit request: hand over now, with context"
    if case.get("policy_covers") is False:                return True,  "authority gap: policy silent or ambiguous"
    if case.get("check_failed"):                          return True,  "verification flag: confirm before continuing"
    if case.get("stakes") == "high" and case.get("confidence", 1) < 0.7:
                                                          return True,  "high stakes, low confidence"
    reasons = [r for r, k in (("frustration", "frustrated"), ("complexity", "complex")) if case.get(k)]
    return False, ("not a trigger on its own: " + " and ".join(reasons)) if reasons else "resolve"

cases = [
    ("Angry customer, refund status question",           dict(frustrated=True, policy_covers=True)),
    ("Calm customer: 'can I talk to a person?'",         dict(asks_for_human=True)),
    ("Asks us to match a competitor's price",            dict(policy_covers=False)),
    ("Refactor across 30 files, tests still passing",    dict(complex=True, policy_covers=True)),
    ("Dosage question, model unsure",                    dict(stakes="high", confidence=0.55, policy_covers=True)),
    ("Bank details on file don't match the claim form",  dict(check_failed=True)),
    ("Angry and asks for a manager",                     dict(frustrated=True, asks_for_human=True)),
]
for name, c in cases:
    esc, why = should_escalate(c)
    print(f"{'ESCALATE' if esc else 'resolve ':<8}  {name:<50} {why}")
```

> [read] Frustration and complexity never escalate on their own, but a frustrated customer who *asks* for a manager is escalated at once, because of the request, not the tone. The competitor price-match case escalates even though the agent could compute a price: it has no policy authority to grant one.

### Designing review so it stays real

Reviewing everything is rarely affordable and quickly becomes a rubber stamp. Common patterns: **threshold review** (send low-confidence or high-impact items to people), **random audit sampling** of the rest (to measure the automated path's real error rate), and **two-person review** for the highest-stakes decisions. Size the threshold to the reviewers you actually have.

```python
import random
random.seed(5)
confidences = [min(1.0, max(0.0, random.gauss(0.86, 0.09))) for _ in range(4_000)]   # one day's items
REVIEWERS, PER_REVIEWER = 6, 90          # items each reviewer can check properly per day
AUDIT_RATE = 0.02

for threshold in (0.70, 0.75, 0.80, 0.85):
    flagged = sum(c < threshold for c in confidences)
    audited = round((len(confidences) - flagged) * AUDIT_RATE)
    load = flagged + audited
    fits = "fits" if load <= REVIEWERS * PER_REVIEWER else "over capacity"
    print(f"review below {threshold:.2f}: {flagged:>5} flagged + {audited:>3} audit samples = {load:>5}  ({fits}: capacity {REVIEWERS * PER_REVIEWER})")
```

> [read] A threshold of 0.85 would send almost half the day's items to six reviewers who can properly check 540: guaranteed rubber-stamping. 0.75 fits capacity with an audit sample on top. If the threshold that's *safe* doesn't fit capacity, that's a staffing or scope decision for stakeholders, not something to resolve by quietly lowering the bar. (Confidence must also be calibrated: check that low-confidence items really do fail more often.)

## 5.4 | Regulatory compliance

Architects don't replace legal counsel, but they must turn regulatory requirements into **design decisions** early: where data lives, who processes it, how long it's kept, who can see it, and when a person must decide. Three regimes the blueprint names:

| Regulation | Applies to | Design implications for a Claude system |
|---|---|---|
| **GDPR** (EU/EEA) | Personal data of people in the EU | Lawful basis and purpose limitation; data minimisation; data processing agreements with vendors; transfer safeguards for data leaving the EU; honouring access and erasure requests (including in logs and indexes); impact assessments for high-risk processing; a right to human involvement in solely automated decisions with legal or similarly significant effects |
| **HIPAA** (US healthcare) | Protected health information (PHI) handled by covered entities and their business associates | A **business associate agreement (BAA)** with every vendor that processes PHI; minimum-necessary access; encryption; audit trails; breach procedures. Confirm which provider offerings and configurations are covered by a BAA before PHI flows |
| **FedRAMP** (US federal) | Cloud services used by US federal agencies | Use a deployment path with the required **FedRAMP authorisation level** (e.g. Moderate or High), typically through a cloud platform's authorised government regions; keep the whole data path inside the authorised boundary |

> [warn] Compliance is **end to end**. A compliant model endpoint doesn't help if prompts are logged to an unapproved analytics tool, embeddings are stored in the wrong region, or a third-party MCP server receives the data. Map every hop: input, retrieval stores, model calls, tool calls, logs, traces, backups. India's Digital Personal Data Protection Act and sector rules (banking, insurance) raise similar questions for Indian deployments, and AI-specific laws are emerging: check current obligations with counsel.

```seq title="Every hop is in scope"
Patient app, Gateway, Vector index, Claude (cloud region), Logging SaaS
Patient app -> Gateway: claim + documents (PHI, personal data)
note Gateway: Minimise: strip fields the task doesn't need
Gateway -> Vector index: chunks + embeddings (region? erasure path? DPA/BAA?)
Gateway -> Claude (cloud region): prompt with retrieved context (agreement? region? retention?)
Claude (cloud region) --> Gateway: draft decision
Gateway -> Logging SaaS: trace with redacted prompt (DPA? BAA? retention? access?)
note Logging SaaS: The hop most often forgotten in compliance reviews
```

### A design checked against requirements

```python
DESIGN = {
    "data_region": "ap-south-1", "model_path": "Claude via cloud platform, India region",
    "vendor_agreements": {"model provider": "DPA", "vector DB": "DPA", "logging SaaS": None},
    "baa_signed_with": [], "phi_in_scope": True, "eu_users": True,
    "log_retention_days": 365, "erasure_covers": ["database"], "human_decides_significant": True,
    "encryption_at_rest": True, "audit_trail": True, "fedramp_needed": False,
}

def check(d):
    gaps = []
    missing = [v for v, a in d["vendor_agreements"].items() if a is None]
    if missing: gaps.append(("GDPR", f"no data processing agreement with: {', '.join(missing)}"))
    if d["eu_users"] and d["data_region"] not in ("eu-west-1", "eu-central-1"):
        gaps.append(("GDPR", "EU personal data stored outside the EU: confirm a valid transfer mechanism"))
    if set(["logs", "vector index"]) - set(d["erasure_covers"]):
        gaps.append(("GDPR", "erasure requests don't reach logs and the vector index"))
    if d["phi_in_scope"] and len(d["baa_signed_with"]) < len(d["vendor_agreements"]):
        gaps.append(("HIPAA", "PHI in scope but BAAs not in place with every vendor that processes it"))
    if d["log_retention_days"] > 180:
        gaps.append(("policy", f"logs kept {d['log_retention_days']} days: justify or shorten (minimisation)"))
    if d["fedramp_needed"]:
        gaps.append(("FedRAMP", "confirm the authorisation level of the whole data path"))
    return gaps

for regime, gap in check(DESIGN):
    print(f"{regime:<8} {gap}")
```

> [read] Five findings, none of them about the model. A logging tool without a processing agreement, EU data stored in an Indian region, erasure that can't reach logs or the vector index, PHI flowing to vendors without BAAs, and a long log retention period. This is why compliance belongs in the architecture review, with every data hop on the diagram.

## 5.5 | Bias, fairness and transparency

LLM systems can produce systematically different outcomes for different groups: by language, region, dialect, name, gender, age or disability. Fairness has to be **measured** on your task, not assumed from the model.

| Concept | Question it asks | How to check |
|---|---|---|
| **Outcome parity** | Do groups receive favourable outcomes at similar rates? | Compare approval or resolution rates by group |
| **Error parity** | Is the system equally *accurate* for each group? | Compare error rates (false rejections, false approvals) against ground truth, by group |
| **Counterfactual consistency** | Does changing only a protected attribute change the result? | Swap names, gender, language markers; compare outputs |
| **Transparency** | Do people know AI is involved, and can decisions be explained? | Disclosure, reasons with evidence, documentation of limitations, a route to a person |

### Measuring it

Here are eval results for an eligibility-drafting step, broken down by the language of the claim documents. Ground truth comes from expert adjusters.

```python
RESULTS = {  # language: (cases, eligible per experts, AI said eligible, AI correct on eligible, AI correct on ineligible)
    "English":  (400, 300, 296, 291, 95),
    "Hindi":    (250, 185, 176, 172, 61),
    "Marathi":  (150, 112, 92,  90,  36),
}
print(f"{'language':<9}{'AI approval':>12}{'expert approval':>16}{'missed eligible':>16}{'accuracy':>10}")
for lang, (n, elig, ai_yes, tp, tn) in RESULTS.items():
    missed = (elig - tp) / elig
    print(f"{lang:<9}{ai_yes / n:>12.0%}{elig / n:>16.0%}{missed:>16.1%}{(tp + tn) / n:>10.0%}")
```

> [read] Experts find similar eligibility rates across languages (74–75%), but the AI approves noticeably fewer Marathi claims, and it misses about 20% of eligible Marathi claims against 3% for English. That's an error-parity problem with real harm (wrongful denials), invisible in the overall accuracy figure. Likely causes are in the pipeline (OCR of Devanagari scans, chunking, prompts tested mostly in English), so the fixes are there too, along with a per-language eval slice and a human-review rule for Marathi claims until parity is restored.

> [tip] Counterfactual tests are cheap and revealing: run the same case with only the claimant's name or language changed, and diff the outputs. For transparency, tell people when they're dealing with AI, give reasons with the evidence used, document the system's intended use and known limitations for stakeholders and auditors, and provide a clear route to a person.

```quiz
Q: Overall accuracy is 94%, but per-group analysis shows eligible claims from one language group are wrongly rejected five times as often as others. Which fairness concept is violated?

- [x] Error parity: the system is less accurate, in a harmful direction, for one group
- [ ] Transparency
- [ ] None: overall accuracy is high
why: Error parity compares mistakes against ground truth by group. A much higher false-rejection rate for one group is unfair even when the aggregate looks good.
```
