## 1.1 | From business problem to Claude solution

Most failed AI projects automate the wrong thing well. Before any design, pin down three things: the **requirement** (a need the solution must satisfy), the **use case** (a concrete scenario where Claude addresses it) and the **success criteria** (how you'll know it worked, in numbers).

```flow title="From problem statement to solution concept"
Problem | "Claims take 9 days to settle; 40% of that is staff reading documents."
Requirements | Extract 14 fields from claim packs; flag missing documents; keep an audit trail.
Use cases | Intake triage, document extraction, missing-item letters, adjuster summary.
Success criteria | Median settle time under 5 days; field accuracy ≥ 97%; zero unaudited decisions.
Solution concept | Workflow: extract → validate → draft → human approves. No autonomous payouts.
```

> [concept] **Claude's job and people's job.** A good solution concept says explicitly what Claude does (read, extract, draft, classify, explain), what code does (validate, calculate, enforce rules, record) and what people do (decide, approve, handle exceptions). Architects who leave that split implicit end up with an agent making decisions nobody signed off.

### Requirements you can trace

At architecture level, every requirement should map to the component that delivers it and the test that proves it. A **traceability matrix** makes gaps visible before they become production incidents. Here's one for the claims solution, checked in code.

```python
REQUIREMENTS = {
    "R1": "Extract 14 fields from each claim pack with ≥97% accuracy",
    "R2": "Flag missing mandatory documents",
    "R3": "Every payout decision approved by a licensed adjuster",
    "R4": "Audit trail of inputs, model version, prompt version and outputs",
    "R5": "Median end-to-end time under 5 days",
    "R6": "Patient health data never leaves the India region",
}
COMPONENTS = {   # component → requirements it implements
    "extractor (Claude Sonnet, structured outputs)": ["R1"],
    "document checklist (rules in code)":           ["R2"],
    "approval queue (adjuster UI)":                  ["R3"],
    "trace store":                                   ["R4"],
    "claims dashboard":                              [],
}
TESTS = {        # test → requirements it verifies
    "eval: 300 labelled claim packs":     ["R1"],
    "unit: checklist rules":              ["R2"],
    "integration: payout blocked without approval": ["R3"],
    "load test: 2,000 packs/day":         ["R5"],
}

implemented = {r for rs in COMPONENTS.values() for r in rs}
verified = {r for rs in TESTS.values() for r in rs}
for rid, text in REQUIREMENTS.items():
    gaps = [g for g, ok in (("no component", rid in implemented), ("no test", rid in verified)) if not ok]
    print(f"{rid} {'OK ' if not gaps else 'GAP'} {text[:58]:<58} {', '.join(gaps)}")
orphans = [c for c, rs in COMPONENTS.items() if not rs]
print("\ncomponents serving no requirement:", orphans)
```

> [read] Three gaps surface before any code is written. R4 (audit trail) has a component but nothing proves it works. R5 (speed) is tested but nothing in the design delivers it: no component is responsible for throughput. R6 (data residency) has neither, a compliance requirement nobody owns. And the dashboard serves no requirement: either one is missing from the list, or it's scope creep.

> [exam] Domain 1 questions often describe a business goal and ask for the best *next step* or *solution shape*. Prefer answers that clarify success criteria and split responsibilities between Claude, code and people over answers that jump straight to a model, a framework or "an agent".

```quiz

why: Without a clear requirement and measurable success criteria there's nothing to design against. Model, framework and access decisions follow from them, and "agent" may not even be the right pattern.
```

```quiz
Q: A traceability matrix shows a requirement with a test but no component that implements it. What does that indicate?
- [ ] The requirement is complete
- [x] The design has a gap: nothing is responsible for delivering it, so the test will fail or pass by accident
- [ ] The test should be deleted

```

## 1.2 | End-to-end architecture and feedback loops

A Claude solution is never just "prompt in, answer out". An architecture covers the whole path: **input** (where requests come from, how they're validated), **processing** (retrieval, Claude calls, tools, rules), **output** (how results are checked, delivered and stored), and the **feedback loop** that makes it better over time.

```seq title="End to end, including the loop most designs forget"
Channel, Gateway, Orchestrator, Claude, Reviewer, Eval store
Channel -> Gateway: claim pack upload (PDFs, photos)
Gateway -> Orchestrator: validated, PII-tagged, size-checked request
Orchestrator -> Claude: extract fields (structured output, pinned model)
Claude --> Orchestrator: 14 fields + confidence notes
Orchestrator -> Reviewer: draft decision + evidence links
Reviewer --> Orchestrator: approve / correct (corrections recorded)
Orchestrator -> Eval store: corrected cases become new eval items
note Eval store: Next prompt or model change is tested against them
```

> [concept] **Design the feedback loop on day one.** Every human correction is a labelled example of where the system was wrong. If the architecture doesn't capture corrections with their inputs and the versions used, the team can't measure improvement, catch drift, or test the next change. The loop is part of the architecture, not a later "analytics" feature.

### Latency budgets

An SLA like "a reply within 8 seconds at the 95th percentile" has to be split across stages. Here's a budget for a support assistant, checked against measured p95 latencies (the measurements are illustrative).

```python
SLA_P95_MS = 8_000
stages = [  # stage, budget ms, measured p95 ms
    ("gateway + auth",          200,   140),
    ("retrieval (vector + rerank)", 900, 1_350),
    ("Claude first token",     1_500, 1_200),
    ("Claude full answer",     4_000, 3_900),
    ("output checks",           600,   420),
    ("delivery",                300,   180),
]
budget_total = sum(b for _, b, _ in stages)
measured_total = sum(m for _, _, m in stages)
print(f"{'stage':<30}{'budget':>8}{'p95':>8}")
for name, b, m in stages:
    print(f"{name:<30}{b:>8,}{m:>8,}{'  ← over budget' if m > b else ''}")
print(f"{'total':<30}{budget_total:>8,}{measured_total:>8,}   SLA {SLA_P95_MS:,}")
print(f"headroom vs SLA: {SLA_P95_MS - measured_total:,} ms (summing p95s overstates the true end-to-end p95, so this is conservative)")
```

> [read] The total fits the SLA, but retrieval is 50% over its budget, eating the headroom reserved for slow days. That's the kind of finding a budget exists to surface: fix retrieval (smaller index, better filters, a cache) before the SLA breaks under load. Note too that "Claude full answer" includes first token: streaming makes the user see words at around 1.2 s even though the full answer takes almost 4.

```quiz
- [ ] The UI colour scheme
- [ ] Missing streaming
```


## 1.3 | Choosing the pattern

The blueprint names three patterns. They're a ladder: each step up adds capability, and also cost, latency and unpredictability.

| Pattern | What it is | Who controls the flow | Use when |
|---|---|---|---|
| **Augmented LLM** | One Claude call enhanced with retrieval, tools and/or memory | One call; Claude may use tools within it | One step with the right context answers it: Q&A over documents, classification, extraction |
| **Workflow** | Several LLM calls and code steps along paths **you** define (chaining, routing, parallelisation, orchestrator–workers, evaluator–optimiser) | Your code | The steps are known in advance, and predictability or auditability matters |
| **Agent** | Claude directs its own process in a loop: chooses tools, reads results, decides the next step | Claude | The path can't be specified in advance and errors are recoverable |

> [warn] "Agentic" is not a maturity level to aim for. Anthropic's own guidance is to start with the simplest pattern that meets the requirement and add complexity only when it demonstrably improves outcomes. Most production value comes from augmented LLMs and workflows.

### What each pattern costs

Here are the same claims-intake job built three ways, with illustrative per-run figures. The arithmetic shows why the choice matters at volume.

```python
P_IN, P_OUT = 2.00, 10.00            # Claude Sonnet 5.5, $ per million tokens
designs = {   # calls, input tokens per call, output tokens per call, p95 seconds, accuracy on eval (illustrative)
    "augmented LLM (1 call + retrieval)":      (1, 9_000, 900, 6,  0.93),
    "workflow (extract → validate → draft)":   (3, 5_000, 700, 11, 0.97),
    "agent (explores, calls tools as needed)": (9, 14_000, 600, 48, 0.97),
}
runs_per_month = 60_000
print(f"{'design':<42}{'$/run':>8}{'$/month':>10}{'p95 s':>7}{'acc':>6}")
for name, (calls, tin, tout, p95, acc) in designs.items():
    per_run = calls * (tin * P_IN + tout * P_OUT) / 1e6
    print(f"{name:<42}{per_run:>8.3f}{per_run * runs_per_month:>10,.0f}{p95:>7}{acc:>6.0%}")
```

> [read] On these figures the workflow matches the agent's accuracy at under a fifth of the cost and a quarter of the latency, because the claims process is a known sequence. The agent's extra flexibility buys nothing here. The augmented LLM is cheapest but misses the accuracy target; whether that matters is a requirement question, not a technology one.

### The agentic loop, at architecture level

When you do choose an agent, the loop around it is your responsibility. Three design decisions decide whether it's reliable:

| Decision | Getting it wrong looks like |
|---|---|
| **Stop on `stop_reason`, not on the first tool result** | The loop ends right after a tool runs and returns raw tool output as "the answer" |
| **Keep the full history**: every assistant turn and every `tool_result`, in order | Claude repeats calls or contradicts itself because it never saw what happened |
| **Bound it**: turn limits, budgets, time-outs, and escalation when stuck | Runaway cost, or an agent that loops forever on an impossible task |

```quiz
Q: A team proposes an autonomous agent for invoice processing. The steps are always: extract fields, match the purchase order, flag mismatches, queue for approval. Which pattern fits best?
- [ ] An agent, because it's the most capable pattern
- [x] A workflow, because the steps are known and auditability matters
- [ ] A multi-agent system with one agent per step
- [ ] No Claude at all
why: Fixed, known steps belong in a workflow that code controls: cheaper, faster, more predictable and easier to audit. Claude still does the language-heavy steps such as extraction.
```

```quiz
Q: Which statements about the augmented LLM pattern are true? (Select 2)
- [x] It is a single Claude call enhanced with retrieval, tools or memory
- [ ] It requires a multi-agent framework
- [x] It is often the right starting point when one well-informed step can answer the request

```

## 1.4 | Multi-agent orchestration

A **hub-and-spoke** design puts a **coordinator** at the centre and **subagents** at the spokes. The coordinator plans, delegates, aggregates and handles failures; each subagent does one focused task in its own context. Communication flows through the hub: subagents don't talk to each other.

```seq title="Hub and spoke: everything flows through the coordinator"
Coordinator, Research subagent, Analysis subagent, Writer subagent
Coordinator -> Research subagent: task + context + output format (it knows nothing else)
Research subagent --> Coordinator: findings JSON
Coordinator -> Analysis subagent: findings + question + constraints
Analysis subagent --> Coordinator: analysis + confidence
Coordinator -> Writer subagent: analysis + audience + length
Writer subagent --> Coordinator: draft
note Coordinator: Aggregates, checks coverage, resolves conflicts, returns one answer
```

### Four coordinator responsibilities

| Responsibility | What goes wrong without it |
|---|---|
| **Decompose** into scoped tasks | Overlap, gaps, vague tasks |
| **Pass context explicitly**: task, background, constraints, output format | Subagents guess, because they **have no memory of the coordinator** or of each other |
| **Aggregate**: organise, resolve contradictions, prioritise, check coverage | A final answer missing findings that subagents actually produced |
| **Handle errors** by type | One failed subagent silently drops a section, or the whole run fails for a recoverable error |

> [concept] **Subagents start blank.** In Claude Code and the Agent SDK, a subagent gets its own system prompt, the delegation message the coordinator writes, and project files such as CLAUDE.md, but **not** the coordinator's conversation history. Only its final message comes back. So the delegation message must carry everything: the goal, the relevant facts, file paths, constraints, the expected output. Isolation is deliberate: it keeps subagents predictable and their contexts small.

> [tip] In Claude Code and the Agent SDK, coordinators delegate through the built-in subagent tool, historically named **`Task`** and renamed **`Agent`** in Claude Code 2.1.63 (`Task` still works as an alias). Many study materials say a coordinator must have `Task` in `allowedTools` to delegate; current docs say the tool doesn't prompt for permission either way. The durable lesson: if subagents never run, check that the delegation tool is actually available to the coordinator (not removed by a tool list or a disallow rule) and that subagent descriptions say when to use them.

### Parallel or sequential?

Run subagents in **parallel** when their tasks are independent; run them in **sequence** when one needs another's output. Getting this wrong either wastes time or, worse, has an analysis agent "analysing" results that don't exist yet. A dependency graph settles it. Here's a scheduler that groups tasks into waves that can run together and compares the timing.

```python
TASKS = {   # task: (seconds, depends on)
    "fetch Q3 P&L":        (8, []),
    "fetch Q2 P&L":        (7, []),
    "competitor scan":     (9, []),
    "margin analysis":     (6, ["fetch Q3 P&L", "fetch Q2 P&L"]),
    "risk review":         (5, ["competitor scan"]),
    "executive summary":   (4, ["margin analysis", "risk review"]),
}

def waves(tasks):
    done, out = set(), []
    while len(done) < len(tasks):
        ready = [t for t, (_, deps) in tasks.items() if t not in done and all(d in done for d in deps)]
        if not ready: raise ValueError("cycle in dependencies")
        out.append(ready); done.update(ready)
    return out

plan = waves(TASKS)
for i, w in enumerate(plan, 1):
    print(f"wave {i}: {w}  ({max(TASKS[t][0] for t in w)} s)")
sequential = sum(s for s, _ in TASKS.values())
parallel = sum(max(TASKS[t][0] for t in w) for w in plan)
print(f"\nall in sequence: {sequential} s   in dependency-respecting waves: {parallel} s")
```

> [read] Three fetches have no dependencies and run together; the analyses wait only for what they need; the summary comes last. 39 seconds sequential becomes 19, and nothing ever runs before its inputs exist. (A smarter scheduler would start the risk review as soon as the scan finishes rather than waiting for the whole wave, but waves are easy to reason about and audit.)

### Aggregating, and diagnosing incomplete output

When a coordinator's final answer is missing something, the cause is usually in the orchestration, not the model. Trace it in order: was the topic **assigned** (decomposition)? Did the subagent get the **context** it needed? Did it **return** the finding? Did the coordinator **keep** it when aggregating? Here's a coverage check that runs that trace automatically.

```python
REQUIRED = ["revenue", "margins", "competitors", "staffing risk", "regulatory risk"]
ASSIGNED = {"finance": ["revenue", "margins"], "market": ["competitors"], "risk": ["staffing risk"]}
RETURNED = {"finance": {"revenue": "+12% QoQ", "margins": "31% → 29%"},
            "market": {"competitors": "2 openings within 3 km"},
            "risk": {"error": "permission denied reading HR roster"}}
FINAL = {"revenue": "+12% QoQ", "competitors": "2 openings within 3 km"}

for topic in REQUIRED:
    owner = next((a for a, ts in ASSIGNED.items() if topic in ts), None)
    if owner is None:                        stage = "DECOMPOSITION: never assigned"
    elif "error" in RETURNED.get(owner, {}): stage = f"SUBAGENT ERROR ({owner}): {RETURNED[owner]['error']}"
    elif topic not in RETURNED[owner]:       stage = f"CONTEXT/TASK ({owner}): not returned"
    elif topic not in FINAL:                 stage = "AGGREGATION: returned but dropped"
    else:                                    stage = "ok"
    print(f"{topic:<16} {stage}")
```

> [read] One run, four different failures: margins were found but dropped when the coordinator aggregated; the staffing risk failed on a permission error, so retrying won't help, but asking for access or escalating will; and regulatory risk was never assigned to anyone. "The model missed things" would have been the wrong diagnosis for all of them.

### Handling subagent errors

| Error type | Example | Recovery |
|---|---|---|
| Transient | Timeout, rate limit | Retry with backoff, bounded |
| Invalid output | Missing fields, wrong format | Re-ask with the validation error, once or twice |
| Permission / access | "permission denied" | Don't retry: request access, use another source, or escalate |
| Partial result | 3 of 5 documents analysed | Proceed and report the gap explicitly, or re-run just the missing part |
| Logical failure | Contradicts other subagents | Resolve in aggregation: weigh evidence, or ask a reviewer subagent |

> [concept] **The stakes-proportionate rule.** Claude calibrates how much it trusts an instruction to how much harm acting on it could do. In a multi-agent system, a subagent receiving an unusual, high-impact instruction from a coordinator (or from content it reads) should apply more caution than for a routine one, and so should your design: low-stakes steps can flow automatically; high-stakes ones need verification, approval or a hard control, however confident the upstream agent sounds.

## 1.5 | Decomposition

Ask a model to do five things in one prompt and you often get five mediocre answers. **Task decomposition** breaks a complex objective into smaller subtasks, each with **one clear objective**, defined inputs and a checkable output. It's the skill underneath workflows, prompt chains and multi-agent systems alike.

| Strategy | Split by | Example (quarterly business review) |
|---|---|---|
| **By stage** | Steps of a process | Gather data → analyse → draft → review |
| **By entity** | Independent items | One subtask per clinic, run in parallel |
| **By expertise** | Kinds of judgement | Finance, operations, compliance |
| **By risk** | What can be automated vs needs a person | Auto-draft commentary; human signs off numbers |

> [tip] Good subtasks are **single-objective** (one verb), **self-contained** (everything needed is in the inputs), **checkable** (you can tell if the output is right) and **right-sized** (big enough to be worth a call, small enough to be reliable). Too fine a split adds latency and hand-offs; too coarse brings back the five-things-at-once problem.

Here's a checker for a proposed decomposition: one objective each, defined inputs and outputs, dependencies that exist, and coverage of every requirement.

```python
import re

REQS = {"revenue trend", "margin drivers", "staffing risks", "board-ready summary"}
PLAN = [
    {"id": "A", "objective": "Compute revenue trend per clinic", "inputs": ["P&L Q2", "P&L Q3"], "output": "table", "covers": ["revenue trend"], "after": []},
    {"id": "B", "objective": "Explain margin drivers and draft commentary and check compliance", "inputs": ["A.table"], "output": "text", "covers": ["margin drivers"], "after": ["A"]},
    {"id": "C", "objective": "List staffing risks", "inputs": [], "output": "", "covers": ["staffing risks"], "after": ["D"]},
    {"id": "E", "objective": "Write board summary", "inputs": ["A.table", "B.text", "C.list"], "output": "1-page memo", "covers": ["board-ready summary"], "after": ["A", "B", "C"]},
]

ids = {t["id"] for t in PLAN}
for t in PLAN:
    issues = []
    if len(re.findall(r"\band\b", t["objective"])) >= 1: issues.append("more than one objective")
    if not t["inputs"]: issues.append("no inputs: it will have to guess")
    if not t["output"]: issues.append("no defined output")
    issues += [f"depends on missing task {d}" for d in t["after"] if d not in ids]
    print(f"{t['id']}: {t['objective'][:48]:<48} {'; '.join(issues) or 'ok'}")
covered = {c for t in PLAN for c in t["covers"]}
print("\nuncovered requirements:", sorted(REQS - covered) or "none")
```

> [read] Task B bundles three jobs (explain, draft and check compliance) into one, so it should be split. Task C has no inputs or output and depends on a task "D" that doesn't exist. Coverage is complete, so the problems are in the shape of the tasks, not in what's missing. Catching this at design time is far cheaper than debugging a coordinator that produces "shallow" results.

```quiz
why: Each subtask should have one objective and a checkable output. Splitting analysis, flagging, rewriting and sending lets each be verified, and lets the email (an external action) be gated.
```

## 1.6 | Business value pillars

Architecture decisions are business decisions. The blueprint names the pillars a design must align to: **efficiency** (do the same work faster or with less effort), **transformation** (do things that weren't possible before), **productivity** (more output per person), **cost** (lower cost per unit of work) and **performance SLAs** (meet commitments on speed, availability and quality).

| Pillar | Measured by | Design levers |
|---|---|---|
| Efficiency | Cycle time, handling time | Workflow automation, parallelism, streaming |
| Transformation | New capabilities, new revenue | Agents, new channels, new products |
| Productivity | Cases per person per day | Drafting and summarising with human approval |
| Cost | $ per case, total cost of ownership | Model choice, caching, batching, smaller context |
| Performance SLAs | p95 latency, availability, accuracy floor | Latency budgets, fallbacks, evals, capacity planning |

### A business case, honestly modelled

Here's a 12-month case for the claims assistant. Every figure is an assumption to be replaced with the client's own; the point is the structure, including the costs people forget (human review, evals, operations) and the sensitivity to adoption.

```python
def business_case(adoption, months=12):
    claims = 6_000                          # claims per month
    minutes_saved_per_claim = 38            # when the assistant is used
    staff_cost_per_hour = 900               # ₹, fully loaded
    review_minutes = 6                      # human checking of each AI draft
    run_cost_per_claim = 9                  # ₹: tokens, retrieval, infra
    build = 4_500_000                       # ₹ one-off: design, build, evals, integration
    ops_per_month = 600_000                 # ₹: monitoring, prompt and eval upkeep, on-call, licences
    used = claims * adoption
    saving = used * (minutes_saved_per_claim - review_minutes) / 60 * staff_cost_per_hour
    run = used * run_cost_per_claim
    net_month = saving - run - ops_per_month
    total = net_month * months - build
    payback = build / net_month if net_month > 0 else float("inf")
    return net_month, total, payback

for adoption in (0.3, 0.6, 0.9):
    net, total, payback = business_case(adoption)
    pb = f"{payback:.1f} months" if payback != float("inf") else "never"
    print(f"adoption {adoption:.0%}: net ₹{net:>10,.0f}/month   12-month ₹{total:>12,.0f}   payback {pb}")
```

> [read] At 30% adoption the project loses money over its first year (payback takes about 18 months); at 60% it pays back in about 4. The model's quality matters less to the business case than whether staff actually use it, which makes change management, UX and trust (Module 6) architecture concerns. Human review time is also a real cost, not a footnote: 6 of every 38 minutes saved go straight back into checking drafts.

### Communicating value and limitations

Stakeholders need a balanced picture: where Claude adds value, where it's limited (it can be confidently wrong; it needs good inputs; it doesn't replace accountable decisions), and what stays with people. Overselling creates mistrust after the first visible error; underselling stalls adoption.

```quiz
Q: A business case shows strong savings at 90% adoption but losses at 30%. What should the architect emphasise to sponsors?
- [ ] That a larger model will raise adoption
- [x] That adoption drives the outcome, so the plan needs user involvement, training and trust-building, with adoption tracked as a key metric
- [ ] That the 90% scenario is guaranteed
- [ ] That cost per token is the main risk
why: The sensitivity analysis shows usage, not model price, decides the return. Making adoption a tracked, managed metric is what protects the business case.
```

```quiz
Q: Which business value pillars does a claims assistant that halves cycle time while keeping accuracy above an agreed floor mainly serve? (Select 2)
- [x] Efficiency
- [ ] Transformation
```
