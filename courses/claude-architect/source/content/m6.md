## 6.1 | Structured discovery

Discovery finds out **what problem is being solved, for whom, and what a good outcome looks like in numbers**. It ends when the problem and success measures are written down and the stakeholders agree with them, not when the first demo works.

### Who to talk to, and what they care about

Different stakeholders see different parts of the problem, and have different power to help or block. Map them early.

| Stakeholder | Typically cares about | Ask them |
|---|---|---|
| Executive sponsor | Business outcome, cost, risk, timeline | "What would make this a success in a year?" |
| Process owner / operations | Throughput, exceptions, staffing | "Walk me through the last ten cases. Where does time go?" |
| End users | Usefulness, trust, effort | "What would make you stop using it?" |
| Subject-matter experts | Correctness in edge cases | "Which cases do new staff get wrong?" |
| Security, privacy, legal, compliance | Data, access, regulation, liability | "What data may never leave which boundary?" |
| IT / platform | Integration, operations, support | "Who runs it at 2 a.m.?" |

```python
STAKEHOLDERS = [  # name, power 1–5, interest 1–5, main concern
    ("CFO (sponsor)", 5, 4, "cost per claim, payback"),
    ("Head of claims operations", 4, 5, "cycle time, staffing"),
    ("Claims adjusters", 2, 5, "trust, extra review work"),
    ("CISO", 5, 2, "PHI handling, vendor risk"),
    ("Legal & compliance", 4, 3, "IRDAI rules, audit trail"),
    ("Customer service team", 2, 2, "fewer 'where is my claim' calls"),
]

def quadrant(power, interest):
    if power >= 4 and interest >= 4: return "manage closely"
    if power >= 4:                   return "keep satisfied"
    if interest >= 4:                return "keep informed"
    return "monitor"

for name, p, i, concern in sorted(STAKEHOLDERS, key=lambda s: (-s[1], -s[2])):
    print(f"{quadrant(p, i):<15} {name:<28} {concern}")
```

> [read] The CISO has high power but low day-to-day interest: easy to under-engage until a late security review blocks the launch. "Keep satisfied" means bringing them the data-flow diagram in week two, not week twelve. The adjusters have little formal power but decide adoption, which the business case in Module 1 showed is what drives the return.

### Discovery that produces numbers

```python
QUESTIONS = {  # area: (question, answer or None, critical?)
    "process":     ("Current steps and handoffs for a claim", "7 steps; 3 handoffs; doc review takes 40%", True),
    "volume":      ("Claims per day, peak vs average", "6,000/month; Monday peak 2.3×", True),
    "baseline":    ("Current cycle time and error rate", "9 days median; 6% rework", True),
    "success":     ("Target outcome, in numbers", "median under 5 days; accuracy ≥97% on fields", True),
    "data":        ("Where documents live; formats; languages", "S3 PDFs; English, Hindi, Marathi", True),
    "constraints": ("Regulatory, residency, retention", None, True),
    "decision":    ("Who may approve payouts", "licensed adjusters only", True),
    "exceptions":  ("Which cases must always go to people", None, False),
    "integration": ("Systems to read from / write to", "core claims system (read), document store", False),
}
answered = [k for k, (_, a, _) in QUESTIONS.items() if a]
blocking = [k for k, (_, a, crit) in QUESTIONS.items() if a is None and crit]
print(f"answered {len(answered)}/{len(QUESTIONS)}")
print("blocking design (critical, unanswered):", blocking or "none")
print("open but not blocking:", [k for k, (_, a, c) in QUESTIONS.items() if a is None and not c])
```

> [read] Discovery isn't finished: constraints (regulation, residency, retention) are unanswered, and that's a critical gap. Designing before it's answered risks rework when legal finally weighs in. Note how every answered question is a number or a named fact, never "faster" or "better".


## 6.2 | Communicating decisions and trade-offs

Every significant architecture decision has alternatives and costs. Record it in an **architecture decision record (ADR)**: what was decided, why, what else was considered, and what it costs. ADRs make decisions reviewable, keep them from being relitigated every month, and tell future teams what would make them worth revisiting.

```file title="docs/adr/0007-workflow-not-agent-for-claims-intake.md" lang=markdown
# ADR 0007: Use a fixed workflow, not an autonomous agent, for claims intake

Status: Accepted (2026-10-21) · Owner: Claims platform architect

## Context
6,000 claims/month; steps are fixed (extract → validate → draft → adjuster approves).
Requirements: field accuracy ≥ 97%, p95 ≤ 11 s per document pack, every payout approved by an adjuster.

## Decision
Implement as a workflow: Claude Sonnet 5.5 (pinned) for extraction and drafting with structured outputs;
validation and routing in code; adjuster approval in the existing claims UI.

## Alternatives considered
- Augmented LLM (single call): 93% accuracy in eval: below the 97% floor.
- Autonomous agent: 97% accuracy but ~6× the cost and p95 of 48 s; harder to audit.

## Consequences
+ ≈ $15,300/month less model spend than the agent design ($3,060 vs $18,360); predictable, auditable steps.
− New claim types need a code change, not just a prompt change.
Revisit if: claim types become open-ended, or the workflow's accuracy falls below 97% on the eval set.
```

### Same decision, different audiences

Explain the decision in each audience's currency. Executives want outcomes, cost and risk; security wants data flows and controls; engineers want interfaces and constraints; operations wants runbooks and failure modes. Here's one decision record rendered for three audiences.

```python
DECISION = {
    "what": "fixed workflow on Claude Sonnet 5.5, adjuster approves every payout",
    "outcome": "median settle time 9 → under 5 days", "cost": "≈ $3,060 a month in model usage",
    "rejected": "autonomous agent: same accuracy, about 6× the cost and 4× slower",
    "risk": "a new claim type needs a code change, about 2 weeks",
    "data": "documents stay in the India region; PHI redacted from logs; no data used for training",
    "controls": "no payout tool; per-user authorisation; audit trail with model and prompt versions",
    "interfaces": "POST /claims/{id}/extract returns the 14-field schema v3; p95 ≤ 11 s; retries 2×",
}
VIEWS = {
    "executive": ["what", "outcome", "cost", "rejected", "risk"],
    "security":  ["what", "data", "controls"],
    "engineering": ["what", "interfaces", "risk", "rejected"],
}
for audience, fields in VIEWS.items():
    print(f"── for {audience}")
    for f in fields:
        print(f"   {f}: {DECISION[f]}")
```

> [tip] Lead with the recommendation and the one or two numbers that justify it; put the detail in an appendix. State trade-offs plainly, including what you're giving up. Stakeholders trust an architect who names the costs more than one who only sells the benefits. And be honest about Claude's limits: it can be confidently wrong; people stay accountable for decisions.

## 6.3 | Feedback loops and SLAs

### SLIs, SLOs and SLAs

| Term | What it is | Example |
|---|---|---|
| **SLI** (indicator) | A measurement, defined precisely | Share of requests answered successfully; p95 total latency measured at the API gateway |
| **SLO** (objective) | A target for an SLI over a period | 99.5% successful over a calendar month; p95 ≤ 8 s |
| **SLA** (agreement) | An SLO written into a contract **with a consequence** | Below 99.5% → 10% service credit for the month |

A workable SLA names the indicator and how it's calculated, the target and period, the **exclusions** (planned maintenance, misuse, customer-side outages), who reports it and how often, and the consequence. Latency targets need a **percentile** and a **measurement point**; averages hide the slow requests users complain about.

> [concept] **Quality is harder to promise than uptime.** Availability and latency can be measured on every request. Output quality can't be fully observed in real time, so quality commitments are usually expressed as **evaluated** targets (e.g. "≥ 95% on the agreed eval set, re-run monthly and after every change"), backed by sampled review in production. Don't sign an SLA on a number nobody measures.

Here's a month's SLA report computed from daily figures, with exclusions applied as the contract defines them.

```python
DAYS = [  # requests, failures, p95_ms, maintenance_window?
    *[(40_000, 120, 6_200, False)] * 26,
    (40_000, 2_900, 9_800, False),      # incident: provider overload
    (38_000, 140, 6_400, True),         # planned maintenance (excluded)
    (41_000, 110, 6_100, False), (39_500, 135, 7_900, False),
]
SLO_SUCCESS, SLO_P95 = 0.995, 8_000
counted = [d for d in DAYS if not d[3]]
reqs = sum(d[0] for d in counted); fails = sum(d[1] for d in counted)
success = 1 - fails / reqs
p95_breach_days = sum(d[2] > SLO_P95 for d in counted)

print(f"success rate (excl. maintenance): {success:.3%}  target {SLO_SUCCESS:.1%}  → {'MET' if success >= SLO_SUCCESS else 'MISSED'}")
print(f"days with p95 > {SLO_P95:,} ms: {p95_breach_days} of {len(counted)}")
credit = 0.10 if success < SLO_SUCCESS else 0.0
print(f"service credit due: {credit:.0%}")
```

> [read] One bad day (a provider overload) pulls the month's success rate to 99.46%, just under the 99.5% objective, so a 10% credit is due. The maintenance day doesn't count, because the contract excludes it. That one day was also the only latency breach. The design lessons: an availability SLA on top of an external model provider needs fallbacks (another region or platform, or a degraded mode), and the SLO you promise must sit below what your dependencies can deliver.

### The stakeholder feedback loop

Collect feedback → decide what to change → change it → **tell people what happened**. Without the last step, people stop giving feedback. Combine **implicit** signals (thumbs down, edited drafts, abandoned sessions, hand-offs to people) with **explicit** ones (expert reviews, structured reports from support teams). A single report is a lead, not a measurement: group and count before acting.

```seq title="The feedback loop, closed"
Users and experts, Product owner, Eval set, Release
Users and experts -> Product owner: thumbs-down, edited drafts, expert reviews, support reports
note Product owner: Group and count: 5× wrong amount, 4× missed exception
Product owner -> Eval set: add the failing cases (they fail today)
Eval set -> Release: fix passes old and new cases
Release --> Users and experts: "You reported X; here's what changed"
```

```python
REPORTS = ["wrong amount", "too long", "wrong amount", "missed hospitalisation exception", "slow", "wrong amount",
           "too long", "missed hospitalisation exception", "missed hospitalisation exception", "slow", "wrong amount",
           "tone too formal", "missed hospitalisation exception", "wrong amount"]
TRAFFIC = 6_000
from collections import Counter
counts = Counter(REPORTS)
for issue, n in counts.most_common():
    action = "add failing cases to eval set; fix" if n >= 4 else ("watch" if n >= 2 else "log")
    print(f"{n:>3}  {issue:<34} {n / TRAFFIC:.2%} of claims   → {action}")
```

> [read] "Wrong amount" and the missed hospitalisation exception dominate, and each becomes a set of eval cases before any fix. The one "tone too formal" report is logged, not acted on: one memorable complaint and a widespread problem look the same in an inbox until you count. Close the loop by telling the reporters what changed.

```quiz

- [ ] No quality commitment at all

why: Real-time accuracy can't be measured on every response, so quality commitments should rest on an agreed evaluation method. Availability and latency are measured directly.
```

```quiz
- [x] A percentile (e.g. p95) and the measurement point (e.g. at the API gateway)
```

## 6.4 | Architecture documentation and implementation guidance

Two documents, two jobs. **Architecture documentation** explains how the system is designed: components and responsibilities, the request flow, integrations and data sources, boundaries, and the constraints it must meet. **Implementation guidance** tells the build team what to do: the order of work, the interfaces and formats others depend on, configuration that must match, standards, and, crucially, **which decisions are fixed and which they can make locally**.

AI systems need items that generic templates miss:

| Item | Why it matters |
|---|---|
| Model and **exact version** called, per route | Behaviour, cost and limits depend on it |
| Where prompts and templates live, and how they're versioned | Prompts are logic; changes are releases |
| How context is assembled: retrieval sources, filters, what's included per request | Most quality issues trace to context |
| Eval set, metrics and **thresholds** to meet | Defines "done" and gates future changes |
| Fallback behaviour when the model or a tool fails | Keeps SLAs and user trust |
| Human review and approval points | Governance and accountability |
| Owner after handoff | A system without an owner stops being maintained |

```file title="docs/implementation-guidance.md (excerpt)" lang=markdown
## Fixed decisions (change only via ADR)
- Model: claude-sonnet-5-5 for extraction and drafting; claude-haiku-5-5 for routing. Pinned in config/models.yaml.
- Output: structured outputs against schemas/claim_fields.v3.json. No free-text parsing.
- Payouts: never callable by the AI path. Adjuster approval via the claims UI only.

## Team decisions (local)
- Internal module structure, test framework, logging library.

## Build order
1. Ingestion + chunking (heading-aware) + index with access metadata.
2. Extraction route + eval harness (eval/claims_v12, 502 items). Gate: F1 ≥ 0.97.
3. Draft route + adjuster UI integration. Gate: adjuster acceptance ≥ 85% in pilot.
4. Monitoring: traces with model + prompt version; burn-rate alerts; sampled judge.

## Failure behaviour
- Model 429/5xx: retry 2× with backoff, then queue and show "processing, about 15 min".
- Validation failure: one retry with the error; then route to manual review.
```

Here's a completeness check for a design document, the kind of gate worth running before handoff.

```python
REQUIRED_SECTIONS = ["components", "request flow", "integrations", "constraints", "model and version",
                     "prompt location and versioning", "context assembly", "eval set and thresholds",

doc = """# Claims assistant: architecture
## Components ... ## Request flow ... ## Integrations ... ## Constraints ...
## Model and version: claude-sonnet-5-5 ... ## Context assembly ... ## Eval set and thresholds ...
## Human review points ..."""

present = [s for s in REQUIRED_SECTIONS if s in doc.lower()]
missing = [s for s in REQUIRED_SECTIONS if s not in present]
```

> [read] The design document covers the system well but omits three things a build and run team needs: where prompts live and how they're versioned, what happens when the model or a tool fails, and who owns the system after handoff. The last one is the most expensive to discover late.

## 6.5 | The solution life cycle

An AI solution moves through five phases. Each produces what the next one needs, and the last feeds back into the first: it's a cycle, not a project plan.

```flow title="Life-cycle phases and their exit criteria"
Discovery | Exit: problem, users, baseline and numeric success measures written down and agreed.
Design | Exit: architecture, model and prompting approach, cost and latency estimates, and the evaluation plan.
Handoff | Exit: docs, implementation guidance, eval set, fixed vs local decisions, and a named owner.
Monitoring | From first real traffic: quality vs eval criteria, errors, latency, cost, review load, with thresholds.
Iteration | Failures become eval cases; changes go through evals; model upgrades are migrations.
```

```seq title="Handoff: what moves from architect to the owning team"
Architect, Build team, Run team (owner)
Architect -> Build team: architecture docs, implementation guidance, ADRs, eval set v12
Build team --> Architect: questions resolved; fixed vs local decisions clear
Build team -> Run team (owner): system, runbooks, dashboards, alert thresholds
Architect -> Run team (owner): monitoring plan, iteration triggers, model migration policy
note Run team (owner): Owns the system from here, including its feedback loop
```

### Iteration triggers

Monitoring is only useful if crossing a threshold *does* something. Define, at handoff, which signals trigger which action.

```python
TRIGGERS = [  # metric, current, threshold, direction, action
    ("eval pass rate (monthly re-run)", 0.952, 0.95, "below", "investigate; block releases until restored"),
    ("judge pass rate, live sample", 0.91, 0.93, "below", "pull failing traces; add cases; fix"),
    ("human review load (items/day)", 610, 540, "above", "recalibrate thresholds or add reviewers"),
    ("cost per settled claim (₹)", 3.4, 4.0, "above", "check cache hits and retries"),
    ("days to model deprecation", 75, 90, "below", "start migration: evals on the successor model"),
]
for metric, cur, thr, direction, action in TRIGGERS:
    fired = cur < thr if direction == "below" else cur > thr
    print(f"{'FIRED' if fired else 'ok   '}  {metric:<32} {cur:<7} ({direction} {thr})  {action if fired else ''}")
```

> [read] Three triggers fire: live quality is slipping, reviewers are over capacity, and the pinned model is within 90 days of deprecation, so the migration (evals on the successor, prompt re-tuning, staged rollout) starts now, not in week twelve. The monthly eval still passes, which is exactly why a live quality signal is needed alongside it.

### Configuration management across the life cycle

Behaviour is set by configuration as much as by code: the **model version** (pinned, never an alias), the **prompt version** (templates in version control, logged per call), and, for teams using Claude Code, **CLAUDE.md** (shared instructions) and **settings.json** (enforced permissions and settings). Changes to any of them are releases: reviewed, evaluated, and recorded.

```quiz
Q: At handoff, which item is most often missing and most costly later?
- [ ] An extra architecture diagram
- [x] A named owner for the running system, with the monitoring plan and iteration triggers they're responsible for
- [ ] A larger eval set

why: Without an owner, alerts go unanswered, feedback isn't acted on and the system degrades. Ownership is part of the handoff, not an afterthought.
```
