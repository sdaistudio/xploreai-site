## 4.1 | Time-series components and ARIMA models

Every time-series project in this course follows the same opening routine:

1. **Declare** the data as a time series with `ts()`.
2. **Plot** it.
3. **Test** for stationarity with ADF.
4. **Transform** it if it's non-stationary (difference it, or take log differences).
5. **Re-test** the transformed series.
6. Only then **forecast** or **test causality**.

### ARIMA(p, d, q): forecasting a series from its own past

A **univariate** model predicts a series using nothing but its own history, such as NIFTY's next 20 days or GDP's next 12 quarters.

| Part | Meaning | Equation piece |
|---|---|---|
| **AR(p)** | Autoregressive: today depends on the last *p* values | φ₁yₜ₋₁ + … + φₚyₜ₋ₚ |
| **I(d)** | Integrated: difference *d* times to make it stationary | Δᵈyₜ |
| **MA(q)** | Moving average: today depends on the last *q* forecast errors | θ₁εₜ₋₁ + … + θ_qεₜ₋_q |

Choosing p, d and q by hand means trying (1,1,0), (0,1,1), (2,1,1) and so on, then keeping the model with the lowest AIC. `forecast::auto.arima()` does that search for you.

### Regression is not causality

Yₜ = α + βXₜ + εₜ links two things that happen **at the same time**. For X to **cause** Y, X has to come **first**:

**Yₜ = α + Σ φᵢ Yₜ₋ᵢ + Σ βⱼ Xₜ₋ⱼ + εₜ**

There are three rules: test **both directions** (X → Y and Y → X), test the **short run and the long run**, and always include Y's own lags, because a good causality model is autoregressive.

### Choosing the causality framework

| Stationarity of the series | Framework | Session |
|---|---|---|
| All stationary at level, I(0) | **Granger causality + VAR** | 4.3–4.4 |
| All I(1), stationary after one difference | **Johansen cointegration + VECM** | 4.5 |
| A mix of I(0) and I(1) | **ARDL bounds test** | 4.6 |

## 4.2 | ARIMA in R: forecasting airline passengers

```r
url <- "https://xploreai.co.in/courses/fda-r/data/"
rust <- "#E2571B"; espresso <- "#4A4238"
AP <- read.csv(paste0(url, "AirPassengers.csv"))
AP_T <- ts(AP$Passengers, frequency = 12, start = c(1949, 1))

library(urca)
summary(ur.df(AP_T))@teststat                  # level: above -1.95, so non-stationary
summary(ur.df(diff(AP_T)))@teststat            # first difference: stationary
```

### Let auto.arima choose the model

Give `auto.arima()` the **level** series. It tests and picks the number of differences (d) itself.

```r eval=false
install.packages("forecast")
```

```r
library(forecast)
model <- auto.arima(AP_T)
model
```

> [read] The model is ARIMA(2,1,1)(0,1,0)[12]. The non-seasonal part is **2 AR terms, 1 difference and 1 MA term**, and the `(0,1,0)[12]` adds a **seasonal difference**: this January minus last January. In words, the change in passengers depends on the last two months' changes plus last month's forecast error, measured against the same month a year earlier.

### Forecast four years ahead

The forecast horizon `h` is counted in the data's own units: 48 months is 4 years.

```r
F <- forecast(model, h = 48)
head(as.data.frame(F), 6)
```

```r h=4.6
autoplot(F, fcol = rust) +
  ggplot2::labs(title = "Airline passengers: ARIMA forecast, 1961-64", x = NULL, y = "Passengers ('000)") +
  ggplot2::theme_minimal(base_size = 12)
```

> [read] The orange line is the **point forecast**. The darker band is the **80%** interval and the lighter band the **95%** interval. Both widen as you look further ahead, because uncertainty compounds.

### Is the model any good? Check the residuals

```r h=5
checkresiduals(model)
```

> [read] Good residuals look like white noise: no pattern over time, no ACF spikes outside the blue lines, and a roughly bell-shaped histogram. The **Ljung–Box** test's H₀ is "no autocorrelation left", so you want a p-value **above** 0.05. Here p ≈ 0.014, so some structure is left over, and the residuals also fan out over time.

> [try] Fit `auto.arima(log(AP_T))` instead. The log stabilises the growing seasonal swings, the residual check improves, and `forecast()` still works: just wrap the results in `exp()` to get passengers back.

## 4.3 | Causality with VAR, part 1: stationarity, lags and Granger

Does the Bitcoin **spot** market lead the **futures** market, or the other way round? Start with **returns**.

```r
bitcoin <- read.csv(paste0(url, "bitcoin.csv"))
spot_R_T   <- ts(bitcoin$Spot_Returns,   frequency = 252, start = c(2017, 245))
future_R_T <- ts(bitcoin$Future_Returns, frequency = 252, start = c(2017, 245))
```

> [tip] The `start` and `frequency` arguments only label the x-axis. Being a few days off doesn't change anything statistical. For daily trading data, about 252 days a year is standard.

```r h=5.4
par(mfrow = c(2, 1), mar = c(2.5, 4, 2.5, 1))
plot(spot_R_T,   col = rust,     main = "Bitcoin spot returns",    ylab = "")
plot(future_R_T, col = espresso, main = "Bitcoin futures returns", ylab = "")
par(mfrow = c(1, 1))
```

### Step 1: both must be stationary

```r
summary(ur.df(spot_R_T))@teststat
summary(ur.df(future_R_T))@teststat
```

> [read] Both statistics are far below the 5% critical value of −1.95, so both return series are **I(0)**. That makes this a job for **Granger causality and VAR**.

### Step 2: choose the lag length

```r eval=false
install.packages(c("vars", "lmtest"))
```

```r
library(vars)
VARselect(spot_R_T,   lag.max = 10)$selection
VARselect(future_R_T, lag.max = 10)$selection
```

> [read] AIC, HQ, SC (Schwarz/BIC) and FPE are four information criteria. When they disagree, this course goes with **AIC**. The lag always comes from the **effect** (dependent) variable.

### Step 3: Granger causality in both directions

In `grangertest(effect ~ cause, order = k)` the effect goes on the left. H₀: *the cause does not Granger-cause the effect*.

```r
library(lmtest)
lag_spot   <- VARselect(spot_R_T,   lag.max = 10)$selection[["AIC(n)"]]
lag_future <- VARselect(future_R_T, lag.max = 10)$selection[["AIC(n)"]]
grangertest(future_R_T ~ spot_R_T,   order = lag_future)   # does spot lead futures?
grangertest(spot_R_T   ~ future_R_T, order = lag_spot)     # does futures lead spot?
```

> [read] A **p < 0.05** means reject H₀, so causality runs in that direction. If one direction is significant and the other isn't, causality is **unidirectional**. If both are significant, it's **bidirectional** (feedback).

## 4.4 | Causality with VAR, part 2: estimating and reading the VAR

A VAR fits one equation for each variable, each regressed on the lags of every variable. In `VAR(data.frame(Y, X))` the **first** column is the one you treat as the effect.

```r
model1 <- VAR(data.frame(future = future_R_T, spot = spot_R_T),
              type = "const", lag.max = 5, ic = "AIC")
model1$p                                         # lag chosen by AIC
round(coef(model1)$future, 4)                    # the futures equation only
```

> [read] Read **only the first equation**, the one for futures.
> **`future.l1`, `future.l2`, …** are futures' own lags. That's the autoregressive part, **not causality**, so ignore them for this question.
> **`spot.l1`, `spot.l2`, …** are the causality evidence. A significant positive `spot.l1` means that when spot returns rise today, futures returns tend to rise tomorrow.

```r
model2 <- VAR(data.frame(spot = spot_R_T, future = future_R_T),
              type = "const", lag.max = 5, ic = "AIC")
round(coef(model2)$spot, 4)                       # the spot equation only
```

### A picture of causality: impulse responses

An impulse-response function (IRF) traces how one series reacts over the next few days to a one-standard-deviation shock in the other.

```r h=4.4
ir <- irf(model1, impulse = "spot", response = "future", n.ahead = 8, boot = TRUE, runs = 200)
plot(ir, main = "Futures returns after a shock to spot returns", col = rust)
```

> [read] The x-axis counts days after the shock, starting at 1 for the shock day itself. Futures barely move on the shock day, then jump about **1.2 percentage points the next day**, and the effect has died out within two to three days. The dashed lines are a 95% bootstrap band: wherever it excludes zero, the response is significant. This is spot leading futures by roughly one day.

## 4.5 | Causality with VECM: when prices share a long-run path

Prices, unlike returns, are usually **I(1)**. If two I(1) prices are tied together in the long run, they are **cointegrated**: they can drift apart briefly, but an error-correction force pulls them back.

```r
BS_T <- ts(bitcoin$Spot_Price,   frequency = 252, start = c(2017, 245))
BF_T <- ts(bitcoin$Future_Price, frequency = 252, start = c(2017, 245))
ts.plot(BS_T, BF_T, col = c(rust, espresso), lwd = c(2, 1), ylab = "USD",
        main = "Bitcoin spot (orange) and futures (dark) prices")
```

### Step 1: both prices are I(1)

```r
c(spot_level   = summary(ur.df(BS_T))@teststat,
  spot_diff    = summary(ur.df(diff(BS_T)))@teststat,
  future_level = summary(ur.df(BF_T))@teststat,
  future_diff  = summary(ur.df(diff(BF_T)))@teststat)
```

> [read] Both levels sit above −1.95, so they're non-stationary. Both first differences sit far below it, so they're stationary. **Both prices are I(1)**, which points to Johansen and VECM.

### Step 2: lag length on the differenced series

```r
VARselect(data.frame(diff(BF_T), diff(BS_T)), lag.max = 10, type = "const")$selection
```

### Step 3: the Johansen cointegration test

```r
jo <- ca.jo(data.frame(future = BF_T, spot = BS_T), type = "trace", ecdet = "const", K = 5)
summary(jo)
```

> [read] Look at the row **r = 0**. If the test statistic is **greater** than the 5% critical value, reject "no cointegration": the prices share a long-run relationship. Then check **r <= 1**: if you can't reject it, there is exactly **one** cointegrating vector. Without cointegration a VECM makes no sense; you'd use a VAR on differences instead (Session 6.2).

### Step 4: estimate the VECM

`cajorls()` turns the Johansen result into the error-correction regressions.

```r
vecm <- cajorls(jo, r = 1)
vecm$beta                                        # the long-run (cointegrating) relationship
summary(vecm$rlm)$`Response future.d`$coefficients[1:6, ]
```

> [read] Read the futures equation (`future.d`).
> **`ect1`** is the error-correction term. If it's **negative and significant**, futures adjust back towards the long-run relationship, which means **long-run causality from spot to futures**.
> **`spot.dl1 … spot.dl4`** are the lagged changes in spot. If they're significant, there's **short-run causality** from spot to futures.

```r
summary(vecm$rlm)$`Response spot.d`$coefficients[1:6, ]
```

> [read] The spot equation's `ect1` is **positive**. The long-run relation is normalised on futures (ECT = futures − 1.003 × spot), so when futures trade above spot, a positive loading pushes **spot up** towards futures. Both markets close the gap, but futures do most of the work (−0.60 vs +0.33). Price discovery happens mainly in spot, which is the same story the Granger test told.

> [warn] Some of this lead comes from **timing**. Yahoo's Bitcoin spot "close" is midnight UTC, while CME futures settle at 4 pm Chicago time, so the two closes aren't simultaneous. Always check whether a lead–lag result could just be a clock mismatch. It's the same issue you'll meet with NIFTY and the S&P 500 in Session 6.2.

> [tip] The lecture uses `tsDyn::VECM(data, lag = 5, r = 1, estim = "ML")`, which gives the same model with a different printout. `cajorls()` ships with **urca**, so there's nothing extra to install.

## 4.6 | Causality with ARDL: when the orders of integration are mixed

What if one series is I(0) and the other I(1)? Spot **returns** are I(0) and futures **prices** are I(1). VAR needs everything I(0), and VECM needs everything I(1). **ARDL** (autoregressive distributed lag) works with the mix, and it has two more advantages:

- Y and X can have **different** lag lengths.
- The **current** value Xₜ can enter the model.

**Yₜ = α + Σ φᵢ Yₜ₋ᵢ + β₀Xₜ + Σ βⱼ Xₜ₋ⱼ + εₜ**

### The long run: the Pesaran–Shin–Smith bounds test

| F statistic | Conclusion |
|---|---|
| Below the I(0) lower bound | No cointegration |
| Above the I(1) upper bound | Cointegration, so check the error-correction term |
| In between | Inconclusive |

```r eval=false
install.packages("dLagM")
```

```r
library(dLagM)
btc <- data.frame(Spot_Return = bitcoin$Spot_Returns, Future_Price = bitcoin$Future_Price)
bound1 <- ardlBound(data = btc, formula = Spot_Return ~ Future_Price, case = 3,
                    p = data.frame(Spot_Return = 1, Future_Price = 5))
```

> [read] `p` sets the lag of each variable: **1** for the effect (spot returns) and **5** for the cause (futures prices). Older versions of dLagM took these as separate `p =` and `q =` arguments, as in the lecture. `case = 3` means an unrestricted intercept and no trend, which suits returns that fluctuate around a constant mean. Type `?ardlBound` to see all five cases.
> The **F-statistic (about 542)** is far above the 1% upper bound (7.84), so the series are **cointegrated**. In the error-correction model, **`ec.1` is negative and highly significant**, which means **long-run causality from futures prices to spot returns**. The function also prints residual diagnostics (Breusch–Godfrey, Breusch–Pagan, Shapiro–Wilk and RESET) before the bounds test. Fat-tailed Bitcoin returns fail normality, which is the norm for daily financial data.

### The short run: the distributed-lag model

```r
dlm1 <- ardlDlm(x = btc$Future_Price, y = btc$Spot_Return, p = 5, q = 1)
summary(dlm1)$coefficients
```

> [read] **`X.t`** (today's futures price) and **`X.1` … `X.5`** (its lags) are the causality terms. If they're significant, futures prices drive spot returns in the short run. **`Y.1`** is the autoregressive term.

> [concept] **Module 4 in one line:** all I(0) → **Granger + VAR**. All I(1) → **Johansen + VECM**. Mixed → **ARDL**. Whatever you pick, test **both directions**, separate the **short run** from the **long run**, and never confuse a series' own lags with causality.
