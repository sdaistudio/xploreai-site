Session 8.1

Tool use end to end

Claude never runs a tool itself. It reads the tool definitions you send, decides a tool is needed, and returns a structured request (a tool_use block). Your code, or Anthropic's servers for server tools, does the work and sends the result back. Tool use is a contract: Claude does the reasoning; the system does the execution.

A tool definition (sent in the tools array)
{
  "name": "check_slots",
  "description": "List free appointment times for one doctor on one day at Sunrise Clinic. Use it before offering or booking any appointment. Returns times as HH:MM in IST; an empty list means fully booked.",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": {
      "doctor": { "type": "string", "description": "Doctor's name as in the rota, e.g. \"Dr Rao\"" },
      "date":   { "type": "string", "format": "date", "description": "ISO date, e.g. 2026-10-30" }
    },
    "required": ["doctor", "date"],
    "additionalProperties": false
  }
}

Client tools and server tools

ExamplesYour database lookups, booking API, email senderWeb search, web fetch, code execution
Who executesYour code, after a tool_use block arrivesAnthropic's infrastructure, inside the same request
In the responseA tool_use block; stop_reason: "tool_use"A server_tool_use block followed by its result block (e.g. web_search_tool_result); you return nothing for it
Defined byA name, description and JSON Schema you writeA typed entry such as {"type": "web_search_20260209", "name": "web_search"}
LoopYou run it and return a tool_resultResults come back as blocks in the response; a long turn may stop with pause_turn, and you send it back to continue
ErrorsReturn is_error: true with a useful messageArrive as error objects inside result blocks, not exceptions

Dispatching tool calls safely

A dispatcher maps tool names to functions, validates inputs before running anything, runs independent calls in parallel, and returns every result in one user message. Here's one, run on a response that asks for three tools at once, one of them malformed and one unknown.

Python
import json, re, time
from concurrent.futures import ThreadPoolExecutor

def check_slots(doctor, date):
    time.sleep(0.2)                                   # pretend network call
    return {"Dr Rao": ["10:30", "11:15"], "Dr Iyer": []}.get(doctor, [])

def get_invoice(invoice_no):
    time.sleep(0.2)
    return {"INV-88213": {"amount": 850, "status": "paid twice"}}[invoice_no]

REGISTRY = {
    "check_slots": (check_slots, {"doctor": str, "date": r"^\d{4}-\d{2}-\d{2}$"}),
    "get_invoice": (get_invoice, {"invoice_no": r"^INV-\d{5}$"}),
}

def validate(args, spec):
    for field, rule in spec.items():
        if field not in args: return f"missing required field '{field}'"
        v = args[field]
        if rule is str and not isinstance(v, str): return f"'{field}' must be a string"
        if isinstance(rule, str) and not re.fullmatch(rule, str(v)): return f"'{field}'={v!r} doesn't match {rule}"
    extra = set(args) - set(spec)
    return f"unexpected field(s) {sorted(extra)}" if extra else None

def run_one(block):
    name, args = block["name"], block["input"]
    if name not in REGISTRY:
        return {"type": "tool_result", "tool_use_id": block["id"], "is_error": True,
                "content": f"Unknown tool '{name}'. Available: {sorted(REGISTRY)}"}
    fn, spec = REGISTRY[name]
    problem = validate(args, spec)
    if problem:
        return {"type": "tool_result", "tool_use_id": block["id"], "is_error": True, "content": f"Invalid input: {problem}"}
    try:
        return {"type": "tool_result", "tool_use_id": block["id"], "content": json.dumps(fn(**args))}
    except Exception as e:
        return {"type": "tool_result", "tool_use_id": block["id"], "is_error": True, "content": f"{type(e).__name__}: {e}"}

response_content = [
    {"type": "text", "text": "Let me check both doctors and your invoice."},
    {"type": "tool_use", "id": "tu_1", "name": "check_slots", "input": {"doctor": "Dr Rao", "date": "2026-10-30"}},
    {"type": "tool_use", "id": "tu_2", "name": "check_slots", "input": {"doctor": "Dr Iyer", "date": "30/10/2026"}},
    {"type": "tool_use", "id": "tu_3", "name": "get_invoice", "input": {"invoice_no": "INV-88213"}},
    {"type": "tool_use", "id": "tu_4", "name": "refund_all", "input": {}},
]
calls = [b for b in response_content if b["type"] == "tool_use"]
t0 = time.time()
with ThreadPoolExecutor() as pool:
    results = list(pool.map(run_one, calls))          # order preserved, run concurrently
print(f"{len(calls)} calls in {time.time() - t0:.1f}s\n")
for r in results:
    print(f"{r['tool_use_id']}  {'ERROR ' if r.get('is_error') else 'ok    '}{r['content']}")
next_message = {"role": "user", "content": results}
print("\nall results in one user message:", len(next_message["content"]), "tool_result blocks")
Output · produced by running this code
4 calls in 0.2s

tu_1  ok    ["10:30", "11:15"]
tu_2  ERROR Invalid input: 'date'='30/10/2026' doesn't match ^\d{4}-\d{2}-\d{2}$
tu_3  ok    {"amount": 850, "status": "paid twice"}
tu_4  ERROR Unknown tool 'refund_all'. Available: ['check_slots', 'get_invoice']

all results in one user message: 4 tool_result blocks
How to read it

The two valid lookups ran side by side (about 0.2 s in total, not 0.4). The badly formatted date was rejected before anything ran, with a message that says exactly what's wrong so Claude can fix it, and the unknown tool lists what is available. Nothing crashed, and every tool_use_id got its answer.

Tip

On current models, use strict: true on tool definitions to guarantee schema-valid inputs. Your own validation still matters for business rules a schema can't express. Forcing a specific tool with tool_choice is rejected by Claude Opus 5.5, Sonnet 5.5 and Fable 5.1; use auto and say in the prompt which tool to use, and check that it was called.

Practice questionWhich statement about tool use in the Claude API is correct?

Client tools run in your code; Claude only asks. Server tools such as web search run on Anthropic's side. All of a turn's results go back together in one user message.

Practice questionClaude calls a tool with an input that fails your validation. What should your dispatcher do?

A precise error lets the model fix its own input on the next turn. Running bad input is unsafe, crashing breaks the user's task, and dropping the call leaves an unanswered tool_use, which the API rejects.

Tool descriptions and errors

Claude chooses tools by reading their names and descriptions. A vague description is the most common reason an agent calls the wrong tool, calls none, or passes the wrong input. A production-grade description has five parts:

ElementExample for lookup_order
1. What it does, in one precise sentence"Looks up one order by its order number or tracking ID."
2. Inputs and their formats"order_ref: an order number like ORD-104233, or a tracking ID like BD123456789IN."
3. Example queries it handles"'Where's my order ORD-104233?', 'Has BD123456789IN shipped?'"
4. Edge cases and limits"Orders older than 2 years aren't available. Returns not_found for unknown references; ask the user to check the number."
5. Boundaries: when to use it vs similar tools"For customer details use get_customer; for refunds use refund_status."

Spotting tools Claude will confuse

When two tools' descriptions say similar things, routing becomes a coin toss. A quick check: measure how much each pair of descriptions overlaps in meaningful words.

Python
STOP = set("a an the of for to and or by use it is are with on in this that as e g".split())

TOOLS = {
    "get_customer":  "Gets customer information and account data.",
    "lookup_order":  "Gets order information and account data for customers.",
    "refund_status": "Returns the refund state and expected date for one order number, e.g. ORD-104233. Not for order contents.",
    "find_slots":    "Lists free appointment times for one doctor on one date.",
}

def words(text):
    return {w for w in re.findall(r"[a-z]+", text.lower()) if w not in STOP}

pairs = []
names = list(TOOLS)
for i in range(len(names)):
    for j in range(i + 1, len(names)):
        a, b = words(TOOLS[names[i]]), words(TOOLS[names[j]])
        pairs.append((len(a & b) / len(a | b), names[i], names[j], sorted(a & b)))
for score, a, b, shared in sorted(pairs, reverse=True)[:3]:
    flag = "  ← likely to be confused" if score > 0.4 else ""
    print(f"{score:.2f}  {a} / {b}  shared: {shared}{flag}")
Output · produced by running this code
0.57  get_customer / lookup_order  shared: ['account', 'data', 'gets', 'information']  ← likely to be confused
0.12  refund_status / find_slots  shared: ['date', 'one']
0.06  lookup_order / refund_status  shared: ['order']
How to read it

get_customer and lookup_order share most of their words ("gets ... information and account data"), so Claude has little to go on. Rewriting them with the five elements, especially inputs (an email versus an order number) and boundaries, is the fix. Word overlap is a crude proxy, but it's a fast way to find the pairs to rewrite.

Errors that help the model recover

A tool error is a message to Claude. "Error 500" teaches it nothing. Say what went wrong, whether retrying could help, and what to do instead.

Python
class NotFound(Exception): pass
class RateLimited(Exception): pass

def describe_error(tool, args, exc):
    if isinstance(exc, NotFound):
        return (f"No order matches {args.get('order_ref')!r}. Order numbers look like ORD-123456. "
                "Ask the user to check the number; don't guess another one.")
    if isinstance(exc, RateLimited):
        return "The order service is busy. Wait a few seconds and retry once; if it fails again, tell the user it's temporarily unavailable."
    if isinstance(exc, PermissionError):
        return "This order belongs to a different account. Don't reveal anything about it; ask the user to sign in to the right account."
    return f"{tool} failed unexpectedly ({type(exc).__name__}). Don't retry; apologise and offer the support line."

for exc in [NotFound(), RateLimited(), PermissionError(), ValueError("bad state")]:
    print(f"{type(exc).__name__:<16} → {describe_error('lookup_order', {'order_ref': 'ORD-14233'}, exc)}")

Building a good tool set

  • Fewer, sharper tools. Every extra tool is another choice to get wrong. Consolidate near-duplicates (one lookup_order with an order_ref field, not three variants).
  • Clear, namespaced names. billing_get_invoice and booking_check_slots route better than get and check.
  • Return what's useful, not everything. Trim large payloads; return IDs and the fields the task needs (context is expensive, Module 6).
  • Describe the output as well as the input, so Claude knows what it will get back.
  • Test routing with an eval: a list of requests and the tool each should trigger.

Practice questionAn agent keeps calling get_customer when users ask about orders. Both tools' descriptions say "Gets customer and order information." What's the best fix?

Routing depends on the descriptions, and these two are nearly identical. Distinct purposes, input formats and boundaries make the choice clear. Forcing one tool breaks the other use case (and is rejected on the newest models).

Practice questionWhich tool error message gives Claude the best chance to recover?

A useful error explains the problem, the expected format and the next step. Bare codes give the model nothing to act on, and an empty non-error result invites it to assume success.

Session 8.3

Approval patterns and gates

When an agent can act in real systems, the critical moment is the instant between Claude deciding to act and the action happening. Three mechanisms sit there:

MechanismDecidesExample
Programmatic gateCode allows or blocks, automatically, every timeBlock DELETE and DROP on production databases
InterceptionCode rewrites the call and lets it proceedRedirect a write outside the sandbox into it
Approval patternA person decides, after seeing the proposed action"Send this email to 3,200 patients?" Approve / Deny

An approval pattern has four steps: propose (the agent states exactly what it wants to do), pause (execution stops completely), review (a person sees the action, its target and its consequences), proceed (approve: execute; deny: stop or choose another route).

Watch out

More prompts isn't more safety. Asking for approval on everything causes approval fatigue: people click "approve" without reading, and oversight disappears. Reserve approvals for actions that are high-stakes, external or hard to reverse; allow routine, low-risk actions; block what should never happen.

Here's a policy that sorts each proposed action into allow, ask or deny, with the reason, and counts how many prompts a typical day would produce.

Python
def risk_policy(action):
    t, a = action["tool"], action["args"]
    if t == "run_sql" and re.search(r"\b(drop|truncate|delete)\b", a["query"], re.I):
        return "deny", "destructive SQL is never run by the agent"
    if t in ("read_file", "search_docs", "check_slots", "run_sql"):
        return "allow", "read-only"
    if t == "send_email":
        external = not a["to"].endswith("@sunriseclinic.in")
        bulk = a.get("recipients", 1) > 20
        if external or bulk:
            return "ask", ("external " if external else "") + ("bulk " if bulk else "") + "email"
        return "allow", "internal, small"
    if t == "issue_refund":
        return ("ask", "refund over ₹2,000") if a["amount"] > 2_000 else ("allow", "small refund within policy")
    return "ask", "unknown action: default to a person"

day = ([{"tool": "check_slots", "args": {}}] * 140 + [{"tool": "search_docs", "args": {}}] * 60 +
       [{"tool": "send_email", "args": {"to": "front@sunriseclinic.in"}}] * 25 +
       [{"tool": "issue_refund", "args": {"amount": 850}}] * 12 + [{"tool": "issue_refund", "args": {"amount": 4_200}}] * 2 +
       [{"tool": "send_email", "args": {"to": "patients@list", "recipients": 3_200}}] +
       [{"tool": "run_sql", "args": {"query": "DELETE FROM bookings WHERE date < '2025-01-01'"}}])

tally = {}
for act in day:
    verdict, why = risk_policy(act)
    tally.setdefault(verdict, {}).setdefault(why, 0)
    tally[verdict][why] += 1
for verdict in ("allow", "ask", "deny"):
    total = sum(tally.get(verdict, {}).values())
    print(f"{verdict.upper():<6} {total:>4}  {tally.get(verdict, {})}")
print(f"\nprompts a person sees today: {sum(tally['ask'].values())} out of {len(day)} actions")
Output · produced by running this code
ALLOW   237  {'read-only': 200, 'internal, small': 25, 'small refund within policy': 12}
ASK       3  {'refund over ₹2,000': 2, 'external bulk email': 1}
DENY      1  {'destructive SQL is never run by the agent': 1}

prompts a person sees today: 3 out of 241 actions
How to read it

Of 241 actions, a person is asked about 3: two large refunds and the bulk email. Everything routine flows; the destructive SQL is refused without asking anyone. Three meaningful prompts get read; three hundred trivial ones get rubber-stamped.

Tip

You don't need a hand-written loop to add approvals. With the SDK's Tool Runner, gate inside the tool function (return "the user declined" as the result) or inspect pending tool_use blocks between turns. In Claude Code, ask permission rules and PreToolUse hooks do the same job, and Managed Agents has per-tool permission policies (always_allow, always_ask).

Practice questionAn agent asks for approval before every action, including reading files. After a week, reviewers approve everything within a second. What's the best change?

Approval fatigue has removed real oversight. Tiering actions (allow / ask / deny) keeps the prompts few and meaningful, so people actually review the ones that matter.

Practice questionSelect 2Which actions usually warrant an approval step even though they could be undone? (Select 2)

External messages and public posts are seen by others the moment they happen, so "reversible" in the system doesn't undo their effect. Reads and lookups are routine and low-risk.

Session 8.4

Building an MCP server

Before MCP, connecting M AI applications to N systems meant M × N one-off integrations. The Model Context Protocol is an open standard that turns that into M + N: build one MCP server for your ticketing system, and every MCP-compatible application can use it.

RoleWhat it isExample
HostThe AI application the user works inClaude Code, Claude Desktop, your own agent
ClientA connector inside the host, one per serverClaude Code's connection to your inventory server
ServerA program that exposes capabilities over MCPinventory-mcp, wrapping your inventory REST API

A server offers three kinds of capability. The most testable fact about them is who decides when each is used:

PrimitiveControlled byWhat it isExample (inventory server)
ToolsThe modelActions Claude chooses to callcheck_stock(sku), reserve_items(sku, qty)
ResourcesThe applicationRead-only context the host decides to attachinventory://warehouses (list of sites)
PromptsThe userReusable templates a person picks explicitly"Weekly stock-out report"

Messages are JSON-RPC 2.0, with methods such as tools/list, tools/call, resources/list, resources/read, prompts/list and prompts/get. Two transports are current:

TransportHowUse for
stdioThe host starts the server as a local process and talks over its standard input and outputLocal tools: file systems, local databases, developer tooling
Streamable HTTPThe server runs remotely; clients send HTTP requests (optionally receiving a stream back)Shared, remote services used by many hosts and users

The older HTTP + SSE transport is deprecated.

The wire format, for real

To show exactly what travels over stdio, here's a tiny hand-written server that speaks MCP-style JSON-RPC, one message per line. The cell writes it to a file, starts it as a real subprocess, and talks to it through its stdin and stdout, as a host would. It's deliberately minimal (no initialisation handshake or capability negotiation); real servers should use the official SDK, shown after.

Python
import json, os, subprocess, sys, tempfile

SERVER = r'''
import json, sys
STOCK = {"GLV-M-100": 412, "MSK-N95-20": 0}
TOOLS = [{"name": "check_stock", "description": "Units in stock for one SKU, e.g. GLV-M-100.",
          "inputSchema": {"type": "object", "properties": {"sku": {"type": "string"}}, "required": ["sku"]}}]
RESOURCES = [{"uri": "inventory://warehouses", "name": "Warehouses", "mimeType": "text/plain"}]
PROMPTS = [{"name": "stockout_report", "description": "Weekly report of SKUs at zero stock"}]

def handle(req):
    m, p = req["method"], req.get("params", {})
    if m == "tools/list":     return {"tools": TOOLS}
    if m == "resources/list": return {"resources": RESOURCES}
    if m == "prompts/list":   return {"prompts": PROMPTS}
    if m == "resources/read": return {"contents": [{"uri": p["uri"], "text": "Andheri, Thane, Pune"}]}
    if m == "tools/call":
        sku = p["arguments"]["sku"]
        if sku not in STOCK:
            return {"content": [{"type": "text", "text": f"Unknown SKU {sku}"}], "isError": True}
        return {"content": [{"type": "text", "text": f"{STOCK[sku]} in stock"}]}
    raise KeyError(m)

for line in sys.stdin:
    req = json.loads(line)
    try:
        out = {"jsonrpc": "2.0", "id": req["id"], "result": handle(req)}
    except KeyError as e:
        out = {"jsonrpc": "2.0", "id": req["id"], "error": {"code": -32601, "message": f"Method not found: {e}"}}
    print(json.dumps(out), flush=True)
'''

path = os.path.join(tempfile.mkdtemp(), "inventory_server.py")
open(path, "w").write(SERVER)
proc = subprocess.Popen([sys.executable, "-I", path], stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)

def rpc(i, method, params=None):
    msg = {"jsonrpc": "2.0", "id": i, "method": method, **({"params": params} if params else {})}
    proc.stdin.write(json.dumps(msg) + "\n"); proc.stdin.flush()
    reply = json.loads(proc.stdout.readline())
    print(f"→ {json.dumps(msg)}\n← {json.dumps(reply)}\n")
    return reply

rpc(1, "tools/list")
rpc(2, "tools/call", {"name": "check_stock", "arguments": {"sku": "GLV-M-100"}})
rpc(3, "tools/call", {"name": "check_stock", "arguments": {"sku": "XYZ"}})
rpc(4, "resources/read", {"uri": "inventory://warehouses"})
rpc(5, "tools/delete")
proc.stdin.close(); proc.wait()
print("server process exited with code", proc.returncode)

How to read it

Every exchange is one JSON object per line: requests carry an id and a method; responses echo the id with either a result or an error. A failed tool (unknown SKU) is a normal result with isError: true, which Claude reads and can act on; an unsupported method is a JSON-RPC error. When the host closes stdin, the server exits.

With the official Python SDK

The SDK handles the protocol details: initialisation, schemas generated from type hints, both transports. Current documentation uses MCPServer (install with pip install "mcp[cli]"); shown, not run.

Watch out

An MCP server is code that runs with your credentials (stdio) or a service you hand data to (HTTP). Install only servers you trust, scope their tokens narrowly, and remember that everything a server returns is untrusted input to Claude (Module 7): a compromised server can inject instructions through its tool results.

Practice questionIn MCP, which primitive is controlled by the user, rather than the model or the application?

Prompts are templates a person selects explicitly. Tools are model-controlled (Claude decides to call them); resources are application-controlled context the host chooses to attach.

Practice questionA team wants Claude to use a database tool that runs on each developer's laptop. Which transport fits, and what can't they use?

stdio is the transport for local servers launched by the host. The API's MCP connector connects to publicly reachable HTTP servers only, so a laptop-local server needs Claude Code (or another local host).

Session 8.5

Tools, Skills or MCP?

Several mechanisms extend what Claude can do. They are complementary, not competing, and choosing the lightest one that fits avoids over-engineering.

MechanismGives ClaudeBest whenExample
Built-in / server toolsReady-made abilities: web search and fetch, code execution, file editing, bashThe ability is generic and Anthropic already provides itResearch with current web sources
Custom tools (in your app)A specific action or data source, defined in one applicationOne app needs a capability tied to its own codeissue_refund inside your billing app

HookDeterministic actions at fixed pointsSomething must always or never happenBlock force pushes; format after edits
The idea

Access versus know-how. MCP servers and tools give Claude access: to systems, data and actions. Skills give Claude know-how: how to carry out a kind of task well. They combine naturally: an MCP server lets Claude read the ledger; a skill teaches it your reconciliation procedure.

Skills, briefly

A skill is a folder with a SKILL.md file (front matter, then instructions) and optional scripts and reference files. Skills load in stages: the name and description (about 100 tokens) are always visible; the body loads when a task matches; extra files are read only when needed. In the Claude API, name and description are required (the name is lowercase letters, numbers and hyphens, up to 64 characters); skills there run in the code execution container. In Claude Code they live in .claude/skills/ or ~/.claude/skills/, and in claude.ai you upload them under Settings.

skills/monthly-reconciliation/SKILL.md
---
name: monthly-reconciliation
description: Reconcile the clinic's monthly UPI and card settlements against invoices. Use when asked to reconcile payments, find unmatched transactions or close the month.
---
# Monthly reconciliation

1. Export settlements with `scripts/fetch_settlements.py --month YYYY-MM`.
2. Match on invoice number first, then on amount and date within ±1 day.
3. List unmatched items in a table: date, amount, channel, probable cause.
4. Duplicate payments (same invoice, two channels) go to the refunds queue, never auto-refunded.

See `reference/edge-cases.md` for split payments and partial refunds.

Choosing, as code

The official sample question for this domain asks exactly this kind of thing: an internal inventory REST API that several Claude applications must use, maintained independently of any one of them. Here's a decision function run on it and five other needs.

Python
def choose(need):
    if need.get("generic_capability"):                       return "built-in / server tool"
    if need.get("procedure_or_style") and not need.get("new_access"):
                                                             return "Skill"
    if need.get("new_access") and need.get("apps", 1) > 1:   return "MCP server"
    if need.get("new_access"):                               return "custom tool in that app"
    if need.get("must_always_happen"):                       return "hook"
    return "CLAUDE.md / prompt"

needs = [
    ("Inventory REST API, used by several Claude apps, owned by the ops team", dict(new_access=True, apps=3)),
    ("Look up current news for a research brief",                             dict(generic_capability=True)),
    ("Our 9-step month-end reconciliation procedure",                         dict(procedure_or_style=True)),
    ("Issue refunds from inside the billing app only",                        dict(new_access=True, apps=1)),
    ("Run the formatter after every edit",                                    dict(must_always_happen=True)),
    ("Always use British spelling in this repo",                              dict()),
]
for name, n in needs:
    print(f"{choose(n):<26} ← {name}")

M, N = 4, 6
print(f"\n{M} apps × {N} systems: {M * N} custom integrations, or {M + N} MCP pieces ({M} clients + {N} servers)")

Exam lens

For the inventory scenario, the answer is an MCP server exposing the operations as tools. Hard-coding logic into prompts isn't reusable or maintainable, pasting data into the context gives no live access and wastes tokens, and built-in tools can't reach arbitrary internal APIs.

Beyond MCP: agents talking to agents

MCP connects an agent to tools and data. A different family of protocols connects agents to other agents, each with its own model, tools and permissions.

ProtocolOrigin and statusIdea
A2A (Agent2Agent)Created by Google (April 2025); now an open project under the Linux FoundationAgents discover each other through an Agent Card and exchange tasks and messages over JSON-RPC 2.0
ACP (Agent Communication Protocol)Created by IBM Research; merged into A2A under the Linux Foundation in 2025Structured, REST-based agent messaging; its ideas now continue in A2A
Watch out

"ACP" is ambiguous: today it often means Zed's unrelated Agent Client Protocol (editors talking to coding agents). Read the context of a question before answering.

An Agent Card is a JSON document an agent publishes (at /.well-known/agent-card.json) describing who it is, where to reach it and what it can do:

  "provider": { "organization": "Sunrise Clinic" },
  "url": "https://agents.sunriseclinic.in/a2a/scheduling",
  "capabilities": { "streaming": true, "pushNotifications": false },

Practice questionA team needs Claude to call an internal inventory service exposed as a REST API. The capability must be reusable across several Claude applications and maintained independently of any one app. What fits best?

An MCP server is a reusable, independently maintained interface that any MCP-capable application can connect to. Prompts aren't integrations, pasted data is stale and costly, and built-in tools don't reach arbitrary internal APIs.

Practice questionClaude already has read access to the accounting system through an MCP server, but its month-end reconciliations are inconsistent from run to run. What should you add?

The problem is know-how, not access. A Skill packages the procedure so Claude follows it the same way every time, loading it only when reconciliation is requested.

Practice questionHow does A2A differ from MCP?

MCP is agent-to-tools; A2A is agent-to-agent. They complement each other: an agent might use MCP servers for its own tools and A2A to delegate to another organisation's agent.
