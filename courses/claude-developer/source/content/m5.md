## 5.1 | How an LLM generates text

### Tokens

A **token** is the unit a model reads and writes: often a whole common word, sometimes part of a rare word, sometimes punctuation. Billing, limits and the context window are all counted in tokens, not words or characters. A rough rule for English is **about 4 characters, or ¾ of a word, per token**; other languages and scripts often need more tokens for the same idea.

Here's a toy tokenizer to show the idea: greedy longest-match against a small vocabulary. Real tokenizers learn vocabularies of tens of thousands of pieces, but behave the same way: common words stay whole, rare ones split.

```python
VOCAB = {"the", "cat", "sat", "un", "believ", "able", "appoint", "ment", "s", "clinic", " ", ".", "!",
         "re", "schedul", "ing", "tele", "consult", "a", "b", "c", "d", "e", "i", "l", "n", "o", "t", "u", "v"}

def tokenize(text):
    out, i, text = [], 0, text.lower()
    while i < len(text):
        for j in range(len(text), i, -1):          # longest piece in the vocabulary first
            if text[i:j] in VOCAB:
                out.append(text[i:j]); i = j; break
        else:
            out.append(text[i]); i += 1           # unknown character: its own token
    return [t for t in out if t != " "]

for s in ["The cat sat.", "Unbelievable!", "Rescheduling teleconsult appointments"]:
    toks = tokenize(s)
    print(f"{s:<40} {len(toks)} tokens  {toks}")
```

> [warn] Character rules of thumb are for quick estimates only. Token counts also change between model generations: Anthropic's tokenizer introduced with Claude Opus 4.7 produces roughly 1 to 1.35 times as many tokens for the same text as earlier models. For real numbers, use the **token counting endpoint** (`client.messages.count_tokens(...)`) with the model you'll actually call.

### The context window is one shared budget

The **context window** is everything the model can consider in one request: system prompt, tools, history, documents, tool results, *and* the reply it's about to write. Current Claude models have a 1M-token window and can write up to 128K tokens in one reply, but every request still has to fit.

```python
WINDOW = 1_000_000
parts = {"system prompt": 3_500, "tool definitions": 4_200, "conversation history": 61_000,
         "retrieved documents": 140_000, "tool results": 38_000}
used = sum(parts.values())
max_tokens = 32_000
for k, v in parts.items():
    print(f"{k:<22} {v:>9,}")
print(f"{'input total':<22} {used:>9,}  ({used / WINDOW:.1%} of the window)")
print(f"{'reserved for reply':<22} {max_tokens:>9,}")
print(f"{'headroom':<22} {WINDOW - used - max_tokens:>9,}")
```

> [tip] Fitting in the window isn't the goal; the useful question is whether everything in it *helps*. Long, stale context dilutes attention and costs money on every turn (Module 6). Trim, summarise and retrieve only what's needed.

### Next-token generation

The model doesn't plan a whole reply and then type it out. It predicts **one token at a time**, each based on everything before it (the prompt plus what it has already written), then repeats until it stops. This is called autoregressive generation. Two consequences matter for developers: text can be streamed as it's produced, and early tokens steer everything after them.

```seq title="Autoregressive generation: one token per step"
Context so far, Model
Context so far -> Model: "The best way to learn a language is to practise"
Model --> Context so far: + " daily"
Context so far -> Model: "... is to practise daily"
Model --> Context so far: + "."
Context so far -> Model: "... is to practise daily."
Model --> Context so far: end of turn (stop)
```

At each step the model produces a probability for every possible next token, and **sampling** picks one. Two classic controls shape that choice:

- **Temperature** sharpens (low) or flattens (high) the probabilities before sampling.
- **Top-p** (nucleus sampling) keeps only the smallest set of top tokens whose probabilities add up to *p*.

Here are both applied to one real-looking step: the next word after "The best way to learn a language is to practise".

```python
import math, random

logits = {"daily": 3.1, "often": 2.4, "speaking": 2.0, "with": 1.6, "online": 0.9, "backwards": -1.5}

def probs(logits, temperature):
    exps = {t: math.exp(v / temperature) for t, v in logits.items()}
    z = sum(exps.values())
    return {t: e / z for t, e in exps.items()}

def nucleus(p, top_p):
    kept, total = [], 0.0
    for t, v in sorted(p.items(), key=lambda kv: -kv[1]):
        kept.append(t); total += v
        if total >= top_p: break
    return kept

for T in (0.3, 1.0, 1.8):
    p = probs(logits, T)
    print(f"temperature {T}: " + "  ".join(f"{t} {v:.0%}" for t, v in p.items()))
print("\ntop-p 0.9 at temperature 1.0 keeps:", nucleus(probs(logits, 1.0), 0.9))

rng = random.Random(11)
p = probs(logits, 1.0)
draws = [rng.choices(list(p), weights=list(p.values()))[0] for _ in range(8)]
print("8 samples at temperature 1.0:      ", draws)
```

> [read] At 0.3, "daily" takes almost all the probability; at 1.8 even "backwards" gets a real chance. Top-p 0.9 drops the long tail before sampling. Eight draws from the same distribution give three different words: that's **non-determinism** from sampling, in miniature.

> [warn] **What's changed on current models.** Claude 4.7 and later models accept `temperature`, `top_p` and `top_k` only at their default values, and from API version `2026-10-21` sending any of them returns a 400 error on every model. So on today's Claude you don't tune sampling: you get consistency from **clear instructions, examples, structured outputs and lower effort**. Learn the concepts (the exam lists them), but don't design a new app around a temperature knob.

### Non-determinism: design for it

Identical requests can give different outputs. Sampling is one cause; tiny numerical differences in large-scale parallel computation are another. It's a property to design around, not a bug to fix.

- Don't trust one passing run: test with enough cases, and repeat important ones.
- Constrain the output: schemas and structured outputs leave less room for variation to matter.
- Validate in code: check the shape and the facts that matter, every time.
- Log the exact input, model and prompt version, so any output can be investigated.

```quiz

why: LLM outputs vary across runs, and on current Claude models sampling parameters can't be lowered anyway. Tests should check properties (fields present, facts correct, format valid) across enough cases, and the app should constrain output with schemas. Retry-until-pass hides real failures.
```

## 5.2 | Thinking, effort and fast mode

Four controls trade speed, cost and depth of reasoning against each other. They're easy to mix up, so be precise about what each one changes.

| Control | What it changes | Use when | Don't use when |
|---|---|---|---|
| **Adaptive thinking** | Claude decides per request whether, and how much, to reason before answering | Most work on current models: it's the default on Opus 5.5 and Sonnet 5.5 | (It's on by default; you tune it with effort) |
| **Extended thinking** | The older name for reasoning before answering; on current models it's adaptive, and the fixed `budget_tokens` setting is deprecated or rejected | Hard multi-step reasoning, analysis, code | Simple lookups: it adds latency and output tokens |
| **Effort** (`low` … `max`) | How thorough Claude is overall: thinking depth, number of tool calls, length | Tune per route: `low` for chat and classification, `high`/`xhigh` for hard coding and agents | Don't set `max` by default; raise it only when measurement shows a gain |
| **Fast mode** (research preview) | The *same Opus model* generating output up to about 2.5× faster, at premium prices | Latency-critical work that needs Opus-level quality | Cheap, simple, high-volume tasks: use Haiku instead |

> [warn] Some study material describes "fast mode" as the cheap option for simple tasks. In the Claude API it's the opposite: fast mode makes **Opus** faster and **costs more** (on Claude Opus 5.5, $8 / $40 per million tokens instead of $4 / $20). For cheap and quick, choose a smaller model or lower effort.

### Effort in practice

```python eval=false
response = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=16000,
    output_config={"effort": "low"},        # low | medium | high | xhigh | max
    messages=[{"role": "user", "content": "Classify this message: billing, booking or clinical?\n\n" + text}],
)
```

Defaults differ by model, so set effort explicitly rather than inheriting it: **Claude Opus 5.5 and Claude Haiku 5.5 default to `medium`**; most other current models default to `high`. Lower effort means fewer and more consolidated tool calls, less preamble and terser answers. Judge cost **per completed task**, not per request: a cheaper call that needs extra turns or retries isn't cheaper.

Here's a per-route policy as a small function, applied to six routes in one app:

```python
def pick_options(route):
    hard, waiting, volume = route["hard"], route["user_waiting"], route["per_day"]
    if hard and waiting and route.get("latency_critical"):
        return "Opus 5.5, effort high, fast mode (premium price: check it pays)"
    if hard:
        return "Opus 5.5, effort high or xhigh, adaptive thinking"
    if volume > 10_000 and not waiting:
        return "Haiku 5.5, effort low, via the Batches API"
    if volume > 10_000:
        return "Haiku 5.5, effort low"
    return "Sonnet 5.5, effort medium"

routes = [
    ("FAQ chat replies",                dict(hard=False, user_waiting=True,  per_day=40_000)),
    ("Overnight tagging of reviews",    dict(hard=False, user_waiting=False, per_day=200_000)),
    ("Contract risk analysis",          dict(hard=True,  user_waiting=False, per_day=60)),
    ("Agentic bug fixing in CI",        dict(hard=True,  user_waiting=False, per_day=30)),
    ("Live triage for on-call doctors", dict(hard=True,  user_waiting=True,  per_day=300, latency_critical=True)),
    ("Weekly report drafting",          dict(hard=False, user_waiting=True,  per_day=25)),
]
for name, r in routes:
    print(f"{name:<33} → {pick_options(r)}")
```

> [tip] These are starting points to measure, not answers. Anthropic's own guidance is that on newer models, a capable model at *lower* effort often matches an older one at high effort, so test "same model, lower effort" before building a multi-model cascade.

### Fast mode, priced out

Fast mode needs the beta flag `fast-mode-2026-02-01` and `speed: "fast"` on the request, and it's only on the Claude API (not Bedrock, Vertex or Foundry, and not with batches). Here's what it costs for one long Opus reply. The baseline speed is a placeholder to make the arithmetic concrete; measure your own.

```python
out_tokens, in_tokens = 3_000, 20_000
baseline_tps = 60                       # PLACEHOLDER output tokens/second; measure your own
for label, p_in, p_out, speedup in [("standard", 4, 20, 1.0), ("fast mode", 8, 40, 2.5)]:
    cost = (in_tokens * p_in + out_tokens * p_out) / 1e6
    secs = out_tokens / (baseline_tps * speedup)
    speed = "baseline" if speedup == 1 else f"up to {speedup}× faster"
    print(f"Opus 5.5 {label:<10} ${cost:.3f} per reply   ~{secs:.0f}s to generate ({speed})")
```

## 5.3 | Zero-, one- and few-shot

How many **examples** you put in a prompt is a design choice:

| Approach | Examples | Works well when |
|---|---|---|
| **Zero-shot** | None; instructions only | The task is common and clearly described |
| **One-shot** | One | You need to show a format or tone that's hard to describe |
| **Few-shot** (multi-shot) | Several, usually 3–5 | You need consistency: classification labels, a house style, tricky edge cases |

```compare
Zero-shot
Classify the patient message as BOOKING, BILLING,
CLINICAL or OTHER. Reply with the label only.

Message: "Can I move Thursday's appointment
to the evening?"
---
Few-shot
Classify the patient message as BOOKING, BILLING,
CLINICAL or OTHER. Reply with the label only.

<examples>
<example><message>Why was I charged twice?</message><label>BILLING</label></example>
<example><message>The rash is spreading since yesterday</message><label>CLINICAL</label></example>
<example><message>Is there parking near the Andheri clinic?</message><label>OTHER</label></example>
<example><message>Book me with Dr Rao next week, and is the follow-up free?</message><label>BOOKING</label></example>
</examples>

Message: "Can I move Thursday's appointment
to the evening?"
```

> [concept] Examples are powerful, and they teach *everything* they contain: length, tone, wording, even the order of labels. Make them **relevant** (like real inputs), **diverse** (cover the categories and the hard cases), and **wrapped in tags** (`<example>`) so Claude can tell them apart from the instructions. The fourth example above deliberately shows how a mixed message is labelled.

Before sending a few-shot prompt, it's worth checking the examples themselves. Here's a small linter, run on two candidate example sets.

```python
from collections import Counter

def lint_examples(examples, labels):
    issues = []
    counts = Counter(lbl for _, lbl in examples)
    missing = [l for l in labels if l not in counts]
    if missing: issues.append(f"no example for {missing}")
    if counts and max(counts.values()) > len(examples) / 2:
        issues.append(f"skewed towards {counts.most_common(1)[0][0]} ({counts.most_common(1)[0][1]}/{len(examples)})")
    lengths = [len(m.split()) for m, _ in examples]
    if max(lengths) - min(lengths) < 3:
        issues.append("all examples are the same length: Claude may copy it")
    if len({m.lower() for m, _ in examples}) < len(examples):
        issues.append("duplicate examples")
    return issues or ["looks balanced"]

LABELS = ["BOOKING", "BILLING", "CLINICAL", "OTHER"]
set_a = [("Book me for Monday", "BOOKING"), ("Move my Friday slot", "BOOKING"),
         ("Cancel my booking", "BOOKING"), ("Why was I charged twice?", "BILLING")]
set_b = [("Why was I charged twice?", "BILLING"), ("The rash is spreading since yesterday", "CLINICAL"),
         ("Is there parking near the Andheri clinic?", "OTHER"),
         ("Book me with Dr Rao next week, and is the follow-up free?", "BOOKING")]

def to_prompt(examples):
    return "<examples>\n" + "\n".join(f"<example><message>{m}</message><label>{l}</label></example>"
                                      for m, l in examples) + "\n</examples>"

print("set A:", lint_examples(set_a, LABELS))
print("set B:", lint_examples(set_b, LABELS))
print("\n" + to_prompt(set_b))
```

> [tip] Start zero-shot with clear instructions; add examples when outputs are inconsistent in format or judgement. If you need a strict output *structure*, structured outputs (a JSON schema) are more reliable than examples alone. Examples teach judgement; schemas enforce shape.

```quiz

why: Few-shot examples teach judgement on exactly the cases the instructions leave ambiguous. Examples of easy cases add skew rather than clarity.
```

## 5.4 | SDKs, REST and websockets

The Claude API is a REST API over HTTPS. The official **SDKs** wrap it so you don't build HTTP requests by hand. They add typed request and response objects, authentication from the environment, automatic retries with backoff, timeouts, streaming helpers and helpers for pagination, batches and files.

| Layer | You write | You get |
|---|---|---|
| Raw HTTP | URL, headers (`x-api-key`, `anthropic-version`), JSON body, status handling, SSE parsing | Full control, any language |
| Official SDK | `client.messages.create(...)` | Types, retries, timeouts, streaming helpers, typed errors |
| Framework or agent SDK on top | A prompt and tools | A loop, memory and orchestration (Module 1) |

### How streaming travels: server-sent events

Streaming responses use **server-sent events (SSE)**: an ordinary HTTP response that stays open while the server writes `event:` and `data:` lines. The SDK parses them for you; here's what that parsing does, run on a raw stream in the documented format.

```python
import json

RAW = """event: message_start
data: {"type": "message_start", "message": {"id": "msg_ex", "usage": {"input_tokens": 25}}}

event: content_block_delta
data: {"type": "content_block_delta", "index": 0, "delta": {"type": "text_delta", "text": "Hello"}}

event: ping
data: {"type": "ping"}

event: content_block_delta
data: {"type": "content_block_delta", "index": 0, "delta": {"type": "text_delta", "text": ", Mrs Iyer."}}

event: message_delta
data: {"type": "message_delta", "delta": {"stop_reason": "end_turn"}, "usage": {"output_tokens": 7}}

event: message_stop
data: {"type": "message_stop"}
"""

def parse_sse(raw):
    for block in raw.strip().split("\n\n"):              # events are separated by a blank line
        fields = dict(line.split(": ", 1) for line in block.splitlines())
        yield fields["event"], json.loads(fields["data"])

text = ""
for name, data in parse_sse(RAW):
    if name == "content_block_delta":
        text += data["delta"]["text"]
    elif name == "message_delta":
        print("stop_reason:", data["delta"]["stop_reason"], "| output tokens:", data["usage"]["output_tokens"])
    elif name == "ping":
        print("(keep-alive ping ignored)")
print("assembled text:", text)
```

### Where websockets fit

A **WebSocket** keeps one connection open in **both directions**, so either side can send messages at any time, without a new request for each. SSE, by contrast, streams one way: server to client, in answer to one request.

| | HTTP request/response | Server-sent events | WebSocket |
|---|---|---|---|
| Direction | Client asks, server answers | Server → client, for one request | Both ways, any time |
| Connection | One per request | Open while the reply streams | Long-lived |
| Claude use | Ordinary Messages API calls | Streaming Messages API replies | Between *your* browser app and *your* server (live chat, collaborative UIs); event feeds a tool watches |

```seq title="Live streaming in a web app: two different connections"
Browser, Your backend, Claude API
Browser -> Your backend: WebSocket message: "Can I move Thursday's appointment?"
Your backend -> Claude API: POST /v1/messages, stream: true (API key stays here)
Claude API --> Your backend: SSE: content_block_delta "Yes, "
Your backend --> Browser: WebSocket: "Yes, "
Claude API --> Your backend: SSE: content_block_delta "6 pm is free."
Your backend --> Browser: WebSocket: "6 pm is free."
Claude API --> Your backend: SSE: message_stop
```

> [exam] A common design for a live chat app: the browser talks to your backend over a **WebSocket**; your backend calls the Claude API with `stream: true` and relays the **SSE** deltas down the WebSocket. Your API key stays on the server, never in the browser. Claude Code can also *watch* an existing WebSocket feed (with its Monitor tool, after you approve the connection) to react to events instead of polling.

```quiz

```

## 5.5 | Opus, Sonnet or Haiku

Claude comes in tiers that share core abilities but trade capability against speed and cost. Current models, with list prices per million tokens (input / output) on the Claude API:

| Model | Model ID | Price in / out | Context | Best at |
|---|---|---|---|---|
| **Claude Fable 5.1** | `claude-fable-5-1` | $10 / $50 | 1M | The most demanding reasoning and long-horizon agent work |
| **Claude Opus 5.5** | `claude-opus-5-5` | $4 / $20 | 1M | Complex reasoning, agentic coding, hard analysis; Anthropic's default recommendation |
| **Claude Sonnet 5.5** | `claude-sonnet-5-5` | $2 / $10 | 1M | Balance of capability and speed: everyday coding, agents, enterprise workloads at volume |
| **Claude Haiku 5.5** | `claude-haiku-5-5` | $0.10 / $0.50 (prompts up to 100K tokens) | 1M | Fast, high-volume, simple tasks: classification, extraction, sub-agents |

All support up to 128K output tokens, vision and tools. Prices change: check Anthropic's pricing page before you plan a budget.

> [concept] **Two ways to start.** *Capability-first*: begin with the most capable model, prove the task can be done well, then try cheaper models or lower effort against your eval and keep the cheapest that holds quality. *Efficiency-first*: begin small and move up only where evals show it falls short. Either way, the eval set decides, not a hunch.

```python
P = {"Haiku 5.5": (0.10, 0.50), "Sonnet 5.5": (2.00, 10.00), "Opus 5.5": (4.00, 20.00)}

def monthly(model, calls_per_day, tin, tout):
    pin, pout = P[model]
    return calls_per_day * 30 * (tin * pin + tout * pout) / 1e6

workloads = [("classify 50k messages/day", 50_000, 600, 5),
             ("support replies 5k/day", 5_000, 4_000, 300),
             ("code review 200 PRs/day", 200, 30_000, 2_000)]
print(f"{'':<28}" + "".join(f"{m:>13}" for m in P))
for name, n, tin, tout in workloads:
    print(f"{name:<28}" + "".join(f"{'$' + format(monthly(m, n, tin, tout), ',.0f'):>13}" for m in P))
```

> [read] For classification, Haiku is 20× cheaper than Sonnet ($94 against $1,875 a month here), so if it passes the eval, it's the obvious choice. For 200 code reviews a day, Opus costs $480 a month more than Sonnet: small next to the cost of one missed bug, so there it's quality, not price, that should decide.

### Breaking changes between model releases

A newer model is not a drop-in replacement. Model releases can **remove parameters, change defaults, and change behaviour** (how much it says, how it uses tools, what it declines). Some breaking changes fail loudly with a 400; others succeed with different output. Recent examples:

| Change | Since | Effect on old code |
|---|---|---|
| Assistant **prefill** (ending messages with a partial assistant turn) removed | Claude 4.6 generation | 400 error; use structured outputs or instructions |
| Fixed thinking `budget_tokens` replaced by adaptive thinking + effort | Deprecated on 4.6, rejected on newer models | 400 error on the newest models |
| `temperature` / `top_p` / `top_k` only at defaults | Claude 4.7 and later | 400 for non-default values |
| New tokenizer | Claude Opus 4.7 | ~1–1.35× more tokens for the same text: budgets and costs shift |
| Forced `tool_choice` (`any` / a named tool) rejected | Opus 5.5, Sonnet 5.5, Fable 5.1 | 400; use `auto` with `strict: true` or structured outputs |
| Thinking can't be disabled; effort defaults to `medium` | Claude Opus 5.5 | 400 if code sends `thinking: {type: "disabled"}`; output depth shifts |

Here's a pre-migration check that scans request configurations for those changes before you switch the model ID.

```python
RULES = [  # (applies to target models, test on the request, message)
    ({"claude-opus-5-5", "claude-sonnet-5-5", "claude-fable-5-1"},
     lambda r: r.get("tool_choice", {}).get("type") in ("any", "tool"), "forced tool_choice → use auto + strict tools"),
    ({"claude-opus-5-5"}, lambda r: r.get("thinking", {}).get("type") == "disabled", "thinking can't be disabled → lower effort instead"),
    ({"*"}, lambda r: "budget_tokens" in r.get("thinking", {}), "budget_tokens → adaptive thinking + effort"),
    ({"*"}, lambda r: any(k in r for k in ("temperature", "top_p", "top_k")), "sampling parameters → remove them"),
    ({"*"}, lambda r: r["messages"][-1]["role"] == "assistant", "assistant prefill → structured outputs or instructions"),
    ({"claude-opus-5-5", "claude-haiku-5-5"}, lambda r: "effort" not in r.get("output_config", {}), "effort defaults to medium here → set it explicitly"),
]

def check_migration(request, target):
    return [msg for models, test, msg in RULES if ("*" in models or target in models) and test(request)] or ["no known breaking changes"]

legacy = {"model": "claude-sonnet-4-6", "temperature": 0.2, "tool_choice": {"type": "tool", "name": "extract"},
          "thinking": {"type": "enabled", "budget_tokens": 4000},
          "messages": [{"role": "user", "content": "..."}, {"role": "assistant", "content": "{"}]}
for target in ("claude-sonnet-5-5", "claude-opus-5-5"):
    print(f"{legacy['model']} → {target}:")
    for issue in check_migration(legacy, target): print("   -", issue)
```

> [tip] Migrate like any risky release: read the migration guide, pin the new ID in config (never an alias), run the full eval set on both models, re-tune effort and prompts (prompts written for older models are often too prescriptive for newer ones), and roll out gradually with a way back.

## 5.6 | Token budgets and cost models

**Token usage tracking** records the tokens each request uses; **cost modelling** turns that into money, by route, model and day. Every response's `usage` tells you what you need:

| `usage` field | Billed at |
|---|---|
| `input_tokens` | Base input price (uncached input) |
| `cache_creation_input_tokens` | About 1.25× input (5-minute cache) or 2× (1-hour) |
| `cache_read_input_tokens` | About 0.1× input (0.05× on Opus 5.5) |
| `output_tokens` | Output price, including thinking tokens |

Here's a cost model built from a day of logged `usage` records (the records are a sample we wrote; the aggregation is real). It answers the questions that matter: where does the money go, is caching working, and what does a *completed task* cost?

```python
PRICES = {"claude-haiku-5-5": (0.10, 0.50, 0.01), "claude-sonnet-5-5": (2.00, 10.00, 0.20)}  # in, out, cache read

LOG = [  # route, model, task_id, input, cache_write, cache_read, output
    ("faq",    "claude-haiku-5-5",  "t1", 900,  0,      14_000, 120),
    ("faq",    "claude-haiku-5-5",  "t2", 850,  0,      14_000, 140),
    ("faq",    "claude-haiku-5-5",  "t3", 950,  14_000, 0,      110),
    ("triage", "claude-sonnet-5-5", "t4", 2_100, 0,     22_000, 400),
    ("triage", "claude-sonnet-5-5", "t4", 2_600, 0,     22_000, 380),   # same task, 2nd turn
    ("triage", "claude-sonnet-5-5", "t5", 2_300, 22_000, 0,     420),
    ("report", "claude-sonnet-5-5", "t6", 48_000, 0,    0,      3_900),
    ("report", "claude-sonnet-5-5", "t6", 52_000, 0,    0,      3_600),   # retry after a bad draft
]

def cost(model, inp, cw, cr, out):
    pin, pout, pread = PRICES[model]
    return (inp * pin + cw * pin * 1.25 + cr * pread + out * pout) / 1e6

by_route, tasks = {}, {}
for route, model, task, inp, cw, cr, out in LOG:
    c = cost(model, inp, cw, cr, out)
    r = by_route.setdefault(route, {"usd": 0, "calls": 0, "read": 0, "uncached": 0})
    r["usd"] += c; r["calls"] += 1; r["read"] += cr; r["uncached"] += inp + cw
    tasks.setdefault((route, task), 0); tasks[(route, task)] += c

for route, r in by_route.items():
    n_tasks = len([t for t in tasks if t[0] == route])
    hit = r["read"] / (r["read"] + r["uncached"])
    print(f"{route:<7} ${r['usd']:.4f}  {r['calls']} calls, {n_tasks} tasks  "
          f"→ ${r['usd'] / n_tasks:.4f} per task   cache-read share {hit:.0%}")
total = sum(r["usd"] for r in by_route.values())
print(f"\nreport route is {by_route['report']['usd'] / total:.0%} of today's spend with no caching at all")
```

> [read] The report route is a single task but most of the day's spend: two large uncached calls, one of them a retry. That's where to look first: cache its stable prefix, or fix whatever made the first draft fail. The FAQ route's cache works (most input tokens are reads). Per-*task* cost exposes the triage conversation's two turns that per-call cost hides.

> [warn] Usage-based cost figures computed in your app (and the `total_cost_usd` estimates Claude Code and the Agent SDK report) are **client-side estimates** for monitoring and planning. The bill comes from Anthropic's usage and cost reporting.

### Cost versus latency: not equal weights

Latency is usually a **constraint** set by the people using the system: a live chat needs an answer in seconds; a nightly report needs to be there by morning. Cost is what you **optimise within** that constraint. So the question isn't "cost or latency?" but "given the latency we must meet, what's the cheapest way to meet it?"

```flow title="Optimising cost inside a latency constraint"
Fix the latency need | Someone waiting? Seconds, minutes, or by tomorrow?
Pick the API pattern | Real time (streamed) if waiting; batch at half price if not.
Cache the stable prefix | Usually the biggest free saving.
Trim the input | Shorter history, pruned tool output, smaller images.
Lower effort, then smaller model | Each only as far as the eval still passes.
```

```quiz

- [x] Why tasks need retries, since per-task cost includes every failed attempt

why: Zero cache reads on large repeated inputs is the classic free saving; retries multiply cost per completed task. Fast mode would raise prices, and `max_tokens` doesn't reduce input cost.
```
