## 4.1 | Error types and recovery

When a Claude app breaks, the instinct is to blame the model. Often that's wrong. Errors fall into **four categories**, and the category tells you where to look first and who owns the fix.

| Category | Symptoms | Where to look first |
|---|---|---|
| **Integration / API** | `401`, `429`, `500`, empty or malformed responses, parsing crashes | Status codes, API logs, the exact request payload |
| **Infrastructure** | Timeouts, dropped connections, a downstream service down, intermittent failures | Network and service status, retries, dependency health |
| **Prompt / input** | The model answers the *wrong* question; context missing; input malformed | The fully **rendered** prompt actually sent that turn |
| **Model / output** | Correct input, but a confident wrong answer, a refusal, or the wrong format | The trace: exact input and exact output |

Triage in order, from the outside in:

```flow title="Four questions, in this order"
Did it reach the model? | Check the status code and the response. If not, it's integration or infrastructure.
Was the input right? | Read the rendered prompt and tool results. Missing or wrong data is a prompt/input problem.
Is the output wrong, or just shaped differently? | A wrong fact differs from a wrong format, and the fixes differ too.
Does it reproduce every time? | Consistent points to logic or prompt; intermittent points to load, timing or sampling.
```

### Four recovery strategies

Decide how each kind of error is handled **before** it happens. Improvised handling is how a small hiccup becomes a broken experience.

| Strategy | What it does | Right for |
|---|---|---|
| **Retry** (with backoff, bounded) | Try again after a short, growing wait | Transient errors: `429`, `5xx`, `529`, network blips |
| **Fallback** | Serve a default, a cached answer or a simpler path | The live call can't succeed now, and *something* useful can be shown |
| **Graceful degradation** | Return the parts that worked, and say what's missing | Partial failure: some sections or sources failed |
| **Escalation** | Hand off to a person | High stakes with low confidence, or a decision Claude shouldn't make |

> [warn] The exam's favourite wrong answers: **silent failure** (the user gets nothing and no explanation), **unbounded retries** (cost and time burn while hiding the real fault), showing **raw stack traces** to users, and using **one strategy for every error**. Retrying a refusal or a reasoning error just repeats it.

Here's a recovery policy as code, run on seven incidents from a clinic assistant.

```python
POLICY = [   # (test, category, strategy), checked in order
    (lambda e: e.get("status") in (429, 500, 529) or e.get("timeout"), "integration/infra (transient)", "retry with backoff, max 3"),
    (lambda e: e.get("status") in (400, 401, 403, 404),                 "integration (permanent)",       "fail fast, alert the team, show a friendly message"),
    (lambda e: e.get("stop_reason") == "refusal",                       "model output",                  "don't retry blindly: rephrase or escalate"),
    (lambda e: e.get("stop_reason") == "max_tokens",                    "model output (truncated)",      "raise max_tokens or split the task, then retry once"),
    (lambda e: e.get("parts_ok") is not None and e["parts_ok"] < e["parts"], "partial failure",          "graceful degradation: return what worked, flag the rest"),
    (lambda e: e.get("stakes") == "high" and e.get("confidence", 1) < 0.7, "low confidence, high stakes", "escalate to a person"),
]

def recover(event):
    for test, category, strategy in POLICY:
        if test(event):
            return category, strategy
    return "none", "proceed"

incidents = [
    ("Monday 9 am burst",                  {"status": 429}),
    ("Key rotated, old one still deployed", {"status": 401}),
    ("Network timeout to the API",          {"timeout": True}),
    ("Summary cut off mid-sentence",        {"stop_reason": "max_tokens"}),
    ("Weekly report: 1 of 4 sources down",  {"parts": 4, "parts_ok": 3}),
    ("Dosage question, model unsure",       {"stakes": "high", "confidence": 0.55}),
    ("Declined a routine billing question", {"stop_reason": "refusal"}),
]
for name, e in incidents:
    category, strategy = recover(e)
    print(f"{name:<37} {category:<30} → {strategy}")
```

> [read] The two 4xx cases look like "errors", but only the 429 is worth retrying; the 401 will fail the same way until someone deploys the new key. The partial report degrades gracefully instead of failing outright, and the dosage question goes to a person, whatever the model's answer was.

### Graceful degradation, in practice

A report built from four sources shouldn't fail because one is down. Return what worked, and be explicit about what didn't.

```python
def build_report(sources):
    sections, missing = [], []
    for name, fetch in sources:
        try:
            sections.append(f"## {name}\n{fetch()}")
        except Exception as e:
            missing.append(f"{name} ({type(e).__name__})")
    note = f"\n\n> Not included: {', '.join(missing)}. Retrying automatically in 15 minutes." if missing else ""
    return "\n\n".join(sections) + note, ("partial" if missing else "complete")

def down(): raise TimeoutError("billing service did not respond in 10s")

report, status = build_report([("Appointments", lambda: "412 booked, 31 no-shows"),
                               ("Billing", down),
                               ("Feedback", lambda: "4.6 / 5 from 88 reviews"),
                               ("Staffing", lambda: "2 open shifts on Saturday")])
print(f"status: {status}\n")
print(report)
```

## 4.2 | Traces, failure modes and isolating the layer

### What a trace is

A **trace** is the recorded journey of one request: the input (system prompt, user message, injected context), every tool call with its parameters and result, the model's output, and metadata (timing, tokens, status). **Trace analysis** is reading that record to find where things went wrong. It's the right tool for *one specific* reported problem; evals (4.3) measure quality across many cases.

Here is a trace of a real-world kind of bug, stored the way most tracing tools store it: a list of timed steps.

```python
TRACE = [
    {"step": "input",  "ms": 0,    "data": {"user": "What's the refund status for order 4471?"}},
    {"step": "model",  "ms": 820,  "data": {"stop_reason": "tool_use", "tokens_out": 41}},
    {"step": "tool",   "ms": 1010, "data": {"name": "lookup_order", "input": {"order_id": "4471"},
                                            "result": {"error": "order not found"}, "is_error": True}},
    {"step": "model",  "ms": 1790, "data": {"stop_reason": "end_turn", "tokens_out": 36,
                                            "text": "I'm sorry, order 4471 doesn't exist in our system."}},
]
CUSTOMER_ORDERS = ["4417", "3902"]       # what the logged-in customer actually has

def analyse(trace):
    notes = []
    for i, s in enumerate(trace):
        d = s["data"]
        if s["step"] == "tool" and d.get("is_error"):
            notes.append(f"step {i}: {d['name']}({d['input']}) failed: {d['result']['error']}")
            near = [o for o in CUSTOMER_ORDERS if sorted(o) == sorted(d["input"]["order_id"])]
            if near:
                notes.append(f"         likely a typo: the customer owns {near[0]} (same digits, different order)")
        if s["step"] == "model" and d.get("text") and "doesn't exist" in d["text"]:
            notes.append(f"step {i}: model stated a conclusion instead of asking the customer to confirm the number")
    total = trace[-1]["ms"]
    notes.append(f"latency {total} ms: model {820 + (1790 - 1010)} ms, tool {1010 - 820} ms")
    return notes

for n in analyse(TRACE): print(n)
```

> [read] The model's reasoning wasn't the root cause: the tool was called with a transposed order number, straight from what the customer typed. The fix is in two places: the tool's error should suggest the customer's real orders, and the prompt should say "if an order isn't found, ask the customer to confirm the number". Without the trace, this looks like "Claude said the order doesn't exist".

### Failure modes: naming the pattern

A one-off bug is random. A **failure mode** is a recurring pattern you can name, test for and design around. Four account for most LLM-app failures:

| Failure mode | Looks like (in a document summariser) | Typical fix |
|---|---|---|
| **Hallucination** | The summary states a figure that isn't in the document | Ground in sources, require quotes or citations, allow "not stated" |
| **Refusal / over-caution** | Declines to summarise a contract, reading it as a request for legal advice | Explain the legitimate purpose; adjust the system prompt; escalate edge cases |
| **Format drift** | Asked for 3 bullets, returns a paragraph; JSON missing fields | Structured outputs, schemas, validation and a retry |
| **Instruction breakdown** | Asked to summarise *and* flag risks; only the summary comes back | Number the steps; check each one; split into a chain |

Each mode needs its own detector. Here are four simple ones, run over six outputs from a summariser asked for "exactly 3 bullet points, then a line starting 'Risks:'".

```python
import re

SOURCE = "Revenue rose 12% to ₹4.1 crore. Two clinics opened in Pune. Staff turnover was 18%."

def detect(output):
    found = []
    if re.search(r"\b(can't|cannot|unable to) (help|assist|summari[sz]e)", output, re.I):
        return ["refusal / over-caution"]
    numbers = set(re.findall(r"\d+(?:\.\d+)?%?", output)) - set(re.findall(r"\d+(?:\.\d+)?%?", SOURCE)) - {"3"}
    if numbers:
        found.append(f"hallucination? numbers not in source: {sorted(numbers)}")
    bullets = [l for l in output.splitlines() if l.startswith("- ")]
    if len(bullets) != 3:
        found.append(f"format drift: {len(bullets)} bullets")
    if "Risks:" not in output:
        found.append("instruction breakdown: no 'Risks:' line")
    return found or ["ok"]

outputs = {
    "A": "- Revenue up 12% to ₹4.1 crore\n- Two clinics opened in Pune\n- Turnover 18%\nRisks: staff turnover",
    "B": "- Revenue up 15% to ₹4.1 crore\n- Two clinics opened in Pune\n- Turnover 18%\nRisks: staff turnover",
    "C": "Revenue rose 12% and two clinics opened in Pune, with turnover at 18%.\nRisks: turnover",
    "D": "- Revenue up 12%\n- Two clinics opened in Pune\n- Turnover 18%",
    "E": "I can't summarise documents that may contain financial advice.",
    "F": "- Revenue up 12%\n- Two Pune clinics\n- Turnover 18%, up from 11%\nRisks: hiring",
}
for k, out in outputs.items():
    print(k, "→", "; ".join(detect(out)))
```

> [read] B invents 15%, F invents "up from 11%", C drifts into a paragraph, D drops the second instruction, and E refuses a harmless request. Rule-based detectors like these are crude (a hallucinated *name* would slip past the number check), which is why 4.3 adds a model-based grader. But naming the mode is what tells you which fix to reach for.

### Integration layer or model output?

The same bad answer can come from two very different places. The **integration layer** is your code: prompt construction, parsing, tool wiring, API calls. The **model output** is what Claude generates from correct input. The key technique is the **isolation test**: capture the exact rendered input the model received, check it, then replay it directly, outside your app, and see whether the problem reproduces.

```seq title="The isolation test"
You, Your app's logs, Claude (direct)
You -> Your app's logs: Pull the exact rendered request for the bad case
Your app's logs --> You: system + messages + tools, as actually sent
note You: Is the input complete and correct? If not → integration layer
You -> Claude (direct): Replay that exact request (console, notebook or script)
Claude (direct) --> You: Same problem? → model output. Problem gone? → integration layer (after the call)
```

Three bug reports from a PDF summariser, run through that test. The "model" is a scripted stand-in that behaves the way a real one would for these inputs; the rendering, checking and replay logic is real.

```python
TEMPLATE = "Summarise this report in 3 bullets.\n<report>\n{text}\n</report>"
TRUE_TEXT = {"q3_review.pdf": "Sales grew. Costs fell. Conclusion: expand to Nashik.",
             "audit_2026.pdf": "Audit found 3 billing errors. Conclusion: retrain front desk.",
             "pune_ops.pdf": "Wait times fell. Two nurses hired. Conclusion: extend hours."}

def parse_pdf(name):                       # our integration code: scanned PDFs come back empty
    return "" if name == "audit_2026.pdf" else TRUE_TEXT[name]

def stand_in_model(prompt):
    body = prompt.split("<report>\n")[1].split("\n</report>")[0]
    if not body.strip():
        return "- (no content provided)"
    first, second = body.split(". ")[:2]
    return f"- {first}\n- {second}\n- Overall positive"          # never mentions the conclusion

def show_in_app(reply, doc):               # our integration code: a display bug for one template
    return reply.splitlines()[0] if doc == "pune_ops.pdf" else reply

def isolation_test(doc, complaint, bug_present):
    rendered = TEMPLATE.format(text=parse_pdf(doc))
    input_ok = TRUE_TEXT[doc] in rendered
    replay = stand_in_model(rendered)                     # the exact request, sent directly
    reproduces = bug_present(replay)
    if not input_ok:
        verdict = "integration layer: the input was already wrong (fix the parser)"
    elif reproduces:
        verdict = "model output: correct input, still wrong (fix the prompt)"
    else:
        verdict = "integration layer: fine when replayed, broken in the app (fix code after the call)"
    print(f"{doc}: {complaint}\n   input complete: {input_ok}   reproduces on replay: {reproduces}\n   → {verdict}")

isolation_test("q3_review.pdf", "summary misses the conclusion", lambda out: "Nashik" not in out)
isolation_test("audit_2026.pdf", "summary is empty", lambda out: "no content" in out)
isolation_test("pune_ops.pdf", "summary has only one bullet", lambda out: len(out.splitlines()) < 3)
print("\nwhat the Pune user saw:", repr(show_in_app(stand_in_model(TEMPLATE.format(text=parse_pdf("pune_ops.pdf"))), "pune_ops.pdf")))
```

> [read] Three reports of "a bad summary", three different owners. The Q3 input was complete and the replay still drops the conclusion: a **model-output** problem, fixed in the prompt (it never asks for the conclusion). The audit's rendered input had no report text: an **integration** bug in the PDF parser, visible before the model was ever called. The Pune summary is fine when replayed but broken in the app: an **integration** bug *after* the call, in the code that displays the reply.

> [exam] If a scenario says the problem "disappears when the same request is sent directly to the API", the fault is in the integration layer. If it "reproduces with the exact rendered prompt", look at the prompt or the model's behaviour.

## 4.3 | Evals and monitoring

### What an eval is

Changing a prompt, trying it three times and shipping it because "it looks good" is a **vibe check**. An **eval** is a structured, repeatable test: a set of **test cases**, **grading criteria**, and a **score or threshold**. It's the LLM equivalent of a test suite, and it's how you compare two prompts, two models or two settings on equal terms.

```flow title="Designing and running an eval"
Define the objective | What does "good" mean here? Accurate, on-brand, resolves the question.
Build the test set | 30–50+ real cases: common, edge, adversarial, angry. Keep it versioned.
Choose the grading | Rule-based where you can; a model judge for nuance; people for high stakes.
Run it | Every case, every time, automatically; save every output.
Analyse and act | Read the failures by category, fix, rerun to prove the fix worked.
```

| Grading | Best for | Watch out for |
|---|---|---|
| **Rule-based** (code) | Format, required fields, keywords, length, exact answers | Can't judge tone, nuance or correctness of free text |
| **Model-based** (LLM as judge) | Subjective quality at scale: tone, helpfulness, faithfulness to a source | The judge itself needs validating against human labels |
| **Human** | High stakes, ambiguous calls, building the reference labels | Slow and expensive: use sparingly and deliberately |

### An eval harness, step by step

Twelve support emails, two prompt versions. The replies were written by us to stand in for the two versions' outputs; the harness, grading and statistics are real code.

```python
CASES = [  # (id, category, must_mention, reply_v1, reply_v2)
    (1, "refund",   "7 days",       "Refunds take 7 days.",                         "Your refund will arrive within 7 days."),
    (2, "refund",   "7 days",       "We will look into it.",                        "Refunds reach your account within 7 days."),
    (3, "booking",  "reschedule",   "You can reschedule online.",                   "You can reschedule online or by phone."),
    (4, "booking",  "reschedule",   "Please call us.",                              "To reschedule, use the link in your SMS."),
    (5, "angry",    "sorry",        "Calm down, it's being handled.",               "I'm sorry about the wait; it's being handled today."),
    (6, "angry",    "sorry",        "Sorry for the trouble.",                       "I'm sorry for the trouble."),
    (7, "clinical", "nurse",        "Take paracetamol and rest.",                   "A nurse will call you within the hour."),
    (8, "clinical", "nurse",        "A nurse will call you.",                       "A nurse will call you shortly."),
    (9, "billing",  "invoice",      "Your invoice is attached.",                    "Your invoice is attached."),
    (10, "billing", "invoice",      "Check your email.",                            "We've re-sent the invoice to your email."),
    (11, "refund",  "7 days",       "Refunds take 7 days.",                         "Refunds take about a week."),
    (12, "booking", "reschedule",   "You can reschedule online.",                   "You can reschedule online."),
]
BANNED = ["calm down", "paracetamol"]          # tone and safety rules

def grade(reply, must):
    if any(b in reply.lower() for b in BANNED): return False, "banned phrase"
    if must.lower() not in reply.lower():       return False, f"missing '{must}'"
    return True, ""

def run_eval(version):
    col = 3 if version == "v1" else 4
    results = [(c[0], c[1], *grade(c[col], c[2])) for c in CASES]
    return results

def wilson(passes, n, z=1.96):                 # 95% interval for a pass rate
    p = passes / n; d = 1 + z * z / n
    centre = (p + z * z / (2 * n)) / d; half = z * ((p * (1 - p) / n + z * z / (4 * n * n)) ** 0.5) / d
    return centre - half, centre + half

for v in ("v1", "v2"):
    res = run_eval(v)
    passes = sum(ok for _, _, ok, _ in res)
    lo, hi = wilson(passes, len(res))
    fails = {}
    for _, cat, ok, why in res:
        if not ok: fails.setdefault(cat, []).append(why)
    print(f"{v}: {passes}/{len(res)} pass ({passes / len(res):.0%}, 95% CI {lo:.0%}–{hi:.0%})  failures: {fails}")
```

> [read] v2 fixes the unsafe paracetamol advice and the "calm down" tone, and v2's one failure (case 11, "about a week") is arguably a grading problem: the rule demands the literal words "7 days". That's the lesson in two parts. Rule-based grading is strict, so read your failures before trusting the score. And with only 12 cases, the intervals are wide: even 58% against 92% gives overlapping 95% intervals, so the result is a strong hint, not proof; two prompts scoring 85% and 90% on 12 cases would tell you nothing. More cases, not more runs of the same few, is what narrows the interval.

### LLM as judge

For qualities code can't check (is this reply empathetic? faithful to the policy?), a model can grade, quickly and at scale, if you give it a precise rubric and ask for a structured verdict.

```prompt title="A judge prompt"
You are grading a clinic's reply to a patient email. Grade only against the rubric.

<policy>{policy_text}</policy>
<patient_email>{email}</patient_email>
<reply>{reply}</reply>

Rubric (each pass/fail):
1. accurate: every factual statement is supported by the policy
2. resolves: it answers what the patient actually asked
3. safe: no medical advice; clinical issues are routed to a nurse
4. tone: polite and warm; no blame or dismissiveness

Think through each criterion briefly, then output JSON only:
{"accurate": true|false, "resolves": true|false, "safe": true|false, "tone": true|false,
 "evidence": "the phrase that decided any failure"}
```

> [warn] Don't let a model grade its own homework without checking it. Use a judge prompt (ideally a different model or at least a separate call), validate it against human labels on a sample, and recheck whenever you change the judge. Prefer pass/fail per criterion over a 1–10 score: it's more consistent and easier to act on.

Validating a judge means measuring how often it agrees with people, beyond what chance would give. Cohen's kappa does that. Here are 20 replies labelled by a person and by two candidate judge prompts.

```python
human   = "PPFPPFFPPPFPPFPPPFPP"
judge_a = "PPFPPFFPPPFPPPPPPFPP"
judge_b = "PPPPPPPPPPPPPPPPPPPP"            # says "pass" to everything

def kappa(a, b):
    n = len(a)
    observed = sum(x == y for x, y in zip(a, b)) / n
    pa, pb = a.count("P") / n, b.count("P") / n
    expected = pa * pb + (1 - pa) * (1 - pb)
    return observed, (observed - expected) / (1 - expected) if expected < 1 else 0.0

for name, j in [("judge A", judge_a), ("judge B", judge_b)]:
    agree, k = kappa(human, j)
    print(f"{name}: agrees on {agree:.0%} of cases, Cohen's kappa = {k:.2f}")
```

> [read] Judge B agrees with the person 70% of the time, which sounds fine, but it simply passes everything; kappa of 0 shows it adds nothing. Judge A agrees on 95% and has a kappa near 0.9: worth using. Raw agreement flatters lazy judges.

### Monitoring production quality

An eval is a pre-flight checklist on a fixed set; **monitoring** is the cockpit dashboard on live traffic. Track signals over time (error rates, thumbs up/down, escalations, refusals, cost, latency), **read a sample of real traces** regularly, and alert on thresholds. The loop closes when a production failure becomes a new eval case.

```seq title="Closing the loop"
Monitoring, Trace analysis, Eval set, Release
Monitoring -> Trace analysis: Alert: thumbs-down rate doubled on Tuesday
Trace analysis --> Monitoring: Cause: new "teleconsult" questions the prompt doesn't cover
Trace analysis -> Eval set: Add 15 teleconsult cases (they fail today)
Eval set -> Release: Prompt v5 passes old and new cases
Release --> Monitoring: Ship; watch the same signal
```

Even with a pinned model, quality can slip, because **the inputs drift**: new products, seasons, user groups and phrasing. Comparing this week's mix of request types with the mix your eval set was built on is a cheap early warning. The population stability index (PSI) is one common measure; above about 0.2 is usually treated as a significant shift.

```python
import math

def psi(expected, actual):
    total = 0
    for k in expected:
        e, a = max(expected[k], 1e-4), max(actual.get(k, 0), 1e-4)
        total += (a - e) * math.log(a / e)
    return total

eval_mix   = {"booking": 0.45, "billing": 0.20, "refund": 0.15, "clinical": 0.15, "teleconsult": 0.05}
week_mix   = {"booking": 0.42, "billing": 0.21, "refund": 0.16, "clinical": 0.15, "teleconsult": 0.06}
launch_mix = {"booking": 0.30, "billing": 0.15, "refund": 0.10, "clinical": 0.15, "teleconsult": 0.30}

for label, mix in [("an ordinary week", week_mix), ("week teleconsults launched", launch_mix)]:
    v = psi(eval_mix, mix)
    print(f"{label:<27} PSI = {v:.3f}  → {'DRIFT: refresh the eval set' if v > 0.2 else 'stable'}")
```

> [tip] Tools such as LangSmith (from LangChain, usable without LangChain itself) bundle this: traces of every step, online and offline evals, LLM-as-judge evaluators, human feedback, and dashboards with alerts. OpenTelemetry tracing of the Claude SDKs feeds the same kind of tooling. Whatever you use, the practice is the same: traces for single failures, evals for change, monitoring for drift.
