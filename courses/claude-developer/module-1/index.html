Session 1.1

Workflow or agent?

Every Claude feature you build sits on one of three tiers. Pick the lowest tier that does the job: each step up costs more, takes longer and is harder to test.

TierWho decides the next step?Good forExample
Single callNobody: one request, one responseClassify, extract, summarise, rewriteTag a patient message as booking, billing or clinical
WorkflowYour code, along a path you wroteMulti-step jobs whose steps you can list in advanceExtract invoice fields, validate them, then draft an email
AgentClaude, one tool call at a timeOpen-ended jobs you can't fully specify up front"Find why last night's build failed and fix it"
The idea

The difference is who holds the steering wheel. In a workflow, Claude is a component inside a path your code controls. In an agent, Claude chooses which tool to call next, reads the result, and decides again, until it judges the goal met. That freedom is what makes agents powerful, and what makes them slower, costlier and less predictable.

Generative and agentic, side by side

You'll hear "generative AI" and "agentic AI" contrasted. Generative AI answers a prompt: one input, one output, no actions. Agentic AI is given a goal, plans, uses tools, checks results and keeps going. The same model can be both. What changes is the code around it.

Workflow patterns worth knowing by name

Most production "AI features" are workflows, not agents. Five patterns cover most of them:

PatternWhat your code doesUse when
Prompt chainingOutput of step 1 becomes the input of step 2, with a check in betweenThe task splits cleanly into fixed stages
RoutingClassify first, then send to a specialised prompt or modelInputs fall into distinct types needing different handling
ParallelisationRun independent calls at once, then merge (or vote)Sub-tasks don't depend on each other
Orchestrator–workersOne call plans sub-tasks, workers do them, results are mergedYou can't know the sub-tasks until you see the input
Evaluator–optimiserOne call drafts, another grades against criteria, loop until it passesThere are clear quality criteria and iteration helps

Four questions before you build an agent

An agent is justified only when the answer to all four is yes. If any answer is no, drop to a workflow or a single call.

  • Complexity: is the task multi-step and hard to specify in advance?
  • Value: is the outcome worth the extra cost and latency?
  • Viability: is Claude actually good at this kind of task?
  • Cost of error: can mistakes be caught and undone (tests, review, rollback)?

Here are those four questions as code, run against five tasks. The scoring is ours, a way to make the reasoning explicit, not an official formula.

Python
def choose_tier(task):
    """Return the lowest tier that fits, with the reason."""
    if task["steps_known_in_advance"] and task["steps"] == 1:
        return "single call", "one step, nothing to orchestrate"
    if task["steps_known_in_advance"]:
        return "workflow", "the path can be written down, so code should own it"
    # Open-ended: an agent is a candidate, but only if all four checks pass
    checks = {
        "complexity": not task["steps_known_in_advance"],
        "value": task["value_per_run_usd"] >= 5 * task["est_cost_usd"],
        "viability": task["claude_good_at_it"],
        "cost of error": task["errors_reversible"],
    }
    failed = [k for k, ok in checks.items() if not ok]
    if failed:
        return "workflow (+ human)", "agent ruled out by: " + ", ".join(failed)
    return "agent", "open-ended, worth it, feasible, and errors can be undone"

tasks = [
    ("Tag a message as booking/billing/clinical", dict(steps_known_in_advance=True,  steps=1, value_per_run_usd=0.02, est_cost_usd=0.001, claude_good_at_it=True,  errors_reversible=True)),
    ("Invoice: extract, validate, draft email",   dict(steps_known_in_advance=True,  steps=3, value_per_run_usd=1.5,  est_cost_usd=0.01,  claude_good_at_it=True,  errors_reversible=True)),
    ("Fix last night's failing build",            dict(steps_known_in_advance=False, steps=0, value_per_run_usd=60,   est_cost_usd=1.2,   claude_good_at_it=True,  errors_reversible=True)),
    ("Research a competitor, write a brief",      dict(steps_known_in_advance=False, steps=0, value_per_run_usd=40,   est_cost_usd=0.8,   claude_good_at_it=True,  errors_reversible=True)),
    ("Move money between client accounts",        dict(steps_known_in_advance=False, steps=0, value_per_run_usd=25,   est_cost_usd=0.5,   claude_good_at_it=True,  errors_reversible=False)),
]

for name, t in tasks:
    tier, why = choose_tier(t)
    print(f"{name:<44} → {tier:<18} {why}")

How to read it

The first two tasks never reach the agent checks: their steps are known, so code should own the path. The money transfer is open-ended, but a wrong transfer can't be undone, so it stays a workflow with a human approving each step.

Exam lens

Expect scenario questions that describe a task and ask for the most appropriate architecture. Watch for the words that settle it: "the steps are always the same" points to a workflow; "unpredictable", "open-ended" or "explore" points to an agent; "irreversible", "regulated" or "must be auditable" pulls you back towards fixed steps and a human.

Types of agent, from simplest up

Textbooks sort agents into five types. You won't build a "simple reflex agent" with Claude, but the ladder is a useful vocabulary.

TypeDecides byEveryday example
Simple reflexIf-then rules on the current inputA thermostat; lock an account after five bad passwords
Model-basedRules plus an internal picture of the world over timeA spam filter that learns each sender's pattern
Goal-basedPlanning steps towards a stated goalA Claude agent asked to "get the tests passing"
Utility-basedChoosing the option that scores best on a trade-offRoute planning that weighs time against cost

Practice questionA clinic wants every new lab report PDF to be read, the key values extracted into their system, and a summary sent to the doctor. The steps never change. What's the most appropriate design?

The steps are fixed and known in advance, so code should own the path and Claude should do the parts that need language understanding. An agent adds cost and unpredictability for no benefit; a single call leaves the integration undone; multiple agents add coordination overhead to a linear job.

Practice questionSelect 2Which two facts most strongly argue against using an agent for a task? (Select 2)

Irreversible errors fail the "cost of error" check, and a fixed sequence of steps means a workflow can do the job more cheaply and predictably. Needing several tools or taking an hour by hand doesn't, by itself, call for model-driven control.

Session 1.2

The agentic loop

An agent isn't a special model or a special endpoint. It's a loop in your code around the Messages API. The model can't run anything: it can only ask for a tool call. Your code runs the tool, sends the result back, and asks again, until the model says it's done.

The loop has four stages, and it repeats them until the model stops asking for tools:

Watch out

The API is stateless. The model remembers nothing between requests. Whatever isn't in messages doesn't exist for it. Send a partial history and you get answers based on a partial picture.

What stop_reason tells your code

stop_reasonMeaningWhat your loop does
end_turnThe model has finishedRead the final text and stop
tool_useIt wants one or more tools runRun them all, send back all results, loop
max_tokensIt was cut off by your max_tokens limitDon't run a half-written tool call; raise the limit or continue
pause_turnA server-side tool paused a long turnSend the conversation back as is so it can continue
refusalThe model declined for safety reasonsDon't read content as an answer; handle it (and check stop_details)
stop_sequenceIt hit one of your stop sequencesTreat as finished, or handle as your design intends

The loop with the real SDK

This is the shape you'd write against the API. It needs an API key, so it's shown here, not run.

Pythonshown, not run here
import anthropic

client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY from the environment
messages = [{"role": "user", "content": "Is Dr Rao free on Friday morning? If so, hold 10:30 for Mrs Iyer."}]

while True:
    response = client.messages.create(
        model="claude-opus-5-5", max_tokens=16000,
        system=SYSTEM, tools=TOOLS, messages=messages,
    )
    messages.append({"role": "assistant", "content": response.content})   # keep the whole turn

    if response.stop_reason != "tool_use":
        break

    results = []
    for block in response.content:                     # there may be several tool_use blocks
        if block.type == "tool_use":
            output, failed = run_tool(block.name, block.input)
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": output, "is_error": failed})
    messages.append({"role": "user", "content": results})   # all results, one user turn

print(next(b.text for b in response.content if b.type == "text"))

The same loop, run here

To show the loop running without an API key, we replace Claude with a scripted stand-in: a function that returns the replies we wrote for it, in the same shape the API uses (a list of content blocks plus a stop_reason). Everything else, the tools, the dispatch and the history, is real code doing real work.

First, two tools and a dispatcher. The calendar is a plain dictionary.

Python
import json

CALENDAR = {("Dr Rao", "Fri"): {"09:00": "Mr Shah", "10:30": None, "11:15": None}}
HOLDS = []

def check_slots(doctor, day):
    slots = CALENDAR.get((doctor, day))
    if slots is None:
        raise KeyError(f"no calendar for {doctor} on {day}")
    return [t for t, who in slots.items() if who is None]

def hold_slot(doctor, day, time, patient):
    if CALENDAR[(doctor, day)].get(time, "taken") is not None:
        raise ValueError(f"{time} is not free")
    CALENDAR[(doctor, day)][time] = patient + " (held)"
    HOLDS.append((doctor, day, time, patient))
    return f"held {time} on {day} with {doctor} for {patient}"

TOOLS = {"check_slots": check_slots, "hold_slot": hold_slot}

def run_tool(name, args):
    """Route a tool call to its function. Return (content, is_error)."""
    if name not in TOOLS:
        return f"unknown tool: {name}", True
    try:
        return json.dumps(TOOLS[name](**args)), False
    except Exception as e:                       # report the failure to the model, don't crash the loop
        return f"{type(e).__name__}: {e}", True

print(run_tool("check_slots", {"doctor": "Dr Rao", "day": "Fri"}))
print(run_tool("check_slots", {"doctor": "Dr Rao", "day": "Sun"}))

('["10:30", "11:15"]', False)

Now the stand-in for Claude. On its first turn it asks for two tool calls at once (models often do), then a hold, then gives its answer.

Python
SCRIPT = [
    {"stop_reason": "tool_use", "content": [
        {"type": "text", "text": "I'll check Friday, and Saturday as a fallback."},
        {"type": "tool_use", "id": "tu_1", "name": "check_slots", "input": {"doctor": "Dr Rao", "day": "Fri"}},
        {"type": "tool_use", "id": "tu_2", "name": "check_slots", "input": {"doctor": "Dr Rao", "day": "Sat"}}]},
    {"stop_reason": "tool_use", "content": [
        {"type": "tool_use", "id": "tu_3", "name": "hold_slot",
         "input": {"doctor": "Dr Rao", "day": "Fri", "time": "10:30", "patient": "Mrs Iyer"}}]},
    {"stop_reason": "end_turn", "content": [
        {"type": "text", "text": "Done: 10:30 on Friday with Dr Rao is held for Mrs Iyer."}]},
]

def scripted_claude(messages, turn):
    """A stand-in for client.messages.create: returns the next scripted reply."""
    return SCRIPT[turn]

And the loop itself, the same logic as the SDK version, printing what crosses the wire.

Python
def run_agent(user_text, model=scripted_claude, max_turns=10):
    messages = [{"role": "user", "content": user_text}]
    for turn in range(max_turns):
        reply = model(messages, turn)
        messages.append({"role": "assistant", "content": reply["content"]})
        calls = [b for b in reply["content"] if b["type"] == "tool_use"]
        print(f"turn {turn + 1}: stop_reason={reply['stop_reason']}, tool calls={len(calls)}")
        if reply["stop_reason"] != "tool_use":
            return reply["content"][-1]["text"], messages
        results = []
        for c in calls:
            content, failed = run_tool(c["name"], c["input"])
            print(f"   {c['name']}({c['input']['day']}) → {'ERROR ' if failed else ''}{content}")
            results.append({"type": "tool_result", "tool_use_id": c["id"], "content": content, "is_error": failed})
        messages.append({"role": "user", "content": results})
    raise RuntimeError(f"no answer after {max_turns} turns")

answer, history = run_agent("Is Dr Rao free on Friday morning? If so, hold 10:30 for Mrs Iyer.")
print("\nfinal answer:", answer)
print("messages in history:", len(history), "→", [m["role"] for m in history])
Output · produced by running this code

   check_slots(Fri) → ["10:30", "11:15"]
   check_slots(Sat) → ERROR KeyError: 'no calendar for Dr Rao on Sat'
turn 2: stop_reason=tool_use, tool calls=1
   hold_slot(Fri) → "held 10:30 on Fri with Dr Rao for Mrs Iyer"

How to read it

Saturday failed (there's no calendar for it), and the loop didn't crash: the error went back to the model as a tool_result with is_error: true, so it can adapt. The history alternates user, assistant, user... and the tool results travel in user turns. Six messages for three model calls: each call saw everything before it.

The mistakes that break agents

Three bugs account for most broken loops. The API rejects the first one outright; the other two fail quietly.

  • Dropping a tool call. If you only handle the first tool_use block, the second has no matching tool_result, and the next request is rejected.
  • Splitting the results. Return every tool_result from a turn in one user message. Spreading them over several messages teaches the model to stop making parallel calls.
  • Hiding failures. If a tool fails and you return an empty string, the model may carry on as if it worked, and give a confident wrong answer. Return the error with is_error: true.

Here's a checker for the first two, run on our good history and on a broken one.

Python
def check_history(messages):
    problems = []
    for i, m in enumerate(messages):
        if m["role"] != "assistant" or isinstance(m["content"], str):
            continue
        asked = {b["id"] for b in m["content"] if b["type"] == "tool_use"}
        if not asked:
            continue
        nxt = messages[i + 1] if i + 1 < len(messages) else {"content": []}
        answered = {b.get("tool_use_id") for b in nxt["content"] if isinstance(b, dict)}
        for missing in sorted(asked - answered):
            problems.append(f"message {i}: tool_use {missing} has no tool_result in the next user turn")
    return problems or ["ok"]

print("good history:  ", check_history(history))

broken = [dict(m) for m in history]
broken[2] = {"role": "user", "content": broken[2]["content"][:1]}     # handled only the first call
print("broken history:", check_history(broken))
Output · produced by running this code
good history:   ['ok']
broken history: ['message 1: tool_use tu_2 has no tool_result in the next user turn']

Practice questionClaude's response contains a text block and three tool_use blocks. What should your code send next?

Every tool_use needs a tool_result with the same id, in the user turn that immediately follows, and all of a turn's results belong in one message. Dropping some is rejected by the API; splitting them discourages parallel calls; plain text loses the id link.

Practice questionA tool times out during an agent run. Which response gives the model the best chance of recovering?

An error result keeps the loop alive and tells the model what went wrong, so it can retry with different input, try another tool, or explain the problem. An empty result invites a confident wrong answer; endless retries can hang the agent.

Session 1.3

Coordinators and subagents

When one agent tries to research, analyse, decide and write all at once, its context fills with everything it read and its attention spreads thin. The hub-and-spoke (or orchestrator–worker) pattern splits the job: a coordinator plans and assigns, subagents each do one focused piece and report back, and the coordinator combines the results.

Multi-agent systems usually have four roles, though one agent may play more than one:

RoleJob
Orchestrator (coordinator)Understands the goal, breaks it down, assigns, merges
Workers (subagents)Each does one specialised task: research, code, write
Critic (reviewer)Checks the workers' output against criteria
State managerTracks what's done and what's pending; holds shared context

Work moves between them in two ways. Sequential handoff is a relay: research, then write, then review. Parallel collaboration runs independent pieces at once and merges them: faster, but the coordinator must reconcile overlaps and contradictions.

Why subagents help: context isolation

Each subagent runs in its own context window. It can read fifty pages and return a one-paragraph summary; only the summary lands in the coordinator's context. That keeps the coordinator's context small and focused, and stops one task's detail from distracting another.

Python
# Rough token accounting: what each design puts in the deciding model's context
reading = {"finance": 38_000, "market": 52_000, "risk": 27_000}   # tokens each piece of research reads
summary = 400                                                       # tokens each subagent sends back
brief_instructions = 1_500

single = brief_instructions + sum(reading.values())
coordinator = brief_instructions + summary * len(reading)

print(f"one agent does everything : {single:>7,} tokens in context when it writes the brief")
print(f"coordinator + 3 subagents : {coordinator:>7,} tokens in the coordinator's context")
print(f"largest subagent context  : {max(reading.values()) + 600:>7,} tokens (its own window)")
print(f"total tokens processed    : {sum(reading.values()) + 600 * 3 + coordinator:>7,} (more in total, but no window is overloaded)")

How to read it

Subagents don't make the whole job cheaper. Here they process slightly more tokens in total. What they buy is a coordinator that decides with 2,700 tokens of distilled findings instead of 118,500 tokens of raw reading, and workers that can run in parallel.

Decomposition decides quality

When a multi-agent system gives a poor answer, the cause is usually the coordinator's breakdown, not the subagents. A subagent can only do the task it's given; it won't notice that a responsibility was never assigned, and it can't see the context the coordinator forgot to pass.

✗ Weak decomposition
To subagent: "Analyse the company's performance."

(No scope, no time period, no data sources,
no output format, no length. The subagent has
to guess what matters, and the coordinator
gets back something it can't merge.)
✓ Strong decomposition
To finance subagent:
Objective: compare Q3 revenue and gross margin for our 4 clinics against Q2.
Inputs: the attached Q2 and Q3 P&L exports only.
Out of scope: forecasts, marketing spend.
Output: a table (clinic, revenue Q2, Q3, % change, margin Q2, Q3)
then at most 150 words on the two biggest changes and their likely causes.
If a figure is missing, write "missing", don't estimate.

A coordinator can check its own task specs before it dispatches anything. Here the check is code, and the subagents are plain functions standing in for real ones, run in parallel with a thread pool.

Python
from concurrent.futures import ThreadPoolExecutor
import time

REQUIRED = ("objective", "inputs", "output", "out_of_scope")

plan = [
    {"agent": "finance", "objective": "Q3 vs Q2 revenue and margin per clinic", "inputs": "P&L exports",
     "output": "table + 150 words", "out_of_scope": "forecasts"},
    {"agent": "market", "objective": "competitor openings within 3 km since July", "inputs": "maps search",
     "output": "list of name, date, distance", "out_of_scope": "pricing"},
    {"agent": "risk", "objective": "analyse risks"},                       # under-specified on purpose
]

def missing_fields(spec):
    return [f for f in REQUIRED if not spec.get(f)]

for spec in plan:
    gaps = missing_fields(spec)
    print(f"{spec['agent']:<8} {'ready' if not gaps else 'REJECTED, missing: ' + ', '.join(gaps)}")

def subagent(spec):                      # stand-in: a real one would be its own Claude loop
    time.sleep(0.2)                      # pretend to work
    return {"agent": spec["agent"], "summary": f"[{spec['agent']}] findings on: {spec['objective']}"}

ready = [s for s in plan if not missing_fields(s)]
t0 = time.time()
with ThreadPoolExecutor() as pool:
    reports = list(pool.map(subagent, ready))
print(f"\n{len(reports)} subagents ran in parallel in {time.time() - t0:.1f}s (each takes 0.2s)")
for r in reports:
    print(" ", r["summary"])
Output · produced by running this code
finance  ready
market   ready
risk     REJECTED, missing: inputs, output, out_of_scope

2 subagents ran in parallel in 0.2s (each takes 0.2s)
  [finance] findings on: Q3 vs Q2 revenue and margin per clinic
  [market] findings on: competitor openings within 3 km since July
Tip

Give every subagent task the same five things: objective, inputs, scope (and what's out of it), output format, and what to do when stuck. Ask for a fixed output shape so the coordinator can merge reports without guessing. Start with copies of one agent, and move reading-heavy work to a cheaper model only once the design works.

Exam lens

If a scenario says the final report "misses" something or subagents "overlap", look for an answer that fixes the coordinator's decomposition (clearer scope, explicit ownership, a required output format), not one that swaps in a bigger model for the subagents.

Practice questionA coordinator sends three subagents the instruction "research the market" and gets back three overlapping reports, none covering pricing. What's the best fix?

Overlap and gaps both come from poor decomposition. Explicit, non-overlapping scopes with clear ownership fix both; a bigger model still gets a vague task, and sharing reports mid-run undoes context isolation.

Practice questionSelect 2What is the main benefit of running research in subagents rather than in the coordinator's own loop? (Select 2)

Context isolation and parallelism are the two wins. Total tokens often go up slightly, because each subagent needs its own instructions, and subagents are no more stateful than any other model call.

Session 1.4

Building agents with Claude

You've seen that an agent is a loop plus tools. In practice you rarely write that loop from scratch. There are four ways to build a Claude agent, and two questions separate them: who supplies the harness (the loop, tool execution, context management) and who runs the infrastructure it lives on.

ApproachYou writeHarnessHostingTools
Manual loop on the Messages APIThe while stop_reason == "tool_use" loopYouYouOnly the ones you define
Tool Runner (in the anthropic SDK, beta)Just the tool functionsThe SDKYouOnly the ones you define
Claude Agent SDK (claude-agent-sdk)A prompt and optionsThe SDK: Claude Code's harness as a libraryYouBuilt-in Read, Write, Edit, Bash, Grep, web search..., plus MCP and subagents
Claude Managed Agents (beta)An agent config, plus results for any tools you hostAnthropicAnthropic, in a managed sandboxHosted bash, files and code, plus Skills, MCP and your tools
The idea

Harness and hosting are separate choices. The Tool Runner and the Agent SDK both give you a harness, but you still deploy and run them, on your servers, under your security controls. Managed Agents is the only option where Anthropic runs the loop and the environment the tools execute in. That's the self-hosted versus Anthropic-hosted choice the exam expects you to weigh.

The Tool Runner: tools as decorated functions

The SDK reads each function's signature and docstring to build the tool definition, then runs the loop for you. Shown, not run (it needs an API key).

Pythonshown, not run here
import anthropic
from anthropic import beta_tool

client = anthropic.Anthropic()

@beta_tool
def check_slots(doctor: str, day: str) -> str:
    """List the free appointment times for a doctor on a given day.

    Args:
        doctor: The doctor's name exactly as it appears in the rota, e.g. "Dr Rao".
        day: Three-letter day name, e.g. "Fri".
    """
    return json.dumps(free_slots(doctor, day))

runner = client.beta.messages.tool_runner(
    model="claude-opus-5-5", max_tokens=16000,
    tools=[check_slots],
    messages=[{"role": "user", "content": "When is Dr Rao free on Friday?"}],
)
for message in runner:          # one BetaMessage per model turn; stops when Claude is done
    print(message.content)

The Agent SDK: Claude Code as a library

The Agent SDK gives you the same harness that powers Claude Code: built-in tools, permissions, context management, subagents and hooks. You pass a prompt and options and iterate over the messages it streams back.

Pythonshown, not run here
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

options = ClaudeAgentOptions(
    system_prompt="You maintain the clinic booking service. Never touch production config.",
    allowed_tools=["Read", "Grep", "Glob", "Bash"],   # pre-approved; not a whitelist on its own
    permission_mode="default",
    max_turns=30,
    model="claude-opus-5-5",
    agents={                                           # subagents Claude can delegate to
        "test-runner": AgentDefinition(
            description="Runs the test suite and reports failures concisely.",
            prompt="Run the tests. Report only failing tests with file, line and error.",
            model="claude-haiku-5-5",
        ),
    },
)

async def main():
    async for message in query(prompt="Find why test_booking fails and fix it.", options=options):
        print(message)

asyncio.run(main())
Watch out

In the Agent SDK, allowed_tools pre-approves tools; it doesn't by itself stop Claude using others. To keep a tool away from the agent, use disallowed_tools, a permission mode, or a hook that denies it. A question that treats allowed_tools as a hard sandbox is testing exactly this.

Tip

query() starts a fresh session on every call. When you need several exchanges in one session, or the ability to interrupt, use ClaudeSDKClient instead.

What a harness adds on top of the loop

The bare loop from 1.2 works, but production needs guard rails around it. Here are two, a turn limit and a token budget, added to the loop. The stand-in model this time never finishes: it keeps asking to search, as a confused agent might.

Python
def stuck_model(messages, turn):
    """A scripted stand-in that never stops calling tools."""
    return {"stop_reason": "tool_use", "usage": {"input_tokens": 1_800 + 900 * turn, "output_tokens": 120},
            "content": [{"type": "tool_use", "id": f"tu_{turn}", "name": "check_slots",
                         "input": {"doctor": "Dr Rao", "day": "Fri"}}]}

def guarded_agent(user_text, model, max_turns=8, token_budget=12_000):
    messages, spent, trace = [{"role": "user", "content": user_text}], 0, []
    for turn in range(max_turns):
        reply = model(messages, turn)
        spent += reply["usage"]["input_tokens"] + reply["usage"]["output_tokens"]
        trace.append((turn + 1, reply["stop_reason"], spent))
        if spent > token_budget:
            return "stopped: token budget exceeded", trace
        messages.append({"role": "assistant", "content": reply["content"]})
        if reply["stop_reason"] != "tool_use":
            return "finished", trace
        results = [{"type": "tool_result", "tool_use_id": b["id"], "content": run_tool(b["name"], b["input"])[0]}
                   for b in reply["content"] if b["type"] == "tool_use"]
        messages.append({"role": "user", "content": results})
    return "stopped: turn limit reached", trace

for limit, budget in [(8, 12_000), (3, 50_000)]:
    status, trace = guarded_agent("Find me a slot.", stuck_model, limit, budget)
    print(f"max_turns={limit}, budget={budget:,}: {status}")
    for t, why, spent in trace:
        print(f"   turn {t}: {why:<8} tokens so far {spent:>6,}")

How to read it

Without either guard this agent would loop forever and bill you for every turn. Notice how the token count climbs faster each turn: every request resends the growing history (1.6 comes back to this). Real harnesses add more: retries with backoff, logging every call for traces, permission checks, and context management.

Practice questionA team wants an agent that runs every night, works for up to an hour on a repository, and needs no servers of their own. Which approach fits best?

Only Managed Agents supplies both the harness and the hosting. The Agent SDK has the right tools but must still run on infrastructure the team operates; the manual loop and Tool Runner leave both the loop's hosting and any sandbox to them.

Practice questionWhat is the key difference between the Tool Runner and the Claude Agent SDK?

Both are harness-only libraries you host yourself. The Tool Runner (part of the anthropic SDK) automates the request–execute–loop cycle for your tools; the Agent SDK (claude-agent-sdk) packages Claude Code's whole harness.

Session 1.5

Hooks for deterministic actions

A system prompt that says "never delete files outside the project" is a request. The model will usually follow it. A hook is code that runs at a fixed point in the agent's life cycle, every time, whatever the model decides. Use hooks for anything that must always or never happen.

The hook events you'll meet most:

EventFiresTypical use
PreToolUseAfter Claude chooses a tool call, before it runsBlock dangerous calls, require approval, rewrite inputs
PostToolUseAfter the tool has runFormat or lint edited files, log, check output, give Claude feedback
UserPromptSubmitWhen a prompt is submittedAdd context, reject prompts that break policy
Stop / SubagentStopWhen the agent or a subagent finishesCheck the work is complete; run tests before stopping
SessionStartWhen a session beginsLoad context such as recent tickets or the branch name
PreCompactBefore the context is compactedSave state you don't want summarised away
Watch out

PostToolUse runs after the tool. It can't un-run a command or un-write a file; it can only react: log, fix up, or tell Claude what went wrong. Anything that must be prevented belongs in PreToolUse.

Registering a hook in Claude Code

Hooks live in settings.json: an event, then matcher groups (which tools), then the handlers to run.

.claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",

      {
        "matcher": "Write|Edit",

Three things a PreToolUse hook can do

The hook receives the event as JSON on stdin and answers in one of three ways:

AnswerHowEffect
Step asideExit 0 and print nothingThe normal permission flow carries on
Block (a gate)Exit code 2 with the reason on stderr, or JSON with permissionDecision: "deny"The tool doesn't run; Claude gets your reason and can adjust
Fix silently (interception)JSON with updatedInput inside hookSpecificOutputThe tool runs with your corrected arguments

Here's one hook script doing all three. A real script would read sys.stdin; to run it on this page we pass it four sample events, shaped like the JSON Claude Code sends.

Python
import json, os, re

SANDBOX = "/tmp/agent-sandbox"
DANGEROUS = {                                   # what the rule stops: the pattern that spots it
    "rm -rf reaching outside the project": r"\brm\s+-rf?\b.*(\s/|\s\.\.|~)",
    "force-pushing": r"\bgit\s+push\b.*--force",
    "dropping a table": r"\bDROP\s+TABLE\b",
    "piping a download into a shell": r"curl[^|]*\|\s*(ba)?sh",
}

def pre_tool_use(event):
    """Return (exit_code, stdout, stderr), as a hook script would."""
    tool, args = event["tool_name"], event["tool_input"]
    if tool == "Bash":
        for rule, pattern in DANGEROUS.items():
            if re.search(pattern, args["command"], re.I):
                return 2, "", f"Blocked by policy: {rule} is not allowed. Work inside the project only."
    if tool in ("Write", "Edit"):
        path = args["file_path"]
        if not os.path.abspath(path).startswith(SANDBOX + "/"):
            fixed = dict(args, file_path=os.path.join(SANDBOX, os.path.basename(path)))
            out = {"hookSpecificOutput": {"hookEventName": "PreToolUse",
                                          "permissionDecision": "allow", "updatedInput": fixed}}
            return 0, json.dumps(out), ""
    return 0, "", ""                                    # silence = no opinion

events = [
    {"hook_event_name": "PreToolUse", "tool_name": "Bash", "tool_input": {"command": "pytest -q tests/"}},
    {"hook_event_name": "PreToolUse", "tool_name": "Bash", "tool_input": {"command": "rm -rf build/ ../shared"}},
    {"hook_event_name": "PreToolUse", "tool_name": "Write", "tool_input": {"file_path": "/etc/report.txt", "content": "..."}},
    {"hook_event_name": "PreToolUse", "tool_name": "Write", "tool_input": {"file_path": SANDBOX + "/notes.md", "content": "..."}},
]
for e in events:
    code, out, err = pre_tool_use(e)
    shown = e["tool_input"].get("command") or e["tool_input"]["file_path"]
    verdict = "BLOCK" if code == 2 else ("REWRITE" if out else "pass")
    print(f"{e['tool_name']:<6} {shown:<28} exit={code}  {verdict}")
    if err: print("       stderr →", err)
    if out: print("       stdout →", json.loads(out)["hookSpecificOutput"]["updatedInput"]["file_path"])
Output · produced by running this code
Bash   pytest -q tests/             exit=0  pass
Bash   rm -rf build/ ../shared      exit=2  BLOCK
       stderr → Blocked by policy: rm -rf reaching outside the project is not allowed. Work inside the project only.
Write  /etc/report.txt              exit=0  REWRITE
       stdout → /tmp/agent-sandbox/report.txt
Write  /tmp/agent-sandbox/notes.md  exit=0  pass
How to read it

The test run passes untouched. The rm reaching outside the project is blocked, and Claude receives the stderr text as the reason. The write to /etc isn't blocked but redirected into the sandbox: no error, no retry, and Claude doesn't see the change. The write already inside the sandbox passes.

The idea

Gate or intercept? Block when the action itself is wrong (deleting outside the project). Intercept when the action is right but a detail is off (a path one level too high), because blocking would only make Claude retry and possibly repeat the mistake.

Practice questionYour agent must never run git push --force. Where should that rule live to be guaranteed?

Prompts and CLAUDE.md are instructions the model usually follows; a PreToolUse hook is code that runs before every matching call, so it enforces the rule deterministically. A PostToolUse hook runs after the push has already happened.

Practice questionA PreToolUse hook script exits with code 2 and writes "Use the staging database" to stderr. What happens?

Exit code 2 is the blocking signal: the call doesn't run, and the stderr text is fed back so Claude can adjust. Modifying the input needs updatedInput in JSON on stdout with exit 0.

Session 1.6

Memory and context in agents

The model has no memory of its own between requests. Everything an agent "remembers" is something your harness put back into the context, or stored outside it and fetched again. Agent designs use four kinds of memory:

MemoryWhere it livesLastsClaude example
In-context (working)The messages sent with each requestThis run onlyThe conversation and tool results so far
ExternalA database, files, a vector storeAs long as you keep itA memory tool or a retrieval step fetching notes
EpisodicA log of past runs and their outcomesAcross runs"Last time, the migration failed on the index step"
ProceduralInstructions on how to do thingsUntil editedCLAUDE.md files, Skills, system prompts
The idea

The context window is a whiteboard. Everything on it is available to the model at once, but it has a fixed size (1M tokens on current Claude models), and every token on it is paid for on every request. Long-running agents fail when the whiteboard fills with stale tool output, not because the model "forgets".

Why long agent runs get expensive

Because the API is stateless, turn 20 resends turns 1 to 19. If every tool result is large, input tokens grow with every turn, and the total grows roughly with the square of the number of turns. Here's a 20-turn run where each tool returns about 3,000 tokens, with and without pruning old tool results down to a one-line stub.

Python
def run_cost(turns, tool_tokens, keep_last=None, base=2_500, per_turn_text=150, price_in=2.00):
    """Total input tokens (and $ at price_in per million) for an agent run."""
    history, total = [], 0
    for t in range(turns):
        context = base + sum(history)
        total += context
        history.append(per_turn_text + tool_tokens)        # this turn's reply + tool result join the history
        if keep_last is not None and len(history) > keep_last:
            i = len(history) - keep_last - 1
            history[i] = per_turn_text + 40                 # old result replaced by a short stub
    return total, total * price_in / 1e6, base + sum(history)

for label, keep in [("keep every tool result", None), ("keep only the last 3", 3)]:
    total, usd, final = run_cost(20, 3_000, keep)
    print(f"{label:<24} total input {total:>9,} tokens  ≈ ${usd:.2f} at $2/MTok   context at the end {final:>6,}")

How to read it

Pruning cuts total input tokens by more than half here (about 2.6 times fewer), and the final context is under a quarter of the size. The prices use Claude Sonnet 5.5's input rate. Giving an agent memory that outlasts the run

External and episodic memory are just storage your harness, or a tool, reads and writes. The simplest useful version is a notes file the agent can append to and search. Claude's API also has a ready-made memory tool (memory_20250818) that lets the model create, read and edit files in a memory directory you control.

Python
NOTES = []        # in production: a file, a database table, or the memory tool's directory

def remember(topic, note):
    NOTES.append({"topic": topic, "note": note})
    return "saved"

STOP = {"the", "a", "an", "and", "of", "to", "for", "in", "on", "my", "our"}

def recall(query):
    words = set(query.lower().split()) - STOP
    hits = [n for n in NOTES if words & set((n["topic"] + " " + n["note"]).lower().split())]
    return hits[-3:] or "nothing relevant"

# Run 1 (episodic): the agent records what happened
remember("migration", "Step 3 failed: the index on bookings.created_at took 40 min. Build it concurrently.")
remember("style", "Clinic prefers dates as 12 Oct 2026, never 10/12/26.")

# Run 2, days later: a fresh context. The harness recalls before the agent starts work.
print(recall("plan the bookings migration"))
print(recall("format the appointment dates"))

[{'topic': 'style', 'note': 'Clinic prefers dates as 12 Oct 2026, never 10/12/26.'}]
Tip

Keep memory small and deliberate. Store decisions, outcomes and preferences, not raw transcripts. Save state before a context is compacted (the PreCompact hook exists for this), and treat what you read back as data to check, not as instructions.

Practice questionAn agent works well for the first 15 turns of a long task, then starts ignoring earlier instructions and repeating searches. Each tool returns around 20,000 tokens of logs. What is the most likely cause and fix?

Large, stale tool results crowd the context, dilute attention on the instructions and raise cost on every turn. Pruning old results (or isolating the reading in subagents) addresses the cause; a bigger window just postpones it.

Practice questionWhich kind of memory is a project's CLAUDE.md file?

CLAUDE.md holds standing instructions on how to work in the project (conventions, commands, rules), which is procedural memory. It's loaded into the context at the start of a session, but its role is "how we do things here", not a record of past events.

Session 1.7

Agent frameworks

You can build any agent on the Messages API alone. Frameworks earn their place when they remove scaffolding you would otherwise write and maintain. The blueprint names three, and each makes a different bet:

Core ideaModel-driven: give it a model, tools and a prompt; the model plans the loopYour workflow as an explicit graph of state, nodes and edgesA strictly typed agent definition; the model is a swappable back end
ControlLight: the model manages more of its own flowHigh: you define every step and transitionMedium: typed tools and validated outputs, no graph orchestration
StrengthsLittle code; MCP tools; pairs with Amazon Bedrock AgentCoreBranching, retries, checkpoints, pause-and-resume, human-in-the-loop; LangSmith tracingType safety, validated results, dependency injection, model portability
Trade-offLess built-in state management; you wire in persistenceMore abstraction to learnDoesn't orchestrate complex multi-agent flows
Reach for it whenYou want an agent running fast and trust the model to planYou need to see, control and resume every stepA Python team wants typed correctness without an orchestration layer
Exam lens

There's no "most advanced" framework; the question is the shape of the system. "Explicit control of multi-step flows, checkpointing, human approval mid-flow" points to LangGraph. "Minimal code, let the model drive, AWS" points to Strands. "Typed, validated outputs and swapping model providers" points to PydanticAI. "One straightforward tool loop" may need no framework at all.

The graph idea in 30 lines

LangGraph's core concepts are state (a shared snapshot of the data), nodes (functions that read and update state) and edges (rules that pick the next node). Here is that idea in plain Python, not LangGraph itself: a triage flow with a conditional edge, a retry loop and a checkpoint after every node, so a run could be paused for human review and resumed.

Python
def classify(state):
    msg = state["message"].lower()
    state["category"] = "clinical" if any(w in msg for w in ("pain", "bleeding", "fever")) else "admin"
    return state

def draft_reply(state):
    state["attempts"] = state.get("attempts", 0) + 1
    state["draft"] = "Thanks, we've received your message." if state["attempts"] == 1 else \
                     "Thanks, Mrs Iyer. Your 10:30 Friday booking is confirmed."
    return state

def check_reply(state):
    state["ok"] = "booking" in state["draft"]           # stand-in for a real quality check
    return state

def escalate(state):
    state["routed_to"] = "duty nurse"
    return state

NODES = {"classify": classify, "draft": draft_reply, "check": check_reply, "escalate": escalate}
EDGES = {
    "classify": lambda s: "escalate" if s["category"] == "clinical" else "draft",
    "draft":    lambda s: "check",
    "check":    lambda s: "END" if s["ok"] or s["attempts"] >= 3 else "draft",   # retry loop
    "escalate": lambda s: "END",
}

def run_graph(state, start="classify"):
    node, checkpoints = start, []
    while node != "END":
        state = NODES[node](dict(state))
        checkpoints.append((node, dict(state)))           # a resumable snapshot after every node
        node = EDGES[node](state)
    return state, checkpoints

for text in ["Can you confirm my Friday booking?", "Sharp pain since this morning"]:
    final, cps = run_graph({"message": text})
    print(f"{text!r}\n   path: {' → '.join(n for n, _ in cps)}")
    print(f"   result: {final.get('draft') or 'routed to ' + final['routed_to']}")
Output · produced by running this code
'Can you confirm my Friday booking?'
   path: classify → draft → check → draft → check
   result: Thanks, Mrs Iyer. Your 10:30 Friday booking is confirmed.
'Sharp pain since this morning'
   path: classify → escalate
   result: routed to duty nurse
How to read it

The booking message loops through draft → check twice before the check passes; the clinical one is routed to a nurse without drafting anything. Every transition is explicit and every step leaves a checkpoint. That visibility is LangGraph's selling point, and also why it carries more machinery than a model-driven framework.

Typed outputs, the PydanticAI idea

PydanticAI's bet is that the model's output should be validated into a typed object before your code touches it. The same idea works with plain dataclasses, shown here on two candidate outputs.

Python
from dataclasses import dataclass

@dataclass
class Triage:
    category: str
    urgency: int
    reply: str

    def __post_init__(self):
        if self.category not in {"admin", "clinical", "billing"}:
            raise ValueError(f"category {self.category!r} not allowed")
        if not 1 <= self.urgency <= 5:
            raise ValueError(f"urgency {self.urgency} outside 1–5")

for raw in ['{"category": "clinical", "urgency": 4, "reply": "A nurse will call you."}',
            '{"category": "urgent!!", "urgency": 9, "reply": "Go to A&E"}']:
    try:
        print("valid  →", Triage(**json.loads(raw)))
    except ValueError as e:
        print("invalid →", e, "(send the error back to the model and ask again)")

Practice questionA team needs a multi-step approval flow where a refund agent pauses for a manager's sign-off, can resume the next day from where it stopped, and every step must be traceable. Which framework fits best?

Pausing, resuming from a checkpoint and tracing each step are exactly what an explicit, persisted graph provides. Strands deliberately leaves state management light, and PydanticAI focuses on typed correctness rather than flow control.

Practice questionSelect 2Which statements about agent frameworks are accurate? (Select 2)

Strands is model-driven and PydanticAI is built around type safety and model portability. LangGraph is platform-agnostic, and tool use is a Messages API feature: a hand-written loop works without any framework.
